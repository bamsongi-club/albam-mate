# P1 알림 구현 명세

이 문서는 최종 성공한 방·참가 변경을 사용자별 서비스 내 웹 알림으로 전달하고, 본인 알림을 조회·읽음 처리하는 `NOTI-01`~`NOTI-03`의 구현 규칙과 완료 기준을 정의한다. 현재 계약·생산 코드·자동 검증·운영 상태는 [P1 기능 상태 정본](README.md#기능별-현재-상태)을 따른다. 여기서 앱 내 알림은 브라우저나 OS의 Web Push가 아니라 Albam Mate 웹 알림함을 뜻한다.

공통 범위와 개인정보 원칙은 [P1 공통 명세](../P1-spec.md), P1 HTTP 계약은 [API 명세](../API.md), 저장 계약은 [ERD의 P1 알림 저장 계약](../ERD.md#p1-알림-저장-계약), 모듈과 트랜잭션 구조는 [아키텍처](../ARCHITECTURE.md)를 따른다. 이 문서는 해당 정본의 계약을 구현·검증할 기준이며, 문서 존재만으로 현재 제공 상태를 판정하지 않는다.

알림 원인·수신자·트랜잭션·중복 방지·조회 권한의 공통 불변식은 [알림 생성과 조회](../P1-spec.md#알림-생성과-조회)에 한 번만 둔다. 이 문서는 알림 유형 매핑, 기능별 HTTP·화면 동작과 완료 기준만 추가한다.

### 알림 유형 매핑

아래 표는 Outbox 원인 사실의 `eventType`을 사용자 알림의 `type`으로 변환하는 정본이다. relay는 enum 문자열을 그대로 복사하거나 이름 규칙으로 추론하지 않고 이 매핑을 적용한다.

| Outbox `eventType` | Notification `type` | 사용자 의미 |
| --- | --- | --- |
| `PARTICIPATION_JOINED` | `PARTICIPANT_JOINED` | 참가·재참가 성공으로 주최자에게 새 참가자 알림 |
| `PARTICIPATION_CANCELED` | `PARTICIPANT_CANCELED` | 자동 승격 없이 참가 취소가 끝나 실제 빈자리가 남은 경우 주최자에게 빈자리 알림 |
| `ROOM_CANCELED` | `ROOM_CANCELED` | 방 취소 성공으로 확정 참가자에게 방 취소 알림 |

### 기능 규칙

NOTI-01은 [P1 공통 알림 불변식](../P1-spec.md#알림-생성과-조회)과 위 [알림 유형 매핑](#알림-유형-매핑)을 함께 적용한다. 트랜잭션·시각·저장·relay 규칙은 [구현 컨텍스트](#구현-컨텍스트)에 연결한 정본을 따르며 이 절에서 반복하지 않는다. 구현 완료 여부는 아래 완료 기준과 [P1 기능 상태 정본](README.md#기능별-현재-상태)으로 판정한다.

### 완료 기준

- `NOTI-01-AC1` 참가·재참가, 참가 취소와 방 취소의 최종 성공 트랜잭션이 원인 업무 변경과 Outbox 이벤트를 함께 커밋하고 정의된 수신자를 보존한다.
- `NOTI-01-AC2` 실패·롤백된 업무와 낙관적 락 충돌 시도는 처리 가능한 이벤트나 알림을 남기지 않으며, 재시도 뒤 성공하면 최종 성공 시도의 이벤트만 남는다.
- `NOTI-01-AC3` 방 취소와 참가·취소가 동시에 실행돼도 실제 커밋 순서에 따른 `ACTIVE` 수신자와 기존 방·참가 불변식을 함께 만족한다.
- `NOTI-01-AC4` 원인 업무 커밋 직후 프로세스가 종료돼도 재기동한 relay가 남은 이벤트로 알림을 생성한다.
- `NOTI-01-AC5` 같은 이벤트의 반복·동시 처리와 일부 수신자 저장 뒤 재처리에서도 대상자별 알림은 한 건이고 누락 대상은 최종적으로 채워진다.
- `NOTI-01-AC6` relay 처리 실패는 재시도 근거와 최종 실패 상태를 남기며 이미 성공한 방·참가 업무의 응답과 데이터를 바꾸지 않는다.
- `NOTI-01-AC7` 승인 ADR과 PostgreSQL 검증은 relay 선점, 재시도 상한·간격, 처리 지연 목표, 실패 이벤트 보존·재처리와 외부 broker 재검토 지표를 고정한다.

### 제외 범위

- Kafka, RabbitMQ와 별도 메시지 broker
- 이메일·모바일 푸시·SMS와 업무 트랜잭션 안의 동기 외부 발송
- 방 수정·종료·자동 종료·시작 임박·후기·운영 알림
- 모든 도메인 이벤트를 수집하는 범용 이벤트 플랫폼
- 이벤트의 전역 총순서와 정확히 한 번 실행된다는 보장
- 운영자용 실패 이벤트 관리 화면

## NOTI-02 내 알림 목록·미확인 개수

| 구분 | 정본 |
| --- | --- |

| API 인벤토리 | [P1 기능별 문서와 API 목록](../P1-spec.md#기능별-문서와-api-목록) |
| 인증·응답 | [API 인증·세션·CSRF](../API.md#12-인증세션csrf), [공통 응답](../API.md#13-공통-응답), [페이지네이션](../API.md#14-페이지네이션) |
| 저장 계약 | [사용자별 알림과 조회 인덱스](../ERD.md#notifications), [P1 알림 인덱스](../ERD.md#p1-알림-인덱스) |

### 기능 규칙

- 로그인한 사용자의 알림만 반환한다. 다른 사용자의 알림은 목록·개수 계산에 포함하지 않는다.
- 목록은 `createdAt DESC, id DESC`로 정렬해 생성 시각이 같아도 순서를 고정한다.
- 결과가 없으면 빈 목록을 반환한다. 정확한 응답 필드와 페이지네이션 방식은 [API 명세의 NOTI-02 계약](../API.md#noti-02-내-알림-목록)을 따른다.
- 미확인 알림은 본인 알림 중 `readAt IS NULL`인 행이다.
- 목록 항목은 알림 ID, 유형, 관련 방 ID, 읽은 시각과 생성 시각을 구분할 수 있어야 한다.
- 목록과 미확인 개수는 SSE·WebSocket 없이 polling만으로 완전하게 동작한다.
- 알림을 선택해 관련 방으로 이동할 때 현재 세션과 관계로 방 상세 권한을 다시 검사한다.

| 기능 | Method / Path | 인증 | CSRF |
| --- | --- | :---: | :---: |
| 내 알림 목록 | `GET /api/users/me/notifications` | 필요 | 불필요 |
| 내 미확인 수 | `GET /api/users/me/notifications/unread-count` | 필요 | 불필요 |

### 완료 기준

- `NOTI-02-AC1` 로그인한 사용자는 본인 알림만 `createdAt DESC, id DESC` 순서로 조회하고 결과가 없으면 빈 목록을 받는다.
- `NOTI-02-AC2` 페이지 경계를 이동해도 정렬이 안정적이고 다른 사용자의 알림이 섞이지 않는다.
- `NOTI-02-AC3` 본인 미확인 개수는 같은 DB 상태에서 `readAt IS NULL`인 본인 알림 수와 일치한다.
- `NOTI-02-AC4` 응답·본문·로그는 참가자 식별자, 이메일, 정확한 장소, 전체 참가자 목록과 인증 정보를 노출하지 않는다.
- `NOTI-02-AC5` 실시간 연결 없이 목록과 미확인 개수 polling이 동작하고 두 `GET` 경로가 현재 세션·엔드포인트 정책 대조 검증을 통과한다.
- `NOTI-02-AC6` 관련 방 이동은 저장된 알림을 권한으로 사용하지 않고 현재 방 조회 권한과 존재 여부 은닉 규칙을 적용한다.

### 제외 범위

- 다른 사용자의 알림 조회와 운영자용 알림 열람
- 알림 검색·유형 필터·사용자 지정 정렬
- SSE·WebSocket 기반 실시간 도착 표시
- 참가자 닉네임이나 프로필을 포함한 actor 표시

## NOTI-03 알림 읽음 처리

### 구현 컨텍스트

| 구분 | 정본 |
| --- | --- |
| API 인벤토리 | [P1 기능별 문서와 API 목록](../P1-spec.md#기능별-문서와-api-목록) |
| 인증·CSRF | [API 인증·세션·CSRF](../API.md#12-인증세션csrf) |
| 오류 응답 | [API 오류 코드](../API.md#10-오류-코드), [공통 응답](../API.md#13-공통-응답) |
| 저장 계약 | [사용자별 알림과 읽음 시각](../ERD.md#notifications), [P1 알림 CHECK 제약](../ERD.md#p1-알림-check-제약) |

### 기능 규칙

- 수신자 본인만 알림을 읽음 처리할 수 있다. 존재하지 않는 알림과 다른 사용자의 알림은 같은 not-found 계약으로 처리한다.
- 단건 읽음은 읽음 SQL 내부에서 PostgreSQL `clock_timestamp()`를 한 번 평가한 `operationTime`을 최초 `readAt`에 기록한다. 저장·비교는 UTC 기준 Instant를 사용하고 API 응답은 공통 시각 계약에 따라 `+09:00`으로 표현한다. 반복 요청은 성공하되 최초 시각을 유지한다.
- 일괄 읽음은 기본 `READ COMMITTED`의 단일 data-modifying CTE/`UPDATE` 문장에서 `operationTime`, 본인에게 보이는 알림 집합의 최대 ID 경계, 갱신 건수와 응답을 같은 문장 스냅샷으로 고정한다.
- 일괄 요청은 경계 안의 미확인 알림에 같은 `operationTime`을 기록하고, 기존에 읽은 알림의 최초 `readAt`은 바꾸지 않는다.
- 문장 스냅샷 획득 뒤 생성·커밋된 알림은 ID나 생성 시각과 관계없이 읽지 않은 상태로 남긴다.
- 읽지 않음으로 되돌리는 기능은 제공하지 않는다.

| 기능 | Method / Path | 인증 | CSRF |
| --- | --- | :---: | :---: |
| 내 알림 단건 읽음 | `PATCH /api/users/me/notifications/{notificationId}` | 필요 | 필요 |
| 내 알림 일괄 읽음 | `PATCH /api/users/me/notifications` | 필요 | 필요 |

### 완료 기준

- `NOTI-03-AC1` 본인 알림의 첫 단건 읽음 요청은 읽음 SQL이 고정한 PostgreSQL `operationTime`을 기록하고 반복 요청에도 최초 `readAt`을 유지한다.
- `NOTI-03-AC2` 존재하지 않는 알림과 다른 사용자의 알림은 같은 오류 계약을 반환하며 다른 사용자의 상태를 변경하지 않는다.
- `NOTI-03-AC3` 일괄 읽음은 단일 PostgreSQL 문장의 스냅샷·`operationTime`으로 고정한 경계 안의 본인 미확인 알림만 같은 시각으로 처리하고 기존 읽은 시각은 보존한다.
- `NOTI-03-AC4` 일괄 읽음과 알림 생성이 동시에 실행돼도 읽음 문장 스냅샷 획득 뒤 커밋된 새 알림은 응답 경계에 포함되지 않고 미확인 상태로 남는다.
- `NOTI-03-AC5` 단건·일괄 요청을 반복해도 추가 부수효과 없이 같은 상태로 수렴한다.
- `NOTI-03-AC6` 두 `PATCH` 경로가 로그인·CSRF 보호와 엔드포인트 정책 대조 검증을 통과한다.

### 제외 범위

- 알림을 읽지 않음으로 되돌리기
- 알림 삭제·보관과 보존 기간 사용자 설정
- 다른 사용자의 알림 상태 변경

## 프론트엔드 UX 계약

이 절은 `NOTI-02`·`NOTI-03`을 사용하는 P1 웹 알림함의 기본 동작을 정의한다. 서버는 표시용 `message`를 반환하지 않으며, 클라이언트가 `type`과 조회 시점의 `roomTitle`로 문구를 만든다. API 요청·CSRF 처리와 최종 서버 상태 반영은 [API 명세의 알림 계약](../API.md#9-알림채팅-api)을 따른다.

### 조회와 polling

- 로그인 성공 또는 새로고침 뒤 세션 복구가 끝나면 알림 목록 첫 페이지(`page=0`, `size=10`)와 미확인 개수를 즉시 조회한다.
- 로그인 세션이 있고 문서가 보이는 동안 미확인 개수를 10초마다 조회한다. 알림함이 열려 있으면 목록 첫 페이지도 같은 주기로 다시 조회해 서버 응답으로 교체한다.
- 알림함을 열 때는 직전 polling 시각과 관계없이 목록 첫 페이지와 미확인 개수를 즉시 조회한다. 숨겨졌던 브라우저 탭이 다시 보이면 열린 알림함의 목록과 미확인 개수를 즉시 조회한다.
- 같은 종류의 이전 조회가 진행 중이면 다음 polling 요청을 겹쳐 보내지 않는다. 문서가 숨겨졌거나 로그아웃했으면 주기 조회를 중단하고, `401 UNAUTHENTICATED`는 공통 세션 만료 흐름으로 처리한다.
- 미확인 배지는 목록 한 페이지에서 계산하지 않고 미확인 개수 API의 마지막 성공 응답을 사용한다.

### 표시 문구와 이동

| `NotificationType` | 기본 문구 |
| --- | --- |
| `PARTICIPANT_JOINED` | `'${roomTitle}' 모임에 새 참가자가 있어요.` |
| `PARTICIPANT_CANCELED` | `'${roomTitle}' 모임에 빈자리가 생겼어요.` |
| `ROOM_CANCELED` | `'${roomTitle}' 모임이 취소됐어요.` |

- `${roomTitle}`은 API가 반환한 현재 방 제목으로 치환하고 HTML로 해석하지 않은 일반 텍스트로 렌더링한다. 참가자 닉네임·사용자 ID·이메일·정확한 장소는 문구에 추가하지 않는다.
- 읽지 않은 알림을 선택하면 임의의 `readAt`을 만들지 않고 해당 행만 읽음 스타일로 바꾸며, 마지막 성공 미확인 개수를 `max(0, unreadCount - 1)`로 먼저 표시한 뒤 단건 읽음 요청을 보낸다. 읽음 요청 완료를 기다리느라 이동을 막지 않고 `roomId`로 방 상세 이동을 시도한다.
- 방 상세 이동은 현재 세션과 권한으로 다시 조회한다. 방이 없거나 현재 접근할 수 없으면 저장된 알림으로 우회하지 않고 `현재 확인할 수 없는 모임입니다.`를 표시한다.

### 읽음 상태 동기화

- 단건 읽음 성공 시 응답의 `readAt`을 같은 알림에 적용하고 미확인 개수를 즉시 다시 조회한다. 실패하면 낙관적 상태를 확정하지 않고 목록과 미확인 개수를 다시 조회한다.
- 일괄 읽음은 요청 중 중복 제출을 막는다. 요청을 시작하면 목록·미확인 개수 polling을 중지하고 알림 조회 세대(generation)를 증가시켜 이전 세대의 진행 중인 `GET`을 취소한다. 성공·실패가 확정되면 세대를 다시 증가시킨 뒤 목록 첫 페이지와 미확인 개수를 즉시 재조회하고, 각 응답은 요청이 캡처한 세대가 현재 세대와 같을 때만 적용하며 두 재조회가 끝난 뒤 polling을 재개한다.
- 일괄 읽음 성공 응답의 `boundaryNotificationId`는 실제 갱신 ID 집합이나 클라이언트 읽음 경계가 아니므로 현재 목록을 직접 변경하는 데 사용하지 않는다. 목록과 배지는 후속 재조회 응답으로만 교체하고 `updatedCount`만 보고 배지를 계속 `0`으로 두지 않는다.
- 읽음 동기화 재조회가 실패하면 마지막 성공 목록을 유지하고 `알림 상태를 갱신하지 못했습니다. 다시 시도해 주세요.`와 재시도 동작을 제공한다.

### 로딩·빈 목록·실패

- 최초 목록 응답 전에는 `알림을 불러오는 중입니다.`를 표시한다.
- 조회가 성공했고 `content`가 비어 있으면 `새로운 알림이 없습니다.`를 표시한다.
- 최초 목록 조회가 실패하면 `알림을 불러오지 못했습니다.`와 명시적인 재시도 동작을 제공한다.
- 이미 성공한 목록이 있는 상태에서 polling이 실패하면 기존 목록과 배지를 지우거나 오류 화면으로 바꾸지 않는다. 같은 오류 알림을 주기마다 반복 노출하지 않고 다음 polling 또는 사용자의 재시도에서 다시 조회한다.
