# P1 알림 구현 명세

이 문서는 최종 성공한 방·참가 변경을 사용자별 서비스 내 웹 알림으로 전달하고, 본인 알림을 조회·읽음 처리하는 `NOTI-01`~`NOTI-03`의 구현 규칙과 완료 기준을 정의한다. 세 기능은 현재 미구현이다. 여기서 앱 내 알림은 브라우저나 OS의 Web Push가 아니라 Albam Mate 웹 알림함을 뜻한다.

공통 범위와 개인정보 원칙은 [P1 공통 명세](../P1-spec.md), 현재 HTTP 계약은 [API 명세](../API.md), 저장 계약은 [ERD](../ERD.md), 모듈과 트랜잭션 구조는 [아키텍처](../ARCHITECTURE.md)를 따른다. 이 문서의 신규 API와 저장 개념은 API·ERD·승인 ADR에 반영되기 전까지 현재 제공 계약이나 구현 완료를 뜻하지 않는다.

알림 원인·수신자와 중복 방지 공통 규칙은 [알림 생성과 조회](../P1-spec.md#알림-생성과-조회)에 한 번만 둔다. P1은 참가·재참가, 참가 취소와 방 취소만 알림 원인으로 사용하며, 방 수정·종료·자동 종료 알림은 포함하지 않는다.

## NOTI-01 모임 변경 알림 생성

### 구현 컨텍스트

| 구분 | 정본 |
| --- | --- |
| 공통 규칙 | [알림 생성과 조회](../P1-spec.md#알림-생성과-조회), [측정 근거와 최소 기반 우선](../P1-spec.md#측정-근거와-최소-기반-우선) |
| 원인 업무 계약 | [방 참가·재참가](../API.md#part-01-방-참가재참가), [참가 취소](../API.md#part-02-참가-취소), [방 취소](../API.md#room-05-방-취소) |
| 트랜잭션·재시도 | [방 변경](../ARCHITECTURE.md#방-변경), [기준 시각과 재시도](../ARCHITECTURE.md#기준-시각과-재시도) |
| 저장 계약 | [ERD](../ERD.md) — 구현 전에 Outbox와 알림 테이블·제약 추가 필요 |
| 필수 ADR | [ADR-0029](../adr/notification/0029-room-integration-event-transactional-outbox.md)의 통합 이벤트·Transactional Outbox 경계와 [ADR-0030](../adr/notification/0030-postgresql-notification-relay-processing-recovery.md)의 relay 처리·복구 정책 승인됨, 구현 검증 필요 |
| 과한 설계 제한 | [외부 broker 도입 제한](../CONVENTIONS.md#과한-설계-제한) |

### 기능 규칙

- 원인 업무 데이터와 Outbox 이벤트는 실제 상태를 커밋하는 Command Executor의 같은 PostgreSQL 트랜잭션에 저장한다.
- 업무 검증 실패, DB 쓰기 실패, 낙관적 락 충돌 시도와 최종 실패 요청이 롤백되면 Outbox 이벤트도 함께 롤백한다.
- 참가·재참가와 참가 취소는 최종 성공 트랜잭션에서 방 주최자를 수신자로 확정한다.
- 방 취소는 최종 성공 트랜잭션에서 현재 `ACTIVE` 참가자를 수신자 목록으로 고정한다. relay 처리 시점의 참가 관계를 다시 조회해 목록을 바꾸지 않는다.
- 방 취소 시 `ACTIVE` 참가자가 없으면 전달할 수신자가 없으므로 Outbox 이벤트를 만들지 않고 방 취소만 정상 커밋한다.
- 서로 다른 업무 성공은 서로 다른 `sourceEventId`를 사용한다. 같은 이벤트를 재처리할 때는 기존 식별자를 유지한다.
- PostgreSQL polling relay는 at-least-once 처리를 전제로 하며, `(sourceEventId, recipientUserId)` DB 유일 제약으로 수신자별 알림을 한 건으로 수렴시킨다.
- relay 실패는 원인 업무를 되돌리지 않는다. 시도 횟수, 마지막 오류, 다음 처리 가능 시각과 최종 실패 상태를 남긴다.
- 알림은 일반 문구, 유형과 관련 방 ID만 저장한다. 관련 방 ID는 조회 권한이 아니며 화면 이동 시 현재 방 조회 권한을 다시 검사한다.
- 알림 `createdAt`은 relay 처리 시각이 아니라 원인 이벤트 시각이다. relay는 전역·방별 처리 순서를 보장하지 않으며 각 이벤트를 독립 처리한다.
- P1 전달 기반은 PostgreSQL Transactional Outbox와 DB polling relay다. Kafka·RabbitMQ는 독립 consumer 수, 지연, 적체 또는 DB polling 부하가 측정된 뒤 후속 ADR에서 검토한다.

### 완료 기준

- `NOTI-01-AC1` 참가·재참가, 참가 취소와 방 취소의 최종 성공 트랜잭션이 원인 업무 변경과 Outbox 이벤트를 함께 커밋하고 정의된 수신자를 보존한다.
- `NOTI-01-AC2` 실패·롤백된 업무와 낙관적 락 충돌 시도는 처리 가능한 이벤트나 알림을 남기지 않으며, 재시도 뒤 성공하면 최종 성공 시도의 이벤트만 남는다.
- `NOTI-01-AC3` 방 취소와 참가·취소가 동시에 실행돼도 실제 커밋 순서에 따른 `ACTIVE` 수신자와 기존 방·참가 불변식을 함께 만족한다.
- `NOTI-01-AC4` 원인 업무 커밋 직후 프로세스가 종료돼도 재기동한 relay가 남은 이벤트로 알림을 생성한다.
- `NOTI-01-AC5` 같은 이벤트의 반복·동시 처리와 일부 수신자 저장 뒤 재처리에서도 대상자별 알림은 한 건이고 누락 대상은 최종적으로 채워진다.
- `NOTI-01-AC6` relay 처리 실패는 재시도 근거와 최종 실패 상태를 남기며 이미 성공한 방·참가 업무의 응답과 데이터를 바꾸지 않는다.
- `NOTI-01-AC7` 승인 ADR과 PostgreSQL 검증은 relay 선점, 재시도 상한·간격, 처리 지연 목표, 실패 이벤트 보존·재처리와 외부 broker 재검토 지표를 고정한다.

### 제외 범위

- Kafka, RabbitMQ와 별도 메시지 broker
- 이메일·모바일 푸시·SMS와 업무 트랜잭션 안의 동기 외부 발송
- 방 수정·종료·자동 종료·시작 임박·후기·운영 알림
- 모든 도메인 이벤트를 수집하는 범용 이벤트 플랫폼
- 이벤트의 전역 총순서와 정확히 한 번 실행된다는 보장
- 운영자용 실패 이벤트 관리 화면

## NOTI-02 내 알림 목록·미확인 개수

### 구현 컨텍스트

| 구분 | 정본 |
| --- | --- |
| 제품 흐름 | [중요한 변경 알림 확인](../P1-spec.md#중요한-변경-알림-확인) |
| API 인벤토리 | [P1 기능별 문서와 API 목록](../P1-spec.md#기능별-문서와-api-목록) |
| 인증·응답 | [API 인증·세션·CSRF](../API.md#12-인증세션csrf), [공통 응답](../API.md#13-공통-응답), [페이지네이션](../API.md#14-페이지네이션) |
| 저장 계약 | [ERD](../ERD.md) — 구현 전에 알림 제약·조회 인덱스 추가 필요 |

### 기능 규칙

- 로그인한 사용자의 알림만 반환한다. 다른 사용자의 알림은 목록·개수 계산에 포함하지 않는다.
- 목록은 `createdAt DESC, id DESC`로 정렬해 생성 시각이 같아도 순서를 고정한다.
- 결과가 없으면 빈 목록을 반환한다. 정확한 응답 필드와 페이지네이션 방식은 [API 명세의 NOTI-02 계약](../API.md#noti-02-내-알림-목록)을 따른다.
- 미확인 알림은 본인 알림 중 `readAt IS NULL`인 행이다.
- 목록 항목은 알림 ID, 유형, 관련 방 ID, 읽은 시각과 생성 시각을 구분할 수 있어야 한다.
- 목록과 미확인 개수는 SSE·WebSocket 없이 polling만으로 완전하게 동작한다.
- 알림을 선택해 관련 방으로 이동할 때 현재 세션과 관계로 방 상세 권한을 다시 검사한다.

| 기능 | Method / Path | 인증 | CSRF |
| --- | --- | :---: | :---: |
| 내 알림 목록 | `GET /api/users/me/notifications` | 필요 | 불필요 |
| 내 미확인 수 | `GET /api/users/me/notifications/unread-count` | 필요 | 불필요 |

### 완료 기준

- `NOTI-02-AC1` 로그인한 사용자는 본인 알림만 `createdAt DESC, id DESC` 순서로 조회하고 결과가 없으면 빈 목록을 받는다.
- `NOTI-02-AC2` 페이지 경계를 이동해도 정렬이 안정적이고 다른 사용자의 알림이 섞이지 않는다.
- `NOTI-02-AC3` 본인 미확인 개수는 같은 DB 상태에서 `readAt IS NULL`인 본인 알림 수와 일치한다.
- `NOTI-02-AC4` 응답·본문·로그는 참가자 식별자, 이메일, 정확한 장소, 전체 참가자 목록과 인증 정보를 노출하지 않는다.
- `NOTI-02-AC5` 실시간 연결 없이 목록과 미확인 개수 polling이 동작하고 두 `GET` 경로가 현재 세션·엔드포인트 정책 대조 검증을 통과한다.
- `NOTI-02-AC6` 관련 방 이동은 저장된 알림을 권한으로 사용하지 않고 현재 방 조회 권한과 존재 여부 은닉 규칙을 적용한다.

### 제외 범위

- 다른 사용자의 알림 조회와 운영자용 알림 열람
- 알림 검색·유형 필터·사용자 지정 정렬
- SSE·WebSocket 기반 실시간 도착 표시
- 참가자 닉네임이나 프로필을 포함한 actor 표시

## NOTI-03 알림 읽음 처리

### 구현 컨텍스트

| 구분 | 정본 |
| --- | --- |
| API 인벤토리 | [P1 기능별 문서와 API 목록](../P1-spec.md#기능별-문서와-api-목록) |
| 인증·CSRF | [API 인증·세션·CSRF](../API.md#12-인증세션csrf) |
| 오류 응답 | [API 오류 코드](../API.md#10-오류-코드), [공통 응답](../API.md#13-공통-응답) |
| 저장 계약 | [ERD](../ERD.md) — 구현 전에 읽은 시각과 일괄 갱신 경계 추가 필요 |

### 기능 규칙

- 수신자 본인만 알림을 읽음 처리할 수 있다. 존재하지 않는 알림과 다른 사용자의 알림은 같은 not-found 계약으로 처리한다.
- 단건 읽음은 처음 읽을 때의 서버 기준 시각을 `readAt`에 기록한다. 저장·비교는 UTC 기준 Instant를 사용하고 API 응답은 공통 시각 계약에 따라 `+09:00`으로 표현한다. 반복 요청은 성공하되 최초 시각을 유지한다.
- 일괄 읽음은 요청 트랜잭션이 시작될 때 본인에게 보이는 알림 집합과 안정적인 마지막 알림 ID를 경계로 고정한다.
- 일괄 요청은 경계 안의 미확인 알림에 같은 서버 시각을 기록하고, 기존에 읽은 알림의 최초 `readAt`은 바꾸지 않는다.
- 경계를 정한 뒤 생성·커밋된 알림은 생성 시각이 같아도 읽지 않은 상태로 남긴다.
- 읽지 않음으로 되돌리는 기능은 제공하지 않는다.

| 기능 | Method / Path | 인증 | CSRF |
| --- | --- | :---: | :---: |
| 내 알림 단건 읽음 | `PATCH /api/users/me/notifications/{notificationId}` | 필요 | 필요 |
| 내 알림 일괄 읽음 | `PATCH /api/users/me/notifications` | 필요 | 필요 |

### 완료 기준

- `NOTI-03-AC1` 본인 알림의 첫 단건 읽음 요청은 서버 시각을 기록하고 반복 요청에도 최초 `readAt`을 유지한다.
- `NOTI-03-AC2` 존재하지 않는 알림과 다른 사용자의 알림은 같은 오류 계약을 반환하며 다른 사용자의 상태를 변경하지 않는다.
- `NOTI-03-AC3` 일괄 읽음은 요청 시작 때 고정한 경계 안의 본인 미확인 알림만 같은 시각으로 처리하고 기존 읽은 시각은 보존한다.
- `NOTI-03-AC4` 일괄 읽음과 알림 생성이 동시에 실행돼도 경계 뒤에 커밋된 새 알림은 미확인 상태로 남는다.
- `NOTI-03-AC5` 단건·일괄 요청을 반복해도 추가 부수효과 없이 같은 상태로 수렴한다.
- `NOTI-03-AC6` 두 `PATCH` 경로가 로그인·CSRF 보호와 엔드포인트 정책 대조 검증을 통과한다.

### 제외 범위

- 알림을 읽지 않음으로 되돌리기
- 알림 삭제·보관과 보존 기간 사용자 설정
- 다른 사용자의 알림 상태 변경
