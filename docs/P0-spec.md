# 알밤메이트 1차 MVP 기획서 (수정안)

> 본 문서는 알밤메이트의 핵심 유저 흐름을 빠르게 구현하고 검증하기 위한 1차 MVP 범위를 정의한다.
>
> 1차 MVP에서는 핵심 성공 흐름과 이 문서 7절에 명시한 권한·시간·정원 경계를 구현한다. 운영 제재, 결제, 대규모 동시 요청의 성능 목표처럼 P0에 포함하지 않는 후속 기능은 실제 도입 시 별도 정책으로 구체화한다.
>
> 세부 요청·응답 필드, 오류 코드, 데이터베이스 구조, 인증 방식 등은 별도의 API 명세서와 기술 설계서에서 관리한다.

## 관련 문서

- 본 문서: 1차 MVP 범위, 화면 흐름, 도메인, 운영 규칙과 완료 기준
- [API 명세서](API.md): 요청·응답 필드와 오류 코드
- [ERD](ERD.md): 데이터 모델과 제약
- [PRD](PRD.md): P0 이후 검토할 기능 후보

## 1. 서비스 개요

### 1.1 서비스 비전

알밤메이트는 유저가 게임 정보와 모임 조건을 참고하여 보드게임 모임을 찾고, 일반 유저 또는 룰마스터가 만든 모임에 참가할 수 있도록 돕는 보드게임 플레이 매칭 플랫폼을 지향한다.

### 1.2 1차 MVP 정의

1차 MVP에서는 홍대에서 열리는 오프라인 보드게임 방을 대상으로 다음 경험을 제공한다.

- `게임부터 찾기`와 `사람부터 만나기` 두 가지 탐색 방식 제공
- 게임 목록 조회
- 게임 중심 방 목록 탐색
- 사람 중심 방 목록 탐색
- 게임 중심 또는 사람 중심 방 생성
- 방의 일시, 홍대 지역, 정원, 경험 수준, 룰마스터 진행 여부 확인
- 남은 자리에 선착순 참가
- 내가 참가하거나 개설한 방 확인
- 주최자와 현재 `ACTIVE` 참가자가 방 상세에서 정확한 장소와 참가자 확인

### 1.3 해결하려는 문제와 검증 가설

알밤메이트는 보드게임을 하고 싶은 유저가 게임·참가자·룰마스터를 빠르게 찾아 실제 플레이 모임을 성립시킬 수 있도록 돕는다. 원하는 시간과 장소에 함께할 사람, 플레이할 게임, 규칙을 설명할 사람이 동시에 맞지 않아 모임이 성립되지 않는 문제를 해결한다.

> 게임, 일시, 장소, 경험 수준, 룰마스터 진행 여부와 남은 자리를 확인할 수 있다면, 함께할 사람이 없는 유저도 보드게임 방 참가를 완료할 수 있다.

### 1.4 대상 유저와 역할

대상 유저는 함께 갈 일행을 구하기 어려운 보드게임 카페 방문 유저, 새로운 게임을 가볍게 경험하고 싶은 초보·라이트 유저, 자신이 아는 게임을 다른 유저에게 설명하고 진행하고 싶은 유저다.

> 핵심 페르소나는 오늘이나 이번 주에 보드게임을 하고 싶지만, 함께할 사람을 구하고 게임을 선택하며 규칙을 익히는 과정이 부담스러운 초보·라이트 유저다.

한 명의 유저는 방에 따라 여러 역할을 수행할 수 있다.

- 참가자: 게임 또는 사람 중심 방을 탐색하고 참가·취소하며, 참가한 방을 확인한다.
- 방 개설자: 방을 생성·수정·취소·종료하고 참가자를 확인한다.
- 룰마스터: 방에서 규칙 설명과 게임 진행을 담당한다고 직접 표시하는 개설자 역할이다. MVP에서는 별도의 유저 유형이나 인증 자격이 아니다.

## 2. 1차 MVP 구현 원칙

### 2.1 성공 흐름 우선

1차 구현에서는 다음 세 가지 유저 흐름을 처음부터 끝까지 연결하는 것을 가장 중요한 목표로 한다.

1. 게임부터 찾고 방에 참가하는 흐름
2. 사람 중심 방을 찾고 참가하는 흐름
3. 개설자가 방을 만들고 참가자를 확인하는 흐름

### 2.2 원칙과 운영 규칙의 분리

1차 구현에서는 정상적인 입력과 일반적인 사용 순서에 따른 성공 흐름을 우선한다. 생성·참가·정원·상태에 관한 실제 운영 규칙은 7절에서 단일 기준으로 관리한다.

### 2.3 복합 예외는 후속 보완

P0 API의 권한, 허용 상태, 시간 경계, 정원 규칙은 7절과 [API 명세서](API.md)에 모두 정의한다. 운영 제재와 대규모 동시 요청의 성능 목표처럼 P0 밖의 정책은 실제 도입 시 별도로 결정한다.

## 3. 1차 MVP 범위

### 3.1 포함 범위

- 이메일·비밀번호 기반 회원가입
- 로그인
- 본인 프로필 조회
- 본인 프로필 수정
- 게임 목록 조회(+기본 키워드 검색 조회)
- 게임 상세 조회
- 게임 중심·사람 중심 통합 방 목록 조회
- 게임 중심·사람 중심 통합 방 상세 조회
- 게임 중심 방 생성
- 사람 중심 방 생성
- 방 수정
- 방 취소
- 방 종료
- 방 참가
- 참가 취소
- 내 모임 조회

### 3.2 1차 구현 이후 보완 범위

P0 API에 영향을 주는 정책은 이 문서 7절과 [API 명세서](API.md)에 남긴다. P0에 포함하지 않는 후속 기능의 정책은 실제 도입 시 [PRD](PRD.md)의 후보 범위를 기준으로 결정한다.

### 3.3 향후 기능 범위

MVP 이후 검토할 기능 후보는 [PRD](PRD.md)의 후속 기능 후보에서 관리한다.

## 4. 화면 흐름과 표시 기준

게임 중심과 사람 중심은 서버에서 조회하는 카테고리 목록이 아니라, 유저가 서비스를 이용하는 두 가지 고정 탐색 방식이다.

MVP에서는 홈 화면에 다음 두 개의 진입 버튼을 고정으로 제공한다.

- `게임부터 찾기`
- `사람부터 만나기`

### 4.1 게임부터 찾기

플레이하고 싶은 게임을 먼저 선택한 뒤, 해당 게임으로 개설된 방을 찾는 방식이다.

```text
게임부터 찾기
→ 게임 목록·검색
→ 게임 카드 선택
→ 게임 상세 화면
→ 선택한 게임의 게임 중심 방 목록
→ 방 상세 조회
→ 회원가입 또는 로그인
→ 방 참가
→ 내 모임에서 참가한 방 확인
```

#### 게임 목록 화면 기준

게임 목록의 카드 하나는 방이 아니라 게임을 나타낸다.

각 카드에는 다음 정보를 표시할 수 있다.

- 게임명
- 영문명
- 대표 이미지
- 권장 인원
- 예상 플레이 시간
- 난이도 표시
- 예정 모임 수

`예정 모임 수`는 해당 게임으로 생성된 미래 시점의 게임 중심 방 중 `CANCELED`, `FINISHED` 상태가 아닌 방의 수다.

게임 카드를 선택하면 게임 상세 화면으로 이동한다. 게임 상세에서는 게임 카드 수준의 기본 정보를 확인하고, 해당 게임의 게임 중심 방 목록 화면으로 이동해 방을 확인하거나 해당 게임으로 모임을 생성할 수 있다.

### 4.2 사람부터 만나기

플레이할 게임을 먼저 선택하지 않고, 친목과 만남을 우선하는 사람 중심 방을 탐색하는 방식이다.

```text
사람부터 만나기
→ 사람 중심 방 목록
→ 방 상세 조회
→ 회원가입 또는 로그인
→ 방 참가
→ 내 모임에서 참가한 방 확인
```

### 4.3 방 만들기

```text
회원가입 또는 로그인
→ 게임 중심 또는 사람 중심 방 선택
→ 게임 중심인 경우 게임 목록 검색 및 게임 선택
→ 모임 제목, 경험 수준, 정원, 일시, 장소, 한 줄 소개(선택) 입력
→ 룰마스터 진행 여부 선택
→ 방 생성
→ 내 모임에서 개설한 방 확인
→ 방 상세에서 참가자 목록 확인
→ 모임 진행 후 방 종료 처리
```

### 4.4 방 목록 화면 구성

게임 중심과 사람 중심의 목록 화면은 다르게 표현할 수 있지만, 조회 대상은 모두 `Room`이다.

프론트엔드는 방 유형에 따라 목록 카드의 표시 항목과 레이아웃을 다르게 구성할 수 있다.

### 4.5 방 상세 화면 구성

게임 중심과 사람 중심 방 모두 방 상세 화면에서 확인한다.

방 상세 화면은 요청자와 방의 관계에 따라 공개 상세와 관계자 상세로 나뉜다. 방 유형에 따라 표시 항목과 레이아웃을 다르게 구성할 수 있다.

#### 공개 상세

비로그인 유저와 방 관계가 없는 로그인 유저는 `RECRUITING`, `CLOSED` 방의 `PublicRoomResponse`만 조회한다.

- 방 유형
- 모임 제목과 한 줄 소개
- 상태
- 일시
- 지역(홍대)
- 모집 정원, 현재 참가자 수, 남은 모집 좌석 수
- 경험 수준
- 룰마스터 진행 여부

공개 상세에는 정확한 장소, 개설자 정보, 참가자 목록, 사용자 ID를 표시하지 않는다.

#### 관계자 상세

주최자 또는 현재 `ACTIVE` 참가자는 `ParticipantRoomResponse`로 공개 상세의 모든 정보와 아래 정보를 확인한다.

- 정확한 장소
- 개설자 닉네임
- 개설자를 포함한 현재 `ACTIVE` 참가자 닉네임 목록

#### 게임 중심 방

- 선택된 게임 정보가 반드시 포함된다.
- 게임명, 대표 이미지 등 최소 정보만 표시한다.

#### 사람 중심 방

- 게임이 아직 정해지지 않았다면 게임 정보는 `null`이다.
- 화면에는 `게임 미정`으로 표시할 수 있다.
- 게임이 선택되어 있다면 선택된 게임의 최소 정보를 표시할 수 있다.

## 5. 핵심 개념과 방 구성

### 5.1 유저(User)

서비스에 가입하여 방을 만들거나 참가할 수 있는 유저이다.

MVP에서는 이메일, 비밀번호, 닉네임 등 최소 프로필 정보를 사용한다.

### 5.2 게임(Game)

게임은 방에서 플레이할 보드게임을 선택하기 위한 참조 데이터다.

게임은 알밤메이트 MVP의 핵심 관리 도메인이 아니며, 운영자가 사전에 입력한 더미 또는 초기 데이터를 사용한다.

게임 데이터는 다음 네 곳에서 사용한다.

1. `게임부터 찾기` 화면의 게임 목록
2. 게임 상세 화면
3. 게임 중심 방 생성 시 게임 선택
4. 방 상세의 선택 게임 정보 표시

MVP에서는 다음 기능을 제공하지 않는다.

- 유저의 게임 등록
- 유저의 게임 수정·삭제
- 게임별 리뷰
- 게임별 룰마스터 목록 조회

게임 목록에서 사용할 수 있는 필드는 다음과 같다.

- 게임 ID
- 게임명
- 게임 영문명
- 대표 이미지
- 권장 최소·최대 인원
- 예상 플레이 시간
- 난이도 표시
- 예정 모임 수

### 5.3 방(Room)

홍대 내 특정 일시와 장소에서 진행되는 보드게임 모임 단위다.

방은 다음 정보를 가진다.

- 방 유형
- 모임 제목
- 한 줄 소개(선택)
- 선택 게임
- 경험 수준
- 룰마스터 진행 여부
- 정원
- 시작 일시
- 지역(홍대)
- 장소
- 개설자
- 상태

### 5.4 방 유형(RoomType)

MVP에서는 다음 두 가지 방 유형을 제공한다.

- `GAME_FOCUSED`: 게임 중심 방
- `PERSON_FOCUSED`: 사람 중심 방

방 유형은 방이 가지는 유형값이며, 생성 시 선택한다.

#### 게임 중심 방

- 게임 카탈로그에서 게임 1개를 반드시 선택한다.
- 선택한 게임을 함께 플레이할 참가자를 모집한다.
- `gameId`는 필수다.
- 게임 목록의 게임 카드를 선택하면 해당 게임의 게임 중심 방 목록을 조회한다.

#### 사람 중심 방

- 친목과 네트워킹을 우선하는 방이다.
- 플레이할 게임은 현장에서 결정할 수 있다.
- 게임 선택은 선택 사항이다.
- 게임이 정해지지 않은 경우 `게임 미정`으로 표시한다.

### 5.5 참가와 정원

#### 정원(Capacity)

정원 입력값은 개설자를 제외한 모집 인원이다. 방 생성 시 개설자는 자동으로 참가자 목록에 포함된다.

예를 들어 개설자가 정원 8명을 설정하고 방을 생성한다면,

- 전체 정원: 9명(개설자 1명 + 모집 인원 8명)
- 방 상세에는 개설자를 포함한 전체 정원과 현재 참가자 수를 표시한다.
- 참가자 목록에는 개설자가 포함된다.
- 남은 좌석은 전체 정원에서 현재 참가자 수를 뺀 값이다.

모집 정원은 개설자를 제외하고 최소 1명, 최대 10명으로 제한한다. 따라서 전체 정원은 최소 2명, 최대 11명이다.

#### 참가(Participation)

유저가 특정 방에 참가한 관계를 의미한다.

- 참가 성공 시 별도의 승인 없이 즉시 참가자로 등록된다.
- 동일 유저는 같은 방에 활성 참가 상태를 하나만 가진다.
- 참가를 취소한 경우, 시작 시각 전 방이 `RECRUITING` 상태이고 남은 좌석이 있을 때 다시 참가할 수 있다.

### 5.6 방 속성 및 상태

#### 경험 수준(ParticipantLevel)

경험 수준은 개설자가 해당 방에 어떤 수준의 유저를 권장하는지 표시하는 안내 정보다.

MVP에서는 다음과 같은 값을 사용할 수 있다.

- `ALL_LEVELS`: 경험 무관
- `BEGINNER_WELCOME`: 초보자 환영
- `EXPERIENCED_PREFERRED`: 경험자 위주

해당 값은 안내 목적으로만 사용하며, 서버가 참가자의 실제 경험 수준을 검사하거나 참가를 차단하지 않는다.

경험 수준을 이용한 검색·필터는 P0 이후 기능 후보로 검토한다.

#### 룰마스터 진행 여부

방 개설자가 해당 방에서 규칙 설명과 게임 진행을 담당하겠다고 직접 표시한 것을 의미한다.

- 개설자의 자기신고 정보다.
- 플랫폼은 룰 숙련도나 자격을 검증하지 않는다.
- 게임 중심과 사람 중심 방 모두 설정할 수 있다.

#### 방 상태(RoomStatus)

MVP에서는 다음 상태를 사용한다.

- `RECRUITING`: 모집 중이며, 시작 시각 전 참가할 수 있는 상태
- `CLOSED`: 정원이 찼거나 시작 시각에 도달하여 모집이 종료된 상태
- `CANCELED`: 개설자가 취소한 상태
- `FINISHED`: 개설자가 종료 처리했거나 시스템이 자동 종료 처리한 상태

방은 생성 직후 `RECRUITING` 상태로 생성된다. 상태 전이는 다음의 정상 흐름만 MVP에서 다룬다.

- 모집 정원이 모두 차거나 시작 시각에 도달하면 `RECRUITING`에서 `CLOSED`로 전환한다.
- 시작 시각 전 참가 취소로 좌석이 생기면 `CLOSED`에서 `RECRUITING`으로 되돌아간다.
- 개설자는 `RECRUITING` 또는 `CLOSED` 상태의 방을 `CANCELED`로 변경할 수 있다.
- 개설자는 `status = CLOSED`이고 `now >= startsAt`일 때만 방을 `FINISHED`로 변경할 수 있다.
- `now >= startsAt + 24시간`일 때 방이 여전히 `CLOSED`이면 시스템이 `FINISHED`로 변경한다.
- `CANCELED`, `FINISHED` 상태에서는 수정하거나 참가할 수 없다.

## 6. 1차 MVP API

1차 MVP에서는 총 15개의 API를 제공한다.

| #  | API | 메서드/경로 | 인증 필요 | 정상 성공 기준 |
|----|---|---|---|---|
| 1  | 회원가입 | `POST /api/auth/signup` | N | 신규 유저 생성 |
| 2  | 로그인 | `POST /api/auth/login` | N | 인증 토큰 발급 |
| 3  | 내 프로필 조회 | `GET /api/users/me` | Y | 본인 프로필 조회 |
| 4  | 내 프로필 수정 | `PATCH /api/users/me` | Y | 본인 프로필 수정 |
| 5  | 게임 목록·검색 | `GET /api/games?keyword=...&page=...&size=...` | N | 게임 목록 조회 및 게임명 검색 |

| 9  | 방 상세 조회 | `GET /api/rooms/{roomId}` | N | 공개 또는 참가자 전용 방 상세 조회 |
| 10 | 방 수정 | `PATCH /api/rooms/{roomId}` | Y | 개설자가 방 정보 수정 |

| 12 | 방 종료 | `PATCH /api/rooms/{roomId}/status` | Y | 방을 `FINISHED` 상태로 변경 |
| 13 | 방 참가 | `POST /api/rooms/{roomId}/participants` | Y | 신규 참가·재활성화 후 `201 Created`와 `participationStatus = ACTIVE`, `roomStatus`, 인원·잔여석 반환 |
| 14 | 참가 취소 | `DELETE /api/rooms/{roomId}/participants/me` | Y | 본인 참가 취소 후 `200 OK`와 `participationStatus = CANCELED`, `roomStatus`, 인원·잔여석 반환 |
| 15 | 내 모임 조회 | `GET /api/users/me/rooms?role=all\|joined\|hosted&page=...&size=...` | Y | `role` 기준 본인의 참여·개설 방 이력 조회 |

### 6.1 목록 조회 경로와 파라미터

게임 목록은 다음 경로로 조회한다.

```http
GET /api/games?keyword=...&page=...&size=...
```

- `keyword`는 게임명을 대상으로 하는 MVP의 기본 검색이다.

방 목록은 다음 경로로 조회한다.

```http
GET /api/rooms?type=GAME_FOCUSED&gameId=...&page=...&size=...
GET /api/rooms?type=PERSON_FOCUSED&keyword=...&page=...&size=...
```

- `type`은 필수 파라미터다.
- `type=GAME_FOCUSED` 목록은 `gameId`가 필수이며, 선택한 게임의 게임 중심 방 목록을 조회한다. `keyword`는 받을 수 없고 포함하면 `VALIDATION_ERROR`다.
- `type=PERSON_FOCUSED` 목록은 `gameId`를 생략해야 하며, 값이 전달되면 `VALIDATION_ERROR`다. `keyword`는 선택값이며 방 제목을 부분 일치로 검색한다.
- `type`, `gameId`는 탐색 경로를 위한 목록 구분값이며, 방 조건 필터가 아니다.
- `keyword`는 사람 중심 방의 기본 제목 검색이며, 1차 MVP에서 제외한 조건 필터가 아니다.
- 게임 목록·방 목록·내 모임 목록은 `page`(기본값 0)와 `size`(기본값 10, 최대 100)를 사용한다. `page`는 0 이상, `size`는 1 이상 100 이하여야 하며 범위를 벗어나면 `VALIDATION_ERROR`다.
- `CANCELED`와 `FINISHED` 상태의 방은 목록 조회에서 제외한다.
- 게임 목록에서는 게임명 기본 키워드 검색만 제공한다.
- 방 상태, 인원, 예상 플레이 시간, 난이도, 경험 수준, 태그 기반 필터는 1차 MVP에서 제공하지 않는다.

내 모임은 다음 기준으로 조회한다.

- 경로는 `GET /api/users/me/rooms?role=...&page=...&size=...`다.
- `role=joined`: `Participation.status = ACTIVE`이고 `Room.status != CANCELED`인 본인 참가 방만 반환한다. 참가 취소한 `CANCELED` 관계와 방이 취소된 `CANCELED` 방은 제외하고, `FINISHED` 방은 실제 참여 이력으로 포함한다.
- `role=hosted`: 본인이 개설한 방
- `role=all`: `joined`와 `hosted`의 중복 없는 합집합

## 7. 1차 MVP 운영 규칙

### 7.1 프로필

- 유저는 본인의 프로필을 조회하고 수정할 수 있다.
- 방 개설자와 참가자 표시를 위해 닉네임을 사용한다.
- 타 유저 공개 프로필 조회는 MVP에서 제공하지 않는다.
- 프로필 이미지의 등록·변경은 P0 범위에서 제공하지 않는다.

### 7.2 게임

- 게임 데이터는 운영자가 사전에 더미 또는 초기 데이터로 입력한다.
- 비로그인 유저도 게임 목록과 검색 결과를 조회할 수 있다.
- 유저의 신규 게임 등록·수정·삭제는 지원하지 않는다.

### 7.3 방 생성

- 유저는 방을 생성할 수 있다.
- 게임 중심 방은 게임을 반드시 선택한다.
- 사람 중심 방의 게임 선택은 선택 사항이다.
- 방 시작 시각은 생성 시점보다 미래여야 한다.
- MVP 서비스 제공 지역은 홍대로 고정하며, 생성 시 지역은 입력받지 않고 장소만 입력한다
- 개설자가 입력하는 모집 정원은 개설자를 제외한 1명 이상 10명 이하의 인원이다.
- 방 생성 직후 상태는 `RECRUITING`이다.
- 개설자는 생성 시 자동으로 참가자 목록에 포함된다.
- 룰마스터 진행 여부는 개설자가 직접 선택한다.

### 7.4 참가

- 참가 신청은 선착순 즉시 확정 방식이다.
- 개설자의 별도 승인 과정은 없다.
- 시작 시각 전 `RECRUITING` 상태의 방에만 참가할 수 있다.
- `CANCELED`, `FINISHED` 상태의 방에는 참가할 수 없다.
- 동일 유저는 같은 방에 활성 참가 상태를 하나만 가진다.
- 동일 유저는 시간대가 겹치는 다른 방에도 추가 참가할 수 있다.
- 신규 참가와 기존 `CANCELED` 관계 재활성화는 모두 `201 Created`를 반환한다. 공통 응답 객체의 `data`에는 `participationStatus = ACTIVE`와 참가 관계 변경·상태 전이 뒤의 `roomStatus`, `participantCount`, `remainingRecruitmentSeats`를 포함한다.

### 7.5 정원 및 모집 상태

- 방을 생성할 때 개설자를 제외한 정원을 입력하며, 개설자는 자동으로 참가자 목록에 포함된다.
- 개설자를 포함한 현재 참가자 수가 전체 정원에 도달하면 상태를 `CLOSED`로 변경한다.
- `CLOSED` 상태에서는 추가 참가를 받지 않는다.
- 시작 시각 전 참가 취소로 자리가 생기면 `RECRUITING`으로 되돌린다.
- 시작 시각 이후에는 참가 취소로 자리가 생겨도 `RECRUITING`으로 되돌리지 않는다.
- 참가 요청은 대상 방의 상태·남은 자리·중복 참가를 확인하고 참가 관계를 생성 또는 재활성화한 뒤 상태를 계산하는 하나의 트랜잭션으로 처리한다.
- 인증과 방 존재 확인 뒤 참가 요청 실패 오류는 다음 우선순위로 반환한다.
  1. 방이 `CANCELED`, `FINISHED`인 경우: `ROOM_NOT_RECRUITING`
  2. 요청자가 주최자이거나 현재 `ACTIVE` 참가 관계가 있는 경우: `ALREADY_PARTICIPATING`
  3. `remainingRecruitmentSeats = 0`인 경우: `CAPACITY_EXCEEDED`
  4. `now >= startsAt`이거나 `status != RECRUITING`인 경우: `ROOM_NOT_RECRUITING`
- 마지막 좌석 참가로 정원이 가득 차 방이 `CLOSED`로 전환된 경우, 이후 참가 요청에는 `CAPACITY_EXCEEDED`를 반환한다.
- P0는 선착순 처리 순서의 공정성이나 대규모 동시 요청의 성능 목표는 정하지 않지만, 어떤 요청에서도 모집 정원을 초과해 `ACTIVE` 참가 관계를 만들지 않는다.

### 7.6 수정

- 수정은 개설자만 할 수 있으며, 저장된 `startsAt`보다 현재 시각이 이르고 `status = RECRUITING`이며 개설자 외 `ACTIVE` 참가자가 없을 때만 허용한다.
- `roomType`과 지역은 수정할 수 없다. 수정 가능한 필드와 `null`·생략의 의미는 [API 명세서](API.md)의 `RoomUpdateRequest`를 따른다.
- 개설자 외 `ACTIVE` 참가자가 한 명 이상이면 수정은 `ROOM_UPDATE_NOT_ALLOWED_WITH_ACTIVE_PARTICIPANTS`로 거절한다.

### 7.7 참가 취소

- 개설자가 아닌 참가자는 자신의 참가를 취소할 수 있다.
- 개설자는 참가 취소 API를 사용할 수 없다.
- 참가 취소는 `now < startsAt`일 때만 가능하다. 시작 시각 이후 요청은 `INVALID_ROOM_STATUS_TRANSITION`으로 거절한다.
- 인증과 방 존재 확인 뒤 참가 취소 실패 오류는 다음 우선순위로 반환한다.
  1. 요청자가 주최자인 경우: `FORBIDDEN`
  2. 현재 `ACTIVE` 참가 관계가 없는 경우: `PARTICIPATION_NOT_FOUND`
  3. `now >= startsAt`인 경우: `INVALID_ROOM_STATUS_TRANSITION`
- 참가 취소 성공 시 `200 OK`를 반환하며, 공통 응답 객체의 `data`에는 `participationStatus = CANCELED`와 취소 뒤의 `roomStatus`, `participantCount`, `remainingRecruitmentSeats`를 포함한다.
- 취소 후 시작 시각 전 방이 `RECRUITING` 상태이고 자리가 있다면 다시 참가할 수 있다.

### 7.8 방 취소

- 개설자는 `RECRUITING` 또는 `CLOSED` 상태의 자신이 만든 방을 취소할 수 있다.
- 개설자가 자신의 모임을 그만두려면 방 자체를 취소한다.
- 방 취소는 데이터를 물리적으로 삭제하지 않고 `CANCELED` 상태로 변경한다.
- 방 취소 시 참가자 알림은 1차 MVP 범위에서 제외한다.
- 개설자는 방을 유지한 채 자신의 참가만 취소할 수 없다.

### 7.9 방 종료

- 개설자는 `status = CLOSED`이고 `now >= startsAt`일 때만 방을 `FINISHED` 상태로 변경할 수 있다.
- `now >= startsAt + 24시간`일 때 방이 여전히 `CLOSED`이면 시스템이 `FINISHED` 상태로 변경한다.

### 7.10 조회

- 비로그인 유저도 게임 목록·검색·상세를 조회할 수 있다.
- 비로그인 유저와 방 관계가 없는 로그인 유저는 `RECRUITING`, `CLOSED` 방의 공개 정보만 조회할 수 있다. 일반 방 목록에서는 `CANCELED`, `FINISHED` 상태를 제외한다.
- 참가와 방 생성은 로그인 후 사용할 수 있다.
- 공개 방 응답에는 사용자 ID, 주최자·참가자 목록, 정확한 `place`를 포함하지 않는다. 주최자와 현재 `ACTIVE` 참가자만 정확한 장소와 닉네임 기준 참가자 목록을 조회할 수 있다.
- `CANCELED`, `FINISHED` 방의 직접 상세는 주최자와 현재 `ACTIVE` 참가자만 조회할 수 있고, 그 외 요청에는 404를 반환한다.
- 내 모임 이력은 해당 유저 본인만 조회할 수 있으며, 각 항목은 `myRole`, `participationStatus`, 현재 요청자 기준 `joinable`을 반환한다. `role=joined`에는 현재 `ACTIVE` 참가 관계의 방만 남기고, 참가 취소한 관계와 `CANCELED` 방은 제외한다. `FINISHED` 방은 실제 참여 이력으로 포함한다. 정확한 장소와 참가자 목록은 반환하지 않는다.
- 이메일, 인증 정보, 사용자 ID는 다른 유저에게 노출하지 않는다.

## 8. 1차 MVP 구현 완료 기준

- 6절의 15개 API가 [API 명세서](API.md)의 요청·성공 응답·오류 코드대로 재현된다.
- 모든 성공 응답은 HTTP 상태 코드와 같은 `status`와 `data`를, 실패 응답은 `status`, `code`, `message`, `data: null`을 반환한다. 목록 API의 `data`는 `content`, `page`, `size`, `totalElements`, `totalPages`, `hasNext`를 포함하며 기본 `page=0`, `size=10`, 최대 `size=100`을 따른다.
- 비로그인 또는 방 관계가 없는 유저는 공개 방 응답만 받고, 주최자·현재 `ACTIVE` 참가자만 정확한 장소와 참가자 목록을 받는다. `CANCELED`, `FINISHED` 상세는 권한 없는 요청에 404를 반환한다.
- `recruitmentCapacity` 1과 10은 생성할 수 있고 0과 11은 `VALIDATION_ERROR`로 거절한다. 마지막 자리에 참가하면 `CLOSED`가 되며, 시작 전 참가 취소로 자리가 생기면 `RECRUITING`으로 되돌아가고 재참가할 수 있다.
- 참가 요청은 정원을 초과하지 않으며, 주최자 또는 중복 활성 참가 요청은 `ALREADY_PARTICIPATING`으로, 시작 시각 이후 참가 요청은 `ROOM_NOT_RECRUITING`으로, 참가 취소 요청은 `INVALID_ROOM_STATUS_TRANSITION`으로 거절한다. 신규 참가·재활성화는 모두 `201 Created`를 반환하고, 마지막 좌석이면 응답 `data`의 `roomStatus = CLOSED`, `remainingRecruitmentSeats = 0`이 검증된다. 마지막 좌석 이후 추가 참가 요청은 `CAPACITY_EXCEEDED`를, `CANCELED`·`FINISHED` 또는 모집 정원에 도달하지 않은 `CLOSED` 방 참가 요청은 `ROOM_NOT_RECRUITING`을 반환한다.
- 수정은 개설자·시작 전·`RECRUITING`·외부 `ACTIVE` 참가자 없음 조건에서만 가능하고, `roomType`은 변경할 수 없다.
- 모집 정원 충족 또는 `startsAt` 도달 시 `CLOSED`, `CLOSED && now >= startsAt`일 때 주최자 수동 `FINISHED`, `startsAt + 24시간` 경과 시 시스템 자동 `FINISHED` 전이가 검증된다.
