# P2 실시간 파티 매칭 기능 명세

이 문서는 P2에서 원하는 인원 범위의 사용자를 함께할 파티로 구성하는 `MATCH-01`의 축소 MVP 범위와 완료 기준을 정의한다. 현재 계약 준비·생산 코드·자동 검증·운영 배포와 실측 상태는 [P2 기능 상태 정본](README.md#기능별-현재-상태)에서만 판정한다. 이 문서만으로 현재 API·저장·아키텍처 계약이나 구현 상태를 판정하지 않는다.

P2 전체 범위와 공통 규칙은 [P2 명세](../P2-spec.md), 제품 방향은 [PRD](../PRD.md), 요청·응답·오류는 [API 명세](../API.md), 저장 구조와 제약은 [ERD](../ERD.md), 모듈 책임은 [아키텍처](../ARCHITECTURE.md), 논쟁적 기술 선택은 [ADR](../adr/README.md)이 소유한다. 이 문서는 제품 규칙·완료 기준만 소유하며, 구현 계약의 현재 내용은 각 정본을 따른다.

`MATCH-01`은 공개 사용자가 원하는 최소·최대 인원 범위만 등록해 함께할 파티를 찾는 기능이다. `매칭 요청 등록 → 인원 범위가 겹치는 후보 필터링 → 제한된 FIFO → 30초 제안 응답 → 전원 수락에 따른 매칭 확정 → 전용 채팅 연결`을 하나의 깊은 세로 흐름으로 구현한다. 게임 선택·플랫폼 연동·외부 게임 실행·시작·완료는 MATCH가 판정하지 않으며, 성공 파티 채팅에서 사용자가 원하는 게임을 직접 정한다. 기존 오프라인 ROOM 모집을 자동화하거나 온라인 ROOM·별도 플레이 세션을 만드는 기능도 아니다.

## MATCH-01 실시간 파티 매칭

사용자가 희망 파티 인원의 최소·최대 범위를 등록하면 인원 조건과 안전 조건을 만족하는 매칭 요청으로 후보 파티를 만들고, 전원 수락 뒤 성공 파티 채팅으로 이동하도록 돕는다. 채팅에서 참가자들이 게임을 정하고 진행하며, 공개 출시에는 신고 접수와 차단 목록을 포함한다.

### 축소 MVP의 핵심 범위

| 단계 | 이번 MVP의 책임 | 깊이를 증명하는 기준 |
| --- | --- | --- |
| 매칭 요청 | 사용자가 원하는 인원 최소·최대와 대기 시도를 저장한다. `minPlayers > 0`이고 `minPlayers <= maxPlayers`인지 검증한다 | 사용자당 활성 매칭 요청 하나, 중복 요청 멱등성 |
| 후보 | 인원 범위 교집합과 차단 관계를 만족하는 매칭 요청만 선별한다. 실제 파티 인원은 교집합의 하한으로 정한다 | 실제 구성 가능한 후보만 필터링하고 쿼리 계획·p95를 측정한다 |
| 우선순위 | 구성 가능한 후보 안에서 현재 대기 시도의 `prioritySince`가 이른 매칭 요청부터 실제 파티에 필요한 인원만 선택한다 | 다중 matcher 경합에도 중복 제안·부분 성공이 없다 |
| 제안 | 후보 파티와 30초 응답 기한을 제시하고 프로필 이미지·인원 수만 보여준 뒤 수락·이번 제안 건너뛰기·취소를 받는다 | 확정 후 닉네임·이미지 표시와 응답·만료·취소 경합을 검증한다 |
| 확정 | 전원 수락을 한 번만 원자적으로 확정한다 | 재시도·서버 재시작 뒤에도 성공 파티가 중복 생성되지 않는다 |
| 채팅 | 성공 매칭 전용 접근 관계로 기존 `chat`에 연결한다 | 연결 중단 뒤 상태 조회 복구, 24시간 종료·7일 삭제를 검증한다 |
| 안전 | 신고 접수와 `설정 > 차단 목록`의 차단·해제를 제공한다 | 차단된 두 사용자가 새로운 후보에 함께 들어가지 않는다 |
| 검증 | 정상 흐름과 동시성·재접속·부하·성능 개선 전후 측정을 함께 완료한다 | 테스트·측정 증거가 없으면 기능 완료로 판정하지 않는다 |

이번 MVP에서는 시스템 게임 선택·게임 투표·게임 추천, 룰 설명 가능 여부와 링크 공유 담당자 매칭, 5분 대기 후 조건 완화 선택지, `베스트 인원`·`추천 인원` 표시와 점수화를 제공하지 않는다. 사용자는 조건을 바꾸려면 기존 매칭 요청을 취소하고 새 매칭 요청을 등록한다.

### 기능 규칙

#### 매칭 조건과 매칭 요청

- 로그인 사용자만 현재 인증·인가와 CSRF 규칙을 통과해 매칭 요청을 등록·조회·취소한다.
- 한 사용자는 동시에 하나의 비종료 매칭 요청만 가진다. 동시·중복 요청으로 `WAITING`, `PROPOSED`, `PAUSED` 매칭 요청을 중복 생성하지 않는다.
- `PREPARING` 또는 아직 명시적으로 나가지 않은 `ACTIVE` 성공 파티의 참가자 접근 관계가 있는 사용자는 새 매칭 요청을 등록하거나 재대기하지 않는다. `ACTIVE` Party에서 명시적으로 나간 사용자는 해당 접근을 잃고 다른 현재 매칭 상태가 없으면 새 대기 시도를 시작할 수 있다. 이 예외도 재접속 상태 조회가 현재 요청과 현재 성공 파티를 동시에 반환하지 않도록 한다.
- 매칭 요청에는 사용자가 입력한 `minPlayers`와 `maxPlayers`만 저장한다. `1 <= minPlayers <= maxPlayers <= 32767`이어야 하며, 저장된 값은 사용자가 입력한 범위와 같다.
- MATCH 요청·후보·제안·성공 파티·현재 상태 조회에는 게임과 플랫폼을 포함하지 않는다. 게임 카탈로그를 읽거나 게임 지원 인원 범위를 검증·추천하지 않는다.
- 유효한 요청은 후보가 없더라도 등록해 `WAITING`으로 유지한다. 후보 선별 시 두 요청의 인원 범위가 겹치지 않으면 후보로 구성하지 않는다.
- 후보 파티가 확정되면 실제 파티 인원은 선택된 모든 매칭 요청의 인원 범위 교집합의 하한, 즉 각 요청의 `minPlayers` 중 최댓값으로 정한다. 이 값이 교집합의 상한을 넘으면 후보를 만들지 않는다.
- 대기 화면과 현재 상태 조회는 사용자가 등록한 `minPlayers`·`maxPlayers`를 그대로 보여준다. 게임 지원 범위에 맞춰 범위를 조정하거나 이를 알리는 별도 문구를 제공하지 않는다.

#### 우선순위와 대기 시도

| 용어 | 의미 | `MATCH-01` 적용 |
| --- | --- | --- |
| `queuedAt` | 현재 대기 시도를 시작한 서버 시각 | 해당 시도 시작 시 고정한다 |
| `prioritySince` | 실제 매칭 가능한 매칭 요청끼리 FIFO 순서를 정할 기준 시각 | MVP에서는 현재 대기 시도의 `queuedAt`과 같다. 자동 재대기에서는 유지하고, 사용자가 새 대기 시도를 시작하면 새 `queuedAt`으로 바꾼다 |

- 후보 선별은 [ADR-0077](../adr/matching/0077-match-no-game-player-range.md)의 결정적 절차를 따른다. 가장 오래된 `WAITING` 요청을 anchor로 고정하고, anchor의 `minPlayers`부터 `maxPlayers`까지 `targetPartySize`를 오름차순으로 시도한다. 각 시도에서 `prioritySince ASC, matchRequestId ASC` 순으로 호환 요청을 스캔해 차단 요청은 제외하고 `targetPartySize`명에서 멈춘다. 정확히 그 수를 선택했고 선택된 `minPlayers`의 최댓값도 `targetPartySize`일 때만 후보를 확정한다. 호환되지 않는 요청은 건너뛰지만 먼저 선택된 호환 요청을 뒤 요청으로 바꾸는 backtracking은 하지 않는다. 모든 시도가 실패하면 anchor는 `WAITING`으로 남는다.
- 각 대기 시도는 `queuedAt`과 `prioritySince`를 고정한다. 다른 참가자 때문에 제안이 종료되거나 채팅 준비가 실패해 같은 대기 시도에서 자동 재대기하면 두 값(`queuedAt`, `prioritySince`)을 유지한다.
- `WAITING` 매칭 요청은 시간 경과만으로 자동 만료되지 않는다. `PAUSED` 사용자가 `다시 찾기`를 누르거나 사용자가 기존 매칭 요청을 취소한 뒤 새 매칭 요청을 등록하면 새 대기 시도를 시작해 두 값을 현재 시각 기준으로 리셋한다.
- 사용자가 대기 화면을 벗어나거나 네트워크·WebSocket 연결이 일시적으로 끊겨도 서버의 매칭 요청과 두 시각은 유지된다. 사용자가 명시적으로 취소하거나 열린 제안이 수락·재대기·취소·미응답으로 처리되거나 채팅 준비 실패를 시스템이 복구 처리할 때만 매칭 요청 상태가 바뀐다.
- 이번 MVP는 대기 중 조건 완화 화면을 제공하지 않는다. 조건을 바꾸려면 기존 매칭 요청을 취소하고 새 매칭 요청을 등록한다.

#### 후보 파티와 제안

- 후보 파티의 실제 인원은 선택된 모든 매칭 요청의 인원 범위 교집합의 하한이다.
- 차단된 두 사용자는 새로운 후보 파티에 함께 포함하지 않는다.
- 한 사용자에게 동시에 둘 이상의 유효 제안을 만들지 않는다. 후보 목록과 파티 구성은 제안 생성 시 고정한다.
- 제안에는 실제 파티 인원과 제안 생성 시각부터 30초 뒤로 고정한 응답 기한 `respondBy`를 표시한다. 매칭 제안 화면에는 참가 예정자의 공개 프로필 이미지와 실제 파티 인원 수만 표시하며, 전원 수락 전에는 닉네임·사용자 ID·이메일·매칭 조건을 표시하지 않는다.
- 사용자는 `수락`, `이번 제안 건너뛰고 재대기`, `매칭 취소` 중 하나를 선택한다. 최초 유효 응답은 최종이며 중복 요청은 응답과 상태를 중복 전이시키지 않는다.
- 한 명이 재대기·취소를 선택하면 다른 사용자의 30초 기한을 기다리지 않고 현재 제안을 종료한다.
- 마지막 `ACCEPT`, `REQUEUE`, `CANCEL`, 매칭 요청 취소와 30초 기한 만료가 동시에 오면 한 제안은 하나의 종결 결과만 가진다. 각 사용자의 결과 규칙은 이 절을 따르고, 종결 경합의 실행 순서는 [아키텍처](../ARCHITECTURE.md#p2-match-제안채팅-복구-흐름)가 소유한다.
- 다른 사용자 때문에 제안이 끝난 수락자와 조기 종료 시점의 미결정 사용자는 기존 대기 시도의 시간과 우선순위로 자동 재대기한다. `이번 제안 건너뛰고 재대기`를 직접 선택한 사용자는 새 대기 시도를 시작한다.
- `respondBy`까지 응답하지 않은 사용자는 `PAUSED`가 된다. 그 때문에 제안이 종료된 수락자는 기존 `queuedAt`·`prioritySince`로 자동 재대기하고, 미응답 사용자는 `다시 찾기`를 눌러야 새 대기 시도를 시작한다.
- [성공 파티 채팅](#성공-파티-채팅)의 명시적 나가기 뒤에는 자동 충원·자동 재매칭하지 않는다. 마지막 사용자가 아닌 경우 남은 성공 파티는 유지한다.

#### 성공 파티 채팅

- 전원 수락 전에는 성공 파티나 채팅 접근 권한을 부여하지 않는다. 전원이 수락하면 성공 파티와 참가자 접근 관계를 한 번만 원자적으로 확정한다.
- 매칭 성공은 기존 ROOM·참가 상태나 별도 `OnlinePlaySession`으로 표현하지 않는다. 성공 매칭 결과와 참가자 관계를 MATCH 채팅 접근 근거로 사용한다.
- 성공 확정 시각부터 5분 동안 `PREPARING` 채팅 생성을 자동 재시도하고 사용자에게 `채팅 준비 중`을 표시한다. 5분 뒤에도 채팅 생성에 실패하면 시스템은 실패한 파티와 채팅 접근 관계를 정리하고, 연결된 모든 매칭 요청을 `WAITING`으로 자동 복귀시킨다. 이때 기존 `queuedAt`·`prioritySince`를 유지해 후순위로 밀지 않으며, 사용자가 취소하거나 새 매칭 요청을 만들도록 선택하게 하지 않는다. 시스템은 다른 사용자를 자동 충원하지 않는다.
- 채팅이 처음 사용 가능해진 서버 시각을 `chatOpenedAt`, 그로부터 24시간 뒤를 예약 종료 시각 `closesAt`으로 고정한다.
- 활성화 시 시스템 메시지로 종료 예정 시각과 `CLOSED` 후 7일 뒤 URL 텍스트를 포함한 메시지 삭제 예정 사실을 안내한다. 예약 종료 1시간 전에는 종료까지 남은 시간과 삭제 예정 시각을 다시 안내한다. 재접속한 사용자는 기존 시스템 메시지 이력을 확인한다.
- 외부 URL은 채팅 메시지 본문으로만 공유한다. 별도 링크 등록·조회, 링크 미리보기와 링크 유효성 검증은 MVP 범위에 넣지 않는다.
- 사용자의 **명시적 나가기**만 성공 파티 접근을 끝낸다. 브라우저·WebSocket 연결 종료와 서버 재시작은 나가기가 아니므로 재접속 뒤에도 같은 성공 파티를 복구할 수 있다. 마지막 현재 사용자가 명시적으로 나가면 그 시각에 채팅을 조기 종료하고, 예약 종료 1시간 전 시스템 메시지는 추가로 만들지 않는다. 마지막 사용자가 아닌 경우 나간 사용자만 접근을 잃고 남은 파티는 유지한다.
- 예약 종료 또는 마지막 사용자의 명시적 나가기로 `CLOSED`가 되면 모든 사용자의 조회·전송·실시간 구독을 즉시 차단한다.
- URL 텍스트를 포함한 MATCH 채팅 메시지와 성공 파티·참가자 접근 관계는 실제 `CLOSED` 시각부터 7일 동안 사용자에게 공개하지 않은 채 보존한 뒤 물리 삭제한다. 기존 ROOM 채팅의 30일 보존 정책은 그대로 유지한다.

#### 신고와 차단

- 공개 사용자는 다른 사용자를 신고하거나 차단할 수 있다. 신고는 접수만 제공하며, 신고자·피신고자·고정 사유 카테고리·접수 시각만 접수 시각부터 7일 보관한다. 자유 입력과 첨부는 받지 않고, 신고 사실·사유·기록은 신고자·피신고자 및 다른 일반 사용자에게 공개하지 않는다. 관리자 화면·운영자 검토·자동 제재·이의제기는 MVP 범위에서 제외한다.
- 신고는 현재 제안·성공 파티·이후 매칭 후보에 자동으로 영향을 주지 않는다. 이후 매칭 제외는 사용자가 별도로 차단할 때만 적용한다.
- 차단 목록은 `설정 > 차단 목록`에서 확인하고 차단 해제할 수 있다.
- 차단은 이후 새로운 매칭 후보에 함께 포함되지 않도록만 적용한다. 차단 사실을 직접 알리는 알림·사유·전용 오류를 제공하지 않는다.
- 차단은 안전을 위한 일방 관계로만 사용하며, 사용자 간 친구 관계를 만들거나 친구 관계 기반 매칭 조건·우선순위·추천·초대를 제공하지 않는다.
- 이미 같은 성공 파티에 있는 사용자를 차단해도 파티를 자동 퇴장시키거나 재매칭하지 않는다.

#### 상태·동시성·복구

상태 이름은 의미를 설명하는 초안이며 API enum과 저장값은 API·ERD 변경에서 확정한다.

| 대상 | 상태 의미 |
| --- | --- |
| 매칭 요청 | `WAITING`, `PROPOSED`, `PAUSED`, `MATCHED`, `CANCELED` |
| 매칭 제안 | `OPEN`, `CONFIRMED`, `DECLINED`, `EXPIRED`, `CANCELED` |
| 성공 파티 채팅 | `PREPARING`, `ACTIVE`, `CLOSED`, `PURGED` |

- PostgreSQL을 매칭 요청·제안·응답·성공 파티의 정본으로 사용한다. 조건부 갱신, 유니크 제약과 멱등키로 중복 생성·중복 응답·부분 성공을 막는다. 구체적인 잠금 방식과 인덱스는 측정과 ADR로 확정한다.
- 기존 채팅의 Redis 세션·Pub/Sub·전송 제한은 재사용한다. MATCH 후보 점유·응답·채팅 정합성을 위해 Redis 분산 락을 새로 도입하는 것은 선행 조건이 아니며, DB 경합 측정에서 필요성이 확인될 때만 별도 ADR로 결정한다.
- 여러 matcher가 같은 후보를 선택해도 하나만 점유하고, 전원 수락·재대기·취소·제안 응답 기한 만료·채팅 준비 실패가 경합해도 하나의 최종 결과로 수렴한다.
- 채팅 생성·복구와 종료·삭제를 재시도해도 채팅방과 시스템 메시지를 중복 생성하지 않는다.
- 서버 재시작 뒤 열린 제안의 응답 기한과 채팅 종료·삭제 대상을 최신 영속 상태에서 다시 판단한다.
- 실시간 이벤트는 정본이 아니다. 이벤트 유실·중복·순서 역전과 연결 해제 뒤에도 현재 상태 조회로 매칭 요청·제안·채팅 상태를 복구하며, 연결 해제를 자동 수락·거절로 해석하지 않는다.

#### 개인정보와 운영 데이터

- 제안 전에는 다른 사용자의 전체 대기 목록·조건 원문·식별 정보를 공개하지 않는다.
- 전원 수락으로 매칭이 확정된 뒤 성공 파티 채팅에는 현재 공개 프로필의 닉네임과 프로필 이미지만 제공하고 사용자 ID·이메일·인증 정보를 노출하지 않는다.
- 사용자 ID·이메일·세션·자유 입력 원문(외부 URL 텍스트 포함)을 metric label로 사용하지 않는다.
- 종료 매칭 요청·제안·응답·성공 파티·참가자 접근 관계의 사용자별 원자료는 각 업무 종료 시점부터 7일 뒤 완전 삭제한다. 이후에는 사용자와 연결할 수 없는 집계 결과 코드만 보존한다.
- 신고 접수 자료는 접수 시각부터 7일 보관한 뒤 물리 삭제하며, 신고 사유 카테고리도 그 이후에는 보존하지 않는다.
- 관측 수집 실패는 매칭·채팅 결과를 바꾸지 않는다.

### 완료 기준

- `MATCH-01-AC1` 사용자가 입력한 최소·최대 인원 범위로 매칭 요청을 등록·조회·취소하고, 유효한 요청은 후보가 없어도 `WAITING`을 유지한다. `PREPARING`·아직 명시적으로 나가지 않은 `ACTIVE` 성공 파티 접근 관계가 있는 사용자는 새 요청을 만들지 않아 한 사용자에게 현재 매칭 흐름 하나만 남긴다.
- `MATCH-01-AC2` 인원 범위 교집합의 하한을 만족하는 후보만 구성하고 차단된 두 사용자를 같은 새 후보에 포함하지 않는다.
- `MATCH-01-AC3` 실제 구성 가능한 후보 안에서 현재 대기 시도의 `prioritySince` 오름차순으로 실제 파티에 필요한 인원만 선택하고, 같은 시각 동점은 결정적으로 처리한다.
- `MATCH-01-AC4` 제안은 고정된 파티와 30초 응답 기한을 제공하며 제안 화면에는 공개 프로필 이미지·인원 수만, 매칭 확정 후 성공 파티 채팅에는 공개 프로필 닉네임·이미지를 제공하고 수락·재대기·취소·미응답을 중복 없이 처리한다. 게임은 채팅에서 사용자들이 정한다.
- `MATCH-01-AC5` `WAITING` 매칭 요청은 시간 경과만으로 자동 만료되지 않는다. 자동 재대기는 기존 `queuedAt`·`prioritySince`를 유지하고, 사용자의 `다시 찾기`·직접 재대기·취소 후 새 매칭 요청은 새 대기 시도를 시작한다.
- `MATCH-01-AC6` 전원 수락을 한 번만 원자적으로 확정하고 자동 충원·부분 성공·중복 성공을 만들지 않는다.
- `MATCH-01-AC7` 성공 파티 채팅을 `PREPARING`에서 최대 5분 복구하고, 실패하면 성공 파티·참가자 접근 관계와 채팅 접근 권한을 정리한 뒤 연결된 모든 매칭 요청을 기존 `queuedAt`·`prioritySince`로 `WAITING`에 자동 복귀시킨다. 활성화·종료 1시간 전 시스템 메시지, 24시간 종료, 전원의 명시적 나가기 조기 종료와 `CLOSED` 후 7일 삭제도 적용한다.
- `MATCH-01-AC8` 다중 matcher·인스턴스, 중복 요청, 응답·제안 응답 기한 만료 경합, 서버 재시작과 연결 중단·재접속을 PostgreSQL 통합 테스트로 재현하고 하나의 최종 상태로 수렴함을 검증한다.
- `MATCH-01-AC9` candidate claim transaction·제안 생성·응답 완료 지연과 DB lock 대기를 부하 조건에서 측정하고, 인덱스·쿼리·트랜잭션 개선 전후의 p95·처리량·실패율을 비교한다. candidate claim transaction의 fixture·p95 범위는 별도 측정 계약을 따르고, 최종 확정·현재 상태 복구는 통합 검증으로 닫는다.
- `MATCH-01-AC10` `설정 > 차단 목록`의 차단·해제와 신고 접수를 제공하고, 신고 기록 비공개·7일 보관 후 물리 삭제·신고의 자동 차단 미발생·차단 우회 미발생을 검증한다.

- 기존 ROOM을 확장한 온라인 ROOM 또는 별도 `OnlinePlaySession`
- 종료된 성공 파티 채팅의 읽기 전용 제공
- 기존 오프라인 ROOM·참가·대기열 계약의 전면 교체

## 검증 증거 매핑

완료 기준은 자동 검증과 운영 측정 증거로 닫는다. 현재 통과 여부는 이 절에 반복하지 않고 [P2 기능 상태 정본](README.md#기능별-현재-상태)의 `자동 검증`·`운영 배포·실측` 열에서만 관리한다. 테스트와 측정은 MATCH-01의 핵심 기능이며, 정상 흐름만 통과한 상태를 완료로 표시하지 않는다.

### 운영 측정

실제 목표값은 기준선과 최소 표본을 확보한 뒤 확정한다. 후보 탐색 baseline의 fixture·round·원자료·통계·결과 채택 방법은 [MATCH-01 후보 탐색 baseline 측정 계약](../measurements/match-01-candidate-search-baseline-contract.md)만이 소유한다. 다음은 운영에서 관측할 제품 지표이며, baseline runner의 통계를 여기에서 다시 정의하지 않는다.

- 활성 매칭 요청 수, 매칭 요청 등록부터 제안 생성까지의 지연과 p50·p95·p99
- 후보 탐색 쿼리 시간, 반환 후보 수, DB lock 대기와 트랜잭션 재시도율
- 30초 제안의 수락·재대기·취소·미응답·일시 중지 비율
- 중복 활성 매칭 요청·중복 제안·중복 성공·부분 성공 건수. 정합성 위반 목표는 0건이다.
- WebSocket 이벤트 전달 지연, 연결 중단 후 상태 복구 시간과 복구 실패율
- 채팅 생성·자동 복구 결과, `PREPARING` 경과 시간, 24시간 종료와 실제 `CLOSED` 시각부터 7일 뒤 성공 파티·접근 관계·메시지·외부 링크 삭제 성공·실패 건수
- 예약 종료 1시간 전 대상 ACTIVE Party의 `CLOSES_IN_ONE_HOUR` SYSTEM 메시지 생성 성공·누락·중복·지연 건수. 조기 `CLOSED` Party는 대상에서 제외한다.
- 차단·해제·신고 접수 결과와 처리 지연. 사용자 ID·프로필·신고 본문은 metric label이나 일반 로그에 남기지 않는다.
- 부하 단계별 처리량·p95·실패율과 인덱스·쿼리·트랜잭션 개선 전후 비교

HTTP `2xx`, matcher 실행 또는 실시간 이벤트 발행만으로 매칭 성공·채팅 준비 완료를 판정하지 않는다. 영속 상태 전이와 사용자에게 복구 가능한 조회 결과가 모두 확인돼야 한다.

### 중단·재검토 조건

- 동일 매칭 요청 중복 제안·중복 성공·부분 성공이 재현되거나 DB lock 대기와 후보 탐색 p95가 측정 기준을 초과한다.
- 연결 중단·서버 재시작 뒤 매칭 요청·제안·채팅 상태가 복구되지 않거나 이벤트 중복이 사용자 응답을 중복 전이시킨다.
- 성공 파티 채팅의 접근 관계·시스템 메시지·자동 복구가 기존 채팅 계약과 충돌하거나 24시간 종료·7일 삭제가 기한 안에 수렴하지 않는다.
- 신고 접수·차단 동작이 실패하거나 차단 우회가 재현되면 공개 출시 전 안전 범위를 다시 검토한다.
