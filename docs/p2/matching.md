# P2 실시간 파티 매칭 기능 명세

이 문서는 P2에서 지금 온라인 보드게임을 함께할 파티를 구성하는 `MATCH-01`의 기능 규칙과 완료 기준을 정의한다. 현재 계약 준비·생산 코드·자동 검증·운영 배포와 실측 상태는 [P2 기능 상태 정본](README.md#기능별-현재-상태)에서만 판정한다. 현재 `MATCH-01`은 `선행 계약 필요`이며, 이 문서만으로 현재 API·저장·아키텍처 계약이나 구현이 준비됐다고 판정하지 않는다.

P2 전체 범위와 공통 규칙은 [P2 명세](../P2-spec.md), 제품 방향은 [PRD](../PRD.md), 요청·응답·오류는 [API 명세](../API.md), 저장 구조와 제약은 [ERD](../ERD.md), 모듈 책임은 [아키텍처](../ARCHITECTURE.md), 논쟁적 기술 선택은 [ADR](../adr/README.md)이 소유한다. 현재 API·ERD·아키텍처에는 `MATCH-01` 계약과 `matching` 모듈이 없으며, 이 문서만으로 현재 제공 기능이나 구현 계약이 변경됐다고 판정하지 않는다.

`MATCH-01`은 P2에서 정식 채택하는 공개 매칭 기능이다. 별도 초대 기반 파일럿 없이 공개 사용자를 대상으로 하며, 전원 수락으로 확정된 파티가 공통 외부 플랫폼으로 이동하기 전까지 필요한 투표와 채팅을 제공한다. 기존 오프라인 ROOM 모집을 자동화하거나 온라인 ROOM·별도 플레이 세션을 만드는 기능이 아니며, 실제 게임 실행·시작·완료는 판정하지 않는다.

## MATCH-01 실시간 파티 매칭

사용자가 여러 게임, 희망 파티 인원, 함께 사용할 외부 플랫폼, 룰 설명과 외부 링크 공유 가능 여부를 등록하면 조건에 맞는 파티와 고정 게임 후보를 제안하고, 전원 수락 뒤 게임 투표와 성공 파티 채팅으로 외부 온라인 보드게임 플레이를 시작하도록 돕는다. 공개 출시에는 신고·차단을 포함하고, 친구 관계와 친구 초대 큐는 포함하지 않는다.

| 구분 | 정본 |
| --- | --- |

| 사용자 문제 | 원하는 게임·인원·룰 설명 가능 사용자를 맞추고, 여러 후보 중 실제 플레이 게임과 링크 공유자를 빠르게 정하기 어렵다 |
| 핵심 사용자 | 특정 게임을 희망하고 룰 설명이 필요한 초보 사용자 |
| 허용 사용자 | 특정 게임을 고르지 않았지만 자신이 승인한 게임 목록과 선택한 외부 플랫폼에서 지금 함께 플레이할 파티가 필요한 사용자 |
| 검증 가설 | 여러 게임·희망 인원·룰 설명·링크 공유 조건을 수락 전에 맞추고 전원 수락 뒤 제한 시간 투표를 제공하면 외부 플랫폼으로 이동하기 전 조율 부담을 줄일 수 있다 |
| 기존 제품 경계 | [P1 ROOM·참가](../p1/room.md)의 상태를 매칭 상태로 재사용하지 않고, 성공 매칭 전용 접근 관계로 채팅을 연결한다. [P1 채팅](../p1/chatting.md)·[P1 알림](../p1/notification.md)의 기존 ROOM 의미는 재해석하지 않는다 |
| 신규 업무 경계 | `matching`이 티켓·후보 파티·제안·응답·투표·성공 파티 접근 관계를 소유하고, `chat`이 성공 파티 메시지·실시간 전달·종료 후 삭제를 소유한다 |
| 현재 계약 | [API](../API.md)에는 매칭 요청·응답이 없고, [ERD](../ERD.md)는 온라인 자동 매칭을 제외하며, [아키텍처](../ARCHITECTURE.md)에는 `matching` 모듈이 없다 |
| 제품 연결 | P2 정식 채택에 따라 [PRD의 후속 온라인 후보](../PRD.md#5-기능-요구사항)에 매칭 목적·공통 플랫폼·성공 파티 채팅 경계를 반영한다. 이 PR은 기능 문서의 정책을 먼저 확정한다 |
| 운영 연결 | [운영 관측](monitoring.md)과 [운영 대시보드 정책](dashboard.md)의 공통 원칙만 참조한다. `MATCH-01` 전용 관측 계약은 아직 등록하지 않는다 |

### 착수 전 기술 계약

다음 항목은 제품 추가 질문이 아니라 구현 전에 소유 정본과 ADR에서 대안을 비교해 확정할 기술 계약이다. 모두 반영·승인되기 전에는 `MATCH-01`을 `계약 준비 완료`로 바꾸지 않는다.

1. 필수 조건을 만족하는 후보만 남긴 뒤 `prioritySince`가 이른 순서로 처리하는 제한된 FIFO를 구현하고, 같은 시각의 결정적 동점 처리 근거를 남기는 방식
2. 티켓·제안·응답·투표·성공 파티·채팅 handoff의 API와 저장 구조·조건부 상태 전이
3. 다중 matcher의 후보 점유, 전원 수락·투표 종료 경합과 무작위 결과의 재현·감사 근거
4. 채팅 생성 자동 복구, `PREPARING` 5분·제안 30초·투표 5분·티켓 30분·채팅 24시간·원자료 7일 기한과 서버 재시작 뒤 만료 수렴 방식
5. P1 실시간 기반을 포함한 WebSocket·SSE·polling 조합과 공통 화면의 상태 복구 방식
6. 서버 작성 시스템 메시지, MATCH 전용 접근 관계·7일 보존 채팅과 기존 ROOM 채팅의 스키마·모듈 경계
7. 신고 사유·운영자 검토 큐·보존 기간과 차단 관계의 API·저장 구조. 신고·차단이 공개 출시에서 제공된다는 제품 범위는 이 문서가 소유하고, 세부 운영 계약은 별도 정본에서 확정한다.

### 기능 규칙

#### 매칭 조건과 티켓

- 로그인 사용자만 현재 인증·인가와 CSRF 규칙을 통과해 티켓을 등록·조회·취소한다.
- 한 사용자는 동시에 하나의 비종료 티켓만 가진다. 동시·중복 요청으로 `WAITING`, `PROPOSED`, `PAUSED` 티켓을 중복 생성하지 않는다.
- 사용자는 한 개 이상의 게임을 선택하거나 허용 범위를 선택한다. 서버는 티켓을 만들거나 사용자가 조건을 완화한 순간 화면에 보인 게임 ID 목록을 스냅샷으로 고정한다. 이후 게임 카탈로그가 바뀌어도 승인 범위가 자동으로 넓어지지 않는다.
- 게임을 지정한 사용자와 지정하지 않은 사용자를 별도 큐로 나누지 않는다. 친구 관계·친구 초대 큐·친구 그룹 매칭 없이 모든 티켓은 독립적으로 매칭한다.
- 사용자는 본인을 포함한 전체 파티의 최소·최대 희망 인원을 선택한다. 최소값은 최대값보다 클 수 없고, 게임 선택 화면에는 희망 인원 범위와 지원 인원이 하나 이상 겹치는 게임만 보여준다.
- 사용자는 티켓마다 함께 사용할 외부 플랫폼 하나를 선택한다. 후보 파티는 같은 플랫폼을 선택한 티켓으로만 구성하고, 해당 게임과 플랫폼의 조합이 지원되지 않으면 후보에서 제외한다.
- 사용자는 선택하거나 허용한 게임마다 룰 설명 가능 여부와 외부 플랫폼 링크 공유 가능 여부를 독립적으로 자기 선언한다.
- 룰 설명 필요 여부는 티켓 전체 조건이다. 룰 설명이 필요한 사용자가 한 명이라도 포함된 후보 파티는 각 후보 게임마다 해당 게임을 설명할 사용자를 최소 한 명 포함한다.
- 모든 후보 게임에는 해당 게임의 외부 링크를 공유할 수 있다고 선언한 사용자를 최소 한 명 포함한다.
- 외부 플랫폼 계정 ID·비밀번호·token을 수집하거나 계정 보유 여부·룰 설명 자격을 외부에서 검증하지 않는다.
- 설명 가능 사용자가 파티 확정 뒤 나가더라도 시스템이 새 사용자를 자동 충원하거나 확정 파티를 다른 파티로 바꾸지 않는다.

#### 안전 관계와 차단

- 공개 출시에는 다른 사용자를 신고하거나 차단할 수 있는 진입점을 제공한다. 신고는 차단과 독립된 행동이며 신고 사실·사유·처리 결과를 피신고자에게 알리지 않는다. 신고의 운영자 처리 세부는 별도 운영 계약에서 확정한다.
- 차단은 일방향 요청으로 시작하지만 결과는 양방향으로 적용한다. 차단한 두 사용자는 서로의 프로필·개인정보를 확인할 수 없고, 새로운 매칭 후보에 함께 포함되지 않는다.
- 이미 친구 관계였으면 차단 시 양쪽 친구 관계와 대기 중 친구 요청을 조용히 제거한다. 친구 관계 생성·관리는 MVP 기능이 아니며, 차단 목록 관리만 안전 기능으로 제공한다.
- 차단 목록은 `친구 관리 > 차단된 친구`에서 확인하며, 차단 해제는 즉시 적용하되 친구 관계를 자동 복구하지 않는다. 다시 친구가 되려면 새 친구 요청이 필요하다.
- 차단 사실을 직접 알리는 알림·사유·전용 오류를 제공하지 않는다. 차단으로 인한 프로필·매칭 접근 불가는 서비스 정책상 비공개 결과로 처리한다.
- 이미 같은 성공 파티에 있는 사용자를 차단해도 파티를 자동 퇴장시키거나 재매칭하지 않는다. 기존 파티의 접근·공용 채팅 표시 세부는 `chat` 계약에서 정하되, 차단을 이유로 부분 성공을 만들지 않는다.

#### 대기와 조건 완화

- 서버는 최초 대기 진입 시각 `queuedAt`과 `queuedAt + 30분`인 `expiresAt`을 고정한다. 재대기·일시 중지·재개로 총 유효 시간을 연장하지 않는다.
- 실제로 구성 가능한 후보 파티만 먼저 필터링하고, 그 안에서는 `prioritySince`가 이른 티켓을 먼저 처리한다. 베스트·추천 인원은 오래 기다린 티켓을 추월시키는 점수로 사용하지 않으며, 같은 시각의 결정적 동점 처리는 ADR에 남긴다. 최초 `prioritySince`는 `queuedAt`이다.
- 사용자는 대기 중 게임 중심·사람 중심 오프라인 모임 화면을 둘러볼 수 있다. 페이지 이동과 실시간 연결 해제는 티켓을 취소하거나 우선순위를 바꾸지 않는다.
- 공통 매칭 상태 화면은 서버 시각 기준 대기 경과 시간과 남은 유효 시간을 함께 표시한다.
- 대기 시작 5분 뒤에도 후보 파티를 구성하지 못하면 다음 선택지를 한 번 안내한다.

  1. 현재 조건으로 계속 기다리기
  2. 룰 설명이 가능한 다른 게임까지 허용 범위 넓히기
  3. 희망 파티의 최소·최대 인원 범위 넓히기
  4. 룰 설명 조건을 직접 해제하고 함께할 사람만 찾기
  5. 매칭 취소

- 5분 도달만으로 조건을 자동 변경하지 않는다. 사용자가 고른 변경만 최신 조건에 반영하고 기존 제안의 후보 목록을 뒤에서 수정하지 않는다.
- `expiresAt`에 도달한 `WAITING`, `PROPOSED`, `PAUSED` 티켓은 만료한다. `MATCHED`는 성공 파티를 확정한 종단 상태이므로 티켓 만료 대상이 아니다.
- `PAUSED` 사용자는 `다시 찾기`를 눌러야 `WAITING`으로 재개되며, 재개 시각을 새 `prioritySince`로 사용한다. 자동으로 다시 대기시키지 않고, `expiresAt`이 지난 뒤에는 새 티켓으로만 시작한다.

#### 후보 파티와 매칭 제안

- 후보 파티의 실제 인원은 모든 파티원의 최소·최대 희망 인원과 각 후보 게임의 지원 인원을 만족해야 한다.
- 투표 후보 게임은 모든 파티원이 승인한 고정 목록 안에 있고 실제 파티 인원과 공통 외부 플랫폼을 지원해야 한다. 룰 설명이 필요하면 설명 가능 사용자를, 모든 경우에 링크 공유 가능 사용자를 포함해야 한다.
- 가능한 후보가 여러 개여도 필수 조건을 통과한 후보 안에서 `prioritySince` 순서를 적용한다. 베스트·추천 인원은 필수 조건을 깨지 않는 표시·보조 신호일 뿐이며, FIFO를 뒤집는 가중치로 사용하지 않는다.
- 한 사용자에게 동시에 둘 이상의 유효 제안을 만들지 않는다. 무작위 선택만으로 전체 매칭 알고리즘을 정의하지 않는다.
- 제안에는 실제 파티 인원, 고정된 투표 후보 게임 목록, 공통 외부 플랫폼, 게임별 예상 시간과 룰 설명·링크 공유 가능 사용자 존재 여부를 보여준다.
- 제안 전에는 다른 사용자의 식별 정보를 공개하지 않는다. 수락 전 판단에는 능력 보유자의 존재 여부만 제공한다.
- 수락은 고정 후보 목록 안의 어떤 게임이 투표 또는 승인된 무작위 규칙으로 선정돼도 참여한다는 뜻임을 화면에 표시한다.
- 후보 목록은 제안 뒤 추가·제거하지 않는다. 목록이 달라지면 현재 제안을 종료하고 새 제안을 만든다.
- 모든 후보 티켓에 30초 이상의 유효 시간이 남았을 때만 제안을 만든다. 제안 생성 서버 시각부터 30초인 `respondBy`를 고정하고 어느 참가자의 `expiresAt`도 넘지 않게 한다.
- 사용자가 다른 화면에 있어도 같은 후보 게임 목록과 30초 응답창을 표시한다.

#### 응답·재대기·만료

- 사용자는 `수락`, `이번 제안 건너뛰고 재대기`, `매칭 취소` 중 하나를 선택한다. 재대기는 우선순위를 현재 시각부터 다시 계산한다는 점을 선택 전에 알린다.
- 사용자의 최초 유효 응답은 최종이며 중복 요청은 응답과 상태를 중복 전이시키지 않는다.
- 한 명이 재대기 또는 매칭 취소를 선택하면 다른 사용자의 30초 기한을 기다리지 않고 현재 제안을 종료한다.
- 다른 사용자 때문에 제안이 끝난 수락자와 조기 종료 시점의 미결정 사용자는 기존 `prioritySince`를 유지해 자동 재대기한다. 조기 종료된 제안의 미결정 응답은 기한 내 미응답으로 취급하지 않는다.
- `이번 제안 건너뛰고 재대기`를 선택한 사용자는 선택 시각을 새 `prioritySince`로 사용해 자동 재대기한다.
- `respondBy`까지 응답하지 않은 사용자의 티켓은 `PAUSED`가 된다. 사용자는 `다시 찾기`를 눌러야 재개되며, 재개 시각을 새 `prioritySince`로 사용한다. 일시 중지 중에도 `expiresAt`은 계속 흐른다.
- 제안이 `respondBy` 또는 후보 티켓 만료로 종료되면 미응답자를 자동 수락·거절로 바꾸지 않는다. 제안이 조기 종료된 경우에는 미결정 사용자를 `PAUSED`로 만들지 않고 기존 `prioritySince`로 재대기하며, 정상적인 30초 미응답자만 `PAUSED`가 된다.
- `매칭 취소`를 선택한 사용자의 티켓은 종료한다. 이 선택으로 제안이 조기 종료된 다른 사용자는 기존 `prioritySince`를 유지한다.
- 전원 수락 전에는 파티 성공이나 성공 파티 채팅 접근 권한을 부여하지 않는다. 전원이 수락하면 파티를 한 번만 원자적으로 확정한다.

#### 게임 투표와 링크 공유

- 전원 수락 뒤 후보 수와 관계없이 성공 파티 채팅을 `PREPARING`으로 생성한다. 고정 후보가 둘 이상이면 최대 5분의 게임 투표를 시작하고, 후보가 하나면 투표 없이 즉시 해당 게임을 확정한다.
- 한 사용자는 후보 게임 하나에 한 표만 행사한다. 최초 유효 투표는 최종이며 같은 요청을 재시도해도 표를 중복 반영하지 않는다.
- 서버는 투표 시작 시각부터 5분인 `voteEndsAt`을 고정한다. 전원이 먼저 투표하면 즉시 종료하고, 그렇지 않으면 `voteEndsAt`에 종료한다.
- 최다 득표 게임을 선택한다. 최다 득표 동률이면 동률 게임 중에서, 한 표도 없으면 전체 후보 중에서 서버가 하나를 무작위로 선택한다.
- 게임 결과와 무작위 적용 여부를 모든 파티원에게 표시한다.
- 게임이 확정되면 해당 게임에 링크 공유 가능으로 표시한 사용자 중 한 명을 무작위로 `링크 공유 담당자`로 안내한다.
- 링크 공유 담당자는 리더나 별도 권한자가 아니며 미공유 제재를 받지 않는다. 담당자가 나가거나 공유하지 않으면 남아 있는 링크 공유 가능 선언자 중 한 명을 다시 안내하고, 없으면 파티원이 직접 공유해야 한다. 성공 파티의 누구나 외부 링크를 일반 채팅 메시지로 공유할 수 있다.
- 투표 시작·진행·종료와 결과 표시는 채팅 조회·전송·실시간 수신을 막지 않는다.

#### 성공 파티 채팅

- 매칭 성공은 기존 ROOM·참가 상태나 별도 `OnlinePlaySession`으로 표현하지 않는다. 성공한 매칭 결과와 참가자 관계를 채팅 접근 근거로 사용한다.
- `matching`은 전원 수락 뒤 성공 파티와 승인된 사용자 목록을 `chat`의 공개 contract에 전달한다. 사용자가 먼저 나가면 `matching`은 같은 contract로 해당 사용자의 접근 관계 제거를 전달하고, `chat`은 최신 접근 관계를 기준으로 메시지 저장·이력·실시간 전달을 판정한다.
- MATCH 성공 파티는 기존 ROOM과 다른 일시적 채팅 유형이며, 성공 매칭 접근 관계를 채팅 접근 근거로 사용한다. 기존 ROOM 채팅의 30일 보존 정책을 이 채팅에 묵시적으로 적용하지 않는다.
- 채팅 생성이 실패해도 확정 파티를 해제하거나 자동 재대기시키지 않는다. 성공 확정 시각부터 5분 동안 `PREPARING` 자동 복구를 시도하고 사용자에게 `채팅 준비 중`을 표시한다. 5분 뒤에도 실패하면 사용자에게 파티 취소 또는 새 티켓 등록을 선택하게 하며, 다른 사용자를 자동 충원하지 않는다.
- 채팅을 처음 사용할 수 있게 된 서버 시각을 `chatOpenedAt`, 그로부터 24시간 뒤를 `closesAt`으로 고정한다.
- 채팅 상단에는 절대 종료 시각과 남은 시간을 항상 표시한다. 채팅 활성화 시와 종료 1시간 전에 각각 한 번씩 서버 작성 시스템 메시지를 저장·전달하고, 재접속 시 기존 메시지 이력을 보여준다.
- 투표 종료, 게임 결과 또는 링크 공유 여부는 `closesAt`을 앞당기지 않는다. 사용자는 먼저 나갈 수 있고, `chat`은 퇴장 시점부터 해당 사용자의 조회·전송·실시간 구독을 차단한다. 마지막 사용자가 나가면 채팅을 조기 종료한다.
- 채팅 종료 즉시 조회·전송·실시간 구독을 차단한다. MATCH 채팅 메시지와 외부 링크는 사용자에게 공개하지 않은 채 종료부터 7일 보존한 뒤 물리 삭제한다. 기존 ROOM 채팅의 30일 보존은 그대로 유지한다.
- 알밤메이트는 선택한 공통 외부 플랫폼의 계정 보유 여부·링크 유효성·게임방을 검증하지 않고, 외부 플랫폼 게임방을 자동 생성하거나 실제 플레이 상태를 추적하지 않는다.

#### 상태·동시성·복구

상태 이름은 의미를 설명하는 초안이며 API enum과 저장값은 API·ERD 변경에서 확정한다.

| 대상 | 상태 의미 |
| --- | --- |
| 매칭 티켓 | `WAITING`, `PROPOSED`, `PAUSED`, `MATCHED`, `CANCELED`, `EXPIRED` |
| 매칭 제안 | `OPEN`, `CONFIRMED`, `DECLINED`, `EXPIRED`, `CANCELED` |
| 게임 투표 | `OPEN`, `DECIDED` |
| 성공 파티 채팅 | `PREPARING`, `ACTIVE`, `CLOSED`, `PURGED` |

- `queuedAt`과 `expiresAt`은 티켓 전체 생명주기 동안 바뀌지 않는다. 재대기·재개는 `prioritySince`만 변경한다.
- 후보 파티 선택은 필수 조건 필터 후 `prioritySince` 오름차순으로만 처리한다. 같은 시각의 동점은 결정적이며, 베스트·추천 인원이 대기 순서를 역전시키지 않는다.
- 사용자별 제안 응답은 `PENDING`, `ACCEPTED`, `DECLINED` 의미를 구분하고 미응답과 명시적 거절을 같은 결과로 덮어쓰지 않는다.
- `PAUSED`는 사용자의 `다시 찾기` 전까지 대기열에 복귀하지 않는다. `MATCHED`는 성공 파티가 유지되는 종단 상태다.
- 한 사용자를 둘 이상의 성공 파티에 포함하지 않고, 여러 matcher가 같은 후보를 선택해도 중복 제안·중복 성공을 만들지 않는다.
- 차단된 두 사용자를 같은 새 후보에 포함하지 않으며, 차단 해제는 친구 관계를 복구하지 않는다.
- 전원 수락, 재대기, 취소, 만료와 matcher 실행이 경합해도 하나의 최종 결과로 수렴하며 일부 사용자만 성공하는 부분 성공을 허용하지 않는다.
- 투표 제출·종료·무작위 결과 확정이 경합해도 선택 게임을 한 번만 결정한다.
- 채팅 생성·복구와 종료·삭제를 재시도해도 채팅방과 시스템 메시지를 중복 생성하지 않는다.
- 서버 재시작 뒤 열린 제안·투표, 티켓·채팅 만료와 삭제 대상을 복구하고 최신 영속 상태에서 다시 판단한다.
- 실시간 이벤트는 정본이 아니다. 이벤트 유실·중복·순서 역전과 연결 해제 뒤에도 현재 상태 조회로 티켓·제안·투표·채팅 상태를 복구하며 연결 해제를 자동 수락·거절로 해석하지 않는다.
- PostgreSQL 잠금·조건부 갱신, ShedLock, Redis와 WebSocket·SSE·polling의 구체적 조합은 측정과 ADR 없이 확정하지 않는다.

#### 개인정보와 운영 데이터

- 제안 전에는 다른 사용자의 전체 대기 목록·조건 원문·식별 정보를 공개하지 않는다.
- 전원 수락 뒤 성공 파티 채팅에는 현재 공개 프로필의 닉네임과 프로필 이미지만 제공하고 사용자 ID·이메일·인증 정보를 노출하지 않는다.
- 차단된 두 사용자는 서로의 프로필·개인정보를 조회할 수 없고, 차단 사실을 직접 알리는 알림·사유·전용 오류를 받지 않는다.
- 사용자 ID·이메일·세션·자유 입력 원문·초대 링크를 metric label로 사용하지 않는다.
- 구조화 로그에는 제한된 결과 코드와 필요한 상관 키만 남기며 매칭 조건·투표 원문·메시지 본문·외부 링크를 기록하지 않는다.
- 종료 티켓·제안·응답·투표의 사용자별 원자료는 각 업무 종료 시점부터 7일 뒤 완전 삭제한다. 비식별 원자료를 남기지 않으며, 이후에는 사용자와 연결할 수 없는 집계 결과 코드만 보존한다. 신고·차단 운영 자료의 보존은 별도 운영 계약에서 정한다.
- 관측 수집 실패는 매칭·투표·채팅 결과를 바꾸지 않는다.

### 완료 기준

- `MATCH-01-AC1` 사용자가 게임 ID 스냅샷 또는 허용 게임 범위, 전체 파티의 최소·최대 희망 인원, 공통 외부 플랫폼, 룰 설명 필요와 게임별 설명·링크 공유 가능 여부로 티켓을 등록·조회·취소하고 단일 비종료 티켓 불변식을 지킨다.
- `MATCH-01-AC2` 티켓은 `queuedAt`부터 총 30분 동안 화면 이동·재대기·일시 중지와 무관하게 유지되고, 공통 화면에서 대기 경과·남은 시간을 복구하며 대기 5분 뒤 조건 완화 선택지를 한 번 제공한다. 조건 완화 후에도 사용자가 확인한 게임 ID 목록을 고정한다.
- `MATCH-01-AC3` 게임 지정·미지정 사용자를 별도 큐로 분리하지 않고 모든 참가자의 희망 인원 범위와 공통 외부 플랫폼 안에서 실제 파티 인원을 정하며, 모든 사용자가 승인하고 해당 인원·플랫폼을 지원하는 게임만 고정 후보로 제안한다.
- `MATCH-01-AC4` 룰 설명이 필요한 제안의 각 후보 게임에는 설명 가능 사용자를, 모든 후보 게임에는 링크 공유 가능 사용자를 최소 한 명 포함한다.
- `MATCH-01-AC5` 설명 가능 사용자나 다른 필수 조건을 찾지 못해도 자동 완화하지 않고 사용자가 선택한 최신 조건으로만 다시 탐색한다.
- `MATCH-01-AC6` 제안은 실제 파티 인원·공통 외부 플랫폼·고정 후보 게임 목록을 보여주고 총 티켓 유효 시간 안에서 30초 동안 수락·재대기·취소를 받는다. 조기 종료 시 미결정 사용자는 기존 우선순위로 재대기하고, 직접 재대기를 선택한 사용자는 새 우선순위를 받으며 정상적인 30초 미응답자만 `PAUSED`가 된다.
- `MATCH-01-AC7` 전원 수락 전에는 성공·채팅 접근 권한을 부여하지 않고, 전원 수락 뒤 후보 수와 관계없이 채팅을 준비한다. 후보가 둘 이상이면 최대 5분 투표·조기 종료·동률/0표 무작위 규칙으로, 하나면 투표 없이 게임을 한 번 확정한다.
- `MATCH-01-AC8` 선택 게임의 링크 공유 가능 사용자 중 한 명을 무작위로 안내하고 담당자 이탈·미공유 시 남은 선언자에게 재안내하되, 다른 파티원의 링크 공유와 공통 외부 플랫폼 이용을 제한하지 않고 외부 계정·게임방·링크를 연동하거나 검증하지 않는다.
- `MATCH-01-AC9` 전원 수락, 재대기, 만료, 취소, matcher와 투표 종료가 경합해도 하나의 최종 결과로 수렴하고 중복 파티·중복 표·부분 성공을 만들지 않는다.
- `MATCH-01-AC10` 다중 인스턴스, 재시도와 서버 재시작 환경에서 티켓·제안·투표·채팅 생성·종료·삭제를 복구한다.
- `MATCH-01-AC11` 성공 파티 채팅 생성이 실패해도 파티를 유지해 성공 확정 시각부터 최대 5분 자동 복구하고, 실패가 지속되면 자동 재매칭 없이 취소·새 티켓 선택을 제공한다. 채팅은 `chatOpenedAt`부터 24시간 동안 제공하며 활성화 시 및 종료 1시간 전 시스템 메시지와 전원 퇴장 조기 종료를 적용한다.
- `MATCH-01-AC12` 사용자가 먼저 나가면 해당 사용자의 조회·전송·실시간 구독을 즉시 차단하고, 채팅이 종료되면 모든 사용자 접근을 차단한다. MATCH 채팅 메시지·외부 링크와 종료된 매칭의 사용자별 원자료는 업무 종료 후 7일 뒤 완전 삭제하며 원문을 metric label이나 중앙 로그에 넣지 않는다.
- `MATCH-01-AC13` PostgreSQL 기반 자동 검증과 고정 release 배포 시나리오로 정상 매칭, 후보 없음, 조건 완화, 제안 응답·`다시 찾기`, 투표, 동시성, 연결 중단·복구, 채팅 생명주기와 삭제를 재현한다.
- `MATCH-01-AC14` 사용자가 차단 목록에서 차단·해제할 수 있고, 차단된 두 사용자의 프로필·개인정보·새 매칭을 양방향으로 차단하며 기존 친구 관계와 대기 중 친구 요청을 조용히 제거한다. 차단 해제는 친구 관계를 복구하지 않는다.
- `MATCH-01-AC15` 공개 사용자에게 신고 진입점을 제공하고 신고 사실을 피신고자에게 알리지 않으며, 신고 기록을 운영자 검토 계약으로 전달한다. 친구 관계·친구 초대 큐·친구 그룹 매칭은 제공하지 않는다.

- 음성·화상 통화
- 검증된 룰마스터 자격·등급·후기·신뢰 시스템과 룰 설명 품질 자동 평가
- AI 게임 추천과 AI 규칙 설명

- 친구 관계 생성·관리, 친구 초대 큐, 친구 그룹 매칭과 친구 우선순위. 이번 MVP의 안전 기능인 차단 목록은 제외하지 않는다.
- 링크 공유 담당자 전용 권한·강제 수행·미공유 제재
- 반복 노쇼·거절 제재. 신고·차단은 공개 출시 필수 범위로 포함한다.
- 별도 초대 기반 파일럿 운영. 공개 출시를 목표로 하며 파일럿 전용 기능을 만들지 않는다.
- 결제·포인트·보상
- Redis 분산 락, 메시지 브로커 또는 마이크로서비스의 선행 도입
- 모든 외부 온라인 보드게임 플랫폼 동시 지원
- 기존 ROOM을 확장한 온라인 ROOM 또는 별도 `OnlinePlaySession`
- 종료된 성공 파티 채팅의 읽기 전용 제공
- 기존 오프라인 ROOM·참가·대기열 계약의 전면 교체

### 운영 측정

실제 목표값은 기준선과 최소 표본을 확보한 뒤 확정한다. `MATCH-01` 고유 결과 신호와 원문 수집 금지 범위만 이 절에서 정의한다.

- 매칭 대기 시간 p50·p95
- 티켓 30분 만료율과 5분 조건 완화 선택 분포
- 티켓 대비 제안 생성률과 인원·게임·룰 설명·링크 공유 조건별 후보 없음 사유
- 30초 제안의 전원 수락·재대기·취소·미응답·일시 중지 비율
- 우선순위 보존·갱신 위반, 중복 활성 티켓·중복 제안·중복 파티·부분 성공 건수
- 룰 설명·링크 공유 가능 사용자 포함률과 위반 건수
- 투표 참여율·결정 시간과 동률·0표 무작위 선택률
- 채팅 생성·자동 복구 결과와 `PREPARING` 경과 시간
- 24시간·전원 퇴장 종료와 종료 7일 뒤 삭제 성공·실패 건수
- 링크 공유 담당자 선정 결과. 외부 링크 본문이나 실제 공유·플레이 여부는 측정하지 않는다.
- 차단·해제·신고 접수 결과와 처리 지연. 사용자 ID·프로필·신고 본문은 metric label이나 일반 로그에 남기지 않는다.

HTTP `2xx`, matcher 실행, 투표 이벤트 또는 실시간 이벤트 발행만으로 매칭 성공·게임 결정·채팅 준비 완료를 판정하지 않는다.

## 후속 변경 시 확인

- 설명 가능 사용자가 부족하거나 게임·인원 조건이 지나치게 세분화돼 대부분의 티켓이 제안에 도달하지 못한다.
- 30초 제안의 미응답·일시 중지 또는 5분 조건 완화 뒤 이탈이 반복된다.
- 후보 게임 목록을 수락한 뒤 투표 결과나 동률·0표 무작위 선택 때문에 반복 이탈한다.
- 설명 가능 사용자나 링크 공유 담당자에게 요청이 집중돼 파티 시작 실패가 반복된다.
- 중복 제안·중복 성공·부분 성공이 재현되거나 matcher의 데이터베이스 비용·잠금 대기가 허용 기준을 초과한다.
- 외부 플랫폼 정책상 비공개 테이블·초대 링크 연결이 불가능하다.
- 성공 파티 채팅의 접근 관계·시스템 메시지·자동 복구가 기존 채팅 계약과 충돌하거나 24시간 종료·7일 삭제가 기한 안에 수렴하지 않는다.
- 신고량·차단 우회·운영자 처리 지연이 공개 출시의 안전 기준을 넘으면 운영자 대응·제재 정책을 별도 승인한다. 반복 노쇼·거절 제재는 이 문서의 MVP 범위에 포함하지 않는다.
