# P2 채팅 기능 명세

이 문서는 P2에서 ROOM 채팅방에 입장·퇴장 안내를 남기는 `CHAT-06`과, 채팅 목록의 마지막 메시지·방별 미읽음 상태를 다루는 `CHAT-07`의 범위와 완료 기준을 정의한다. 현재 계약 준비·생산 코드·자동 검증·운영 배포와 실측 상태는 [P2 기능 상태 정본](README.md#기능별-현재-상태)에서만 판정한다. 이 문서만으로 현재 API·저장·아키텍처 계약이나 구현 상태를 판정하지 않는다.

P2 전체 범위와 공통 규칙은 [P2 명세](../P2-spec.md), 제품 방향은 [PRD](../PRD.md), 요청·응답·오류는 [API 명세](../API.md), 저장 구조와 제약은 [ERD](../ERD.md), 모듈 책임은 [아키텍처](../ARCHITECTURE.md), 논쟁적 기술 선택은 [Chat ADR](../adr/chat/README.md)이 소유한다. 이 문서는 제품 규칙·완료 기준만 소유하며, 구현 계약의 현재 내용은 각 정본을 따른다.

`CHAT-01`~`CHAT-05`는 P1에서 종료·아카이브한 기능이며 그 기록은 [P1 방 채팅 기능 명세](../archive/p1/chatting.md)에 동결돼 있다. `CHAT-06`은 그 문서를 수정하거나 재해석하지 않고, 현재 활성 계약인 [API 명세](../API.md#채팅-공통-계약)·[ERD](../ERD.md)·[아키텍처](../ARCHITECTURE.md) 위에 새 계약을 더한다.

## CHAT-06 입장·퇴장 시스템 메시지

ROOM 채팅방에서 누가 새로 들어왔고 누가 나갔는지를 방의 모든 참여자가 같은 시간축에서 확인하도록 시스템 메시지를 남긴다. 지금 채팅방에는 이 안내가 없다. 이는 프런트 표시 회귀가 아니라 저장·응답·실시간 전달 계약이 아직 없는 미구현 기능이다.

### 핵심 흐름

| 단계 | 책임 | 이번 범위의 기준 |
| --- | --- | --- |
| 참가 확정·참가 취소 확정 | `room`이 참가 관계를 전이시킨 트랜잭션에서 그 사실을 공개 계약으로 발행한다 | 상태를 전이시킨 요청에서만 발행하고, 발행 실패는 참가 요청 자체를 실패시킨다 |
| 안내 저장 | `chat`이 같은 트랜잭션에서 종류·사건 키·안내 대상만 `CHAT_MESSAGES`에 남긴다 | 참가 전이와 안내가 함께 커밋되거나 함께 롤백된다 |
| 실시간 전달 | 원인 트랜잭션 커밋 뒤 기존 채팅 실시간 경로로 같은 이벤트를 발행한다 | 커밋 전 안내를 미리 내보내지 않고, 전달 실패는 저장을 되돌리지 않는다 |
| 이력·재연결 조회 | 서버가 사건 키와 대상의 현재 공개 닉네임으로 문장을 조립해 사용자 메시지와 하나의 구간으로 반환한다 | 같은 메시지 ID 순서·커서·`size` 계수를 공유한다 |
| 화면 표시 | 클라이언트가 서버가 준 문장을 시간순 이력에 그대로 표시한다 | 클라이언트는 문구를 조립하지 않는다 |

사용자 관점의 흐름은 `다른 사용자가 참가·참가 취소함 → 채팅방을 열거나 보고 있음 → 해당 시점의 입장·퇴장 안내를 이력에서 확인함`이다. 참가 취소한 사용자는 그 방의 채팅 접근을 잃으므로 자신의 퇴장 안내를 확인하지 않는다.

### 구현 컨텍스트

| 구분 | 정본 |
| --- | --- |
| 범위 상태 | P2 정식 범위. 계약·코드·검증·배포·실측의 현재 상태는 [P2 기능 상태 정본](README.md#기능별-현재-상태)에서만 판정한다 |
| 사용자 문제 | 채팅방 참여자가 바뀌어도 화면에 아무 흔적이 없어, 지금 대화 상대가 누구인지와 언제 바뀌었는지 알 수 없다 |
| 핵심 사용자 | 모집 중·모집 완료 ROOM의 주최자와 현재 `ACTIVE` 참가자 |
| 검증 가설 | 참가·참가 취소가 확정된 시점을 채팅 이력의 같은 시간축에 남기면, 별도 알림을 열지 않아도 참여자 변화를 채팅 화면에서 파악할 수 있다 |
| 기존 제품 경계 | [P1 채팅](../archive/p1/chatting.md)의 방별 채팅방·접근 판정·커서 이력·실시간 전달·30일 보존을 그대로 사용한다. 참가·참가 취소의 업무 규칙은 [P1 ROOM·참가](../archive/p1/room.md)가 계속 소유하며 이 기능이 바꾸지 않는다 |
| 신규 업무 경계 | `room`이 참가·참가 취소 확정 사실을 공개 계약으로 발행하고, `chat`이 그 사실을 시스템 메시지로 저장·조립·전달한다 |
| 구현 계약 정본 | 요청·응답·문구는 [API](../API.md#채팅-공통-계약), 저장 구조는 [ERD](../ERD.md#chat-06-입장퇴장-시스템-메시지-저장-계약), 모듈·트랜잭션 경계는 [아키텍처](../ARCHITECTURE.md#p2-chat-06-입장퇴장-시스템-메시지-흐름-계획미구현), 저장 모델·문구 소유의 선택 이유는 [ADR-0078](../adr/chat/0078-chat-system-message-storage-and-read-time-composition.md) |
| 운영 연결 | [운영 관측](monitoring.md)과 [운영 대시보드 정책](dashboard.md)의 공통 원칙을 사용한다. 안내 누락·중복과 이력 조립 지연을 고유 지표로 측정한다 |

위 표의 구현 계약 정본은 이 문서의 제품 규칙을 구현 가능한 계약으로 구체화한다. 같은 내용을 이 문서에 다시 정의하지 않는다.

`계약 준비 완료`는 그 정본과 필수 ADR이 승인됐다는 뜻이며, 생산 코드·자동 검증·배포·실측 완료를 뜻하지 않는다. `CHAT_MESSAGES`의 `sender_user_id`·`client_message_id`·`content` NOT NULL을 푸는 전진 migration은 다른 이슈가 소유한 선행 전환이 아니라 후속 구현 이슈의 범위이므로, 호환 가능한 expand migration과 `SYSTEM` reader·비활성 writer는 같은 변경에서 구현·병합한다. 구현 착수가 아니라 `SYSTEM` 쓰기 전역 활성화가 뒤로 미뤄지는 단계이며, 그 진입 조건은 [혼합 버전 순서](../ERD.md#chat-06-혼합-버전-배포활성화rollback-순서)의 1·2단계가 모든 인스턴스에 반영된 것을 확인하는 것이다. 상태는 [P2 기능 상태 정본](README.md#기능별-현재-상태)에서만 갱신한다.

### 기능 규칙

#### 안내를 남기는 사건

- 시스템 메시지를 남기는 사건은 **참가 확정**과 **참가 취소 확정** 둘뿐이다. 두 사건 모두 `room`의 쓰기 트랜잭션이 참가 관계를 실제로 전이시켰을 때만 성립한다.
- 참가 확정은 신규 참가와 취소했던 관계의 재참가를 모두 포함한다. 같은 사용자가 나갔다가 다시 들어오면 그때마다 새 안내를 남긴다.
- 이미 `ACTIVE`인 사용자의 중복 참가 요청, 참가 관계가 없는 사용자의 취소 요청처럼 상태를 전이시키지 못한 요청은 안내를 남기지 않는다.
- 주최자는 참가 관계를 만들지 않으므로 주최자의 방 생성·존재로는 안내를 남기지 않는다.
- 대기열 자동 승격, 방 취소, 방 종료는 이번 범위의 사건이 아니다. 승격으로 참가자가 된 사용자에게는 입장 안내가 남지 않으며, 이 경계는 [ADR-0078](../adr/chat/0078-chat-system-message-storage-and-read-time-composition.md#보류-및-재검토)의 재검토 조건으로 관리한다.

#### 저장 모델과 문구 소유

- 시스템 메시지는 사용자 메시지와 같은 `CHAT_MESSAGES`에 저장한다. 별도 테이블·별도 식별자 순서·별도 커서를 만들지 않는다.
- 저장하는 것은 메시지 종류, 사건 키와 안내 대상 사용자 참조뿐이다. 완성된 안내 문장, 표시용 닉네임 사본과 사건 당시의 프로필 값은 저장하지 않는다.
- 참가·참가 취소의 행위자는 항상 안내 대상 사용자 자신이므로 행위자 식별자를 대상과 따로 저장하지 않는다. 주최자·운영자가 다른 사용자를 내보내는 사건은 이번 범위에 없다.
- 안내 문장은 서버가 이력·실시간 응답을 만들 때 사건 키와 대상 사용자의 **현재** 공개 닉네임으로 조립해 기존 본문 필드로 내려준다. 프런트엔드는 문구를 조립하지 않고 서버가 준 문장을 그대로 표시한다.
- 닉네임이 바뀌면 과거 안내도 현재 닉네임으로 보인다. 사건 당시의 닉네임을 보여주는 화면은 제공하지 않는다.
- 대상 사용자의 공개 프로필을 찾지 못하면 조회를 실패시키지 않고 고정된 대체 표시명으로 조립한다. 대체 표시명 문자열의 정본은 [API 명세](../API.md#채팅-공통-계약)다.
- 시스템 메시지는 사용자가 만들 수 없다. 메시지 전송 API로는 사용자 메시지만 저장하며, 시스템 메시지는 전송 제한 quota를 소비하지 않는다.

#### 이력·실시간 전달

- 시스템 메시지는 사용자 메시지와 같은 메시지 ID 순서를 사용한다. 이력 커서와 재연결 catch-up 기준은 [ADR-0031](../adr/chat/0031-chat-history-cursor-pagination.md)을 그대로 따르며, 시스템 메시지도 요청한 `size`에 포함해 센다.
- 실시간 전달은 [ADR-0032](../adr/chat/0032-http-send-websocket-receive.md)·[ADR-0033](../adr/chat/0033-postgresql-source-after-commit-delivery.md)을 따른다. 원인 트랜잭션이 커밋된 뒤에만 발행하며, 커밋 전 안내를 미리 내보내지 않는다.
- 재연결한 클라이언트는 마지막 이벤트 ID 뒤의 사용자 메시지와 시스템 메시지를 하나의 오름차순 구간으로 복구한다. 두 종류를 다른 경로로 받지 않는다.
- 실시간 전달 실패는 저장된 안내를 삭제하거나 원인 참가 전이를 되돌리지 않는다. 클라이언트는 재연결 catch-up으로 누락을 복구한다.

#### 접근·보존·개인정보

- 시스템 메시지의 조회·구독 권한은 사용자 메시지와 같다. 요청 시점의 주최자·현재 `ACTIVE` 참가자 관계와 `RECRUITING`·`CLOSED` 방 상태를 서버가 다시 확인한다.
- 참가를 취소한 사용자는 그 방의 채팅 접근을 잃으므로, 자신의 퇴장 안내를 포함한 이력을 더 이상 조회하지 않는다.
- 보존과 삭제는 [ADR-0049](../adr/chat/0049-chat-message-retention-lock-section-boundary.md)의 30일 보존·만료 물리 삭제를 그대로 따른다. 시스템 메시지만 다른 기간을 두지 않는다.
- 저장하는 개인정보는 대상 사용자 ID 참조뿐이다. 안내 문장·닉네임·사용자 ID를 로그와 metric label에 남기지 않는다.

#### 원자성과 실패

- 안내 저장은 원인이 되는 참가·참가 취소 업무 트랜잭션 안에서 끝난다. 참가 상태 전이가 커밋되면 안내도 함께 커밋되고, 안내 저장이 실패하면 참가 상태 전이도 함께 롤백한다. 참가만 성공하고 안내만 빠지는 상태는 만들지 않는다.
- 참가·참가 취소 요청의 성공 응답 계약은 이 기능 때문에 바뀌지 않는다. 안내 저장 실패는 참가 요청 자체의 실패로 사용자에게 전달된다.
- 안내 저장은 별도 재시도 큐·보정 스케줄러를 두지 않는다. 실패는 원인 요청의 재시도로 해소한다.
- 채팅방 잠금 순서는 기존 계약과 같다. 원인 트랜잭션은 ROOM을 먼저 다루고 채팅방을 나중에 잠근다. 상세는 [아키텍처](../ARCHITECTURE.md#p2-chat-06-입장퇴장-시스템-메시지-흐름-계획미구현)가 소유한다.

#### 배포 경계

- 이 계약이 적용되기 전에 만들어진 채팅방에는 안내를 소급 생성하지 않는다. 과거 참가·취소 시각을 원인 사실로 복원할 수 없기 때문이다.
- 기존 채팅방은 배포 이후 발생한 참가·참가 취소부터 안내를 갖는다. 이미 참가 중인 사용자의 입장 안내는 만들지 않는다.
- 소급 생성을 하지 않으므로 배포 시점의 데이터 이관 작업은 없다. 필요한 전진 migration은 컬럼 추가와 NOT NULL 완화, 종류별 CHECK 제약과 전역 활성화 gate 행 생성뿐이다.
- schema 확장과 안내 저장 활성화는 한 배포로 묶지 않는다. 두 인스턴스를 순차로 갱신하는 동안 구버전이 남아 있으므로, schema 확장 → `SYSTEM` 행을 읽을 수 있는 버전의 전 인스턴스 배포 → 안내 저장 활성화 순서로 나눈다. 단계별 조건과 rollback 순서의 정본은 [혼합 버전 배포·활성화·rollback 순서](../ERD.md#chat-06-혼합-버전-배포활성화rollback-순서)다.
- 활성화 경계는 인스턴스별 설정이 아니라 원인 참가 트랜잭션에서 읽는 전역 활성화 시각 하나다. 따라서 순차 배포 구간에도 같은 사건의 안내 유무가 요청이 닿은 인스턴스에 따라 갈리지 않으며, 안내는 그 시각 이후 확정된 사건에만 남는다.
- 안내 저장이 꺼져 있는 동안에도 참가·참가 취소는 기존 계약 그대로 성공한다. 이 gate는 안내를 남길지만 결정하며 참가 성공·실패 판정을 바꾸지 않는다.
- 안내가 한 건이라도 저장된 뒤에는 schema를 되돌리는 rollback을 지원하지 않는다. 되돌리기는 안내 저장을 끄고 읽을 수 있는 버전을 유지하는 범위까지다.

### 완료 기준

- `CHAT-06-AC1` 전역 활성화 시각 이후 확정된 참가와 참가 취소마다 대상 사용자와 사건 키를 가진 시스템 메시지가 해당 ROOM 채팅방에 정확히 한 건 저장된다. 상태를 전이시키지 못한 요청과 활성화 시각 이전 사건은 안내를 남기지 않는다.
- `CHAT-06-AC2` 안내 저장과 원인 참가 상태 전이가 하나의 트랜잭션에서 함께 커밋되거나 함께 롤백된다. 참가만 반영되고 안내가 빠진 상태와 그 반대 상태가 모두 재현되지 않는다.
- `CHAT-06-AC3` 이력·실시간 응답이 메시지 종류·사건 키·대상 표시명과 서버가 조립한 안내 문장을 반환하고, 저장 계층에는 완성 문장과 닉네임 사본이 남지 않는다. 대상 사용자의 공개 프로필을 찾지 못해도 조회가 실패하지 않는다.
- `CHAT-06-AC4` 시스템 메시지와 사용자 메시지가 하나의 메시지 ID 순서를 공유하고, `beforeMessageId` 이력 조회와 재연결 catch-up이 두 종류를 하나의 구간으로 중복·누락 없이 반환한다.
- `CHAT-06-AC5` 시스템 메시지의 접근 판정·30일 보존·만료 물리 삭제가 사용자 메시지와 같은 경계를 따르고, 안내 문장·닉네임·사용자 ID가 로그와 metric label에 남지 않는다.
- `CHAT-06-AC6` 배포 전 생성된 채팅방에 안내가 소급 생성되지 않고, 전진 migration 뒤에도 기존 사용자 메시지의 저장·조회·전송이 회귀하지 않는다. schema만 적용되고 안내 저장이 아직 꺼진 구간에서도 기존 채팅 전송·조회·실시간이 그대로 동작한다.
- `CHAT-06-AC7` 메시지 전송 API로는 시스템 메시지를 만들 수 없고, 안내 저장은 사용자·방 전송 제한 quota를 소비하지 않는다. 참가가 잦은 방에서도 안내 때문에 사용자 메시지 전송이 제한에 걸리지 않는다.

### 제외 범위

- 대기열 자동 승격, 방 취소, 방 종료, 방 정보 수정의 시스템 메시지
- MATCH 성공 파티 채팅의 lifecycle 시스템 메시지 계약 변경
- 사건 당시 닉네임·프로필 이미지의 보존과 표시
- 시스템 메시지의 별도 조회 API, 읽음 상태, 사용자별 표시 설정과 숨김
- 시스템 메시지의 편집·삭제·신고와 답장
- 배포 전 채팅방·참가 이력의 소급 안내 생성과 데이터 이관
- 시스템 메시지의 프런트엔드 렌더링·스타일 구현. 이 문서는 서버가 완성 문장을 내려주고 클라이언트가 조립하지 않는다는 계약만 정하며, 화면 구현은 후속 프런트엔드 작업이 소유한다
- 채팅 화면 밖의 알림 발송. 참가·취소 알림은 기존 [P1 알림](../archive/p1/notification.md) 계약이 계속 소유한다
- 시스템 메시지를 채팅 목록의 마지막 메시지 미리보기와 방별 미읽음 집계에 포함할지 여부. `CHAT-06`은 저장·응답·전달 계약만 정하고 이 판정을 하지 않으며, 결정과 구현은 [#810](https://github.com/bamsongi-club/albam-mate/issues/810)의 `CHAT-07`이 소유한다. `CHAT-07`은 `sender`·`clientMessageId`가 `null`인 `SYSTEM` 메시지를 위 계약 그대로 읽어 자신의 집계 규칙을 정한다
- 기존 커서·실시간 전달·보존 계약의 교체

## CHAT-07 채팅 목록 마지막 메시지·방별 미읽음 상태

사용자가 채팅방에 들어가기 전 채팅 목록에서 마지막 메시지와 방별 미읽음 상태를 확인하고, 채팅방에 들어가 최신 메시지를 확인하면 정확히 읽음 처리한다. 지금 `ChatListView`는 참가자 수·장소만 표시하고 상단 채팅 아이콘에는 미읽음 표시가 없으며, 기존 채팅 API에는 읽음 처리 경계가 없다. 이는 프런트 표시 회귀가 아니라 저장·조회·읽음 처리 계약이 아직 없는 미구현 기능이다.

### 핵심 흐름

| 단계 | 책임 | 이번 범위의 기준 |
| --- | --- | --- |
| 목록 조회 | `room`이 `chat.contract.ChatRoomPreviewQuery`를 호출해 방마다 마지막 메시지·미읽음 개수를 배치로 얻는다 | 방 개수만큼 반복 질의하지 않는다 |
| 미읽음 집계 | `chat`이 `CHAT_ROOM_READ_STATES` 커서를 기준으로 `CHAT_MESSAGES`를 세어 조회 시점에 계산한다 | 저장된 counter가 아니라 매 조회마다 다시 계산한다 |
| 읽음 처리 | 사용자가 방에 들어가 최신 메시지를 확인하면 클라이언트가 명시적 읽음 처리 API를 호출한다 | 커서는 `GREATEST`로만 전진하고 후퇴하지 않는다 |
| 상단 배지 | 미읽음 메시지가 있는 방의 개수를 별도 요약 조회로 제공한다 | 방별 미읽음 개수의 총합이 아니라 방 개수를 센다 |

사용자 관점의 흐름은 `다른 사용자가 메시지를 보냄 → 채팅 목록에 마지막 메시지·미읽음 표시가 나타남 → 채팅방에 들어가 최신 메시지를 확인함 → 읽음 처리로 해당 방 표시가 사라짐`이다. 화면이 채팅 목록에 머무는 동안의 실시간 갱신은 이번 범위가 아니며, 목록·배지는 조회 시점 값을 보여준다.

### 구현 컨텍스트

| 구분 | 정본 |
| --- | --- |
| 범위 상태 | P2 정식 범위. 계약·코드·검증·배포·실측의 현재 상태는 [P2 기능 상태 정본](README.md#기능별-현재-상태)에서만 판정한다 |
| 사용자 문제 | 채팅방에 들어가기 전에는 어느 방에 새 메시지가 있는지, 마지막으로 무슨 대화가 오갔는지 알 방법이 없다 |
| 핵심 사용자 | 여러 ROOM에 동시에 참가·주최 중인 사용자 |
| 검증 가설 | 채팅 목록에 방별 마지막 메시지와 미읽음 상태를 보여주면, 사용자가 매 방을 열어보지 않고도 확인이 필요한 대화를 먼저 찾아갈 수 있다 |
| 기존 제품 경계 | [CHAT-06](#chat-06-입장퇴장-시스템-메시지)까지의 메시지 저장·이력 커서·실시간 전달·30일 보존을 그대로 사용한다. 새 저장·전달 경로를 만들지 않는다 |
| 신규 업무 경계 | `chat`이 사용자×방 읽음 커서를 저장·조회하고, `room`이 그 결과를 채팅 목록 응답에 합성한다 |
| 구현 계약 정본 | 요청·응답은 [API](../API.md#chat-07-채팅-목록-마지막-메시지방별-미읽음-상태-계약), 저장 구조는 [ERD](../ERD.md#chat-07-읽음-커서-저장-계약), 모듈 흐름은 [아키텍처](../ARCHITECTURE.md#p2-chat-07-채팅-목록-미읽음-집계-흐름-계획미구현), 저장·집계 방식 선택 이유는 [ADR-0079](../adr/chat/0079-chat-room-read-cursor-and-derived-unread-count.md) |
| 운영 연결 | [운영 관측](monitoring.md)과 [운영 대시보드 정책](dashboard.md)의 공통 원칙을 사용한다. 배치 조회 지연과 읽음 처리 실패율을 고유 지표로 측정한다 |

위 표의 구현 계약 정본은 이 문서의 제품 규칙을 구현 가능한 계약으로 구체화한다. 같은 내용을 이 문서에 다시 정의하지 않는다.

### 기능 규칙

#### 저장·집계 모델

- 사용자×채팅방마다 `last_read_message_id` 커서 하나만 `CHAT_ROOM_READ_STATES`에 저장한다. 방별 미읽음 개수를 별도 counter 컬럼에 저장하지 않고, 메시지별 읽음 로그도 남기지 않는다.
- 미읽음 개수는 `chat_room_id`·커서를 기준으로 `id > cursor`인 `CHAT_MESSAGES` 행을 세어 조회 시점에 계산한다. 계산 방식과 선택 이유는 [ADR-0079](../adr/chat/0079-chat-room-read-cursor-and-derived-unread-count.md)를 따른다.
- 커서 갱신은 기존 값과 새 값 중 큰 값으로만 전진한다. 이미 반영된 지점보다 같거나 이전인 값으로 다시 요청해도 실패하지 않고 현재 값을 그대로 유지·응답한다.
- 채팅 목록처럼 여러 방을 한 번에 보여줘야 하는 조회는 방 개수만큼 반복 질의하지 않고 배치로 계산한다.

#### 표시 대상과 제외 규칙

- `CHAT-06` `SYSTEM` 메시지는 마지막 메시지 미리보기와 미읽음 집계에 포함한다. 다만 안내 대상 본인에게는 자신의 입장·퇴장 안내를 미읽음으로 세지 않는다. `USER` 메시지의 본인 발신 제외 규칙과 대칭이며, `CHAT-06`의 저장·응답 계약은 바꾸지 않는다.
- 본인이 보낸 `USER` 메시지는 발신자 자신의 미읽음 개수에 포함하지 않는다.
- 채팅 접근 권한이 없는 방(`chatAvailable = false`)은 마지막 메시지를 `null`, 미읽음 개수를 `0`으로 응답한다.
- 여러 메시지가 도착해도 방별 표시 행은 하나만 유지하고, 미읽음 개수만 누적해서 보여준다.

#### 읽음 처리 시점과 API

- 채팅방 진입 후 최신 메시지를 성공적으로 조회·확인한 시점에, 클라이언트가 명시적 읽음 처리 API(`POST /api/rooms/{roomId}/chat/read`)를 호출해 서버가 해당 방을 읽음 처리한다. 메시지 이력 조회 자체는 읽음 처리를 겸하지 않는다.
- 읽음 처리 요청은 클라이언트가 실제로 확인한 최신 메시지 ID(`upToMessageId`)를 함께 보낸다. 그 방에 존재하지 않는 메시지 ID를 넘기면 거절한다.
- 읽음 처리의 접근 판정은 기존 채팅 공통 계약과 같다. 주최자·현재 `ACTIVE` 참가자가 아니거나 방이 `CANCELED`·`FINISHED`이면 거절한다.
- 읽음 처리는 커서를 전진시키는 멱등 갱신이다. 같은 요청을 재시도해도 중복 부작용이 없다.

#### 상단 배지

- 상단 채팅 아이콘의 미읽음 표시는 미읽음 메시지가 1건 이상인 방의 개수를 센다. 방별 미읽음 개수의 총합을 쓰지 않는다.
- 상단 배지는 조회 시점 값이며, 채팅 목록·상단 배지를 위한 새 전역 실시간 채널(WebSocket 등)은 만들지 않는다. 화면은 진입·재진입·명시적 재조회 시점에 최신값으로 갱신된다.

#### WebSocket 중복·순서 역전·재연결

- 미읽음 개수는 저장이 아니라 조회 시점 파생 계산이므로, 기존 방별 WebSocket 전달·재연결 catch-up 경로([CHAT-03](../API.md#chat-03-실시간-메시지-구독))는 변경하지 않는다.
- 같은 메시지가 WebSocket으로 중복 전달되거나 순서가 뒤섞여 도착해도, 다음 조회의 미읽음 개수는 항상 그 시점의 메시지 `id` 상태를 기준으로 다시 계산되므로 두 번 반영되지 않는다.

### 완료 기준

- `CHAT-07-AC1` 메시지가 없는 채팅방은 `lastMessagePreview`·`lastMessageAt`이 `null`이고 `unreadCount`는 `0`이다.
- `CHAT-07-AC2` 다른 사용자의 메시지가 한 건이든 여러 건이든 도착하면 해당 방의 `unreadCount`가 정확한 건수로 반영되고, 채팅 목록에는 방마다 표시 행이 하나만 유지되며 상단 배지의 미읽음 방 개수에 반영된다.
- `CHAT-07-AC3` 본인이 보낸 `USER` 메시지와 본인이 대상인 `SYSTEM` 메시지는 본인의 `unreadCount`에 반영되지 않는다.
- `CHAT-07-AC4` 읽음 처리 API 성공 뒤 해당 방의 `unreadCount`가 `0`으로 수렴하고, 커서는 이전 값보다 후퇴하지 않으며 같은 요청의 재시도에 안전하다.
- `CHAT-07-AC5` 여러 방에 걸친 `unreadCount`·마지막 메시지는 서로 섞이지 않고 방마다 독립적으로 계산된다.
- `CHAT-07-AC6` WebSocket 중복 전달·순서 역전·재연결 catch-up이 반복돼도 같은 메시지가 `unreadCount`에 두 번 반영되지 않는다.
- `CHAT-07-AC7` 주최자·현재 `ACTIVE` 참가자가 아닌 사용자는 다른 방의 마지막 메시지·`unreadCount`를 조회하거나 그 방을 읽음 처리할 수 없다.
- `CHAT-07-AC8` `CHAT-06` `SYSTEM` 메시지가 있는 방에서도 위 포함·제외 규칙이 성립하며, `CHAT-06`의 저장·응답 계약을 바꾸지 않는다.
- `CHAT-07-AC9` 30일 보존 만료로 커서보다 오래된 메시지가 물리 삭제돼도 미읽음 집계·읽음 처리가 오류 없이 동작한다.

### 제외 범위

- 채팅 목록·상단 배지의 실시간 push. 새 전역 WebSocket 채널이나 사용자 단위 구독을 만들지 않으며, 화면은 조회 시점 값을 보여준다
- 방별 미읽음 개수를 저장하는 counter 컬럼과 메시지별 개별 읽음 로그
- [CHAT-06](#chat-06-입장퇴장-시스템-메시지)의 시스템 메시지 저장·응답·전달 계약 자체의 변경
- 기존 웹 알림함의 읽음 처리(`NOTI-*`)와 그 UX 변경
- 비회원·채팅방 비참가자의 채팅 목록 및 읽음 상태 노출
- 메시지 이력 조회(`beforeMessageId`) API 자체를 읽음 처리로 겸하게 하는 것

## 검증 증거 매핑

완료 기준은 자동 검증과 운영 측정 증거로 닫는다. 현재 통과 여부는 이 절에 반복하지 않고 [P2 기능 상태 정본](README.md#기능별-현재-상태)의 `자동 검증`·`배포 상태`·`실측 상태` 열에서만 관리한다.

### CHAT-06 자동 검증

| 테스트 ID | 반드시 재현할 증거 |
| --- | --- |
| `CHAT-06-T1` | 신규 참가·재참가·참가 취소 각각의 안내 한 건 저장, 중복 참가·대상 없는 취소·주최자 요청에서 안내 미생성, 같은 사용자의 반복 입·퇴장에서 사건마다 별도 행 |
| `CHAT-06-T2` | 안내 저장 실패 시 참가 상태 전이·점유 인원 롤백, 참가 실패 시 안내 미저장, 동시 참가·취소 경합에서 안내 수와 최종 참가 관계의 일치 |
| `CHAT-06-T3` | 이력·실시간 응답의 종류·사건 키·대상 표시명과 조립된 안내 문장, 저장 계층의 완성 문장·닉네임 사본 부재, 닉네임 변경 뒤 과거 안내의 현재 닉네임 반영, 공개 프로필 미조회 시 대체 표시명 반환 |
| `CHAT-06-T4` | 사용자 메시지와 시스템 메시지가 섞인 이력의 `beforeMessageId` 구간 연속성과 `size` 계수, 재연결 `afterMessageId` catch-up의 오름차순·중복 제거, 실시간 전달 실패 뒤 catch-up 복구 |
| `CHAT-06-T5` | 참가 취소자·비참가자·`CANCELED`·`FINISHED` 방의 접근 거절, 시스템 메시지 포함 30일 보존과 만료 묶음 물리 삭제, 안내 문장·닉네임·사용자 ID의 로그·metric label 미기록 |
| `CHAT-06-T6` | 전진 migration 뒤 기존 사용자 메시지 행의 유효성과 전송·이력·실시간 회귀 부재, 종류별 CHECK 제약이 잘못된 조합의 저장을 거절, 허용값이 아닌 사건 키 저장의 독립적 거절, 소급 안내 미생성 |
| `CHAT-06-T7` | schema 확장만 적용한 상태에서 `message_type`을 지정하지 않는 INSERT가 default `USER`로 저장, 전역 gate가 비활성인 동안 참가·참가 취소가 안내 없이 성공, 활성화 시각 전후 사건의 안내 유무가 gate 판정만으로 갈리고 인스턴스별 설정이 달라도 같은 결과로 수렴, `SYSTEM` 행이 있는 방의 이력·실시간·재연결 catch-up이 모두 같은 문장으로 동작 |
| `CHAT-06-T8` | 전송 API에 종류·사건 키·안내 대상을 지정하려는 요청이 `USER` 메시지로만 처리되거나 거절되고 `SYSTEM` 행을 만들지 못함, 안내 저장 전후로 사용자·방 전송 제한 bucket의 카운터와 남은 TTL이 변하지 않음, 참가·취소가 반복된 직후에도 사용자 메시지 전송 제한이 기존 임계값 그대로 동작 |

`CHAT-06-T1`~`CHAT-06-T8`은 PostgreSQL 통합 검증으로 재현한다. 종류별 CHECK 제약과 NULL 허용 전이는 H2 테스트만으로 판정하지 않는다. `CHAT-06-T7`은 혼합 버전 구간의 저장·조회 계약을 재현하며, 두 버전을 실제로 동시에 띄우는 배포 리허설까지 요구하지 않는다.

각 완료 기준은 같은 번호의 테스트로 닫되, `CHAT-06-AC6`은 `CHAT-06-T6`·`CHAT-06-T7`을 함께 사용하고 `CHAT-06-AC7`은 `CHAT-06-T8`로 닫는다.

### CHAT-06 운영 측정

실제 목표값은 기준선과 최소 표본을 확보한 뒤 확정한다. 다음은 운영에서 관측할 제품 지표다.

- 참가·참가 취소 확정 건수 대비 저장된 안내 건수. 누락과 중복의 목표는 모두 0건이다.
- 안내 저장이 원인 참가 트랜잭션에 더한 지연과 참가·참가 취소 API의 p95 변화
- 같은 방의 안내 저장과 메시지 전송이 채팅방 append 잠금에서 경합한 대기 시간. 안내 저장은 기존 메시지 전송과 같은 잠금을 얻으므로 참가·취소가 잦은 방의 전송 지연을 함께 본다.
- 시스템 메시지를 포함한 이력 조회의 p95와 대상 공개 프로필 조회 횟수·중복 제거 비율
- 안내 실시간 전달 지연, 전달 실패 건수와 재연결 catch-up으로 복구된 건수
- 안내 저장 실패로 함께 롤백된 참가·참가 취소 요청 건수

참가 API의 `2xx`나 실시간 이벤트 발행만으로 안내 생성을 판정하지 않는다. 커밋된 저장 행과 사용자가 다시 조회할 수 있는 이력이 모두 확인돼야 한다.

### CHAT-06 중단 조건

- 안내 누락·중복이 재현되거나, 안내 저장이 참가·참가 취소의 동시성 계약과 충돌해 최종 상태가 갈라진다.
- 안내 저장이 참가·참가 취소 API 지연을 측정 기준 밖으로 늘리거나, 읽기 시점 조립이 이력 조회 지연 기준을 넘는다.

저장 모델·문구 소유·사건 범위를 다시 검토할 조건은 [ADR-0078](../adr/chat/0078-chat-system-message-storage-and-read-time-composition.md#보류-및-재검토)이 소유한다.

### CHAT-07 자동 검증

| 테스트 ID | 반드시 재현할 증거 |
| --- | --- |
| `CHAT-07-T1` | 메시지가 없는 방의 `lastMessagePreview`·`lastMessageAt` `null`과 `unreadCount` `0` |
| `CHAT-07-T2` | 다른 사용자의 메시지 1건 도착 시 `unreadCount` 1로 반영과 상단 배지 등장, 메시지 3건 도착 시에도 방 표시 행은 하나이고 `unreadCount`가 3으로 누적 |
| `CHAT-07-T3` | 본인이 보낸 `USER` 메시지와 본인이 대상인 `SYSTEM` 메시지가 본인 `unreadCount`에서 제외되고, 다른 참가자의 `unreadCount`에는 정상 반영 |
| `CHAT-07-T4` | 읽음 처리 API 성공 뒤 `unreadCount` 0 수렴, 존재하지 않거나 미래의 `upToMessageId` 거절, 이미 반영된 값 이하로의 재요청이 커서를 후퇴시키지 않고 멱등하게 성공 |
| `CHAT-07-T5` | 두 방에 각각 메시지가 도착했을 때 방별 `unreadCount`·마지막 메시지가 서로 섞이지 않고 독립적으로 계산 |
| `CHAT-07-T6` | 같은 메시지의 WebSocket 중복 전달·순서 역전·재연결 `afterMessageId` catch-up이 반복돼도 이후 조회의 `unreadCount`가 항상 같은 값으로 수렴 |
| `CHAT-07-T7` | 참가 취소자·비참가자·`CANCELED`·`FINISHED` 방의 마지막 메시지·`unreadCount` 조회 거절과 읽음 처리 API 거절 |
| `CHAT-07-T8` | `SYSTEM` 메시지가 있는 방에서 마지막 메시지 미리보기·`unreadCount` 포함과 대상 본인 제외가 성립하고, `CHAT-06`의 저장·응답 계약 값이 그대로 유지 |
| `CHAT-07-T9` | 30일 보존 만료로 커서보다 오래된 메시지가 물리 삭제된 뒤에도 `unreadCount` 계산과 읽음 처리 API가 오류 없이 동작 |

`CHAT-07-T1`~`CHAT-07-T9`는 PostgreSQL 통합 검증으로 재현한다. 각 완료 기준은 같은 번호의 테스트로 닫는다(`CHAT-07-AC1`은 `CHAT-07-T1`, ... `CHAT-07-AC9`는 `CHAT-07-T9`).

### CHAT-07 운영 측정

실제 목표값은 기준선과 최소 표본을 확보한 뒤 확정한다. 다음은 운영에서 관측할 제품 지표다.

- 채팅 목록 조회의 배치 미읽음·마지막 메시지 집계가 더한 지연과 `GET /api/users/me/rooms` p95 변화
- 읽음 처리 API의 성공률과 지연
- 상단 배지 요약 조회(`GET /api/users/me/chat/unread-summary`)의 p95
- 방 개수·메시지 규모가 커질 때 배치 집계 질의의 스캔 비용 추세

### CHAT-07 중단 조건

- 배치 미읽음 집계가 채팅 목록 조회 지연을 측정 기준 밖으로 늘린다.
- 재현 가능한 시나리오에서 `unreadCount`가 실제 미읽음 메시지 수와 다르게 수렴한다.

저장·집계 방식을 다시 검토할 조건은 [ADR-0079](../adr/chat/0079-chat-room-read-cursor-and-derived-unread-count.md#보류-및-재검토)가 소유한다.
