# 알밤메이트 P2 3차 MVP 명세

> **문서 상태: active · 정본 승격일: 2026-08-13**
>
> 이 문서는 P1 종료·아카이브 뒤 사용하는 P2 공통 범위 정본이다. P2 기능의 상세 계약과 현재 제공 상태는 이 문서만으로 완료 판정하지 않고, 기능별 명세·승인 ADR·API·ERD·아키텍처와 [P2 기능 상태](p2/README.md#기능별-현재-상태)를 함께 확인한다.
>
> P2는 AI 챗봇(게임 탐색 도우미 포함), 게임 의미 기반 검색, 실시간 매칭과 운영 관측을 각 기능 문서로 나누어 작성한다. 이 문서는 특정 기능의 상세 명세가 아니라 팀 전체가 공유하는 범위, 문서 규칙, 통합 원칙과 완료 판정 기준을 관리한다.

### 완료 기준 ID

- 각 기능 작성자는 상세 명세를 만들 때 사용할 기능 접두사와 상위 기능 ID를 [P2 문서·기능 상태](p2/README.md)에 먼저 등록한다.
- 이미 사용했거나 과거 단계에서 예약한 ID와 충돌하지 않도록 저장소 전체를 확인한다. 부여한 ID는 바꾸지 않고 삭제한 번호도 다시 사용하지 않는다.
- 완료 기준은 `{기능 ID}-AC{번호}` 형식을 사용하며 각 기능 ID 안에서 `AC1`부터 시작한다.
- 하나의 기능을 여러 구현 완료 단위로 나누면 P1과 같이 상위 기능 ID 뒤에 소문자 알파벳을 붙인다. 상위 기능은 필수 하위 단위와 상위 통합 완료 기준을 모두 충족해야 완료된다.
- 운영 관측은 확정된 `OPS-01`~`OPS-05`를 사용한다. 배포·rollback·백업·복구 자동화 후보 `OPS-06`, `RANK-01`과 `SEC-01`은 다른 기능에 재사용하지 않는다.
- 이슈와 PR은 완료 기준 문장을 복사하는 대신 기능 ID와 정확한 AC 범위를 선언한다.

## 서비스 개요

### 서비스 비전

알밤메이트는 사용자가 게임과 모임을 더 쉽게 찾고 적절한 사람과 실제 플레이까지 이어가도록 돕는다. P2는 P1의 로그인·탐색·대기열·알림·채팅 흐름을 유지하면서 팀원별로 선택한 새로운 경험을 확장하고, 배포된 기능이 실제로 동작하는지 운영 근거로 확인한다.

### P2 정의

P2는 하나의 모니터링 기능을 뜻하지 않는다. 다음 네 기능 영역을 독립된 상세 명세로 작성하고, AI 챗봇 영역의 게임 탐색 도우미(`DISCOVERY-01`)를 별도 계약으로 좁혀 공통 제품 계약과 운영 관측으로 연결하는 3차 MVP 단계다.

| 기능 영역 | P2에서 작성할 핵심 계약 | 현재 문서 상태 |
| --- | --- | --- |
| AI 챗봇 | 사용자 입력·응답, 사용할 데이터, 서비스 기능 호출 권한, 실패·fallback과 품질·안전 검증 | 담당자 상세 명세 작성 예정 |
| AI 챗봇 하위·게임 탐색 도우미 | 자연어 의도 해석, SEARCH-04 읽기 도구 호출, 근거 있는 응답, 권한·안전·fallback과 품질 검증 | [`DISCOVERY-01` 상세 명세](p2/game-discovery-assistant.md#discovery-01) 초안 작성 완료·선행 계약 필요 |
| 게임 의미 기반 검색 | 검색 대상 데이터와 이용 경계, 색인·질의·정렬 방식, 기존 조건 검색과의 관계, 검색 품질 평가 | [`SEARCH-04` 상세 명세](p2/search.md#search-04) 초안 작성 완료·선행 계약 필요 |
| 실시간 매칭 | 매칭 대상·조건·상태·생명주기, 실시간 전달, 동시성·실패·취소·복구와 사용자 화면 | [`MATCH-01` 기능 명세](p2/matching.md) 초안 작성 완료 |
| 운영 관측 | 서비스 생존·지연·실패·AI 사용량·추정 비용과 핵심 업무 기능의 최종 결과 | [운영 관측 명세](p2/monitoring.md) 정본 승격·전송 ADR·[운영 계약](guides/MONITORING_OPERATIONS.md) 반영 |

위 표는 팀 문서의 자리를 정한 것이다. 아직 작성되지 않은 AI 챗봇 본체의 API, 저장 구조, 알고리즘, 화면과 완료 기준을 이 공통 명세에서 추측하지 않는다. 실시간 매칭의 상세 규칙과 완료 기준은 [`MATCH-01` 기능 명세](p2/matching.md)가 소유하며, 계약·생산 코드·자동 검증·배포·실측 상태는 [P2 기능 상태](p2/README.md#기능별-현재-상태)에서만 갱신한다.

### 해결하려는 문제와 검증 가설

P1은 조건 검색, 대기열·자동 승격, 알림과 채팅을 구현하지만 P2 후보는 서로 다른 문제를 다룬다. 챗봇은 자연어 상호작용과 기존 기능 연결, 의미 기반 검색은 기존 조건 검색으로 찾기 어려운 의도 탐색, 실시간 매칭은 사용자가 선택한 단일 게임과 Board Game Arena 조건이 맞는 사용자를 파티로 확정하고 채팅까지 연결하는 경험, 운영 관측은 배포된 기능의 상태와 최종 업무 결과 확인이 중심이다. 하나의 검증 가설이나 완료 기준으로 네 기능을 묶으면 기능별 가치와 실패 경계가 흐려진다.

> 각 기능이 해결할 사용자 문제, 데이터·권한 경계, 처음부터 끝까지 이어지는 흐름과 완료 기준을 독립적으로 정의하고, 기존 P1 계약을 깨지 않은 채 통합·배포한 뒤 자동 검증과 운영 근거를 분리해 남길 수 있다면 P2의 기능 확장과 실제 동작을 함께 설명할 수 있다.

### 대상 사용자와 역할

- P1 사용자: 참가자, 주최자와 룰마스터의 기존 권한·상태·접근 규칙을 기본으로 유지한다.
- P2 기능 사용자: 챗봇·게임 탐색 도우미·의미 기반 검색·실시간 매칭에서 새로 필요한 사용자 행동과 역할은 각 기능 문서가 정의한다.
- 운영 담당자: 배포된 기능의 생존·지연·실패·비용과 최종 업무 결과를 확인한다.
- 개발·검증 담당자: 기능별 계약, 자동 검증, 배포와 실측 증거를 구분해 완료 상태를 갱신한다.

새 관리자 역할이나 별도 사용자 자격은 기능 문서와 필요한 보안 결정을 거치지 않고 추가하지 않는다.

## 구현 원칙

### P1 호환 우선

- P2는 P1에서 확정한 사용자·세션·CSRF, ROOM·참가, 검색, 알림과 채팅 계약을 기본값으로 유지한다.
- P2 기능이 기존 API·상태·권한·저장 구조의 의미를 바꾸면 해당 기능 문서에 변경 범위와 호환 전략을 먼저 적고 소유 정본을 같은 작업에서 갱신한다.
- 기존 성공 응답을 AI 추천이나 매칭 성공으로 재해석하지 않고 새 기능의 최종 결과를 별도로 정의한다.
- 현재 기능을 교체하는 변경과 새 기능을 선택적으로 추가하는 변경을 구분한다.

### 기능별 문제와 완료 기준 우선

- 각 기능 문서는 해결할 사용자 문제와 한 개 이상의 핵심 흐름을 먼저 정의한다.
- 구현 기술이나 화면 목록만으로 기능 범위를 대신하지 않는다.
- 기능별 완료 기준은 기술 수락, 업무 결과와 사용자가 확인하는 최종 결과를 구분한다.
- 다른 팀원의 기능이 준비되지 않아도 독립적으로 검토·구현·검증할 수 있는 경계를 명시한다. 기능 간 선행 관계가 있으면 양쪽 문서에 같은 관계를 연결한다.

### 데이터·권한 경계 우선

- AI 챗봇과 의미 기반 검색은 입력 데이터의 출처, 이용 허용 범위, 보존·가공 가능 여부를 구현 전에 확정한다.
- 현재 승인 범위에서 BGG 원본 데이터는 AI·LLM 입력으로 사용하지 않는다. 별도 팀 소유 데이터나 이용 근거가 확인되기 전에는 이 제한을 우회하지 않는다.
- 챗봇·`DISCOVERY-01`의 Tool Calling이나 실시간 매칭은 현재 API의 인증·인가·CSRF와 업무 불변식을 그대로 통과해야 한다. 서버 권한을 우회하는 내부 호출을 만들지 않는다.
- 프롬프트·응답·검색 질의·매칭 조건에 개인정보나 비밀값이 들어가는 범위와 마스킹·보존 정책은 각 기능 문서가 명시한다.

### 실제 동작과 증거 상태 분리

- 문서, 코드, 자동 테스트, 배포와 실제 시나리오 측정은 서로 다른 상태다. 하나의 완료로 다른 상태를 대신하지 않는다.
- 화면이나 대시보드가 존재한다는 사실만으로 기능 동작을 완료로 판정하지 않는다.
- 각 기능은 고정 release와 재현 가능한 입력에서 핵심 흐름의 시작·최종 결과·실패·복구를 확인한다.
- AI·검색처럼 결과 품질이 필요한 기능은 작성자가 평가 fixture, 기대 결과, 판정 방법과 최소 표본을 기능 문서에 정의한다. 실제 데이터가 없으면 목표 수치를 추측하지 않는다.

### 운영 관측 공통 연결

- 운영 관측은 P2 전체를 대신하는 제품 기능이 아니라 배포된 각 기능의 상태와 결과를 확인하는 공통 기반이다.
- 각 기능 문서는 요청 수·지연·오류·업무 성공·업무 거절처럼 운영에서 확인할 신호와 금지할 개인정보 label·로그를 정의한다.
- 공통 수집·로그·대시보드·경고 방식은 [운영 관측 명세](p2/monitoring.md), [대시보드 정책](p2/dashboard.md)과 [운영 관측 런북](guides/MONITORING_OPERATIONS.md)을 따른다.
- 관측 수집 실패가 챗봇·검색·매칭과 기존 P1 사용자 요청의 결과를 바꾸지 않는다.

### 문서별 단일 책임

- 본 문서는 기능 둘 이상이 함께 사용하는 P2 공통 규칙만 관리한다.
- 기능별 사용자 흐름, 기능 규칙, 완료 기준과 제외 범위는 각 기능 문서가 관리한다.
- 현재 계약·생산 코드·자동 검증·운영 배포와 실측 상태는 [P2 기능 상태](p2/README.md#기능별-현재-상태)에서만 갱신한다.
- 요청·응답과 오류 코드는 [API 명세서](API.md), 테이블·컬럼·제약은 [ERD](ERD.md), 모듈 책임은 [아키텍처](ARCHITECTURE.md), 논쟁적 기술 선택은 [ADR](adr/README.md)이 관리한다.
- 일정, 담당자 배정, Issue·PR 분할과 발표 순서는 제품 명세가 아니라 별도 작업 계획에서 관리한다.

AI 챗봇 본체의 상세 문서와 기능 ID는 담당자가 범위·데이터·권한·흐름을 확정하면서 추가한다. `DISCOVERY-01`, `SEARCH-04`, `MATCH-01`은 상세 명세를 등록했지만 공통 명세가 API, 테이블, 알고리즘이나 UI를 대신 확정하지 않으며, 필요한 기술 계약은 각 기능 문서와 승인 ADR에서 정한다.

### 기능 문서 필수 구성

각 팀원 문서는 P1 기능 문서와 같은 순서로 다음 내용을 포함한다.

1. 문서 책임과 현재 상태 정본 링크
2. 기능 ID별 구현 컨텍스트
3. 해결할 사용자 문제와 핵심 사용자 흐름
4. 기능 규칙과 데이터·권한·실패 경계
5. 기능 ID별 완료 기준
6. 제외 범위와 다시 검토할 조건
7. API·ERD·아키텍처·ADR의 변경 필요 여부
8. 자동 검증, 배포 검증, 품질·운영 측정 기준

문서 작성만으로 `계약 준비 완료`가 되지는 않는다. 필요한 제품 정책과 ADR을 승인하고 API·ERD·아키텍처 등 소유 정본을 반영한 뒤 [P2 기능 상태](p2/README.md#기능별-현재-상태)를 갱신한다.

### P2 공통 제외 범위

- 담당 기능 문서가 없는 상태에서 AI·검색·매칭의 API, 저장 구조, 모델·알고리즘이나 화면을 공통 명세가 대신 확정하는 것
- 데이터 이용 근거를 확인하지 않은 BGG 원본의 AI·LLM 입력과 색인·가공
- 챗봇·매칭 내부 호출이라는 이유로 현재 인증·인가·CSRF와 업무 불변식을 우회하는 것
- 문서·코드·테스트·대시보드 screenshot만으로 실제 배포·기능 동작·품질 측정을 완료로 표시하는 것
- 사용자 ID·이메일·세션·ROOM·메시지·프롬프트·응답 원문을 무제한 메트릭 label이나 중앙 로그로 수집하는 것
- 한 기능 때문에 현재 알림·채팅·대기열·검색의 저장·전달 구조를 근거와 ADR 없이 전면 교체하는 것
- P2 기능 구현과 무관한 24시간 on-call, 자동 확장·rollback, 계정 전체 FinOps와 장기 SLO·SLA 확정

각 기능의 구체적인 제외 범위는 담당 기능 문서에서 추가한다. 운영 관측의 세부 제외 범위는 [운영 관측 명세](p2/monitoring.md#제외-범위)가 소유한다.

## 공통 통합 흐름

### 기능 전달 흐름

~~~text
기능 문서에 사용자 문제·데이터·권한·완료 기준 작성
→ 필요한 API·ERD·아키텍처·ADR 계약 반영
→ 기능 ID와 AC 범위로 구현·자동 검증
→ 고정 release에서 핵심 흐름 배포 검증
→ 기능별 품질 지표와 공통 운영 관측 확인
→ P2 기능 상태에 계약·코드·검증·배포·실측을 각각 기록
~~~

### 기능 간 통합 규칙

- 챗봇이 검색·방 생성·참가 같은 기존 기능을 호출하면 공개된 application/API 경계와 동일한 권한·검증·오류 계약을 사용한다. 실제 호출 목록과 사용자 확인 단계는 챗봇 명세가 소유한다.
- 의미 기반 검색이 기존 조건 검색과 함께 동작할 경우 필터 적용 순서, 결과 정렬·페이지네이션과 값 없음·fallback을 검색 명세와 API가 함께 정의한다.
- 실시간 매칭이 ROOM·참가·채팅을 사용하면 매칭 상태와 기존 ROOM 상태를 섞지 않고 소유 도메인과 전이 책임을 명시한다.
- 운영 관측은 각 기능의 요청·지연·오류·최종 업무 결과를 공통 화면에서 연결하되, 제품 데이터의 정본이나 기능 실행 주체가 되지 않는다.
- 두 기능이 같은 API·테이블·이벤트를 바꾸면 먼저 공통 계약의 최종 소유자를 정하고 각 기능 문서에서 같은 정본을 링크한다.

## 인터페이스와 데이터 변경 범위

- P2 공통 명세는 신규 HTTP·WebSocket endpoint, 요청·응답 필드나 데이터베이스 테이블을 직접 추가하지 않는다.
- 각 기능 문서는 필요한 인터페이스와 저장 변경을 식별하고, 구현 전에 [API 명세서](API.md)·[ERD](ERD.md)·[아키텍처](ARCHITECTURE.md)와 필요한 ADR에 반영한다.
- AI provider·model, embedding·vector 저장소, 실시간 전달 수단과 매칭 알고리즘은 기능 문서의 대안 비교와 승인 없이 공통 선택으로 간주하지 않는다.
- 운영 관측 `OPS-01`~`OPS-05`는 일반 사용자용 제품 API와 신규 업무 테이블을 기본으로 요구하지 않는다. management endpoint와 metric·log export는 운영 내부 인터페이스다.
- 기능 간 계약이 충돌하면 조용히 합치지 않고 충돌하는 요구, 소유 문서와 사용자 결정을 기록한다.

## 구현 완료 기준

- [P2 기능 상태](p2/README.md#기능별-현재-상태)에서 P2 필수 범위로 채택한 모든 기능 ID의 상세 완료 기준을 충족한다.
- 각 기능 문서가 사용자 문제, 핵심 흐름, 데이터·권한·실패 경계, 완료 기준과 제외 범위를 갖는다.
- 필요한 API·ERD·아키텍처·ADR과 기능 문서가 서로 모순되지 않으며 변경하지 않은 P1 계약을 유지한다.
- 각 기능은 생산 코드와 자동 검증을 갖고, 고정 release의 배포 환경에서 핵심 성공·업무 거절·기술 실패·복구 흐름을 확인한다.
- AI 챗봇·게임 탐색 도우미·의미 기반 검색처럼 결과 품질을 판정해야 하는 기능은 기능 문서가 정한 평가 fixture·판정 방법·최소 표본으로 결과를 기록한다.
- 기능 간 호출은 현재 인증·인가·CSRF와 업무 불변식을 우회하지 않으며 통합 실패가 기존 P1 기능의 저장 결과를 바꾸지 않는다.
- 배포된 P2 기능의 생존·지연·실패·사용량과 최종 업무 결과를 [운영 관측 명세](p2/monitoring.md)의 적용 가능한 완료 기준으로 확인한다.
- 문서, 계약, 생산 코드, 자동 검증, 운영 배포와 실측 상태를 각각 구분해 [P2 기능 상태](p2/README.md#기능별-현재-상태)에 기록한다.
