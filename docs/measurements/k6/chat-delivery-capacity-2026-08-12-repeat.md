## 실행 간 편차 — 이번 캠페인의 핵심

같은 release·같은 계단·같은 fixture 규모로 세 번 측정한 원자료다. 다만 08-11 1차는 setup 전 단계 태그 기준점 때문에 단계 비교에서 제외하고, 08-12 2차·3차만 동등 반복으로 비교한다.

| 시나리오 | 단계 | 1차 (08-11 17시, 비교 제외) | 2차 (08-12 04시) | 3차 (08-12 09시) |
| --- | --- | --- | --- | --- |
| `load-rooms` | 방 8개 | 70% | **57.1%** | 65.9% |
| `load-mixed` | 3배 | 84% | 69.4% | **71.8%** |
| `load-mixed` | 4배 | 42% | 44.7% | **44.9%** |
| `load-fanout` | 24명 | 97% | 91.2% | **95.0%** |
| `load-throughput` | 5건/초 | 92.3% | **86.0%** | **100%** |

1차 수치는 원자료 보존을 위해 표에 남겼지만, 단계 태그 기준점이 달라 정상적인 반복 비교에는 사용하지 않는다.

읽는 법은 다음과 같다.

- **경계 위치는 제한적으로 재현된다.** 단계 태그가 같은 2차·3차에서 어느 단계에서 무너지는지가 같다. 1차까지 포함한 3회 결론은 보류한다.
- **성공률은 비교 가능한 두 실행의 범위로 읽는다.** 활성 방 8개는 57.1~65.9%, 혼합 3배는 69.4~71.8%다. 단일 값을 인용하면 안 된다.
- **`load-throughput`은 편차가 가장 크다.** 발신자 회전 결함이 남아 있어 축 자체가 불안정하다.
- **두 캠페인 비교로 개선·악화를 판정하지 않는다.** 비교 가능한 2차·3차만으로는 before/after를 판정할 수 없고, 같은 단계 태그 기준으로 최소 3회 이상의 반복이 필요하다.

## 최초 병목 — Redis 연결 실패가 3회 모두 재현됐다

채팅 경로가 받은 응답을 App1 프록시 접근 로그에서 세면 다음과 같다.

| 경로 | 2xx | **500** | 503 |
| --- | --- | --- | --- |
| `POST /api/rooms/{id}/chat/messages` | 4,867 | **331** | 305 |
| `GET /api/rooms/{id}/chat/messages` | 3,063 | **369** | 259 |

3회 캠페인의 재현성은 다음과 같다.

| 지표 | 1차 | 2차 | 3차 |
| --- | --- | --- | --- |
| Redis 누적 수신 연결 | 99,907 | 120,838 | **125,678** |
| `RedisConnectionFailureException` | — | 2,928 | **2,812** |
| 채팅 경로 HTTP 500 | 706 | 760 | **700** |
| Redis 거부 연결 | 0 | 0 | **0** |
| Redis 사용 메모리 | 2.06MB | 2.06MB | **2.05MB** |

**성공률이 크게 흔들리는 동안에도 이 수치들은 좁은 범위를 유지한다.** 편차가 아니라 구조적 결함이라는 근거다.

원인은 [RedisSessionConfiguration](../../../src/main/java/cloud/bamsongi/albammate/infra/redis/RedisSessionConfiguration.java)이 `setShareNativeConnection(false)`로 연결 공유를 끈 채 커넥션 풀이 없어 작업마다 전용 연결을 여는 것이다. 상세는 [#607](https://github.com/bamsongi-club/albam-mate/issues/607)에 있다.

읽기 경로의 500이 369건으로 쓰기 경로(331건)보다 많다. 세션 조회가 모든 인증 요청에 붙으므로 채팅 전송만의 문제가 아니다.

## 한계

- **성공률·p95의 절대값을 인용할 수 없다.** 위 편차 절에 적은 대로 범위로만 읽는다.
- 측정값은 `t4g.micro` 노드와 DB 커넥션 풀 8개 구성에 묶인다.
- 08-11 1차는 setup 전 단계 태그 기준점이 2차·3차와 달라 단계 반복 비교에서 제외했다. 3회 재현 결론을 내리려면 같은 기준으로 추가 측정해야 한다.
- `load-rooms` 4단계와 `load-mixed` 3·4단계는 `dropped_iterations`가 각각 10·18건이라 발생기가 목표 부하를 완전히 내지 못했다. 이 구간의 지연은 하한으로 읽는다.
- `load-throughput`의 발신자 회전 결함은 아직 고치지 않았다. 이 축은 서버 용량 근거로 쓰지 않는다.
- 편차의 원인을 규명하지 않았다. Redis 연결 폭주가 실행마다 다르게 누적되는 것이 유력한 후보이나 확인하지 않았다.
- Run 사이에 schema를 초기화하지 않았다.
- 원자료는 `local-only`다.

## 최소 개선 후보와 재측정 계획

1. **Redis 연결 수립·실패 처리 교정** ([#607](https://github.com/bamsongi-club/albam-mate/issues/607)) — 3회 모두 재현된 유일한 결함이다. 가장 우선한다.
2. **WebSocket 전용 `location` 분리** ([#608](https://github.com/bamsongi-club/albam-mate/issues/608)) — 유휴 연결이 60초에 끊긴다.
3. **`load-throughput` 발신자 회전 수정** — 이 축의 편차를 줄이려면 먼저 고쳐야 한다.
4. **1~2번 수정 후 재측정** — 이번 결과 중 동등 비교가 가능한 2차·3차를 참고하되 before 범위 확정은 보류한다. **단일 실행이 아니라 같은 단계 태그 기준으로 최소 3회를 돌려 범위끼리 비교한다.** 새 Campaign ID와 manifest를 만든다.
