- 읽기 경로는 측정 범위에서 여유가 있었다. 이력 조회는 초당 8건까지 p95 65~70ms로 평평했고 실패가 없었다.

## 최초 병목 — Redis 연결 실패가 HTTP 500이 된다

부하 구간에서 채팅 전송 경로가 받은 응답을 서버 접근 로그에서 세면 다음과 같다.

| 구간 | 201 | 429 | **500** | 503 |
| --- | --- | --- | --- | --- |
| 시나리오 1~3 | 1,589 | 52 | **17** | 13 |
| 시나리오 4~6 | 3,283 | 0 | **689** | 520 |

HTTP 500이 706건이며 애플리케이션 로그의 예외는 전부 같은 것이다.

```
org.springframework.data.redis.RedisConnectionFailureException: Unable to connect to Redis
  at LettuceConnectionFactory$ExceptionTranslatingConnectionProvider.getConnection
  at LettuceConnection.doGetAsyncDedicatedConnection
  at LettuceHashCommands.hGetAll          ← 세션 조회
  at LettuceKeyCommands.pExpireAt         ← 세션 TTL 갱신
```

`GlobalExceptionHandler`가 이 예외를 처리하지 못해 `INTERNAL_SERVER_ERROR`로 변환한다.

### 원인은 커넥션 재사용이 없다는 것이다

Redis 자체는 멀쩡했다.

| 지표 | 값 |
| --- | --- |
| 연결된 클라이언트 | 3 |
| `maxclients` | 10,000 |
| **거부된 연결** | **0** |
| 사용 메모리 | 2.06MB (최대 2.33MB) |
| **누적 수신 연결** | **99,907** |

거부는 0인데 누적 연결이 10만 건이다. 앱 가동 약 69분 기준 초당 24건씩 새 연결을 연 셈이다. 스택의 `doGetAsyncDedicatedConnection`이 이를 뒷받침한다.

저장소에 `commons-pool2` 의존성이 없고 `spring.data.redis.lettuce.pool` 설정도 없다. **Lettuce 커넥션 풀이 구성되지 않았다.**

이 결함은 세 가지를 동시에 설명한다.

1. **전송 실패** — 활성 방 8개의 30%, 혼합 4배의 58% 실패
2. **실시간 전달 중단** — 전송 처리량 5단계에서 전달 표본이 0이 된 것. Pub/Sub 신호 경로도 같은 커넥션 문제를 겪는다
3. **응답 시간 급증** — 연결 수립 재시도가 응답 시간에 그대로 실린다

메시지 자체는 PostgreSQL에 남으므로 유실되지 않는다. 재연결하면 이력으로 복구된다. 하지만 사용자에게는 전송 실패와 실시간 수신 중단으로 나타난다.

## 부가 발견 — 유휴 WebSocket이 60초에 끊긴다

`chat_websocket_session_healthy`가 시나리오 1~3에서 0%였다. 연결은 100% 성립하지만 종료 시점 판정에서 전부 "서버가 먼저 끊음"으로 나온다.

원인은 [nginx.production.conf](../../../frontend/nginx.production.conf)의 `location /api/` 블록이다. 이 블록이 `Upgrade` 헤더를 넘겨 WebSocket을 처리하면서 `proxy_read_timeout 60s`를 함께 적용한다. 서버가 60초 동안 보낼 데이터가 없으면 프록시가 연결을 끊는다. 접근 로그에서 전송 바이트 0인 WebSocket 요청이 다수 확인된다.

조용한 채팅방을 1분 열어두면 재현된다. 사용자는 재연결 전까지 새 메시지를 받지 못한다. 트래픽이 있는 시나리오 4~6에서는 세션 정상률이 45.9~77.8%로 올라간다. **메시지가 흐르는 방은 살아남고 조용한 방만 끊긴다.**

## 측정 스크립트 결함

측정 자체의 신뢰도에 영향을 주므로 함께 남긴다.

**발신자 회전 앨리어싱** — `load-throughput`은 방 3개를 `iterationInTest % 3`으로, 발신자를 `iterationInTest % 9`로 고른다. 3이 9를 나누므로 방마다 9명 중 3명만 쓰인다. 초당 5건이면 사용자 한 명이 0.56건/초를 보내 사용자 전송 제한 0.5건/초를 넘는다. 429 52건이 여기서 나왔다.

같은 방식을 쓰는 `load-rooms`(방 1·2·4·8개)와 `load-mixed`(방 8개)는 방 수와 9가 서로소라 9명이 모두 쓰인다. 영향은 `load-throughput`에만 있다.

**단계 태그 기준점** — `setup()`이 `runId`를 로그인 72회보다 먼저 찍는다. 이번 실행에서 setup은 약 14초 걸렸고 그만큼 단계 경계가 앞당겨졌다. 단계 길이 120초 대비 약 12%다. 이 측정 이후 `runId`를 로그인 뒤에 찍도록 고쳤다.

## 한계

- 측정값은 `t4g.micro` 노드와 DB 커넥션 풀 8개 구성에 묶인다. 절대 처리량으로 인용하면 안 된다.
- CPU 크레딧 상태를 이번 캠페인에서 수집하지 못했다. 버스트 인스턴스라 크레딧이 소진되면 CPU가 기본 속도로 묶이므로 다른 시점과 비교할 때 함께 봐야 한다.
- `load-throughput` 4·5단계는 스크립트 결함이 섞여 서버 용량으로 읽을 수 없다. 3단계까지만 유효하다.
- Run 사이에 schema를 초기화하지 않았다. fixture는 Run마다 새로 만들고 지웠지만, 다른 상태가 Run 간에 이월되지 않았음을 별도로 검증하지 않았다.
- 원자료는 `local-only`다. manifest의 SHA-256은 로컬 bundle이 바뀌었는지 확인하지만 이 저장소만으로 원자료를 독립 재검증할 수 있다는 뜻은 아니다.

## 최소 개선 후보와 재측정 계획

1. **Lettuce 커넥션 풀 구성** — 500 706건의 원인이고 세 가지 증상을 동시에 만든다. 가장 우선한다.
2. **Redis 예외를 500이 아닌 503으로 변환** — 풀을 붙여도 연결 실패는 남을 수 있다. `GlobalExceptionHandler`가 이 예외를 알아야 한다.
3. **WebSocket 전용 `location` 분리** — 타임아웃을 늘리거나 서버가 주기적으로 ping을 보낸다.
4. **`load-throughput` 발신자 회전 수정** — 방 수와 참가자 수가 서로소가 아닐 때도 모든 참가자를 쓰도록 고친다.
5. **1~3번 수정 후 재측정** — 이번 결과를 before로 삼는다. 새 Campaign ID와 manifest를 만들고 이 캠페인의 `후속 없음`을 `superseded by <Campaign ID>`로 바꾼다.
