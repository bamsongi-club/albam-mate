## Immutable run manifest

- 비교 결과 하나는 실행 종료 뒤 생성한 하나의 immutable run manifest로만 보존한다. 이 문서에 실행값을 예시로 채우지 않으며, 실제 실행이 끝난 뒤 수집한 값만 기록한다.
- manifest의 `candidateSourceSha`는 실행한 후보 소스 커밋 SHA이고, `baseToHeadDiff`는 `baseSha`, `headSha`, `diffDigest`를 가진 별도 식별자다. 둘은 run artifact의 `artifactId`, `artifactDigest`와 서로 대체하지 않는다.
- 최종 manifest 문서 커밋에서는 `candidateSourceSha`와 실제 checkout `HEAD`가 같거나, `HEAD`가 해당 소스 커밋의 단일 직계 자식이면서 manifest·receipt·raw artifact 묶음만 변경한 경우를 허용한다. 측정 뒤 CI 계약을 보정할 때에는 `RoomLockStrategyComparisonPostgresTest`, `RoomConcurrencyBaselineSupport`, `RoomWaitlistConcurrencyBaselinePostgresTest` 세 test-only 파일을 artifact 묶음과 함께 변경하는 경우만 추가로 허용하며 production source 변경은 허용하지 않는다. GitHub pull request의 synthetic merge checkout에서는 `HEAD`의 second parent가 그 문서 커밋이고, 해당 문서 커밋의 부모가 `candidateSourceSha`인 같은 artifact bundle 관계도 허용한다. validator는 commit 관계와 변경 경로를 확인한다.
- manifest는 다음 필수 필드를 가져야 한다. 빈 문자열, 누락, 실행 뒤 수정은 허용하지 않는다.

- 최종 C manifest의 `artifactId`와 `rawArtifactId`는 각각 추적 중인 canonical receipt/raw 경로여야 한다. `embedded://`나 임의 외부 파일 경로는 synthetic fixture에서만 허용하고 실제 실행 manifest에서는 `VALID`로 처리하지 않는다.
- 최종 C manifest는 runner의 `-CaptureRaw` 실행이 수집한 `docs/measurements/results/room-lock-01-c-raw.log`와 실행 receipt 파일을 artifact로 참조한다. validator는 파일 bytes, manifest content와 두 SHA-256이 모두 같은지 확인한다.
- manifest validator는 `candidateSourceSha`가 실제 candidate checkout HEAD 정책과 일치하는지, `baseToHeadDiff.headSha`가 같은 SHA인지, artifact·raw artifact content 또는 수집 파일 digest가 일치하는지, Java/PostgreSQL/image·fixture·gate·runner·명령·metric field가 계약과 같은지 확인한다.
- 실행은 `scripts/measurements/run-room-lock-comparison.ps1` runner로만 수행한다. runner가 실제 child Gradle argv, runner 경로와 execution ID를 환경 및 immutable receipt에 주입하고 validator가 세 값을 모두 확인한다.
- runner의 `-CaptureRaw`는 child 실행 중 `ROOM785_CAPTURE_RAW=true`를 사용해 receipt/raw를 새로 수집한다. 이 capture 단계에서는 아직 새 artifact가 publish되지 않았으므로 manifest gate 테스트만 skip하고, capture 성공 뒤 기본 runner 실행에서 T1 manifest gate를 다시 통과시킨다. `build/room-lock-01-c-capture.state`가 남아 있는 동안에는 T1이 manifest를 `INVALID`로 처리하므로 raw와 receipt의 부분 publish를 유효 결과로 사용할 수 없다.
- 위 필수 필드 하나라도 누락·공백이거나 환경·하네스·digest가 불일치하면 해당 run의 `resultStatus`는 `INVALID`다. `INVALID` run은 비교 분포, 후보 우열, 최종 ADR 판단에 사용하지 않는다.

- 일괄 상태 보정 대상은 `startAt ASC, id ASC`로 읽어 모든 실행자가 같은 ROOM 잠금 순서를 사용한다.
- T3의 낙관 충돌 검증은 supplier 실행 횟수가 3회인지 확인하고 기존 `ROOM_CONCURRENT_MODIFICATION` 계약을 검증한다.
