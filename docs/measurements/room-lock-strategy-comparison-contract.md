## Immutable run manifest

- 비교 결과 하나는 실행 종료 뒤 생성한 하나의 immutable run manifest로만 보존한다. 이 문서에 실행값을 예시로 채우지 않으며, 실제 실행이 끝난 뒤 수집한 값만 기록한다.
- manifest의 `candidateSourceSha`는 실행한 후보 소스 커밋 SHA이고, `baseToHeadDiff`는 `baseSha`, `headSha`, `diffDigest`를 가진 별도 식별자다. 둘은 run artifact의 `artifactId`, `artifactDigest`와 서로 대체하지 않는다.
- 최종 manifest 문서 커밋에서는 `candidateSourceSha`와 실제 checkout `HEAD`가 같거나, `HEAD`가 해당 소스 커밋의 단일 직계 자식이면서 manifest·receipt·raw artifact 묶음만 변경한 경우를 허용한다. GitHub pull request의 synthetic merge checkout에서는 `HEAD`의 second parent가 그 문서 커밋이고, 해당 문서 커밋의 부모가 `candidateSourceSha`인 같은 artifact bundle 관계도 허용한다. validator는 commit 관계와 변경 경로를 확인한다.
- manifest는 다음 필수 필드를 가져야 한다. 빈 문자열, 누락, 실행 뒤 수정은 허용하지 않는다.

- 최종 C manifest의 `artifactId`와 `rawArtifactId`는 각각 추적 중인 canonical receipt/raw 경로여야 한다. `embedded://`나 임의 외부 파일 경로는 synthetic fixture에서만 허용하고 실제 실행 manifest에서는 `VALID`로 처리하지 않는다.
- 최종 C manifest는 runner의 `-CaptureRaw` 실행이 수집한 `docs/measurements/results/room-lock-01-c-raw.log`와 실행 receipt 파일을 artifact로 참조한다. validator는 파일 bytes, manifest content와 두 SHA-256이 모두 같은지 확인한다.
- manifest validator는 `candidateSourceSha`가 실제 candidate checkout HEAD 정책과 일치하는지, `baseToHeadDiff.headSha`가 같은 SHA인지, artifact·raw artifact content 또는 수집 파일 digest가 일치하는지, Java/PostgreSQL/image·fixture·gate·runner·명령·metric field가 계약과 같은지 확인한다.
- 실행은 `scripts/measurements/run-room-lock-comparison.ps1` runner로만 수행한다. runner가 실제 child Gradle argv, runner 경로와 execution ID를 환경 및 immutable receipt에 주입하고 validator가 세 값을 모두 확인한다.
- runner의 `-CaptureRaw`는 child 실행 중 `ROOM785_CAPTURE_RAW=true`를 사용해 receipt/raw를 새로 수집한다. 이 capture 단계에서는 아직 새 artifact가 publish되지 않았으므로 manifest gate 테스트만 skip하고, capture 성공 뒤 기본 runner 실행에서 T1 manifest gate를 다시 통과시킨다. `build/room-lock-01-c-capture.state`가 남아 있는 동안에는 T1이 manifest를 `INVALID`로 처리하므로 raw와 receipt의 부분 publish를 유효 결과로 사용할 수 없다.
- 위 필수 필드 하나라도 누락·공백이거나 환경·하네스·digest가 불일치하면 해당 run의 `resultStatus`는 `INVALID`다. `INVALID` run은 비교 분포, 후보 우열, 최종 ADR 판단에 사용하지 않는다.

## T2 gate

- A/B는 기존 deterministic read gate에서 두 요청이 동일 ROOM version을 읽은 뒤 승인된 commit-order로 진행한다.
- C는 첫 요청이 ROOM `PESSIMISTIC_WRITE`를 획득했음을 확인한 뒤 두 번째 요청을 시작하고, 승인된 순서로 첫 요청을 commit 또는 rollback 한다.
- C는 raw lock helper만 성공시키지 않고 실제 직접 참가·대기 신규/재활성 등록·참가 취소/자동 승격과 시작 경계 상태 보정 경로를 deterministic gate로 실행한다.
- 시작 경계는 상태 보정과 직접 참가·대기 등록·참가 취소/승격·대기 취소를 양쪽 commit-order로 실행한다. 각 round 뒤 PostgreSQL snapshot으로 ROOM active count/status/version, Participation 상태·ACTIVE 중복, Waitlist 상태·FIFO·자동 승격 및 rollback 불변식을 단언한다.
- 시작 경계 fixture는 경계 이전 시각의 ROOM에서 준비한 뒤 경합 직전에 `start_at`을 `2026-08-17T00:00:00Z`로 옮긴다. command clock도 같은 시각이므로 `now >= startsAt`이 성립한다.
- 경계 이후에는 직접 참가가 `ROOM_NOT_RECRUITING`, 대기 신규·재활성 등록이 `WAITLIST_NOT_AVAILABLE`, 참가 취소가 `INVALID_ROOM_STATUS_TRANSITION`으로 거절된다. 대기 취소는 C의 실제 `PESSIMISTIC_WRITE` 순서에 따라, 취소 선행에서는 취소와 상태 보정이 모두 성공하고 보정 선행에서는 상태 보정이 먼저 대기를 `EXPIRED`로 만들어 취소가 `WAITLIST_ENTRY_NOT_FOUND`가 된다. 어느 순서에서도 활성 대기는 남지 않는다.
- 각 T2 시나리오와 양쪽 commit order는 3회 반복 실행하고 모든 round의 결과·비용 원자료를 보존한다. 반복 횟수는 manifest의 `fixture.gate`에 선언하며, 반복 표본이 하나라도 누락되면 raw artifact는 `INVALID`다.
- C의 lock timeout·deadlock·낙관 충돌 소진·예상 밖 기술 오류는 PostgreSQL T3에서 실제 production HTTP 또는 service 경로로 각각 유발한다. timeout/deadlock은 SQLState 또는 실제 lock 경계로, 낙관 충돌은 production retrier로 확인하고 재시도 횟수·API 코드·내부 reasonCode·실패 전후 snapshot을 함께 검증한다.
