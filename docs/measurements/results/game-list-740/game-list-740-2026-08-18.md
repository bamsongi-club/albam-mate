# GAME 목록 #740 실제 v4 baseline / SQL / EXPLAIN

첨부된 `albam-mate-170k-patched-v4.zip`을 별도 측정 DB에 직접 import하고, PR #771 최신 head인 `5b2909d`에서 `GET /api/games`를 측정했습니다. 6개 시나리오는 순차 실행했으며, 시나리오마다 warm-up 5회 후 20회를 실측했습니다.

## 결론

- v4 SQL을 `01-games-full.sql → 02-metadata-full.sql` 순서로 적용한 뒤 games `170,005`건과 metadata relation count를 확인했습니다.
- 6개 시나리오 모두 `20/20`회 HTTP `200`이었고, 별도 재조회로 `totalElements`와 page content 길이를 확인했습니다.
- HTTP p95는 `complex` `1,100.341ms`, `relation-theme-mechanism` `370.992ms`, `player-count` `225.079ms` 순이었습니다.
- 실제 SQL capture는 총 20개였습니다. base/player-count는 3개, keyword는 2개, relation/complex는 5개, flags는 2개이며 page 행마다 SQL이 반복되는 N+1은 관찰하지 않았습니다.
- 이번 단일 `EXPLAIN` 기준 가장 큰 SQL은 relation content `296.095ms`입니다. 관련 인덱스는 사용되지만 `HAND_MANAGEMENT` 후보 `24,419`건을 game PK로 조회하고 theme relation을 최대 `78,352`회 확인하는 semi-join 경로라서 느립니다.
- 이번 PR에는 측정·진단과 raw evidence만 포함합니다. 인덱스·쿼리·pagination 계약 변경은 후속 범위입니다.

## 실제 SQL capture

Hibernate SQL debug/bind 로그를 켜고 2026-08-18 14:40:00~14:40:01 UTC에 시나리오별 1회 요청을 순차 실행했습니다. [원문 SQL capture](./game-list-740-2026-08-18-v4-sql-capture.log)에 `Hibernate: select` 20개와 `game_search_completed` 6개가 보존되어 있습니다.

| scenario | statements | 구성 |
| --- | ---: | --- |
| `base` | 3 | game content, game count, page game IDs room count |
| `keyword` | 2 | game content, page game IDs room count |
| `player-count` | 3 | game content, game count, page game IDs room count |
| `relation-theme-mechanism` | 5 | mechanism/theme validation 2, content, count, room count |
| `complex` | 5 | mechanism/theme validation 2, content, count, room count |
| `flags-upcoming-exact` | 2 | upcoming room discovery, discovered game IDs + exact player content |
| 합계 | **20** | 6개 요청 |

확인한 SQL 구조는 다음과 같습니다.

- 기본 목록은 `games content → games count → rooms group/count` 순서의 3개 statement입니다.
- keyword는 `lower(g1_0.name) like ? escape '\\'`에 `ix_games_name_lower_trgm`을 사용합니다.
- relation/complex는 mechanism/theme validation 후 `exists` 두 개가 포함된 content와 count를 실행합니다.
- page content 결과를 다시 읽는 game/relation SQL은 없었으므로 page 행 수에 비례하는 N+1은 관찰하지 않았습니다.
- SQL log는 statement 발생 순서를 증명하며 개별 DB 실행시간은 제공하지 않으므로, 실행시간 판단은 아래 `EXPLAIN` raw output을 기준으로 했습니다.

## EXPLAIN (ANALYZE, BUFFERS)

동일 측정 DB에 capture와 같은 대표 bind 값을 넣어 읽기 전용 SQL을 실행했습니다. [EXPLAIN 원문](./game-list-740-2026-08-18-v4-explain.txt)은 `track_io_timing=on`과 `VERBOSE`를 포함한 text output입니다. 단일 EXPLAIN 실행시간은 warm cache와 HTTP/DTO 비용이 다르므로 HTTP p95와 직접 같은 값으로 비교하지 않습니다.

| SQL | Execution Time | 주요 plan | 핵심 관찰 |
| --- | ---: | --- | --- |
| base content | 0.550ms | `Index Scan ix_games_popularity_score_name_id` | 정렬 순서 인덱스로 첫 24건 제한 |
| base count | 15.720ms | `Parallel Index Only Scan games_pkey` | 170,005건 count, heap fetch 0 |
| keyword content | 0.410ms | `Bitmap Heap Scan` + `ix_games_name_lower_trgm` | 실제 1행, trigram index 사용 |
| player-count content | 0.376ms | `Index Scan ix_games_popularity_score_name_id` | content는 빠르지만 count와 분리됨 |
| player-count count | 180.113ms | `Parallel Seq Scan games` | shared hit 11,883 / read 32,162 |
| relation validation | 0.055ms + 0.016ms | mechanism index / theme seq scan | 작은 lookup 비용 |
| relation content | **296.095ms** | nested-loop semi join + top-N heapsort | shared hit 317,580 / read 10,257 |
| relation count | 88.414ms | nested-loop semi join | shared hit 315,550 / read 139 |
| complex content | 106.275ms | nested-loop semi join + quicksort | shared hit 221,287 / read 9,900 |
| complex count | 93.336ms | nested-loop semi join | relation 후보와 theme 확인 반복 |
| related room queries | 0.019~0.163ms | `Seq Scan rooms` | fixture 60건 규모 |
| flags content | 0.063ms | `Index Scan games_pkey` | exact player 조건에서 30건 제거 |

현재 인덱스 사용 여부와 느린 이유를 분리해서 봐야 합니다.

1. `base` content, keyword content, relation mechanism relation은 각각 정렬·trigram·mechanism/game relation 인덱스를 탑니다.
2. 그러나 relation content는 mechanism relation에서 실제 `24,419` game ID를 만든 뒤 `games_pkey`를 `24,419`회 조회합니다.
3. 그 뒤 theme relation index를 `24,419`회, theme PK를 최대 `78,352`회 확인하고 마지막에 top-N 정렬을 합니다.
4. 따라서 “인덱스를 탔다”는 판단은 맞지만, “인덱스를 탔으니 빨라야 한다”는 결론은 맞지 않습니다. 인덱스가 찾는 후보 수와 반복 횟수가 더 큰 비용을 만들 수 있습니다.
5. player-count는 content 자체는 `0.376ms`지만 `Page` total count가 전체 games를 `Parallel Seq Scan`해 `180.113ms`가 됩니다. content와 count를 반드시 따로 봐야 합니다.

이번 isolated run의 대표 SQL 기준 병목 후보는 relation content `296.095ms`이며, HTTP 기준 가장 느린 시나리오는 relation 조건을 포함한 `complex` p95 `1,100.341ms`입니다. 이 결과는 인덱스 추가를 즉시 승인하는 근거가 아니라, relation filter/count query shape를 후속 개선 이슈로 좁힐 근거입니다.
