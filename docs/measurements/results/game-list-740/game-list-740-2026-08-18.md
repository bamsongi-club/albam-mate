# GAME 목록 #740 실제 baseline / SQL / EXPLAIN

측정 대상은 PR #771에 결과가 추가되기 전 server/runner commit `9775ef4e4408a9249eaa040d233e6de4550a52ae`입니다. 실제 `170,005`건 데이터베이스에서 6개 시나리오를 순차 실행했고, 시나리오마다 warm-up 5회 후 20회를 측정했습니다.

## 결론

- 6개 시나리오 모두 20/20회 HTTP 200이며 응답의 `totalElements=170005`를 확인했습니다.
- HTTP p95 최대는 `complex` 34,601.407ms, 다음은 `relation-theme-mechanism` 13,612.511ms였습니다.
- 실제 SQL은 기본 목록 3개(content/count/related), relation 필터 5개(validation 2/content/count/related), complex 5개로 확인됐습니다. 페이지 행마다 relation SQL이 반복되는 N+1은 관찰하지 않았습니다.
- `EXPLAIN (ANALYZE, BUFFERS)`에서는 relation correlated `exists` 경로가 가장 무거웠습니다. relation content는 1,640.857ms, complex content는 802.860ms였고, player/complex count는 각각 842.480ms/620.986ms였습니다.
- 이번 PR에서는 진단 결과와 raw evidence만 추가했습니다. 인덱스·쿼리·pagination 계약 변경은 후속 이슈 범위로 남겼습니다.

## 실제 SQL capture

Hibernate `show_sql`와 `org.hibernate.orm.jdbc.bind`를 켠 뒤 2026-08-18 12:32:55~12:33:06 UTC에 시나리오별 1회 요청을 실행했습니다. 아래 개수는 해당 요청의 실제 statement 로그를 시나리오별로 묶은 값입니다. scheduler가 실행한 `notification_outbox_events` SQL은 게임 목록 요청 SQL에서 제외했습니다.

| scenario | statements | 구성 |
| --- | ---: | --- |
| `base` | 3 | game content, game count, page game IDs의 room count |
| `keyword` | 2 | game content, page game IDs의 room count |
| `player-count` | 3 | game content, game count, page game IDs의 room count |
| `relation-theme-mechanism` | 5 | mechanism/theme validation 2, content, count, room count |
| `complex` | 5 | mechanism/theme validation 2, content, count, room count |
| `flags-upcoming-exact` | 2 | upcoming room discovery, discovered game IDs + exact player content |

반복되는 scalar projection은 다음 `G`로 표시합니다. 이는 로그의 실제 projection을 줄여 적은 것이며, bind 값은 원문 로그와 동일합니다.

```sql
G = g1_0.id,g1_0.alias,g1_0.bgg_id,g1_0.complexity,g1_0.created_at,
    g1_0.description,g1_0.detail_description,g1_0.english_name,
    g1_0.estimated_play_time,g1_0.image_url,g1_0.max_play_time_minutes,
    g1_0.max_players,g1_0.min_age,g1_0.min_play_time_minutes,
    g1_0.min_players,g1_0.name,g1_0.popularity_score,g1_0.release_year,
    g1_0.supported_player_count,g1_0.tag,g1_0.updated_at

O = order by g1_0.popularity_score desc,g1_0.name,g1_0.id
    offset ? rows fetch first ? rows only
```

실제 predicate 형태는 다음과 같습니다.

```sql
-- base
select G from games g1_0 where 1=1 O
select count(g1_0.id) from games g1_0 where 1=1
select r1_0.game_id,count(r1_0.id) from rooms r1_0
 where r1_0.game_id in (24 page ids)
   and r1_0.room_type=? and r1_0.start_at>?
   and r1_0.status not in (?,?) group by r1_0.game_id

-- keyword
select G from games g1_0
 where lower(g1_0.name) like ? escape '\\' O

-- player-count
select G from games g1_0
 where g1_0.min_players<=? and g1_0.max_players>=? O
select count(g1_0.id) from games g1_0
 where g1_0.min_players<=? and g1_0.max_players>=?

-- relation-theme-mechanism
select G from games g1_0
 where exists (
   select 1 from game_mechanism_relations gmr1_0
   join game_mechanisms m1_0 on m1_0.id=gmr1_0.mechanism_id
   where gmr1_0.game_id=g1_0.id and m1_0.code in (?) and m1_0.is_public
 ) and exists (
   select 1 from game_theme_relations gtr1_0
   join game_themes t1_0 on t1_0.id=gtr1_0.theme_id
   where gtr1_0.game_id=g1_0.id and t1_0.code in (?)
 ) O

-- complex
select G from games g1_0
 where g1_0.min_players<=? and g1_0.max_players>=?
   and g1_0.complexity>=? and g1_0.complexity<=?
   and exists (select 1 from game_mechanism_relations gmr1_0
     join game_mechanisms m1_0 on m1_0.id=gmr1_0.mechanism_id
     where gmr1_0.game_id=g1_0.id and m1_0.code in (?) and m1_0.is_public)
   and exists (select 1 from game_theme_relations gtr1_0
     join game_themes t1_0 on t1_0.id=gtr1_0.theme_id
     where gtr1_0.game_id=g1_0.id and t1_0.code in (?))
 O

-- flags-upcoming-exact
select r1_0.game_id,count(r1_0.id) from rooms r1_0
 where r1_0.room_type=? and r1_0.start_at>?
   and r1_0.status not in (?,?) group by r1_0.game_id
select G from games g1_0
 where g1_0.id in (30 discovered game ids)
   and g1_0.min_players=? and g1_0.max_players=? O
```

검증 bind는 `HAND_MANAGEMENT`, `BOOK_BGG_1117`, player `4`, complexity `2.00~4.00`, page `0/24`였고, page room count에는 `GAME_FOCUSED`, 측정 시각, `CANCELED/FINISHED`가 전달됐습니다. page 행별로 room count/content SQL이 반복되는 형태는 없었습니다.

## EXPLAIN (ANALYZE, BUFFERS)

동일 target DB에 실제 capture SQL과 같은 bind 값을 넣고 `track_io_timing=true` 상태에서 읽기 전용 statement를 실행했습니다. `FORMAT TEXT` 결과의 핵심은 다음과 같습니다. HTTP p95와 EXPLAIN 단일 실행 시간은 warm cache, connection, DTO/HTTP 비용이 달라 직접 같은 값으로 비교하지 않습니다.

전체 plan output은 [EXPLAIN 원문](./game-list-740-2026-08-18-explain.txt)으로 보존했습니다.

| SQL | Execution Time | 주요 plan | Buffers / 관찰 |
| --- | ---: | --- | --- |
| `base` content | 2.090ms | `Index Scan ix_games_popularity_score_name_id` | shared read 27; 정렬 순서에 맞는 인덱스가 첫 페이지를 제한 |
| `base` count | 106.694ms | `Parallel Index Only Scan games_pkey` | hit 84,854 / read 933 |
| `base` related | 0.785ms | `Seq Scan rooms` | read 7; fixture 60개 규모 |
| `keyword` content | 0.906ms | `Bitmap Heap Scan` + `ix_games_name_lower_trgm` | hit 16 / read 11; 실제 1행 |
| `player-count` content | 0.297ms | `Index Scan ix_games_popularity_score_name_id` | hit 27 / read 3 |
| `player-count` count | 842.480ms | `Parallel Seq Scan games` | hit 28 / read 43,516 |
| `relation` content | 1,640.857ms | nested-loop semi join + relation indexes | hit 325,816 / read 29,253; mechanism relation 24,419행을 거쳐 theme exists를 반복 |
| `relation` count | 370.251ms | nested-loop semi join | hit 340,036 / read 2,625 |
| `complex` content | 802.860ms | nested-loop semi join + sort | hit 232,618 / read 15,374 |
| `complex` count | 620.986ms | nested-loop semi join | hit 230,458 / read 17,534 |
| `flags` room discovery | 0.343ms | `Seq Scan rooms` | read 7; 30 `GAME_FOCUSED` rows 발견 |
| `flags` content | 0.280ms | `Index Scan games_pkey` + exact player filter | hit 26 / read 6; 30 rows removed by filter |

`relation`/`complex`의 `exists`는 page 24행에 대한 단순 N+1은 아니지만, 전체 relation 후보를 semi join으로 만든 뒤 game row와 theme relation을 반복 탐색합니다. 다음 개선은 이 실행계획을 기준으로 relation filter와 count를 한 범위에서 다루는 최소 이슈로 분리해야 합니다.
