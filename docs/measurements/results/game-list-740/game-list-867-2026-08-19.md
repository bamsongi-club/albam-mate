## 결론

**V1(query shape)만 채택한다.** V1은 여섯 시나리오 모두 V0 p95의 105% 이내이고, relation·complex p95를 모두 엄격히 낮췄다. V2(index 단독)와 V3(결합)는 relation 실행계획은 더 좁혔지만, 사전 승인한 전 시나리오 회귀 gate를 통과하지 못했다. 따라서 final branch에는 V2/V3의 PostgreSQL migration을 넣지 않는다.

이 선택은 "가장 빠르게 보인 한 번의 EXPLAIN"이 아니라, 같은 fixture·runner에서 round 순서를 교차한 순차 HTTP 16배치의 p95 gate 결과다. 전체 p50/p95/max와 판정 근거는 [기계 비교 결과 요약](game-list-770-relation-variant-comparison-2026-08-19.md)과 이 문서에 보존한다. 원본 HTTP/SQL/EXPLAIN capture는 측정 실행자의 로컬 evidence 디렉터리에 보관하며 저장소에는 커밋하지 않는다.

## 비교 방법

V0는 #770 Slice control, V1은 theme·mechanism의 DB 내부 game-ID subquery query shape, V2는 PostgreSQL `ix_game_theme_relations_theme_game (theme_id, game_id)` index, V3는 V1+V2다. V0/V1은 V31 schema fixture, V2/V3은 V33 index fixture를 각각 사용했다.

각 variant는 다음 네 round를 한 번씩 실행했다. 한 batch는 여섯 시나리오별 warm-up 5회 뒤 HTTP 순차 요청 20회다. 16개 모두 fixture fingerprint·runner SHA·HTTP/Slice metadata 검증을 통과한 `VALID` artifact다.

| round | 실행 순서 |
| --- | --- |
| 1 | V0 → V1 → V2 → V3 |
| 2 | V1 → V2 → V3 → V0 |
| 3 | V2 → V3 → V0 → V1 |
| 4 | V3 → V0 → V1 → V2 |

## SQL·EXPLAIN에서 확인한 구조

각 variant·여섯 scenario의 실제 PostgreSQL statement와 가장 느린 읽기 SQL의 `EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)`를 측정 시 확인했다. relation·complex의 content plan도 별도로 확인했으며, SQL/EXPLAIN 원본은 측정 실행자의 로컬 evidence 디렉터리에 보관한다.

| variant | relation·complex plan에서 확인한 구조 |
| --- | --- |
| V0 | `Nested Loop Semi Join`; mechanism 후보 24,419개에 대해 game PK lookup 24,419회, theme relation lookup 24,419회, theme code lookup 78,352회가 남았다. |
| V1 | 애플리케이션 Criteria query는 DB 내부 `game_id IN (subquery)`로 바뀌었지만, 이 fixture의 PostgreSQL physical plan은 V0와 같이 `Nested Loop Semi Join`과 같은 fan-out을 선택했다. |

## Slice·exact count 계약

네 variant의 `base` raw capture는 모두 응답 `data` 키가 정확히 `content`, `page`, `size`, `hasNext`이고, 첫 페이지는 `content` 24건·`page=0`·`size=24`·`hasNext=true`였다. 각 PostgreSQL log의 content SQL은 `fetch first $2 rows only`와 `$2 = '25'`를 기록해 `size + 1` 조회를 보인다. `games`에 대한 exact `select count(...)` statement는 네 capture 모두에서 발견되지 않았다.
