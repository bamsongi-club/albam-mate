## 반복 실행 조건과 batch 해석

- `albam-mate-771` 전용 Compose의 PostgreSQL·Redis·Spring 2개 인스턴스·proxy를 동일 image로 한 번 기동한 뒤 batch 1~3을 순차 실행했습니다. 세 batch 사이에는 서버를 재시작하지 않았습니다.
- DB/OS cache를 비우지 않았으므로 이는 warm-cache 측정입니다. runner는 순차 요청만 보냈고 별도 부하를 의도적으로 추가하지 않았습니다. Compose health check는 `/actuator/health`를 사용하므로 game-list content/count 요청을 만들지 않습니다.
- runner는 시작과 종료에 두 Spring container의 OCI revision label, 동일 image ID, Compose service/network 및 측정 proxy 결속을 대조합니다. discovery와 모든 실측 응답의 역할·`X-Albam-Mate-Upstream-Address`가 inspect한 해당 container와 일치하지 않으면 성공 artifact를 만들지 않습니다.
- 안전성 보강 전 2026-08-18 artifact는 응답·provenance guard 이전 결과라 최신 완료 근거에서 제외합니다. 이번 세 batch의 p95 편차도 한 개의 빠른 결과를 대표값으로 과장하지 않는 이유입니다.
