# ADR-0005: 방 참가 동시성 제어에 낙관 락을 사용

- 상태: 승인됨
- 작성일: 2026-07-23
- 결정일: 2026-07-24
- 관련: [ADR-0002](../platform/0002-postgresql-primary-database.md), [P0 참가·내 모임 명세](../../p0/participation.md), [API 방 참가·재참가 계약](../../API.md#방-참가재참가), [API 오류 계약](../../API.md#5-오류-코드와-검증), [ERD](../../ERD.md#rooms)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

마지막 자리에 여러 참가 요청이 동시에 들어오거나 참가와 취소가 겹치면 정원을 초과하거나 중복 참가가 생길 수 있다. 참가 가능 상태, 남은 정원과 기존 참가 관계를 확인한 뒤 저장하는 동안 다른 트랜잭션이 같은 방을 변경할 수 있기 때문이다.

팀은 낙관 락, 비관 락과 조건부 갱신을 비교했다. 논의 중에는 정책이 복잡하고 정원 초과 방지가 중요하다는 이유로 방 행에 비관 락을 거는 안전 우선안에 한차례 동의했다. 이후 현재 MVP에서는 같은 방에 동시 요청이 자주 발생하지 않을 것이라는 가정을 두고, 충돌을 테스트하며 확인하기 위해 낙관 락으로 시작하는 방향으로 결론을 바꿨다. 이 낮은 충돌 빈도는 아직 측정된 사실이 아니라 팀의 현재 가정이다.

이번 결정의 기준은 다음과 같다.

- 정원 초과와 중복 참가를 애플리케이션과 데이터베이스에서 함께 방지할 것
- 현재 예상되는 낮은 충돌 빈도에서 불필요한 잠금 대기를 만들지 않을 것
- 충돌 시 재시도 횟수와 데이터베이스 비용을 제한할 것
- 부하 테스트나 운영 측정 결과에 따라 잠금 전략을 바꿀 수 있을 것

현재 저장소에는 방·참가 엔티티, 버전 필드, 재시도 트랜잭션과 데이터베이스 제약이 구현돼 있지 않다. 이 ADR은 구현 전에 낙관 락을 적용할 동시성 루트, 버전 증가 대상, 재시도 트랜잭션 경계와 데이터베이스 방어 원칙을 확정한다. 저장 필드와 정확한 무결성 제약은 [ERD](../../ERD.md#rooms), 외부 오류 계약은 [API 명세](../../API.md#5-오류-코드와-검증)를 정본으로 삼는다.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 낙관 락 | 충돌이 없는 대부분의 요청에서 데이터베이스 행 잠금 대기를 만들지 않고 버전 충돌로 동시 변경을 감지할 수 있다. | 충돌할 때 최신 상태를 다시 읽는 새 트랜잭션이 필요하고, 충돌이 잦으면 재시도와 데이터베이스 부하가 커진다. | 선택 |
| 비관 락 | 참가 처리 전에 방 행을 잠가 상태·정원·중복 여부를 한 트랜잭션에서 순서대로 검사할 수 있다. | 같은 방의 요청이 잠금 해제를 기다리며, 현재 예상보다 강한 직렬화 비용을 먼저 부담한다. | 보류 |
| 조건부 갱신 | 정원과 상태 조건을 데이터베이스 갱신 조건에 포함해 한 번의 성공 여부로 경쟁을 제어할 수 있다. | 현재 팀이 선택한 범위에서는 구현과 업무 오류 매핑의 난도가 더 높다고 판단했다. | 보류 |

## 결정

Albam Mate의 현재 MVP에서 방 참가·취소 동시성 제어의 기본 전략으로 낙관 락을 사용한다.

방을 참가 정합성의 동시성 루트로 정의하고 `ROOMS.version`으로 동시 변경을 감지한다. 참가·재참가·참가 취소와 정원 변경처럼 같은 방의 참가 가능성에 영향을 주는 명령은 `ROOMS` 행을 함께 갱신해 하나의 버전에서 충돌하게 한다. `PARTICIPATIONS`에는 MVP 범위에서 별도 낙관 락 버전을 두지 않는다.

한 번의 명령으로 바뀌는 방과 참가 관계는 같은 트랜잭션에서 변경한다. 어떤 값을 저장하고 어떤 제약으로 방어할지는 [ERD](../../ERD.md#필수-제약과-계산-규칙)를 따르며, 이 ADR에서 물리 필드나 제약식을 중복 정의하지 않는다.

낙관 락 충돌이 발생하면 트랜잭션이 없는 재시도 조정자가 별도 실행 서비스를 호출한다. 실행 서비스는 매 시도마다 독립된 새 트랜잭션을 열어 최신 방과 참가 관계를 다시 읽는다. 최초 시도 1회와 재시도 2회를 합쳐 요청 하나당 최대 3개 트랜잭션으로 제한한다. 업무 규칙 위반과 데이터베이스 제약 위반은 낙관 락 재시도 대상에 포함하지 않는다. 새 시도에서 업무 규칙 위반을 확인하면 해당 업무 오류를 우선 반환하고, 세 시도가 모두 방 버전 충돌로 실패한 경우에만 `409 ROOM_CONCURRENT_MODIFICATION`을 반환한다. 외부 오류의 상세 계약은 [API 명세](../../API.md#5-오류-코드와-검증)를 따른다.

낙관 락은 데이터베이스 무결성 제약을 대신하지 않는다. 데이터베이스는 사용자·방 참가 관계의 유일성과 점유 인원 카운터의 범위를 제약하고, 서비스는 실제 `ACTIVE` 참가 관계 수와 카운터의 일치를 하나의 트랜잭션에서 유지한다. PostgreSQL 기반 통합 테스트는 참가·재참가·취소·롤백·동시 요청 뒤 `active_participant_count = ACTIVE 참가 관계 수`인지 검증한다.

## 결과

- 얻는 것: 충돌이 드물다는 현재 가정 아래 평상시 잠금 대기를 피하면서, 같은 방의 참가 가능성에 영향을 주는 명령을 방 버전 하나에서 충돌시킬 수 있다. 데이터베이스는 참가 관계의 유일성과 점유 인원 카운터의 범위를 서비스 검증과 독립적으로 방어한다.
- 감수할 비용·위험: 충돌할 때마다 새 트랜잭션을 열어 최신 상태를 읽어야 하며, 충돌이 잦아지면 최대 3개 트랜잭션과 결과 처리로 데이터베이스 비용이 늘어난다.
- 후속 작업: 방 엔티티의 `version` 매핑, 재시도 조정자와 독립 트랜잭션 실행 서비스를 구현한다. 동시 참가·취소·재참가·정원 변경과 데이터베이스 방어를 PostgreSQL 기반 통합 테스트로 검증한다.

## 보류 및 재검토

- 지금 하지 않는 것: 비관 락을 기본 전략으로 사용, 조건부 갱신을 직접 구현, 정량 근거 없이 잠금 전략을 추가 확장
- 보류 이유: 현재 MVP는 같은 방의 동시 요청이 드물다는 가정을 두고 있으며 먼저 낙관 락의 충돌과 재시도 비용을 측정하기로 했다.
- 다시 검토할 조건: 부하 테스트나 운영에서 충돌과 재시도가 자주 발생하거나, 재시도에 따른 지연·데이터베이스 부하가 수용하기 어렵거나, 낙관 락으로 정원·중복 정합성을 안정적으로 보호하기 어렵다고 확인될 때
