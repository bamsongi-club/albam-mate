# ADR-0013: P0 비밀번호를 Argon2id로 저장하고 인증 요청을 제한

- 상태: 제안됨
- 작성일: 2026-07-24
- 결정일: 미정
- 관련: [ADR-0003](0003-p0-server-session-spring-security.md), [P0 인증·프로필 명세](../../p0/auth-profile.md), [API 인증 요청 남용 제한](../../API.md#인증-요청-남용-제한), [ERD USERS](../../ERD.md#users)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

ADR-0003은 P0 인증에 서버 세션과 Spring Security를 사용하기로 결정했지만, 비밀번호 저장 알고리즘과 공개 회원가입·로그인 요청의 남용 제한은 정하지 않았다. 빠른 해시나 원문 저장은 비밀번호 유출 피해를 키우고, 비용이 큰 비밀번호 해시를 제한 없이 실행하면 무차별 로그인과 반복 가입이 CPU·메모리·사용자 데이터를 소모할 수 있다.

P0는 단일 애플리케이션 인스턴스를 기본으로 하며 MFA, CAPTCHA와 외부 인증 게이트웨이는 범위에 없다. 따라서 현재 구조에서 구현·검증할 수 있는 최소한의 비밀번호 저장과 요청 제한이 필요하다.

이번 결정의 기준은 다음과 같다.

- 비밀번호 원문을 복구할 수 없고 저장값만으로 대량 추측하기 어렵게 할 것
- 로그인 추측과 반복 가입이 고비용 해시를 제한 없이 실행하지 못하게 할 것
- 다른 사용자의 계정을 영구 잠그는 방식은 사용하지 않을 것
- 제한 결과를 클라이언트와 테스트가 동일하게 판정할 수 있을 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| Argon2id와 요청별·전역 제한을 함께 적용 | 메모리 기반 해시로 저장 비밀번호를 보호하면서 공개 인증 요청의 자원 사용량도 제한한다. | 제한 상태와 경계 테스트를 구현해야 한다. | 선택 |
| Argon2id만 적용 | 저장 비밀번호는 보호하지만 공개 요청이 고비용 해시를 제한 없이 실행할 수 있다. | 무차별 로그인과 자원 고갈 위험이 남는다. | 제외 |
| 고정 계정 잠금 | 구현과 설명이 단순하다. | 공격자가 다른 사용자의 계정을 반복해서 잠그는 서비스 거부를 만들 수 있다. | 제외 |
| 외부 WAF·인증 서비스에서만 제한 | 애플리케이션 구현을 줄일 수 있다. | 현재 P0 배포에 확정되지 않은 외부 구성에 보안 경계를 의존한다. | 보류 |

## 결정

비밀번호 저장은 Spring Security의 `DelegatingPasswordEncoder`를 사용하고 신규 해시의 식별자는 `{argon2}`로 둔다. Argon2id의 최소 설정은 메모리 `19 MiB(19,456 KiB)`, 반복 `2회`, 병렬도 `1`, salt `16바이트`, 해시 `32바이트`다. 운영 배포 전에 실제 환경에서 검증 시간을 측정해 약 1초를 목표로 비용을 상향할 수 있지만 이 최소값보다 낮추지 않는다. 원문 비밀번호, `NoOpPasswordEncoder`, SHA-256 같은 빠른 단일 해시는 저장에 사용하지 않는다.

회원가입 비밀번호는 MFA가 없는 P0 기준 15자 이상 128자 이하로 받는다. Unicode와 공백을 허용하며 앞뒤 공백 제거, Unicode 정규화와 자동 잘라내기를 하지 않는다. 입력·오류·로그에는 원문 비밀번호를 다시 싣지 않는다.

회원가입은 신뢰할 수 있는 원격 IP별 10분 이동 창에서 5회, 로그인은 원격 IP별 같은 창에서 30회까지 허용한다. 로그인 실패는 정규화 이메일과 원격 IP 조합별 10분 이동 창에서 5회까지 허용하며 성공 시 해당 조합의 실패 횟수를 초기화한다. 고정 계정 잠금은 사용하지 않는다. 전달 헤더의 IP는 신뢰된 프록시가 설정된 경우에만 사용한다.

애플리케이션 인스턴스 하나에서 동시에 실행하는 Argon2 작업은 최대 4개다. 요청 제한을 초과했거나 실행 슬롯이 없으면 해시와 사용자 생성을 시작하지 않고 `429 RATE_LIMIT_EXCEEDED`와 초 단위 `Retry-After`를 반환한다. 정확한 적용 순서와 응답 계약은 API 명세를 따른다.

P0 단일 인스턴스에서는 제한 상태를 애플리케이션 메모리에 둘 수 있다. 다중 인스턴스로 확장하기 전에는 모든 인스턴스가 공유하는 제한 저장소나 게이트웨이를 별도로 결정해야 한다.

## 결과

- 얻는 것: 비밀번호 저장값과 공개 인증 엔드포인트의 계산·저장 자원을 함께 보호하며, 제한 경계를 API와 테스트에서 재현할 수 있다.
- 감수할 비용·위험: 인메모리 제한 상태는 프로세스 재시작 때 초기화되고 단일 인스턴스 밖에서는 전역 한도를 보장하지 않는다. 공유 IP 환경에서는 정상 사용자가 일시적으로 제한될 수 있다.
- 후속 작업: Spring Security와 Argon2 구현 의존성, 요청 제한기와 동시 작업 제한을 추가하고 경계값·만료·초기화·`Retry-After`를 테스트한다.

## 보류 및 재검토

- 지금 하지 않는 것: MFA, CAPTCHA, 영구 계정 잠금, 다중 인스턴스 공유 제한 저장소, 외부 WAF만을 신뢰하는 제한
- 보류 이유: P0는 단일 인스턴스의 이메일·비밀번호 로그인 범위이며, 현재 계약은 이 구조에서 자동화 공격과 자원 고갈을 줄이는 최소 경계다.
- 다시 검토할 조건: 다중 인스턴스로 확장할 때, 공격·오탐 지표가 누적될 때, 외부 인증 서비스나 MFA를 도입할 때, 해시 비용 또는 인스턴스 메모리 예산이 바뀔 때

- 상태: 미검증
- 근거: 현재 애플리케이션에는 Spring Security·Argon2 구현 의존성, 인증 요청 제한기와 관련 테스트가 없다. 후속 구현 PR에서 PostgreSQL 사용자 저장, 해시 검증과 요청 제한 경계 테스트를 연결한 뒤 검증 상태를 갱신한다.
