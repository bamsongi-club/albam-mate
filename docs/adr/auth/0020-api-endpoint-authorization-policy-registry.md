# ADR-0020: API 엔드포인트 인가 정책을 등록하고 미분류 경로를 CI에서 거절

- 상태: 승인됨
- 작성일: 2026-07-28
- 결정일: 2026-07-28
- 관련: [ADR-0003](0003-p0-server-session-spring-security.md), [FND-04 인증 기반 구성](../../p0/foundation.md#fnd-04-인증-기반-구성), [API 인증·세션·CSRF 계약](../../API.md#12-인증세션csrf), [API 오류 계약](../../API.md#9-오류-코드)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

Albam Mate는 Spring Security에서 API를 공개 API와 보호 API로 나눈다. 요청 경로에 대응하는 핸들러가 없으면 `404 RESOURCE_NOT_FOUND`를 반환한다. 경로는 있지만 그 HTTP 메서드를 지원하지 않으면 `405 METHOD_NOT_ALLOWED`를 반환한다.

Spring Security의 인증 필터는 Spring MVC(요청을 실제 컨트롤러 코드로 연결하는 계층)가 핸들러를 고르기보다 먼저 실행된다. 그래서 등록되지 않은 모든 요청을 곧바로 인증 대상으로 삼으면, 비로그인 요청이 MVC까지 도달하지 못하고 원래 받아야 할 `404`·`405` 대신 `401 UNAUTHENTICATED`를 받을 수 있다.

현재 `SecurityConfig`는 이 문제를 다음 순서로 피한다. 먼저 지원하는 HTTP 메서드의 공개·보호 규칙을 적용한다. 그다음 알려진 P0 경로의 다른 메서드와 아직 매핑되지 않은 요청은 통과시켜 MVC가 `404`·`405`를 판정하게 한다. 공개 경로의 미래 하위 경로는 별도의 matcher(요청 경로·메서드 패턴에 규칙을 매칭하는 Spring Security 설정 단위)로 인증을 요구한다. 이 구성은 현재 API 오류 계약을 지키지만, 같은 정보(어떤 경로가 어떤 인증을 요구하는지)가 컨트롤러 매핑과 인증·CSRF(Cross-Site Request Forgery, 상태 변경 요청 위조를 막는 토큰 검증) matcher라는 서로 다른 코드에 중복해서 존재한다.

새 API를 추가할 때 이 matcher를 함께 갱신하지 않으면, 실제로는 동작하는 핸들러가 정책상 미분류 상태로 MVC에 도달할 수 있다. 특히 상태를 변경하는 API가 이 상태로 배포되면 인증이나 CSRF 보호가 빠질 수 있다. 코드 리뷰만으로 여러 matcher와 모든 컨트롤러 매핑이 계속 일치하는지 보장하기는 어렵다. 그래서 현재의 `404`·`405` 계약은 유지하면서, 미분류 엔드포인트를 자동으로 찾아내는 단일 정책과 CI 게이트가 필요하다.

이번 결정의 기준은 다음과 같다.

- 공개, 선택 인증, 인증 필수 API를 HTTP 메서드와 경로 단위로 명시할 것
- 상태 변경 API의 CSRF 요구 여부를 인증 정책과 함께 확인할 수 있을 것
- 미매핑 경로와 지원하지 않는 메서드의 `404`·`405` 계약을 유지할 것
- 새 MVC 엔드포인트가 정책에 등록되지 않으면 배포 전에 자동 검증으로 차단할 것
- 인증·인가의 실행 책임은 ADR-0003에 따라 Spring Security에 유지할 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 컨트롤러와 `SecurityConfig` matcher를 계속 수동으로 함께 관리 | 현재 구현과 오류 계약을 바꾸지 않고 추가 구조가 필요 없다. | 새 엔드포인트를 추가할 때 인증·CSRF matcher 일부를 빠뜨려도 컴파일과 애플리케이션 시작이 성공하며, 리뷰에만 의존한다. | 제외 |
| 공개 경로만 허용하고 나머지 요청은 런타임에서 `authenticated()` 또는 `denyAll()` 처리 | 등록 누락이 발생해도 새 API가 기본적으로 공개되지 않는다. | 미매핑 경로와 지원하지 않는 메서드가 MVC에 도달하기 전에 `401`·`403`으로 끝날 수 있어 현재 `404`·`405` 계약을 변경해야 한다. | 보류 |
| API 엔드포인트 정책 등록부를 두고 MVC 매핑과의 일치를 자동 검증 | 현재 오류 계약을 유지하면서 공개·선택 인증·보호 및 CSRF 정책을 한 곳에서 확인하고, 미분류 엔드포인트를 CI에서 차단할 수 있다. | 엔드포인트 추가 시 정책 등록이 필요하고, MVC 매핑 탐색과 정책 비교 테스트를 유지해야 한다. CI를 거치지 않은 실행만으로는 등록 누락을 차단하지 못한다. | 선택 |

## 결정

모든 애플리케이션 `/api/**` 엔드포인트는 HTTP 메서드, 경로 패턴, 인증 모드와 CSRF 요구 여부를 API 엔드포인트 정책 등록부에 등록한다. 인증 모드는 `PUBLIC`, `OPTIONAL_AUTHENTICATION`, `AUTHENTICATED`를 구분한다. 상태 변경 엔드포인트는 CSRF 필요 여부를 별도 속성으로 명시한다.

`SecurityConfig`의 공개·보호·CSRF matcher는 이 등록부를 공통 입력으로 사용한다. 같은 메서드와 경로에 서로 다른 정책을 중복 등록하거나, 공개 경로가 의도하지 않은 하위 경로까지 포괄하는 와일드카드를 사용하지 않는다.

구조 테스트는 Spring MVC의 `RequestMappingHandlerMapping`에서 애플리케이션이 소유한 `/api/**` 핸들러를 수집해 정책 등록부와 비교한다. 다음 조건 중 하나라도 발생하면 테스트와 CI를 실패시킨다.

- MVC에는 존재하지만 정책 등록부에는 없는 엔드포인트
- 정책 등록부에는 존재하지만 MVC에는 없는 엔드포인트
- 같은 메서드·경로에 중복되거나 충돌하는 인증 또는 CSRF 정책
- 인증이 필요한 상태 변경 API인데 CSRF가 비활성화된 정책

정책에 등록된 지원 메서드에는 등록된 인증·CSRF 규칙을 적용한다. 알려진 경로의 지원하지 않는 메서드와 미매핑 요청은 MVC에 위임해 기존 `404 RESOURCE_NOT_FOUND`와 `405 METHOD_NOT_ALLOWED` 계약을 유지한다. 구현 PR은 신규 엔드포인트가 등록되지 않았을 때 구조 테스트가 실패하는 통제 테스트를 포함해야 한다.

## 결과

- 얻는 것: API 인증·CSRF 정책을 한 목록에 모으고 자동으로 검증한다. 그 덕분에 새 엔드포인트의 보안 등록 누락을 배포 전에 발견하면서도, 기존 `404`·`405` 계약은 그대로 유지한다.
- 감수할 비용·위험: 컨트롤러 변경마다 정책 등록부를 함께 갱신해야 하며, MVC 매핑 표현과 경로 패턴 비교 규칙을 Spring Framework 변경에 맞춰 유지해야 한다. CI를 우회한 로컬 실행에서는 미분류 엔드포인트가 런타임에 기본 차단되지 않는다.
- 후속 작업: 정책 등록부와 구조 테스트를 추가하고, `SecurityConfig`의 공개·보호·CSRF matcher가 등록부를 사용하도록 리팩터링한다. 기존 P0 엔드포인트를 모두 등록한 뒤 공개·선택 인증·보호, CSRF, 미매핑 `404`, 미지원 메서드 `405` 회귀 테스트를 실행한다.

## 보류 및 재검토

- 지금 하지 않는 것: 미매핑 `/api/**` 요청을 런타임에서 일괄 인증 또는 거부하는 정책, Spring MVC 인터셉터를 이용한 별도 인증·인가 계층
- 보류 이유: 전자는 현재 `404`·`405` 오류 계약을 바꾸고, 후자는 ADR-0003이 Spring Security에 모은 인증·인가 경계를 두 계층으로 나눈다.
- 다시 검토할 조건: CI를 거치지 않는 배포 경로가 생길 때, 동적 런타임 핸들러처럼 빌드 시점에 수집할 수 없는 API를 도입할 때, 미매핑 요청의 오류 계약보다 런타임 기본 거부를 우선하기로 API 계약을 변경할 때
