# ADR-0034: 최종 상태 채팅 메시지를 30일 보관한 뒤 일괄 삭제

- 상태: 제안됨
- 작성일: 2026-07-31
- 결정일: 미정
- 관련: [P1 방 채팅 명세](../../p1/chatting.md), [ERD](../../ERD.md) — 구현 전 채팅 저장 계약 추가 필요, [아키텍처](../../ARCHITECTURE.md) — 구현 전 채팅 흐름 추가 필요, [ADR-0009 UTC 시간 기준](../platform/0009-utc-time-standard.md), [ADR-0021 AWS 배포 기준선](../platform/0021-p0-aws-ec2-rds-deployment-baseline.md)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

방이 CANCELED 또는 FINISHED가 되면 일반 사용자는 채팅에 다시 접근하지 않는다. 접근할 수 없는 메시지를 영구 보관하면 PostgreSQL 저장 공간과 개인정보 보유 범위만 계속 늘어난다. 반대로 최종 상태 전환과 동시에 삭제하면 장애 확인에 필요한 짧은 유예 기간도 없다.

P1에는 채팅 메시지 신고·운영자 숨김 기능이 없다. 따라서 신고 증거를 위한 별도 예외 보관은 이번 결정에 포함하지 않는다. 운영 데이터베이스는 ADR-0021에 따라 자동 백업을 7일 보관하므로 live DB 삭제와 백업 만료 시점도 구분해야 한다.

판단 기준은 다음과 같다.

- 사용자가 접근할 수 없는 메시지의 장기 보관을 피할 것
- 방 상태 변경 트랜잭션에 대량 삭제를 결합하지 않을 것
- 작은 PostgreSQL에서 장시간 잠금과 한 번의 대규모 실패를 피할 것
- 실패를 관찰하고 다음 실행에서 안전하게 재시도할 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 최종 상태 전환 즉시 물리 삭제 | 저장 공간과 개인정보 보유를 즉시 줄인다. | 방 상태 변경 트랜잭션이 대량 삭제와 결합되고 장애 확인 유예가 없다. | 제외 |
| 최종 상태 전환 뒤 30일 보관 후 물리 삭제 | 짧은 운영 확인 기간을 두면서 보관 비용을 제한한다. | 만료 삭제 스케줄러와 실패 관측이 필요하다. | 선택 |
| 논리 삭제 또는 영구 보관 | 복구·감사 가능성이 가장 크다. | 본문과 개인정보가 계속 남고 저장 비용이 누적된다. | 제외 |

## 결정

RECRUITING·CLOSED 방의 메시지는 삭제하지 않는다. 방이 CANCELED 또는 FINISHED로 전환되면 일반 사용자 접근을 즉시 차단하고, 그 전환 시각부터 30일 동안 메시지를 보관한다.

- 최종 상태 전환은 room.contract.RoomTerminalStateReached를 발행하고 chat의 동기 listener가 같은 트랜잭션에서 CHAT_ROOMS.purge_after를 전환 시각에서 30일 뒤로 설정한다.
- 하루 한 번 Spring 내장 스케줄러가 purge_after가 지난 채팅방을 조회한다.
- 만료된 CHAT_MESSAGES를 설정 가능한 소량 묶음으로 물리 삭제한다.
- 만료 시각과 스케줄 실행 간격 때문에 실제 live DB 삭제는 30일 경과 후 최대 24시간 늦을 수 있다.
- 각 묶음은 독립 트랜잭션이다. 성공한 묶음은 유지하고 실패한 묶음만 롤백한다.
- 실패한 묶음은 무한 즉시 재시도하지 않고 다음 스케줄에서 다시 처리한다.
- 성공·삭제 건수·지연·실패를 메트릭과 로그에 남기고 스케줄 실패 알림을 발생시킨다. 메시지 본문은 기록하지 않는다.
- 삭제가 끝난 채팅방은 CHAT_ROOMS.messages_purged_at을 기록해 반복 전체 스캔을 피한다.

완전 삭제는 운영 live DB의 CHAT_MESSAGES 행 삭제를 뜻한다. 이미 생성된 RDS 자동 백업에서는 개별 행을 선택 삭제하지 않으며, 해당 백업은 ADR-0021의 7일 보존주기가 끝나면 만료된다.

## 결과

- 얻는 것: 최종 상태 메시지의 보관 상한을 정하고 live DB 저장량과 개인정보 보유 범위를 줄인다. 방 상태 전환은 대량 삭제와 분리된다.
- 감수할 비용·위험: 최종 상태 전환 뒤 30일 동안, 그리고 삭제 전 생성된 백업의 보존주기 동안 데이터가 남는다. 삭제는 만료 뒤 최대 24시간 늦을 수 있다.
- 후속 작업: purge_after·messages_purged_at 마이그레이션, 만료 조회 인덱스, 배치 삭제와 실패 메트릭·알림을 구현한다.

## 보류 및 재검토

- 지금 하지 않는 것: 신고 메시지 예외 보관, 사용자별 삭제, 메시지 수정·작성자 삭제, 법적 보존 요청
- 보류 이유: P1에 신고·분쟁 처리 기능이 없고 모든 채팅 메시지에 동일한 단순 정책을 적용한다.
- 다시 검토할 조건: 신고·운영자 조치 기능을 도입하거나 법적·계약상 보존 기간이 정해지거나, 30일 정책 때문에 실제 운영 확인이 불가능해질 때
