# ADR-0079: 방별 읽음 커서를 저장하고 미읽음 개수는 조회 시점에 파생 계산

- 상태: 승인됨
- 작성일: 2026-08-19
- 결정일: 2026-08-19
- 관련: [CHAT-07 문서 이슈 #810](https://github.com/bamsongi-club/albam-mate/issues/810), [CHAT-07 명세](../../p2/chat.md#chat-07-채팅-목록-마지막-메시지방별-미읽음-상태), [API 명세](../../API.md#chat-07-채팅-목록-마지막-메시지방별-미읽음-상태-계약), [ERD](../../ERD.md#chat-07-읽음-커서-저장-계약), [아키텍처](../../ARCHITECTURE.md#p2-chat-07-채팅-목록-미읽음-집계-흐름), [ADR-0031](0031-chat-history-cursor-pagination.md), [ADR-0033](0033-postgresql-source-after-commit-delivery.md), [ADR-0078](0078-chat-system-message-storage-and-read-time-composition.md)

## 맥락

채팅 목록은 방별 마지막 메시지와 미읽음 상태를 보여주지 못한다. 방에 들어가기 전에는 새 메시지가 있는지, 몇 건인지 알 방법이 없다. 이 계약을 만들려면 "사용자가 어디까지 읽었는지"를 저장할 구조와 "지금 몇 건이 안 읽었는지"를 계산할 방식을 정해야 한다.

기존 유사 구현은 웹 알림(`Notification`)의 `read_at` 컬럼뿐이다. 알림은 수신자 단위 사실이라 알림 행 하나에 `read_at` 하나면 충분하지만, 채팅은 방의 연속된 시간축에서 "어디까지 봤는지"를 표현해야 하므로 메시지마다 읽음 여부를 저장하는 모델이 맞지 않는다. 또한 [ADR-0031](0031-chat-history-cursor-pagination.md)이 이미 메시지 `id`를 방별 단일 순서·커서로 확정했고, [ADR-0033](0033-postgresql-source-after-commit-delivery.md)은 PostgreSQL을 정본으로 두고 실시간 신호는 at-most-once로만 취급한다. 미읽음 집계가 이 두 결정과 다른 정합성 기준을 쓰면 실시간 중복·순서 역전·재연결 뒤에 방마다 다른 숫자가 보일 위험이 있다.

판단 기준은 다음 셋이다.

1. 기존 메시지 `id` 순서·커서 계약을 새로 만들지 않고 그대로 재사용하는가.
2. WebSocket 중복 전달·순서 역전·재연결 catch-up이 반복돼도 집계가 항상 같은 값으로 수렴하는가(멱등성).
3. 방 개수만큼 반복 질의하지 않고 채팅 목록 한 번의 조회로 마지막 메시지·미읽음 수를 배치로 얻을 수 있는가.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 방별 미읽음 개수를 정수 컬럼(counter)에 저장하고 메시지 수신·읽음마다 증감 | 조회가 단순 컬럼 읽기라 빠르다 | WebSocket 중복 전달·재연결 catch-up이 같은 메시지를 두 번 세면 counter가 과다 증가한다. 증가와 감소를 서로 다른 트랜잭션·다른 요청 경로에서 갱신해야 해 동시성 버그(경합 시 증분 유실·과다 증가)에 취약하다. `CHAT-07-AC6`(WS 중복·재연결에도 중복 반영 없음)을 만족하려면 별도 멱등 키·dedup 저장이 또 필요하다 | 제외 |
| 사용자·방별 알림처럼 메시지 행마다 읽음 로그를 남기는 read log 테이블 | 어떤 메시지를 읽었는지 개별 추적 가능 | 메시지 1건당 참가자 수만큼 행이 늘어나 쓰기·저장량이 참가자 수에 비례해 커진다. 채팅 목록은 "어디까지 읽었는지 지점"만 필요하므로 메시지별 로그는 필요 이상의 세밀도다 | 제외 |
| 사용자×방 단위 `last_read_message_id` 커서 하나만 저장하고, 미읽음 개수는 조회 시점에 `COUNT(*) WHERE id > cursor`로 파생 계산 | 저장은 참가자당 방 하나의 행이면 충분하다. 집계가 현재 메시지 `id` 상태에서 매번 다시 계산되므로 WebSocket이 몇 번을 중복·역순으로 전달해도 최종 질의 결과는 항상 같다(멱등). 커서 갱신도 `GREATEST(기존값, 새값)`로 후퇴를 막으면 재시도에 안전하다 | 방마다 `COUNT` 질의가 필요해 컬럼 읽기보다 비용이 크다. 채팅 목록의 여러 방을 한 번에 계산하려면 배치 질의를 설계해야 한다 | 선택 |

## 결정

1. 새 테이블 `CHAT_ROOM_READ_STATES`에 사용자×채팅방 하나당 `last_read_message_id` 커서 한 값만 저장한다. 메시지별 읽음 로그나 방별 미읽음 개수 counter 컬럼은 만들지 않는다. 물리 컬럼·제약의 정본은 [ERD](../../ERD.md#chat-07-읽음-커서-저장-계약)다.
2. 미읽음 개수는 저장된 값이 아니라 조회 시점에 `chat_room_id`·`last_read_message_id`를 기준으로 `id > cursor`인 메시지를 세어 계산한다. 저장이 아니라 계산이므로 WebSocket 전달이 몇 번을 중복·역순으로 일어나도 최종 조회 결과는 항상 같은 값으로 수렴한다.
3. 본인이 보낸 `USER` 메시지와 본인이 대상인 `CHAT-06` `SYSTEM` 메시지는 파생 계산에서 제외한다. 그 외 `SYSTEM` 메시지는 마지막 메시지 미리보기·미읽음 집계에 포함한다. `CHAT-06`의 저장·응답 계약은 바꾸지 않는다.
4. 커서 갱신은 `last_read_message_id = GREATEST(last_read_message_id, :upToMessageId)`로만 전진시킨다. 같은 요청의 재시도나 이미 지나간 지점으로의 갱신 요청은 값을 후퇴시키지 않고 그대로 성공 응답한다.
5. 채팅 목록의 마지막 메시지·미읽음 수는 방 개수만큼 반복 질의하지 않고 배치 조회로 계산한다. 구체 SQL은 구현이 정하되, 요청한 채팅방 집합 전체를 상수 회수의 질의로 처리해야 한다.
6. 상단 채팅 아이콘의 미읽음 표시는 "미읽음 메시지가 1건 이상인 방의 개수"를 센다. 방별 미읽음 총합을 그대로 더하지 않는다.
7. 이 기능은 새 전역 실시간 채널을 만들지 않는다. 방 목록·상단 배지는 조회 시점 기준 최신값을 반환하며, 화면이 열려 있는 동안의 서버 push는 이 결정의 범위가 아니다. 기존 방별 WebSocket은 해당 방에 접속해 있는 동안의 이력·재연결에만 쓰인다.
8. `CHAT_ROOM_READ_STATES`는 새로 추가하는 테이블이라 기존 행이 없다. `CHAT-06`처럼 기존 컬럼의 NOT NULL을 완화하거나 구버전 writer와 충돌할 여지가 없으므로, schema 추가와 코드 배포를 인스턴스 순차 전환 없이 한 배포로 묶는다.

## 결과

- 얻는 것:
    - 저장 구조가 참가자×방 하나의 얇은 행이라 쓰기·저장 비용이 작고, 메시지 폭주에도 커서 갱신 자체는 한 행의 UPSERT로 끝난다.
    - 미읽음 집계가 항상 현재 메시지 `id` 상태에서 다시 계산되므로 WebSocket 중복·순서 역전·재연결 catch-up과 무관하게 정답으로 수렴한다. 별도 dedup 키나 이벤트 순번 추적이 필요 없다.
    - 커서가 `GREATEST`로만 전진하므로 읽음 처리 API의 재시도·중복 호출이 안전하다.
- 감수할 비용·위험:
    - 방마다 `COUNT` 파생 질의가 필요해 단순 컬럼 읽기보다 조회 비용이 크다. 채팅 목록처럼 여러 방을 한 번에 보여줘야 하는 화면은 배치 질의 설계가 구현에서 필요하다.
    - 채팅 목록·상단 배지는 조회 시점 값이며 실시간 push가 없으므로, 화면이 열려 있는 동안 새 메시지가 와도 사용자가 재조회하기 전까지는 갱신되지 않는다.
    - 방 목록 조회가 `room` 모듈에서 `chat` 모듈의 미읽음·마지막 메시지 조회 계약을 호출해야 한다. 기존에는 `chat`이 `room.contract`를 참조하는 방향만 있었고([ADR-0078](0078-chat-system-message-storage-and-read-time-composition.md)의 리스너), 이 결정으로 `room → chat.contract` 조회 방향이 새로 생겨 두 모듈이 서로 다른 목적의 계약으로 양방향 의존을 갖는다. 순환 컴파일 의존은 아니지만(각 방향이 별도 `contract` 인터페이스), 아키텍처 검토 시 이 양방향성을 인지해야 한다.
- 후속 작업:
    - 전진 migration, `chat`·`room` 구현, 채팅 목록·읽음 처리 HTTP 경계, 배치 조회 쿼리와 PostgreSQL 통합 검증은 [CHAT-07 명세](../../p2/chat.md#chat-07-채팅-목록-마지막-메시지방별-미읽음-상태)의 완료 기준을 따르는 후속 구현 이슈가 소유한다.

## 보류 및 재검토

- 지금 하지 않는 것: 채팅 목록·상단 배지의 실시간 push(새 전역 WebSocket 채널이나 사용자 단위 구독). 방별 미읽음 개수를 증분 갱신하는 counter 컬럼도 지금 만들지 않는다.
- 보류 이유: 기존 채팅 WebSocket은 방 단위 접속에만 쓰이고, 목록 화면을 위한 사용자 단위 실시간 채널은 새 인프라다. 파생 계산 방식이 이미 WebSocket 중복·재연결 문제를 구조적으로 피하므로, 실시간 push 없이도 제품 완료 기준(`CHAT-07-AC1`~`AC9`)을 만족한다.
- 다시 검토할 조건: 조회 시점 갱신만으로 사용자가 새 메시지 도착을 인지하는 지연이 제품 목표를 벗어나거나, 배치 `COUNT` 질의의 운영 비용이 방·메시지 규모에서 감당하기 어려워질 때.
