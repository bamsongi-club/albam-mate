# ADR-0078: 입장·퇴장 시스템 메시지를 CHAT_MESSAGES 확장에 저장하고 문구는 읽기 시점에 조립

- 상태: 승인됨
- 작성일: 2026-08-19
- 결정일: 2026-08-19
- 관련: [CHAT-06 문서 이슈 #752](https://github.com/bamsongi-club/albam-mate/issues/752), [CHAT-06 명세](../../p2/chat.md#chat-06-입장퇴장-시스템-메시지), [API 명세](../../API.md#채팅-공통-계약), [ERD](../../ERD.md#chat-06-입장퇴장-시스템-메시지-저장-계약), [아키텍처](../../ARCHITECTURE.md#p2-chat-06-입장퇴장-시스템-메시지-흐름-계획미구현), [ADR-0031](0031-chat-history-cursor-pagination.md), [ADR-0032](0032-http-send-websocket-receive.md), [ADR-0033](0033-postgresql-source-after-commit-delivery.md), [ADR-0049](0049-chat-message-retention-lock-section-boundary.md)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

ROOM 채팅방에는 누가 들어오고 나갔는지 알리는 안내가 없다. 참가·참가 취소는 `room`의 쓰기 트랜잭션에서 확정되지만 `chat`에는 그 사실을 남길 저장·응답·실시간 전달 계약이 아직 없다. 이는 프런트 표시 회귀가 아니라 미구현 기능이므로 P2에서 `CHAT-06`으로 계약을 정한다.

기존 ROOM 채팅에는 이미 확정된 계약이 있다. 이력은 메시지 ID 커서로 조회하고([ADR-0031](0031-chat-history-cursor-pagination.md)), 저장은 HTTP·PostgreSQL이 정본이며 커밋 뒤 실시간으로 fan-out하고([ADR-0032](0032-http-send-websocket-receive.md), [ADR-0033](0033-postgresql-source-after-commit-delivery.md)), 최종 상태 방의 메시지는 30일 뒤 일괄 삭제한다([ADR-0049](0049-chat-message-retention-lock-section-boundary.md)). 시스템 메시지도 같은 화면의 같은 시간축에 섞여 보이므로 이 네 계약과 어긋나면 순서·커서·보존이 갈라진다.

판단 기준은 다음 넷이다.

1. 사용자 메시지와 시스템 메시지가 하나의 순서·커서·재연결 기준을 공유하는가.
2. 기존 보존·물리 삭제와 접근 판정 경계를 새로 만들지 않고 그대로 쓰는가.
3. 닉네임이 바뀌거나 표시 규칙이 바뀌어도 저장된 이력을 다시 쓰지 않아도 되는가.
4. 저장하는 개인정보와 프런트엔드가 알아야 하는 규칙을 늘리지 않는가.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 별도 `CHAT_SYSTEM_MESSAGES` 테이블에 저장하고 조회에서 병합 | 기존 `CHAT_MESSAGES` 제약을 건드리지 않는다. | 두 테이블의 ID가 하나의 순서를 만들지 못해 `beforeMessageId` 커서·`afterMessageId` catch-up·중복 제거 기준을 새로 정의해야 하고, 보존·삭제·접근 판정도 두 벌이 된다. | 제외 |
| 기존 알림(`NOTI`) Outbox를 재사용해 채팅 화면에서 함께 표시 | 새 저장 구조가 없다. | 알림은 주최자·승격자 등 수신자 단위 사실이고 채팅 이력은 방 단위 시간축이다. 수신자 모델·읽음 상태·보존 기간이 달라 채팅 커서와 합칠 수 없다. | 제외 |
| `CHAT_MESSAGES`를 확장하고 저장 시점에 완성 문장을 `content`에 함께 기록 | 조회 경로가 사용자 메시지와 완전히 같다. | 닉네임 변경·문구 수정이 과거 이력과 어긋나고, 문구를 고치려면 저장된 행을 다시 쓰거나 두 세대의 문장을 함께 유지해야 한다. 표시용 닉네임 사본을 메시지 행마다 늘린다. | 제외 |

## 결정

1. 입장·퇴장 시스템 메시지는 기존 `CHAT_MESSAGES`에 저장한다. 별도 테이블·별도 커서·별도 보존 경계를 만들지 않는다. 물리 컬럼·제약·인덱스의 정본은 [ERD](../../ERD.md#chat-06-입장퇴장-시스템-메시지-저장-계약)다.
2. 메시지 행은 종류(`message_type`), 사건 키(`system_event_key`)와 안내 대상 사용자(`subject_user_id`)만 저장한다. 완성된 안내 문장은 저장하지 않는다.
3. 안내 문구는 서버가 읽기 시점에 사건 키와 대상 사용자의 현재 공개 닉네임으로 조립해 기존 `content` 필드로 내려준다. 문구 문자열의 정본은 [API 명세](../../API.md#채팅-공통-계약)이며 프런트엔드는 문구를 조립하지 않는다.
4. 시스템 메시지는 사용자 메시지와 같은 `id` 순서를 사용한다. `beforeMessageId` 이력 커서, `afterMessageId` 재연결 catch-up, 30일 보존과 만료 물리 삭제, 방 상태·관계 기반 접근 판정을 그대로 적용한다.
5. 시스템 메시지를 남기는 사건은 참가 확정과 참가 취소 확정뿐이다. 대기열 자동 승격, 방 취소, 방 종료는 이번 결정의 대상이 아니다.
6. 시스템 메시지는 원인이 되는 `room`의 참가·참가 취소 업무 트랜잭션 안에서 저장한다. 참가 상태 전이가 커밋되면 안내도 함께 커밋되고, 안내 저장이 실패하면 참가 상태 전이도 함께 롤백한다. 모듈 간 호출 방향과 잠금 순서의 정본은 [아키텍처](../../ARCHITECTURE.md#p2-chat-06-입장퇴장-시스템-메시지-흐름-계획미구현)다.
7. 이 결정은 P1 ROOM 채팅에만 적용한다. MATCH 전용 `MATCH_CHAT_MESSAGES`와는 행·제약·멱등성 키를 공유하지 않으며, [ADR-0064](../matching/0064-match-chat-url-text-storage.md)가 정한 MATCH SYSTEM lifecycle 알림 계약도 바꾸지 않는다.
8. 이 계약이 적용되기 전에 만들어진 채팅방에는 시스템 메시지를 소급 생성하지 않는다.
9. schema 확장과 `SYSTEM` 쓰기 활성화를 한 배포로 묶지 않는다. 컬럼 추가·NOT NULL 완화·CHECK 추가, `SYSTEM` 행을 읽을 수 있는 신버전 전 인스턴스 배포, `SYSTEM` 쓰기 활성화를 이 순서로 분리하고 각 단계는 앞 단계 반영을 확인한 뒤 진행한다. `message_type`은 DEFAULT `'USER'`로 추가해 구버전 writer의 INSERT를 깨지 않는다. 쓰기 활성화는 인스턴스별 설정이 아니라 원인 참가 트랜잭션에서 읽는 PostgreSQL 전역 gate 행이며 기본값은 비활성이다. 순차 배포로 신·구 버전이 섞인 구간에도 한 사건의 안내 저장 여부가 라우팅된 인스턴스에 따라 갈리지 않게 하려는 것이고, `AC1`은 그 전역 활성화 시각 이후의 사건에만 적용한다. 단계·조건·rollback 순서의 정본은 [ERD](../../ERD.md#chat-06-혼합-버전-배포활성화rollback-순서)다.

## 결과

- 얻는 것:
    - 사용자 메시지와 시스템 메시지가 하나의 시간축·커서·재연결 기준을 공유해 클라이언트가 순서 규칙을 하나만 다룬다.
    - 30일 보존, 만료 물리 삭제, `RECRUITING`·`CLOSED` 접근 판정이 그대로 적용돼 새 보존·권한 경계를 만들지 않는다.
    - 닉네임이 바뀌거나 문구를 고쳐도 저장된 이력을 다시 쓰지 않는다.
    - 메시지 행에 표시용 닉네임 사본을 남기지 않아 저장하는 개인정보가 사용자 ID 참조 하나로 유지된다.
- 감수할 비용·위험:
    - `sender_user_id`·`client_message_id`·`content`의 NOT NULL을 푸는 전진 migration과 종류별 CHECK 제약이 필요하다. 이 migration과 `SYSTEM` reader·비활성 writer는 같은 변경에서 병합할 수 있고, 뒤로 미루는 것은 전역 쓰기 활성화뿐이다.
    - 과거 이력의 문구도 항상 현재 닉네임으로 보인다. 사건 당시의 닉네임을 보여주는 화면은 제공하지 않는다.
    - 이력 한 페이지마다 대상 사용자 공개 프로필을 함께 조회해야 하므로 조회 비용이 늘어난다. 같은 페이지의 중복 사용자 ID는 한 번만 조회한다.
    - 배포 전 채팅방에는 참가자가 있어도 입장 안내가 남지 않아 이력이 사용자마다 비어 보인다.
    - 기능을 켜기까지 schema·reader·writer 세 단계를 나눠 배포해야 하고, 그 사이 전역 활성화 gate 행을 운영 대상으로 관리해야 한다. 참가·참가 취소 트랜잭션마다 이 행을 함께 읽는 비용이 생긴다.
    - `SYSTEM` 행이 한 건이라도 생기면 NOT NULL 복구로 schema를 되돌릴 수 없고, 구버전 애플리케이션으로 되돌리는 것도 그 행의 격리·정리를 먼저 정해야 가능하다.
- 후속 작업:
    - 전진 migration, `room`·`chat` 구현, 이력·실시간 응답 확장과 PostgreSQL 통합 검증은 [CHAT-06 명세](../../p2/chat.md#chat-06-입장퇴장-시스템-메시지)의 완료 기준을 따르는 후속 구현 이슈가 소유한다.

## 적용·호환·rollback

- 적용: 이 변경에서는 ADR과 [CHAT-06 명세](../../p2/chat.md#chat-06-입장퇴장-시스템-메시지), API·ERD·아키텍처의 목표 계약과 혼합 버전 배포 순서만 반영한다. 전진 migration과 생산 코드는 아직 없다.
- 호환: 기존 `ChatMessage` 응답 필드는 이름·의미를 바꾸지 않는다. 새 필드는 추가되며, `messageType`을 모르는 클라이언트도 기존 `content`·`createdAt`으로 시스템 메시지를 시간순 텍스트로 표시할 수 있다. 저장된 기존 사용자 메시지 행은 `USER` 종류로 그대로 유효하다.
- runtime rollback: 시스템 메시지 저장은 원인 참가 트랜잭션과 같은 트랜잭션이므로 부분 저장 상태가 남지 않는다. 기능을 되돌리면 그 시점 이후의 안내가 생기지 않을 뿐 이미 저장된 행은 이력에 남는다.
- 배포 rollback: `SYSTEM` 행이 아직 없는 동안에는 애플리케이션만 이전 버전으로 되돌려도 기존 채팅이 그대로 동작한다. `message_type`을 DEFAULT `'USER'`로 두는 이유가 이 구간을 성립시키기 위해서다. `SYSTEM` 행이 한 건이라도 저장된 뒤에는 구버전 실시간 전달 경로가 sender 없는 행에서 연결을 닫으므로 구버전으로 되돌릴 수 없다. 단계별 rollback 순서의 정본은 [ERD](../../ERD.md#chat-06-혼합-버전-배포활성화rollback-순서)다.

## 보류 및 재검토

- 지금 하지 않는 것: 대기열 자동 승격·방 취소·방 종료의 시스템 메시지, 사건 당시 닉네임 보존, 사용자별 안내 문구 숨김·설정, 시스템 메시지의 별도 조회 API와 읽음 상태, 기존 채팅방의 소급 안내 생성
- 보류 이유: 이번 범위는 참가·참가 취소만 다루기로 확정했고, 나머지 사건은 알림·상태 변경 화면이 이미 다루거나 사용자 문제가 확인되지 않았다. 소급 생성은 과거 참가 시각을 신뢰할 수 있는 원인 사실로 복원할 수 없다.
- 다시 검토할 조건: 승격으로 참가자가 된 사용자의 입장 안내 누락이 사용자 혼선으로 확인되거나, 읽기 시점 조립의 공개 프로필 조회가 이력 조회 지연 기준을 넘거나, 사건 당시 닉네임 표시가 신고·분쟁 처리에 필요해질 때
