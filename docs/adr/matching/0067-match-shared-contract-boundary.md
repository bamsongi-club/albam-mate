# ADR-0067: MATCH 공통 모듈 공개 계약 경계와 chat 접근 오류 매핑

- 상태: 승인됨

- 후속 ADR: [ADR-0077](0077-match-no-game-player-range.md) — 게임 지원 인원 범위 조회·교집합 저장 결정만 부분 대체

## 맥락

MATCH 저장 기반과 기본 chat port를 인계한 뒤, MATCH-01의 기능 구현 세 갈래가 같은 모듈 경계에서 각자 다른 답을 만들기 시작했다. 세 갈래는 차단 목록·차단·해제, MATCH 전용 채팅 저장·전달, 매칭 요청·제안·Party lifecycle이며 각각 별도 브랜치에서 진행 중이다.

세 갈래가 공통으로 필요로 하는 값이 어느 모듈의 공개 계약에도 없었다.

- `game`의 공개 게임 요약은 ID·외부 ID·이름만 담는다. 매칭은 요청 인원 범위와 게임 지원 인원 범위의 교집합을 판정해야 하는데, 그 원천 필드는 게임 Entity 안에만 있다.
- `user`의 공개 조회는 닉네임만 제공한다. 매칭의 차단 목록과 제안·성공 파티 응답은 공개 프로필 이미지도 필요하고, 차단 명령은 두 사용자 행을 함께 잠가 동시 요청을 직렬화해야 한다.
- `matching`의 chat 접근 판정은 접근 가능 여부를 참·거짓 하나로만 반환한다. API 정본은 준비 중인 파티와 종료·비참가·이탈을 사용자에게 다른 의미로 알리도록 요구하므로, 이 반환값으로는 계약을 만족할 수 없다.

계약이 없는 상태에서 기능 구현이 진행되자 실제 위반이 나타났다. 차단 갈래는 사용자 Repository와 사용자 Entity를 직접 주입·반환해 구조 검사 8건을 위반했고, 응답 DTO가 사용자 Entity를 파라미터로 받았다. 목록 조회 JPQL은 다른 모듈의 Entity를 직접 조인했는데, 이 경로는 구조 검사가 타입 참조만 보기 때문에 검출되지 않았다. 채팅 갈래는 접근 판정으로 구분할 수 없는 의미를 채팅방 행의 존재 여부로 대신 판정해 우회하고 있었다. 두 갈래 모두 새 최상위 패키지를 만들었으나 구조 검사의 허용 목록에 없어 검사가 실패했다.

판단 기준은 다섯 가지다. 첫째, 개인정보와 다른 모듈의 Entity가 공개 계약을 통해 새지 않을 것. 둘째, 사용자에게 보이는 오류 의미가 API 정본과 일치할 것. 셋째, 세 갈래가 같은 계약을 각자 정의해 충돌하지 않을 것. 넷째, 이미 여러 호출자를 가진 기존 공개 계약의 호환을 깨지 않을 것. 다섯째, 카탈로그 변경이 진행 중인 요청의 판정을 바꾸지 않아야 한다는 제품 규칙을 지키면서 이미 인계된 저장 범위를 다시 열지 않을 것.

## 검토한 대안

아래 세 축은 판단 기준이 서로 달라 같은 표에서 비교하지 않는다. 축마다 그 축의 기준으로만 대안을 비교한다.

### 축 1. 공통 값을 어느 계약이 소유하는가

판단 기준은 개인정보와 타 모듈 Entity의 노출 범위, 그리고 기존 호출자의 호환이다.

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 기존 공개 게임 요약·사용자 조회를 MATCH가 필요한 모든 필드로 넓힌다 | 계약 종류가 늘지 않는다 | 일반 조회 계약에 MATCH 전용 데이터와 개인정보 표현이 섞인다. 게임 요약은 방 조회 3곳, 닉네임 조회는 방·채팅 6곳이 이미 호출하므로 이들에게 쓰지 않는 필드와 판단 책임을 강요한다 | 제외 |
| 목적이 드러나는 매칭 전용 값 타입·조회 메서드를 각 모듈의 공개 계약에 추가한다 | 필요한 호출자만 새 값을 본다. 기존 호출자는 영향이 없다. 공개 필드를 정본이 허용한 범위로 좁게 고정할 수 있다 | 계약 종류가 늘고, 목록 조회에서 저장 조회와 프로필 조회를 조합하는 코드가 필요하다 | 선택 |
| 세 기능 갈래가 각자 필요한 Repository·Entity를 직접 참조한다 | 당장 코드를 덜 쓴다 | 모듈 경계와 구조 검사를 깨고, 개인정보 노출 범위와 잠금·트랜잭션 규칙이 갈래마다 갈라진다. 실제로 위반 8건이 발생했다 | 제외 |

### 축 2. 게임 지원 인원 범위를 언제 읽고 무엇을 저장하는가

판단 기준은 카탈로그 변경이 기존 요청의 판정을 바꾸지 않아야 한다는 제품 규칙과, 이미 인계된 저장 범위를 다시 여는 비용이다.

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 요청 인원 범위와 게임 지원 인원 범위를 각각 저장하는 컬럼을 매칭 요청에 추가한다 | 두 값을 따로 보존해 사후 진단이 쉽다 | 마이그레이션과 ERD 변경으로 이미 인계된 저장 범위를 다시 연다. 후보 선별이 매번 두 범위를 다시 교차해야 한다 | 제외 |
| 매칭 요청은 교집합만 저장하고, 지원 범위 조회는 요청 등록에서만 호출한다 | 스키마를 바꾸지 않는다. 후보 선별이 저장값만 읽으므로 카탈로그 변경이 기존 요청 판정을 바꾸지 않는다 | 나중에 원래 요청 범위와 게임 범위를 분리해 보고 싶으면 컬럼을 추가해야 한다 | 선택 |
| 후보 선별마다 게임 지원 범위를 다시 조회한다 | 스키마를 바꾸지 않고 최신 카탈로그를 반영한다 | 카탈로그 변경이 기존 요청의 판정을 바꿔 제품 명세의 고정 규칙을 위반한다. 선별 쿼리 비용도 늘어난다 | 제외 |

### 축 3. chat 접근 판정 결과를 어떤 타입으로 공개하는가

판단 기준은 API 정본이 요구한 오류 의미를 표현할 수 있는지와, 권한 없는 호출자에게 파티 존재 여부를 노출하지 않는지다.

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 참·거짓과 단일 거부로 유지한다 | 계약이 가장 단순하다 | 준비 중인 파티와 종료·비참가·이탈을 구분할 수 없어 API 정본의 오류 계약을 만족하지 못한다 | 제외 |
| 허용·준비중·거부의 3-way 결과 타입을 둔다 | 정본이 요구한 두 의미를 구분하면서, 권한 없는 호출자에게 파티 존재 여부를 노출하지 않는다 | 파티 미존재를 거부로 흡수하므로 채팅 경로에서 404를 반환할 수 없고, API 정본의 오류 매트릭스를 함께 정정해야 한다 | 선택 |
| 파티 미존재를 별도 값으로 두어 4-way로 만든다 | 채팅 경로에서도 404를 표현할 수 있다 | 접근 관계가 없으면 거부이므로 파티 미존재는 접근 관계도 없다. 채팅 경로에서 도달할 수 없는 값이 계약에 남고, 어떤 조건에서 404가 나가는지 정본에 새로 정의해야 한다 | 제외 |

## 결정

MATCH가 다른 업무 모듈에서 읽는 값은 목적이 드러나는 매칭 전용 계약으로 각 모듈의 `contract`가 소유한다. 기존 게임 요약과 닉네임 조회는 이미 방·채팅에 여러 호출자가 있으므로 바꾸지 않고, 필요한 계약만 추가한다.

게임 지원 인원 범위는 매칭 전용 값 타입으로 공개하고, 원천은 게임 Entity의 최소·최대 인원 필드로 고정한다. 두 필드는 값이 없을 수 있으므로 하나라도 없으면 지원 범위 미상으로 보고 빈 결과를 반환하며, 매칭은 이를 교집합 없음과 같이 다뤄 요청 등록을 거절한다. 같은 Entity의 표시용 문자열 인원 표기는 판정 원천으로 쓰지 않는다.

매칭 요청은 등록 시점에 확정한 요청 범위와 게임 지원 범위의 교집합만 저장한다. 따라서 게임 범위 조회는 요청 등록 경로에서만 호출하고 후보 선별은 저장값만 읽는다. 저장 스키마는 바꾸지 않으며 이 결정으로 마이그레이션을 추가하지 않는다.

사용자 공개 프로필은 닉네임과 공개 프로필 이미지만 담는 값 타입으로 단건·일괄 조회를 공개한다. 없는 사용자 ID는 기존 일괄 닉네임 조회와 같은 규칙으로 결과에서 제외하고 예외로 만들지 않으며, 이미지가 없으면 빈 값으로 표현한다. 이메일·비밀번호·세션·인증 정보와 사용자 Entity는 공개하지 않는다.

사용자 행 잠금은 `user.contract`의 별도 포트가 소유한다. 호출자 트랜잭션에 참여해 입력 사용자 ID를 오름차순으로 잠그고 실제 존재한 ID만 반환하며, 사용자 Entity를 반환하지 않는다. 매칭은 이 포트로만 사용자 행을 잠그고 사용자 Repository·Entity를 직접 참조하지 않는다.

MATCH 저장 구조와 공개 프로필을 함께 보여주는 목록은 매칭이 자기 테이블만 조회해 사용자 ID를 얻은 뒤, 그 페이지의 ID를 모아 공개 프로필 일괄 조회를 한 번 호출해 조립한다. 매칭의 JPQL은 다른 모듈의 Entity를 조인하지 않는다.

chat 접근 판정은 `matching.contract`가 소유하는 3-way 결과 타입으로 공개한다. 파티가 활성이고 아직 나가지 않은 현재 참가자면 허용, 현재 참가자인데 파티가 준비 중이면 준비중, 그 밖의 종료·비참가·이탈·파티 미존재는 모두 거부다. 파티 존재 여부를 접근 권한이 없는 호출자에게 노출하지 않기 위해 미존재를 거부로 흡수하므로, MATCH 채팅 경로는 파티 미존재 오류를 반환하지 않는다. 준비중과 거부를 각각 어떤 오류로 내보낼지는 매칭이 한 곳에서 매핑하고 채팅이 다시 판정하지 않는다. 쓰기 guard는 파티를 잠근 뒤 같은 판정을 적용한다.

## 결과

- 얻는 것:
    - 매칭이 다른 모듈의 Repository·Entity를 참조하지 않고, 공개되는 사용자 값이 닉네임과 프로필 이미지로 좁게 고정된다.
    - 준비 중인 파티와 종료·비참가·이탈이 사용자에게 다른 의미로 전달되어 API 정본의 오류 계약을 만족한다.
    - 세 기능 갈래가 같은 계약을 공유하므로 갈래마다 다른 조회·잠금·오류 의미가 생기지 않는다.
    - 후보 선별이 저장된 교집합만 읽으므로 카탈로그 변경이 진행 중인 요청의 판정을 바꾸지 않는다.
- 감수할 비용·위험:
    - 공개 계약 종류가 늘고, 목록 조회는 저장 조회와 프로필 일괄 조회 두 번을 조합해야 한다.
    - MATCH 채팅 경로에서 파티 미존재를 404로 구분할 수 없다. 채팅 밖 성공 파티 경로에서만 404를 반환한다.
    - 원래 요청 인원 범위를 나중에 따로 보고 싶으면 컬럼 추가가 필요하다.
    - 매칭의 JPQL이 다른 모듈 Entity를 조인하지 않는다는 규칙은 구조 검사가 타입 참조만 보므로 자동으로 검출되지 않는다.
- 후속 작업:
    - 공개 계약과 구현체, 계약 테스트, 구조 검사 허용 패키지 등록을 [#801](https://github.com/bamsongi-club/albam-mate/issues/801)이 한 변경에서 소유한다.
    - 진행 중인 세 기능 갈래는 #801이 반영된 뒤 rebase해 직접 참조와 미등록 패키지를 정리한다.
    - JPQL 조인 금지는 계약 테스트와 리뷰 확인 항목으로 유지한다.

## 적용·호환·rollback

- 적용: 이 결정은 정본 문서에만 반영한다. 공개 계약 인터페이스와 구현체, 계약 테스트, 구조 검사 허용 패키지 등록은 [#801](https://github.com/bamsongi-club/albam-mate/issues/801)이 한 변경에서 수행한다.
- 호환: 기존 게임 요약·닉네임 조회 계약과 그 호출자는 바꾸지 않고 필요한 계약만 추가하므로 `room`·`chat`의 기존 경로는 영향을 받지 않는다. 저장 스키마와 Flyway 마이그레이션도 바꾸지 않는다. 다만 `MatchPartyAccessQuery`의 반환 타입이 `boolean`에서 `MatchPartyChatAccess`로 바뀌므로, #742가 남긴 해당 계약 테스트는 #801이 함께 갱신한다.
- rollback: 저장 구조와 마이그레이션을 바꾸지 않으므로 데이터 되돌리기가 없다. #801이 추가한 계약 타입·조회 메서드·잠금 port와 구조 검사 허용 패키지 등록을 되돌리면 결정 이전 상태로 돌아간다. 그 경우 `MatchPartyAccessQuery`는 다시 `boolean`이 되어 `MATCH_CHAT_NOT_ACTIVE`를 표현할 수 없으므로, rollback은 API 정본의 chat 오류 계약 정정도 함께 되돌려야 한다.

## 보류 및 재검토

- 지금 하지 않는 것: 매칭 요청에 게임 지원 인원 범위 스냅샷 컬럼을 추가하는 것, MATCH 채팅 경로에서 파티 미존재를 404로 구분하는 것, 다른 모듈 Entity를 참조하는 JPQL을 자동 검출하는 검사를 만드는 것.
- 보류 이유: 앞의 둘은 지금 필요한 사용자 의미와 판정을 이미 만족하면서 저장 범위와 오류 계약을 더 넓히기 때문이다. 마지막은 문자열 쿼리를 정적으로 해석해야 해서 현재 구조 검사 도구의 범위를 벗어난다.
- 다시 검토할 조건: 요청 인원 범위와 게임 지원 범위를 분리해 진단해야 하는 운영 요구가 생기거나, 채팅 클라이언트가 종료된 파티와 접근 권한 없는 파티를 다르게 안내해야 하거나, 다른 모듈 Entity를 참조하는 JPQL이 리뷰를 통과해 실제로 반영된 사례가 나올 때.
