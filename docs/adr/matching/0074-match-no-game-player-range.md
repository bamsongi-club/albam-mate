# ADR-0074: MATCH 게임·플랫폼 없는 인원 범위 매칭

- 상태: 승인됨
- 작성일: 2026-08-18
- 결정일: 2026-08-18
- 관련: [MATCH-01 명세](../../p2/matching.md), [API](../../API.md), [아키텍처](../../ARCHITECTURE.md), [MATCH 측정 계약](../../measurements/match-01-candidate-search-baseline-contract.md), [#835](https://github.com/bamsongi-club/albam-mate/issues/835), [#838](https://github.com/bamsongi-club/albam-mate/issues/838)
- 대체 대상: [ADR-0067](0067-match-shared-contract-boundary.md)의 게임 지원 인원 범위 조회와 게임 범위 교집합 저장 결정
- 후속 ADR: 없음

## 맥락

MATCH-01의 초기 계약은 사용자가 게임을 선택하고 Board Game Arena를 고정한 뒤, 사용자의 인원 범위와 게임 지원 인원 범위의 교집합으로 후보를 제한하도록 했다. 이 구조에서는 게임 카탈로그 조회와 플랫폼 조건이 모든 요청·후보·제안 흐름에 들어가고, 지원 인원 범위가 겹치지 않으면 요청 자체를 거절한다.

이번 MVP에서는 매칭률을 높이는 것을 우선해 MATCH가 특정 게임을 미리 정하지 않기로 했다. MATCH의 책임은 함께할 사람을 인원 범위로 연결하는 데 한정하고, 실제 게임 선택과 진행 방법은 성공 파티 채팅에서 참가자들이 정한다. 판단 기준은 후보 풀 확대, 요청·저장·API 흐름의 단순성, 기존 FIFO·동시성·안전 불변식의 보존, 이후 게임 선택 기능을 다시 도입할 수 있는 경계다.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 게임과 Board Game Arena를 계속 요청·후보 조건으로 사용 | 게임이 같은 사용자만 연결하고 게임 지원 인원을 서버가 검증할 수 있다 | 게임별 후보 풀이 작아 매칭률이 낮아지고, 카탈로그·플랫폼 계약이 매칭의 모든 단계에 결합된다 | 제외 |
| 요청에서는 게임을 없애고 시스템이 매칭 후 게임을 선택·추천 | 후보 풀은 넓어지고 사용자는 게임 선택 부담을 덜 수 있다 | 추천 기준·게임 지원 인원·링크·플랫폼 정책을 새로 결정해야 하므로 현재 MVP 범위를 다시 키운다 | 제외 |
| 게임·플랫폼을 MATCH 전체에서 제거하고 사용자 인원 범위만으로 매칭 | 요청·후보·저장·API가 단순해지고 후보 풀이 넓어진다. 기존 인원·FIFO·차단·동시성 규칙을 유지할 수 있다 | 게임별 검증·추천·외부 링크 생성을 제공하지 않으며, 참가자가 채팅에서 게임을 정해야 한다 | 선택 |

## 결정

MATCH-01은 게임과 플랫폼을 매칭 조건·저장 데이터·응답 표현에서 제거하고, 사용자가 원하는 최소·최대 인원 범위만으로 매칭한다.

- 매칭 요청은 `minPlayers`와 `maxPlayers`만 입력 조건으로 받는다. `minPlayers > 0`, `minPlayers <= maxPlayers`만 검증하고 두 값은 사용자가 입력한 값 그대로 저장·조회한다.
- 후보는 연결된 요청들의 인원 범위 교집합이 존재할 때만 구성한다. 실제 `partySize`는 교집합의 하한, 즉 선택된 요청들의 `minPlayers` 중 최댓값으로 고정한다. 교집합이 없으면 해당 요청은 후보가 되지 않고 `WAITING`으로 남는다.
- `prioritySince ASC, matchRequestId ASC`의 제한된 FIFO, 차단 관계 제외, 사용자당 활성 요청 하나, PostgreSQL 선점·멱등성·응답 경합·채팅 복구 규칙은 유지한다.
- MATCH 요청·제안·성공 파티·현재 상태 조회·채팅 handoff에는 게임과 플랫폼을 포함하지 않는다. `game` 모듈의 카탈로그·지원 인원·플랫폼 정보를 읽거나, 게임을 검증·추천·예약·링크 생성하지 않는다.
- 전원 수락 뒤 연결되는 MATCH 채팅은 참가자를 연결하는 공간만 제공한다. 참가자들은 채팅에서 원하는 게임과 진행 방법을 직접 정한다.
- 기존 저장 구조의 `game_id` 제거와 필요한 참조·인덱스·제약 변경은 [#838](https://github.com/bamsongi-club/albam-mate/issues/838)의 새 forward migration과 같은 변경에서 처리한다. 이미 반영된 V28/V29 migration 파일은 수정하지 않는다.

## 결과

결정 이후 MATCH의 후보 풀과 요청 등록 경로가 게임 카탈로그와 독립한다.

- 얻는 것: 게임을 선택하지 않아도 인원 범위가 맞는 사용자들을 후보로 삼을 수 있고, 요청 등록·후보 탐색·현재 상태 응답이 게임/플랫폼 계약 없이 동작한다. 기존 후보 선점·안전·응답·채팅 lifecycle 규칙은 유지한다.
- 감수할 비용·위험: MATCH가 게임별 인원 지원 여부·추천·플랫폼 계정·게임방 링크를 검증하지 않는다. 서로 다른 게임을 원하는 사용자도 같은 제안에 포함될 수 있으므로 참가자들이 채팅에서 게임을 합의해야 한다.
- 후속 작업: [#838](https://github.com/bamsongi-club/albam-mate/issues/838)이 저장 마이그레이션·ERD·스키마 검증을 수행하고, [#745](https://github.com/bamsongi-club/albam-mate/issues/745)가 새로운 요청·후보·Proposal·Party lifecycle을 구현한다. [#775](https://github.com/bamsongi-club/albam-mate/issues/775)·[#776](https://github.com/bamsongi-club/albam-mate/issues/776)의 측정과 [#746](https://github.com/bamsongi-club/albam-mate/issues/746)의 통합 완료 기준은 이 결정의 인원 범위를 사용한다.

## 적용·배포·되돌리기

- 적용 순서는 이 ADR과 API·아키텍처·MATCH 기능·측정 정본을 반영한 문서 변경, #838의 새 forward migration·Entity·ERD·스키마 검증, #745의 런타임 구현, 후속 측정·통합 검증으로 한다.
- V28/V29를 수정하지 않으며, 이미 배포된 스키마에는 기존 migration 파일을 다시 실행하지 않는다. #838 이후 스키마를 되돌려야 하면 현재 배포 상태를 확인한 뒤 별도의 보정 forward migration과 호환 코드 배포를 결정한다.
- 런타임 구현 전에는 이번 API 계약을 목표 계약으로 사용한다. 구현 후 이전 게임·플랫폼 요청 형식으로 되돌리는 것은 호환되지 않으므로, 되돌림이 필요하면 문서·코드·스키마의 버전을 함께 되돌릴 수 있는 배포 단위로 판단한다.

## 보류 및 재검토

- 지금 하지 않는 것: 게임 선택 UI, 게임별 후보 필터, 플랫폼 계정 연동, 게임 지원 인원 검증, 시스템 게임 추천, 외부 게임방 생성과 링크 유효성 검사.
- 보류 이유: 현재 MVP의 목표가 사람 매칭률과 구현 단순성 확인이며, 채팅에서 참가자들이 게임을 직접 정하는 운영으로 시작하기로 했기 때문이다.
- 다시 검토할 조건: 게임별 매칭이 필요하다는 사용자 요구가 확인되거나, 서로 다른 게임 선택으로 채팅 합의가 반복적으로 실패하거나, 후보 풀이 지나치게 넓어 매칭 품질·안전 문제가 측정되는 경우. 재도입 시에는 게임 선택 시점·지원 인원 snapshot·플랫폼 범위·기존 요청 호환·마이그레이션을 별도 ADR로 결정한다.
