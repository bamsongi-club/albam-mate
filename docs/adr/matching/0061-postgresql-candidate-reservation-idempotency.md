# ADR-0061: PostgreSQL 후보 선점과 매칭 요청 멱등성

## 맥락

MATCH-01은 실제로 구성 가능한 요청만 제한된 FIFO 순서로 제안해야 하며, 다중 matcher가 같은 요청을 동시에 선택해도 중복 제안·중복 성공·부분 성공을 만들면 안 된다. [MATCH-01 명세](../../p2/matching.md#상태동시성복구)는 PostgreSQL을 매칭 요청·제안·응답·성공 파티의 정본으로 두고, 동일한 우선순위 시각은 ADR에서 결정적으로 처리하도록 남겼다.

#737 범위에서 API·ERD·아키텍처 계약은 이 결정을 반영한다. 다만 생산 코드·Flyway 마이그레이션·통합 테스트·배포·실측은 아직 없으므로, 이번 결정은 계약 준비 완료를 구현·검증 완료로 표시하지 않는다. 판단 기준은 PostgreSQL 한 곳에서의 원자성, 잠긴 후보의 동시 처리, 사용자 재전송의 안전성, 자동 재대기의 우선순위 보존, 그리고 이후 측정 가능한 경합 지표다.

## 검토한 대안

### 후보 선점

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 애플리케이션 메모리 또는 Redis 업무 락으로 후보를 먼저 점유 | 구현 시작 시 분산 점유를 눈에 띄게 표현할 수 있다. | PostgreSQL 상태와 별도 업무 정본이 생기고, 락 만료·장애·재시작 때 중복과 복구 경계를 추가로 풀어야 한다. DB 경합 근거도 없다. | 제외 |
| 잠금 없이 후보를 읽은 뒤 각 요청을 독립 갱신 | 읽기 쿼리가 단순하다. | 같은 후보를 여러 matcher가 읽고 일부만 전이하는 부분 성공, 중복 제안, 순서 역전이 생길 수 있다. | 제외 |
| PostgreSQL 행 잠금과 조건부 전이를 한 트랜잭션으로 커밋 | 기존 업무 정본 하나에서 후보 점유와 기록 생성을 함께 판정한다. 잠긴 후보는 다른 matcher가 건너뛰어 진행할 수 있다. | SKIP LOCKED는 잠긴 더 이른 요청을 일시적으로 건너뛰므로 경합 중 전역 절대 FIFO는 보장하지 않는다. 인덱스와 lock wait를 실측해야 한다. | 선택 |

### 요청 재전송

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 클라이언트가 재전송하지 않는다고 가정 | 서버 저장이 필요 없다. | 네트워크 재시도와 중복 탭·버튼에서 중복 등록·응답을 막지 못한다. | 제외 |
| 모든 상태 변경에 Idempotency-Key를 요구 | 한 가지 규칙처럼 보인다. | 취소·차단 해제 같은 목표 상태 요청까지 키 수명과 저장을 강제해 API와 운영 부담을 넓힌다. | 제외 |
| 등록과 제안 응답에만 사용자 범위 키를 보관하고, 취소·차단 해제는 목표 상태로 수렴 | 중복 생성·응답 위험이 큰 두 요청만 보호하면서 반복 취소·해제는 현재 목표 상태를 반환할 수 있다. | 키 의미 비교와 24시간 만료 정리가 필요하다. | 선택 |

## 결정

1. 매칭 후보의 업무 정본은 PostgreSQL이다. 실제 구성 가능 조건을 만족한 WAITING 요청은 prioritySince 오름차순, matchRequestId 오름차순으로 정렬하고, 같은 트랜잭션에서 FOR UPDATE SKIP LOCKED로 선점한다. matchRequestId는 prioritySince가 같은 요청의 결정적 동점 기준이며, 자동 재대기로 prioritySince를 바꾸지 않는다.
2. 선점한 각 요청은 WAITING일 때만 PROPOSED로 바꾸는 조건부 전이를 사용한다. 해당 전이, 제안 행, 제안 참가자 관계는 하나의 데이터베이스 트랜잭션에서 함께 커밋한다. 조건부 전이 결과가 없거나 제안 구성 검증이 실패하면 제안·참가자 관계를 남기지 않고 트랜잭션 전체를 롤백한다.
3. 구현은 한 사용자의 비종료 매칭 요청, 제안 내 참가 관계, 중복 응답 결과를 막는 유니크 제약과 조건부 갱신을 함께 둔다. 제약은 애플리케이션 검사만으로 대체하지 않으며, 멱등 레코드는 같은 PostgreSQL 트랜잭션에서 업무 결과와 연결한다.
4. 새 매칭 요청 등록과 전원 수락 finalization은 관련 `USERS` 행을 userId 오름차순으로 잠근 뒤, 비종료 요청과 `PREPARING`·`ACTIVE` 성공 파티 접근 관계를 함께 판정한다. 이 교차 테이블 불변식으로 한 사용자의 현재 화면 상태가 새 대기와 성공 파티로 동시에 갈라지지 않게 한다. 요청 부분 유니크 제약은 요청 중복 방어이며 이 판정을 대신하지 않는다.
5. Idempotency-Key는 매칭 요청 등록과 제안 응답에만 받는다. 키는 사용자 범위에서 24시간 보관한다. 같은 사용자·같은 업무 종류·같은 의미의 재전송은 이전의 stale 응답을 복제하지 않고 현재 영속 상태 결과를 반환한다. 같은 키에 다른 의미를 보내면 conflict로 거절한다. 의미 비교에 필요한 업무 종류와 정규화된 입력 지문은 저장하지만, 키를 다른 사용자와 공유하거나 사용자 범위를 넘겨 재사용하지 않는다.
6. 취소와 차단 해제는 Idempotency-Key를 요구하지 않는 목표 상태 요청이다. 이미 취소되었거나 이미 차단 해제된 경우에도 현재 목표 상태를 반환하며, 반복 호출이 새 대기 시도·새 prioritySince·새 차단 관계를 만들지 않는다.
7. Redis는 기존 chat 전달 기술로 사용할 수 있어도 MATCH 후보 선점·제안 응답·성공 확정의 업무 락으로 새로 도입하지 않는다. PostgreSQL baseline에서 필요한 근거가 나온 뒤에만 대안·장애 복구·운영 비용을 비교하는 별도 ADR로 재검토한다.

## 결과

- 얻는 것:
    - 후보 점유, WAITING에서 PROPOSED 전이, 제안과 참가 관계가 같은 정본·같은 커밋 경계를 따른다.
    - 다중 matcher와 재전송에서 중복 제안·부분 성공의 방어 지점과 동점 순서가 명시된다.
    - 새 대기 등록과 성공 확정이 같은 사용자에 대해 직렬화되어 현재 상태 조회가 하나의 흐름만 반환한다.
    - 키가 필요한 요청을 두 종류로 한정해 클라이언트 재시도와 목표 상태 요청의 책임을 구분한다.
- 감수할 비용·위험:
    - SKIP LOCKED는 잠긴 선행 요청을 잠시 건너뛸 수 있으므로, 경합이 심한 상황의 공정성·lock wait·재시도율을 측정해야 한다.
    - 유니크 제약, 조건부 전이, 사용자 잠금 순서, 키 지문과 24시간 정리 작업을 API·ERD·마이그레이션·테스트에 일관되게 반영해야 한다.
- 후속 작업:
    - #737에서 반영한 API·ERD·아키텍처 계약을 따르는 후속 구현 이슈에서 Flyway와 PostgreSQL 통합 테스트를 작성한다.
    - [ADR-0063](0063-match-baseline-measurement-gate.md)의 사용자 인원 범위 `[2, 4]` `WAITING` 요청 1,000개·서버 2대 baseline으로 후보 탐색과 lock 경합을 측정한다.

## 적용·호환·rollback

- 적용: #737에서 반영한 API·ERD·아키텍처 계약을 구현할 때 후보 잠금과 조건부 전이의 순서, 유니크 제약, 멱등 레코드의 만료 정리를 하나의 PostgreSQL 계약으로 추가해야 한다. 현재 생산 코드·마이그레이션이 없으므로 이 ADR만으로 endpoint나 테이블이 실제 생성되지는 않는다.
- 호환: 기존 ROOM 참가·대기열의 잠금·우선순위 계약과 P1 chat의 Redis 전달 계약은 바꾸지 않는다. MATCH의 새 후보 점유를 기존 ROOM 대기열이나 Redis 업무 락으로 재해석하지 않는다.
- runtime rollback: 후보 선점 트랜잭션 안에서 오류가 나면 WAITING에서 PROPOSED 전이와 제안·참가 관계를 함께 롤백한다. 이미 커밋된 제안의 종료·재대기는 MATCH 상태 전이 규칙으로 처리하며, 배포 실패를 이유로 prioritySince를 새로 만들지 않는다.
- 배포 rollback: 현재는 배포할 구현과 마이그레이션이 없으므로 운영 rollback 절차도 아직 검증되지 않았다. 구현 PR은 forward migration, in-flight 제안의 안전한 종료·복구, 이전 버전 복귀 때 데이터 보존 방법을 별도로 검증해야 하며, 검증 없이 활성 제안·멱등 레코드를 삭제해서는 안 된다.

## 보류 및 재검토

- 지금 하지 않는 것: Redis 업무 락, 고정 p95 목표, 특정 인덱스·테이블명·HTTP 형식, 취소·차단 해제에 대한 Idempotency-Key 확대
- 보류 이유: API·ERD·아키텍처 계약은 반영됐지만 생산 구현·PostgreSQL 경합 실측이 없고, 성능 기준은 구현 전 임의 수치로 정하지 않는다.
- 다시 검토할 조건: baseline에서 후보 탐색 p95·lock wait·재시도율 또는 정합성 위반이 허용할 수 없는 수준으로 확인될 때, 또는 DB 측정 근거로 Redis 업무 락의 이점이 입증될 때. Redis 도입은 이 ADR을 수정하지 않고 별도 ADR로 결정한다.

## 검증

- 상태: 미검증
- 근거:
    - 구현: V28과 MATCH Entity·Repository·Command Executor가 후보 선점, 조건부 `WAITING → PROPOSED`, 사용자·멱등성 잠금 순서와 `MATCH_IDEMPOTENCY_RECORDS` 결과 재생을 구현한다.
    - PostgreSQL 테스트: `MatchSchemaPostgresTest`, `MatchProposalClaimPostgresTest`, `MatchRequestInvariantPostgresTest`, `MatchProposalTerminalPostgresTest`, `MatchLifecycleConcurrencyPostgresTest`가 제약·SKIP LOCKED·경합·중복 요청/응답을 검증한다.
    - 측정: candidate claim runner와 저장 결과는 측정 계약 자체 판정에서 채택됐고, 통합 gate는 T10을 `DEFERRED_BY_ADR_0091`로 분리한다.
- 미검증:
    - 유효한 T10 운영 before/after에서 후보 탐색 p95·DB lock wait·재시도율·처리량과 정합성을 함께 확인하지 못했다.
