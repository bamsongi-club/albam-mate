# ADR-0002: PostgreSQL을 주 데이터베이스로 채택

- 상태: 승인됨
- 작성일: 2026-07-23
- 결정일: 2026-07-23
- 관련: [build.gradle](../../../build.gradle), [프로젝트 명령](../../COMMANDS.md)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

Albam Mate의 핵심 데이터는 회원, 게임, 세션, 참가처럼 서로 관계를 맺는다. 특히 세션 참가에서는 세션 상태와 정원을 확인하고 중복 참가를 막은 뒤 참가 내역을 저장하는 변경을 하나의 일관된 작업으로 처리해야 한다. 애플리케이션 코드의 사전 검증만으로는 동시 요청이나 다른 쓰기 경로에서 정합성을 보장하기 어려우므로, 트랜잭션과 기본 키·외래 키·고유 제약을 제공하는 관계형 데이터베이스를 주 데이터 저장소로 사용한다.

현재 프로젝트는 Spring Data JPA와 PostgreSQL JDBC 드라이버를 각각 구현 및 런타임 의존성으로 선언했다. 다만 운영용 데이터소스, 스키마, 마이그레이션, PostgreSQL 통합 테스트는 아직 구성하지 않았다. 따라서 의존성이 있다는 사실만으로 선택이 검증됐다고 보지는 않는다. 테스트 런타임의 H2는 운영 데이터베이스 대안으로 논의된 기술이 아니라 빠른 테스트를 위한 현재 구성으로만 취급한다.

이번 결정의 기준은 다음과 같다.

- 관계가 많은 도메인을 스키마와 참조 무결성 제약으로 표현할 수 있을 것
- 여러 행에 걸친 상태 변경과 동시 요청을 트랜잭션으로 다룰 수 있을 것
- 현재 Spring Data JPA 구성과 자연스럽게 결합하고 초기 기술 전환 비용을 줄일 것
- MVP 단계에서 영속성 시스템을 불필요하게 여러 개 운영하지 않을 것
- 미래의 검색 요구를 고려하되, 확정되지 않은 AI·RAG 기능을 현재 선택의 전제로 삼지 않을 것

팀 논의에서는 향후 벡터 검색 가능성이 PostgreSQL 선호 이유로 제시됐다. PostgreSQL에는 벡터 유사도 검색을 추가하는 `pgvector` 확장 경로가 있지만, 해당 기능과 데이터 구조는 현재 MVP 범위가 아니다. 벡터 검색 가능성은 보조적인 확장성 기준일 뿐, PostgreSQL 선택의 주된 이유는 현재 도메인의 관계와 트랜잭션 요구다.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| PostgreSQL | 트랜잭션과 기본 키·외래 키·고유·검사 제약으로 관계형 정합성을 데이터베이스에서도 보호할 수 있다. 현재 런타임 드라이버 선언과 일치하며, 필요가 검증되면 `pgvector`를 같은 데이터베이스의 확장 후보로 검토할 수 있다. | 운영 환경과 백업·모니터링을 구성해야 한다. PostgreSQL 전용 SQL이나 확장을 사용하면 이식 비용이 생기며, `pgvector`는 별도 설치와 운영 환경 지원 확인이 필요하다. | 선택 |
| MySQL(InnoDB) | ACID 트랜잭션, 행 잠금, 외래 키를 제공하므로 현재 관계형 요구를 충족할 수 있고 Spring Data JPA에서도 사용할 수 있다. | 현재 PostgreSQL 드라이버와 프로젝트 기준을 변경해야 하지만, 그 전환 비용을 상쇄할 성능·운영·비용상 이점이 측정되지 않았다. 미래 벡터 검색 경로도 별도로 다시 검증해야 한다. | 제외 |

## 결정

Albam Mate의 운영 환경에서 회원, 게임, 세션, 참가를 포함한 업무 데이터의 주 데이터베이스이자 단일 정본으로 PostgreSQL을 채택한다. 애플리케이션은 Spring Data JPA와 PostgreSQL JDBC 드라이버를 통해 접근하고, 정합성 규칙은 서비스 계층의 트랜잭션과 데이터베이스 제약을 함께 사용해 보호한다.

PostgreSQL의 메이저 버전, 스키마 마이그레이션 도구, 세션 참가의 구체적인 잠금·충돌 처리 방식은 이 ADR에서 확정하지 않는다. 배포 환경과 구현 요구가 구체화될 때 각각 호환성 검토 또는 별도 결정으로 다룬다.

`pgvector`, RAG, 별도 벡터 데이터베이스는 지금 도입하지 않는다. 실제 검색 품질·데이터 규모·지연 시간 요구가 확인되면 PostgreSQL 확장과 별도 검색 시스템을 같은 기준으로 다시 비교한다.

## 결과

- 얻는 것: 핵심 도메인의 관계를 외래 키로, 중복과 상태 조건 일부를 고유·검사 제약으로 표현할 수 있고 여러 데이터 변경을 하나의 트랜잭션 경계에서 처리할 수 있다. 초기에는 하나의 관계형 데이터베이스를 운영하며 현재 JPA·드라이버 구성을 유지한다.
- 감수할 비용·위험: PostgreSQL 배포, 백업, 복구, 모니터링과 스키마 변경 절차가 필요하다. PostgreSQL 전용 기능을 사용할수록 다른 데이터베이스로 이전하는 비용이 커진다. H2 테스트만 유지하면 SQL과 동시성 동작의 차이로 결함을 놓칠 수 있다.
- 후속 작업: 비밀정보를 저장소에 넣지 않는 데이터소스 설정 방식을 정하고, 스키마 마이그레이션 절차와 실제 PostgreSQL 기반 통합 테스트를 추가한다. 세션 참가의 정원 초과·중복 참가 방지 방식은 도메인 정책이 확정된 뒤 별도 ADR에서 결정한다.

## 보류 및 재검토

- 지금 하지 않는 것:
  - `pgvector`·RAG·별도 벡터 데이터베이스
  - 읽기 복제본
  - 캐시
  - PostgreSQL 메이저 버전과 관리형 서비스의 확정
- 보류 이유: 현재 구현과 측정된 부하가 없으며, 검색 품질·데이터 규모·배포 환경 요구도 확정되지 않았다.
- 다시 검토할 조건:
  - 선택한 배포 환경이 PostgreSQL을 지원하지 않거나 운영 비용이 수용 범위를 넘을 때
  - 필수 기능이 다른 저장 모델을 요구할 때
  - 실제 부하 시험에서 PostgreSQL이 목표를 충족하지 못할 때
  - 벡터 검색 요구가 구체화돼 확장과 별도 시스템의 비용·성능을 비교할 수 있을 때

## 검증

- 상태: 검증됨
- 근거:
    - 구현:
        - 애플리케이션은 Spring Data JPA와 PostgreSQL JDBC 드라이버로 접속하고, `application-local.yml`과 `compose.local.yml`은 연결값을 환경변수로 주입한다.
    - 테스트:
        - `SchemaValidationPostgresTest`는 Testcontainers `postgres:18.4`에서 Flyway V1~V3·Hibernate 검증과 PostgreSQL 18 연결, CHECK·FK 제약 위반의 SQLSTATE·제약명 및 동시 가입의 이메일 유일성을 확인한다.
        - `RoomParticipationConcurrencyPostgresTest`는 참가·취소 동시 요청 뒤 `active_participant_count`와 실제 `ACTIVE` 참가 관계 수의 일치를 확인한다.
    - CI:
        - `build` 뒤 `postgresTest`를 실행한다.
