# ADR-0007: 도메인 중심 모듈러 모놀리스를 채택

- 상태: 승인됨
- 작성일: 2026-07-24
- 결정일: 2026-07-24
- 관련: [ADR-0001](0001-java-21-spring-boot-4-baseline.md), [P0 명세](../../P0-spec.md), [프로젝트 컨벤션](../../CONVENTIONS.md)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

Albam Mate는 현재 하나의 Gradle 프로젝트와 하나의 Spring Boot 애플리케이션으로 시작한다. P0에는 인증, 사용자, 게임, 방과 참가처럼 서로 구분되는 업무 책임이 있지만, 아직 애플리케이션 진입점 외의 도메인 코드는 구현되지 않았다. 이 시점에 패키지와 의존 방향을 정하지 않으면 모든 Controller, Service와 Repository가 계층별 전역 패키지에 모이고, 한 기능을 변경할 때 여러 도메인의 내부 구현을 함께 알아야 하는 구조가 되기 쉽다.

반대로 P0부터 Gradle 멀티모듈이나 마이크로서비스로 분리하면 아직 검증되지 않은 경계를 빌드·배포·통신 경계로 먼저 고정하게 된다. 현재 필요한 것은 하나의 프로세스와 트랜잭션을 유지하면서도 업무 책임별 소유권과 접근 경계를 드러내는 구조다.

이번 결정의 기준은 다음과 같다.

- P0를 하나의 배포 단위로 빠르게 구현할 수 있을 것
- 기능을 찾고 변경할 때 관련 코드가 도메인 안에 모여 있을 것
- 다른 도메인의 영속성 구현과 엔티티에 직접 결합하지 않을 것
- 도메인 사이의 순환 의존을 막고 공개한 계약으로만 협력할 것
- 실제 복잡도가 증가할 때 빌드 모듈이나 서비스로 분리할 여지를 남길 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 단일 Gradle 프로젝트의 도메인 중심 모듈러 모놀리스 | 하나의 애플리케이션과 데이터베이스 트랜잭션을 유지하면서 도메인별 코드 소유권과 의존 경계를 드러낼 수 있다. 현재 프로젝트 구조에서 점진적으로 적용할 수 있다. | 패키지 규칙만 선언하고 검증하지 않으면 다른 모듈의 내부 구현을 참조하는 결합이 다시 생길 수 있다. 모듈 경계를 코드 리뷰와 자동화된 구조 테스트로 관리해야 한다. | 선택 |
| 계층 중심 모놀리스 | `controller`, `service`, `repository`처럼 익숙한 계층별 구조를 단순하게 시작할 수 있다. | 한 도메인의 기능이 여러 전역 패키지에 흩어지고, 도메인 소유권과 도메인 간 의존 방향이 코드 구조에 드러나지 않는다. | 제외 |
| Gradle 멀티모듈 모놀리스 | 컴파일·빌드 경계로 모듈 의존을 더 강하게 제한할 수 있다. | 아직 안정되지 않은 도메인 경계를 빌드 구성에 먼저 고정하고 공통 설정과 테스트 구성이 늘어난다. 현재 P0에서 이 비용을 정당화할 요구가 없다. | 보류 |
| 마이크로서비스 | 도메인별 독립 배포와 확장 경계를 가질 수 있다. | 분산 트랜잭션, 네트워크 실패, 관측성, 배포와 운영 복잡도가 생긴다. 현재 팀과 P0에는 독립 배포가 필요한 근거가 없다. | 보류 |

## 결정

Albam Mate 백엔드는 하나의 Gradle 프로젝트와 하나의 Spring Boot 애플리케이션으로 배포하는 도메인 중심 모듈러 모놀리스를 채택한다.

최상위 업무 패키지는 논리적 모듈로 취급하고, 각 모듈 안에 Controller, Service, Repository, DTO와 Entity 등 해당 도메인의 구현을 둔다. 모듈의 하위 패키지는 외부에 공개하지 않는 내부 구현이 기본이다. 다른 모듈은 해당 모듈이 명시적으로 공개한 애플리케이션 서비스·인터페이스 또는 이벤트만 사용하며, 다른 모듈의 Repository, Entity와 내부 DTO를 직접 참조하지 않는다.

모듈 간 의존은 순환하지 않아야 한다. 여러 도메인을 조합하는 유스케이스는 그 유스케이스를 소유한 도메인에 두며, 모든 횡단 흐름을 하나의 공통 Facade에 모으지 않는다. `global`에는 예외 응답, 보안 설정과 공통 설정처럼 업무 의미가 없는 기술 공통 요소만 두고, `infra`에는 외부 시스템 연동과 기술 어댑터를 둔다. 두 패키지를 도메인 로직의 우회 공유 공간으로 사용하지 않는다.

이 결정은 Gradle 멀티모듈 구성이나 Spring Modulith 런타임 의존성 도입을 요구하지 않는다. 패키지 경계가 두 개 이상의 업무 모듈로 구현되면 Spring Modulith 검증 또는 ArchUnit 같은 구조 테스트를 추가해 순환 의존과 내부 패키지 접근을 자동으로 검사한다.

## 결과

- 얻는 것: 한 기능의 코드가 도메인별로 모이고, 모듈의 공개 계약과 내부 구현이 구분된다. P0는 하나의 프로세스와 데이터베이스 트랜잭션을 유지한다.
- 감수할 비용·위험: 개발자가 모듈 경계를 지속적으로 지켜야 하며, 잘못 설계한 공개 API가 도메인 결합을 숨길 수 있다. 자동 검증을 추가하기 전에는 코드 리뷰 의존도가 높다.
- 후속 작업: [프로젝트 컨벤션](../../CONVENTIONS.md)에 패키지·의존 규칙을 반영하고, 첫 도메인 구현에서 패키지 구조를 적용한다. 두 개 이상의 도메인 모듈이 생기면 구조 검증 테스트와 허용 의존 관계를 추가한다.

## 보류 및 재검토

- 지금 하지 않는 것: Gradle 멀티모듈 전환, 마이크로서비스 분리, 모든 도메인 경계의 선행 확정
- 보류 이유: 현재는 P0 구현 전이라 빌드·배포 경계를 나눌 근거와 운영 요구가 없다. 세부 도메인 경계는 실제 유스케이스와 변경 이유를 확인하면서 정하는 편이 안전하다.
- 다시 검토할 조건: 한 모듈의 변경이 다른 모듈을 반복해서 함께 수정하게 만들 때, 빌드 시간이 독립 모듈 분리를 요구할 때, 일부 기능에 독립 배포·확장·장애 격리가 필요할 때
