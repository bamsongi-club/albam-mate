# ADR-0017: 테스트 커버리지를 분기 기준으로 측정하고 회귀 방지선으로 운영

- 상태: 승인됨
- 작성일: 2026-07-28
- 결정일: 2026-07-28
- 관련: [ADR-0010](0010-h2-postgresql-test-boundary.md), [프로젝트 컨벤션](../../CONVENTIONS.md#테스트), [프로젝트 명령](../../COMMANDS.md#분기-커버리지-확인), [build.gradle](../../../build.gradle), [TOOL-02 이슈](https://github.com/bamsongi-club/albam-mate/issues/81)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

P0 구현은 구현 에이전트가 코드와 테스트를 함께 작성하는 방식으로 진행한다. 그런데
"테스트를 추가했다"는 보고를 기계로 확인하는 장치가 없다. `build`는 이미 있는 테스트가
통과했는지만 보고, 코드 리뷰는 회차마다 볼 관점을 골라서 검토하므로 테스트가 빠졌는지를
항상 보지는 않으며, 도입 당시 pre-commit hook은 포맷만 검사했다. 결과적으로 에이전트가 고려하지
않은 분기는 테스트도 신호도 없이 통과한다.

도입 검토에서 실제로 측정하니 라인 커버리지 92.4%에 분기 커버리지 73.0%였다. 라인만
보면 충분해 보이지만, 전체 분기 270개 중 73개는 조건식의 한쪽만 실행돼 나머지 한쪽이
검증되지 않은 상태였다. 구체적으로 인증 요청 제한기에서 이동 창의 남은 시간이 정확히
0인 경계, `Retry-After`의 초 단위 올림, 이미 해제된 검증 슬롯을 다시 해제할 때의 무동작
처리 세 분기가 어떤 테스트에서도 실행되지 않았다. 같은 세 개념은 직전 머지 때 거친 diff
이해도 확인(머지 전에 변경 내용을 퀴즈로 되묻는 절차)에서도 오답이었다. 즉 사람이
이해하지 못한 동작과 테스트가 검증하지 않은 동작이 같은 지점에서 겹쳤다.

이번 결정의 기준은 다음과 같다.

- 경계 조건과 예외 경로의 미검증을 수치가 감추지 않을 것
- 지표를 만족시키려고 값싼 테스트를 쓸 유인을 만들지 않을 것
- 패키지 구조가 바뀌어도 검사가 조용히 통과하지 않을 것
- 구현 에이전트가 스스로 실행할 수 있는 반복 명령으로 제공할 것
- H2 테스트와 PostgreSQL 검증([ADR-0010](0010-h2-postgresql-test-boundary.md)) 결과를 함께 집계할 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 라인 커버리지를 기준으로 삼는다 | 도구 기본값이고 팀이 이해하기 쉽다. | 조건식의 한쪽만 실행해도 올라가므로 경계·예외 경로의 미검증을 감춘다. 실측에서 분기 기준과 19.4%p 차이가 났다. | 제외 |
| 고정 목표치를 운영 기준으로 삼는다 | 목표가 명확하고 프로젝트 간 비교가 쉽다. | 테스트를 작성하는 주체가 구현 에이전트라 목표를 채우는 값싼 단정이 유입된다. 그렇게 축적된 테스트는 사후에 걷어내기 어렵다. | 제외 |
| 분기 커버리지를 도입 시점 실측값에 고정한 회귀 방지선으로 운영한다 | 경계·예외 경로의 미검증을 드러내고, 수치를 채울 유인을 만들지 않는다. 회귀만 차단하므로 도입 비용이 낮다. | 절대 수준이 낮게 유지될 수 있고, 방지선을 올리는 시점은 사람이 판단해야 한다. | 선택 |

## 결정

테스트 커버리지는 라인이 아니라 분기(BRANCH)를 기준으로 판정한다.

다만 분기 커버리지는 조건문이 없는 코드를 세지 않는다. 따라서 조건문 없는 서비스·매핑
코드가 테스트 없이 들어오면 분기 규칙은 아무 반응을 하지 않는다. 이 사각지대를 메우기
위해 전체 라인 최소선을 보조로 함께 둔다. 라인은 판정의 주 기준이 아니며 패키지 단위로는
두지 않는다. 애플리케이션 진입점만 있는 루트 패키지처럼 라인 비율이 구조적으로 낮은
패키지가 있기 때문이다.

최소선은 도입 시점의 실측값을 0.01 단위로 내림한 값으로 고정하며, 이는 달성 목표가
아니라 회귀 방지선이다. 전체 최소선과 함께 분기 10개 이상인 패키지에 개별 최소선을
둔다. 분기 수가 그보다 적은 패키지는 분기 하나가 비율을 크게 흔들어 거짓 경보를 내므로
개별 규칙을 두지 않고 전체 최소선으로만 관리한다. 최소선을 올리는 변경은 그대로 반영하고,
내리는 변경은 이유를 PR 본문에 남긴다. 커버리지 수치 자체를 기능 완료 기준이나 개인
평가 근거로 사용하지 않는다.

최소선 목록이 실제 패키지 구조와 어긋나면 검사가 조용히 약해진다. 어긋나는 방향은 둘이며
둘 다 실패로 만든다.

첫째는 규칙은 있는데 대상이 사라진 경우다. 패키지 규칙은 이름이 정확히 일치할 때만
적용되므로, 클래스가 다른 패키지로 옮겨 가면 그 규칙은 어떤 대상에도 걸리지 않은 채
통과한다. 둘째는 대상은 있는데 규칙이 없는 경우다. 규칙이 없는 패키지에는 전체 최소선만
적용되는데, 새 모듈이 들어오면 그 모듈의 분기가 전체 비율의 분모에도 함께 더해지므로
모듈 자체의 커버리지가 낮아도 전체 비율은 최소선 위에 남을 수 있다. 도입 검토에서 분기
40개 중 20개만 검증한 모듈이 전체 최소선을 통과하는 것을 계산으로 확인했다.

따라서 규칙 대상이 리포트에 없는 경우와, 개별 최소선이 필요한 규모의 패키지에 최소선이
없는 경우를 함께 검사한다.

게이트는 두 단계로 둔다. `check`에 포함되는 빠른 게이트는 H2 테스트 결과만 보므로
Docker 없이 실행되고, 정본 게이트는 H2 테스트와 PostgreSQL 통합 테스트를 합산하며 두
테스트 실행에 모두 의존한다. 두 게이트는 같은 최소선을 공유한다.

각 게이트는 담당 테스트가 남긴 JaCoCo 실행 데이터 파일(`.exec`)만 이름으로 지정해
집계한다. 실행 데이터 디렉터리를 통째로 읽으면 이번 실행에서 돌리지 않은 테스트의 이전
파일까지 함께 집계된다. 그러면 테스트를 고치거나 지워도 과거 실행 기록이 그 분기를 여전히
실행된 것으로 만들어 게이트가 거짓 통과한다.

CI는 정본 게이트로 판정하고 빠른 게이트는 실행 대상에서 제외한다. 제외하지 않으면 순서
때문에 문제가 생긴다. 빠른 게이트는 H2 결과만 보므로 PostgreSQL 통합 테스트로만 검증되는
분기는 그 게이트에서 미검증으로 보인다. 그래서 정본 게이트라면 통과했을 변경이 빠른
게이트에서 먼저 실패하고, 정본 판정까지 가지 못한다.

Lombok이 생성한 코드는 `@lombok.Generated` 표시로 집계에서 제외해, 검증할 대상이 아닌
접근자·생성자가 수치를 왜곡하지 않게 한다.

## 결과

- 얻는 것: 에이전트의 테스트 추가 보고를 기계로 확인할 수 있고, 어느 분기가 검증되지 않았는지 파일과 줄 단위로 확인할 수 있다. 테스트 없이 추가된 분기나 라인이 전체 또는 해당 패키지의 비율을 최소선 아래로 내리면 검사가 실패한다.
- 감수할 비용·위험: 이 게이트는 미검증 코드가 없다는 보장이 아니라 검증 수준이 내려가지 않는다는 보장이다. 비율이 최소선 이상으로 유지되는 범위의 미검증 추가는 통과한다. 커버리지 집계만큼 빌드 시간이 늘어난다. 커버리지는 단정의 품질을 보지 않으므로, 분기나 라인을 실행하기만 하는 테스트는 여전히 통과한다. 패키지를 옮기거나 새로 만들 때 최소선 목록을 같은 변경에서 갱신해야 한다. 새 패키지에 최소선을 아주 낮게 적으면 검사를 우회할 수 있으나, 목록에 남는 값이므로 리뷰에서 드러난다.
- 후속 작업: 검증되지 않은 분기 가운데 인증 요청 제한기의 경계·예외 경로와 `user` 모듈(분기 54.5%)을 테스트로 덮고, 그만큼 최소선을 올린다.

### 2026-07-29 후속 이행

- 인증 요청 제한기의 공개 입력 경계와 `Retry-After` 올림, 로그인 성공·실패의 해시 갱신 분기, 사용자 계약과 프로필 ID 경계를 직접 검증했다.
- 실제 HTTP 서버와 쿠키 저장소로 CSRF 조회, 로그인, 보호 API 성공, 토큰 재발급, 로그아웃, 기존 세션 거절을 한 흐름에서 검증했다.
- H2 전체 테스트의 재측정값을 0.01 단위로 내려 `auth.security` 0.94, `auth.service` 0.80, `global.config` 1.00, `global.security.ratelimit` 0.84, `user.contract` 0.92, `user.service` 0.71로 방지선을 올렸다.
- CI job summary에 전체 분기·라인 비율을 표시하고, 합산 HTML·XML 리포트를 14일간 artifact로 보관해 실패 위치를 바로 확인할 수 있게 했다.

## 보류 및 재검토

- 지금 하지 않는 것: 클래스 단위 최소선, 패키지 단위 라인 최소선, 명령어 커버리지 게이트, 변경 파일만 검사하는 방식, 뮤테이션 테스트
- 보류 이유: 클래스 단위는 대상이 너무 많아 목록 유지 비용이 이득을 넘는다. 패키지 단위 라인 최소선은 애플리케이션 진입점만 있는 패키지처럼 라인 비율이 구조적으로 낮은 곳에서 거짓 경보를 낸다. 명령어 커버리지는 라인보다 세분화되지만 판정에 추가로 얻는 것이 적다. 변경 파일 기준 검사는 기존 코드의 회귀를 놓치므로 전체·패키지 방지선을 먼저 둔다. 뮤테이션 테스트는 단정 품질까지 보지만 실행 비용이 크고, 값싼 단정으로 방지선을 통과시키는 사례가 아직 확인되지 않았다.
- 다시 검토할 조건: 전체·패키지 방지선으로 특정 클래스의 회귀를 반복해서 놓칠 때, 분기를 실행하기만 하는 테스트로 방지선을 통과시키는 사례가 확인될 때(이때 뮤테이션 테스트를 검토한다), 커버리지 집계가 CI 피드백 시간을 수용하기 어렵게 만들 때

## 검증

- 상태: 검증됨
- 근거: 도입 검증에서 전체 분기 73.0%와 라인 92.4%를 측정해 두 기준의 19.4%p 차이를 확인했다. 이어서 게이트가 실제로 실패하는지를 여섯 가지 통제 시험으로 확인했다.

  | 시험 | 결과 |
  | --- | --- |
  | 최소선을 실측값보다 높게 올림 | `jacocoTestCoverageVerification`이 위반 패키지와 실제 비율을 출력하며 실패 |
  | 규칙 대상을 존재하지 않는 패키지로 바꿈 | `verifyCoverageRuleTargets`가 누락된 대상을 출력하며 실패 |
  | 분기 56개인 패키지의 최소선을 목록에서 제거 | 같은 태스크가 해당 패키지와 현재 비율을 출력하며 실패 |
  | 정본 게이트의 최소선을 실측값보다 높게 올림 | 위반 패키지와 실제 비율을 출력하며 실패. 정본 게이트가 H2 결과만으로 통과하지 않음을 확인 |
  | 보조 라인 최소선을 실측값보다 높게 올림 | 전체 라인 비율과 함께 실패 |
  | 이전 실행의 PostgreSQL 통합 테스트 결과가 디렉터리에 남은 상태에서 H2 전용 리포트를 재생성 | 세션 정보가 1건만 기록됨(정본 리포트는 2건). 게이트별로 실행 데이터가 격리됨을 확인 |

  분기 규칙이 전혀 관여하지 않는 범위는 분기가 0인 패키지 12개의 라인 98개다. 이 범위를 지키는 것은 보조 라인 최소선뿐이다.
