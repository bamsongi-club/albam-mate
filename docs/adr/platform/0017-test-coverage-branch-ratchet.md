# ADR-0017: 테스트 커버리지를 분기 기준으로 측정하고 회귀 방지선으로 운영

- 상태: 승인됨
- 작성일: 2026-07-28
- 결정일: 2026-07-28
- 관련: [ADR-0010](0010-h2-postgresql-test-boundary.md), [프로젝트 컨벤션](../../CONVENTIONS.md#테스트), [프로젝트 명령](../../COMMANDS.md#분기-커버리지-확인), [build.gradle](../../../build.gradle), [TOOL-02 이슈](https://github.com/bamsongi-club/albam-mate/issues/81)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

P0 구현은 구현 에이전트가 코드와 테스트를 함께 작성하는 방식으로 진행한다. 그런데
"테스트를 추가했다"는 보고를 기계로 확인하는 장치가 없다. `build`는 존재하는 테스트가
통과했는지만 보고, 코드 리뷰는 테스트 관점을 매번 선택하지 않으며, pre-commit hook은
포맷만 검사한다. 결과적으로 에이전트가 고려하지 않은 분기는 테스트도 신호도 없이 통과한다.

도입 검토에서 실제로 측정하니 라인 커버리지 92.4%에 분기 커버리지 73.0%였다. 라인만
보면 충분해 보이지만 조건식의 한쪽만 실행된 경로가 270개 분기 중 73개였다. 구체적으로
인증 요청 제한기에서 이동 창의 남은 시간이 정확히 0인 경계, `Retry-After`의 초 단위
올림, 이미 해제된 검증 슬롯을 다시 해제할 때의 무동작 처리 세 분기가 어떤 테스트에서도
실행되지 않았다. 같은 세 개념은 직전 머지의 이해도 확인에서도 오답이었다. 즉 사람이
이해하지 못한 동작과 테스트가 검증하지 않은 동작이 같은 지점에서 겹쳤다.

이번 결정의 기준은 다음과 같다.

- 경계 조건과 예외 경로의 미검증을 수치가 감추지 않을 것
- 지표를 만족시키려고 값싼 테스트를 쓸 유인을 만들지 않을 것
- 패키지 구조가 바뀌어도 검사가 조용히 통과하지 않을 것
- 구현 에이전트가 스스로 실행할 수 있는 반복 명령으로 제공할 것
- H2 테스트와 PostgreSQL 검증([ADR-0010](0010-h2-postgresql-test-boundary.md)) 결과를 함께 집계할 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 라인 커버리지를 기준으로 삼는다 | 도구 기본값이고 팀이 이해하기 쉽다. | 조건식의 한쪽만 실행해도 올라가므로 경계·예외 경로의 미검증을 감춘다. 실측에서 분기 기준과 19.4%p 차이가 났다. | 제외 |
| 고정 목표치를 운영 기준으로 삼는다 | 목표가 명확하고 프로젝트 간 비교가 쉽다. | 테스트를 작성하는 주체가 구현 에이전트라 목표를 채우는 값싼 단정이 유입된다. 그렇게 축적된 테스트는 사후에 걷어내기 어렵다. | 제외 |
| 분기 커버리지를 도입 시점 실측값에 고정한 회귀 방지선으로 운영한다 | 경계·예외 경로의 미검증을 드러내고, 수치를 채울 유인을 만들지 않는다. 회귀만 차단하므로 도입 비용이 낮다. | 절대 수준이 낮게 유지될 수 있고, 방지선을 올리는 시점은 사람이 판단해야 한다. | 선택 |

## 결정

테스트 커버리지는 라인이 아니라 분기(BRANCH)를 기준으로 판정한다.

최소선은 도입 시점의 실측값을 0.01 단위로 내림한 값으로 고정하며, 이는 달성 목표가
아니라 회귀 방지선이다. 전체 최소선과 함께 분기 10개 이상인 패키지에 개별 최소선을
둔다. 분기 수가 그보다 적은 패키지는 분기 하나가 비율을 크게 흔들어 거짓 경보를 내므로
개별 규칙을 두지 않고 전체 최소선으로만 관리한다. 최소선을 올리는 변경은 그대로 반영하고,
내리는 변경은 이유를 PR 본문에 남긴다. 커버리지 수치 자체를 기능 완료 기준이나 개인
평가 근거로 사용하지 않는다.

최소선 목록이 실제 패키지 구조와 어긋나면 검사가 조용히 약해지므로, 두 방향을 모두
실패로 만든다. 패키지 규칙은 이름이 정확히 일치할 때만 적용되어 클래스가 다른 패키지로
이동하면 규칙이 어떤 대상에도 매칭되지 않은 채 통과한다. 반대로 규칙이 없는 패키지는
전체 최소선만 적용되는데, 전체 최소선은 새 분기가 분모를 함께 키우므로 새 모듈이 낮은
커버리지로 들어와도 통과할 수 있다. 도입 검토에서 분기 40개 중 20개만 검증한 모듈이
전체 최소선을 통과하는 것을 계산으로 확인했다. 따라서 규칙 대상이 리포트에 없는 경우와,
개별 최소선이 필요한 규모의 패키지에 최소선이 없는 경우를 함께 검사한다.

집계 범위는 `test`와 `postgresTest`의 실행 데이터를 합산한다. 한쪽만 실행한 경우에는
실행된 결과만 사용한다. Lombok이 생성한 코드는 `@lombok.Generated` 표시로 집계에서
제외해, 검증할 대상이 아닌 접근자·생성자가 수치를 왜곡하지 않게 한다.

검사는 `check`에 포함하므로 `build`로도 실행된다. CI는 `postgresTest`가 끝난 뒤 두 실행
데이터를 합쳐 다시 검사한다. `build` 단계의 검사는 `test` 결과만 보기 때문이다.

## 결과

- 얻는 것: 에이전트의 테스트 추가 보고를 기계로 확인할 수 있고, 어느 분기가 검증되지 않았는지 파일과 줄 단위로 확인할 수 있다. 새 기능이 테스트 없이 들어오면 전체 또는 해당 패키지의 분기 비율이 내려가 검사가 실패한다.
- 감수할 비용·위험: 커버리지 집계만큼 빌드 시간이 늘어난다. 분기 커버리지는 단정의 품질을 보지 않으므로, 분기를 실행하기만 하는 테스트는 여전히 통과한다. 패키지를 옮기거나 새로 만들 때 최소선 목록을 같은 변경에서 갱신해야 한다. 새 패키지에 최소선을 아주 낮게 적으면 검사를 우회할 수 있으나, 목록에 남는 값이므로 리뷰에서 드러난다.
- 후속 작업: 검증되지 않은 분기 가운데 인증 요청 제한기의 경계·예외 경로와 `user` 모듈(분기 54.5%)을 테스트로 덮고, 그만큼 최소선을 올린다.

## 보류 및 재검토

- 지금 하지 않는 것: 클래스 단위 최소선, 라인·명령어 커버리지 게이트, 변경 파일만 검사하는 방식, 뮤테이션 테스트
- 보류 이유: 클래스 단위는 대상이 너무 많아 목록 유지 비용이 이득을 넘고, 라인·명령어 게이트는 이 ADR이 배제한 기준이다. 변경 파일 기준 검사는 기존 코드의 회귀를 놓치므로 전체·패키지 방지선을 먼저 둔다. 뮤테이션 테스트는 단정 품질까지 보지만 실행 비용이 크고, 값싼 단정으로 방지선을 통과시키는 사례가 아직 확인되지 않았다.
- 다시 검토할 조건: 전체·패키지 방지선으로 특정 클래스의 회귀를 반복해서 놓칠 때, 분기를 실행하기만 하는 테스트로 방지선을 통과시키는 사례가 확인될 때(이때 뮤테이션 테스트를 검토한다), 커버리지 집계가 CI 피드백 시간을 수용하기 어렵게 만들 때

## 검증

- 상태: 검증됨
- 근거: 도입 검증에서 전체 분기 73.0%와 라인 92.4%를 측정해 두 기준의 19.4%p 차이를 확인했다. 세 가지 통제 시험으로 게이트가 실제로 실패하는 것을 확인했다. 첫째, 최소선을 실측값보다 높게 올렸을 때 `jacocoTestCoverageVerification`이 위반 패키지와 실제 비율을 출력하며 실패했다. 둘째, 규칙 대상을 존재하지 않는 패키지로 바꿨을 때 `verifyCoverageRuleTargets`가 누락된 대상을 출력하며 실패했다. 셋째, 분기 56개인 패키지의 최소선을 목록에서 제거했을 때 같은 태스크가 해당 패키지와 현재 비율을 출력하며 실패했다. `test`와 `postgresTest`의 실행 데이터가 하나의 리포트에 합산되는 것은 리포트의 세션 정보 2건으로 확인했다.
