# ADR-0016: P0 수정 API의 HTTP 메서드를 PATCH로 통일

- 상태: 대체됨
- 작성일: 2026-07-27
- 결정일: 2026-07-27
- 관련: [API 명세](../../API.md), [P0 명세](../../P0-spec.md), [AUTH-04 정본](../../p0/auth-profile.md#auth-04-내-프로필-조회수정), [ROOM-04·05 정본](../../p0/room.md), [ADR-0005](../participation/0005-room-participation-optimistic-locking.md)
- 대체 대상: 없음
- 후속 ADR: ADR-0022

## 맥락

P0가 제공하는 17개 API 중 기존 리소스를 고치는 것은 세 개다. 내 프로필 수정(`/api/users/me`), 방 수정(`/api/rooms/{roomId}`), 방 종료(`/api/rooms/{roomId}/status`)이며 모두 `PATCH`로 정의돼 있다. 그러나 왜 `PATCH`인지가 어디에도 적혀 있지 않아, 구현 중 내 프로필 수정과 방 종료 두 개를 `PUT`으로 바꾸는 변경이 실제로 작성됐다가 철회됐다. 방 수정은 이번에 함께 검토되지는 않았으나 같은 기준이 적용되는 대상이므로 이 ADR에서 함께 다룬다. 같은 논의가 반복되지 않도록 기준을 남긴다.

두 메서드의 차이는 **요청에 담기지 않은 필드를 어떻게 처리하는가**에서 갈린다. `PUT`은 "이 리소스를 지금 보내는 내용으로 바꿔라"라는 뜻이므로, 요청에 없는 필드는 비워지는 것이 원래 의미다. `PATCH`는 "이 부분만 바꿔라"이므로 보내지 않은 필드는 그대로 남는다. 그래서 `PUT`은 클라이언트가 리소스의 최종 모습 전체를 알고 있고 그것을 스스로 정할 수 있을 때 성립한다.

`PUT` 전환이 검토된 이유는 두 가지였다. 프로필 수정은 현재 바꿀 수 있는 필드가 닉네임 하나뿐이라 그 하나를 보내는 것이 곧 전체를 보내는 것으로 읽혔고, 방 종료는 결과가 항상 `FINISHED` 하나로 수렴하므로 몇 번을 보내도 같은 상태가 된다는 점에서 `PUT`의 멱등성에 부합해 보였다.

이번 결정의 기준은 다음과 같다.

- 클라이언트가 리소스 표현 전체를 스스로 결정할 수 있는가
- 수정 요청의 본문이 조회 응답의 표현과 대칭인가
- 같은 요청을 다시 보냈을 때 재시도가 실제로 안전한가
- 수정 가능한 필드가 늘어나도 공개한 계약을 바꾸지 않고 유지할 수 있는가
- 세 엔드포인트에 같은 규칙을 적용해 예외를 설명할 일을 줄일 수 있는가

| 세 엔드포인트 모두 `PATCH` | 세 곳 모두 "허용된 일부만 바꾼다"는 실제 동작과 의미가 맞는다. 수정 필드가 늘어도 계약이 그대로다. "수정은 `PATCH`" 규칙 하나로 정리돼 예외 설명이 필요 없다. | HTTP 명세가 `PATCH`의 멱등성을 보장하지 않으므로, 중간 프록시나 클라이언트 라이브러리의 자동 재시도에 기댈 수 없다. | 선택 |

| 세 엔드포인트 모두 `PUT` | 수정 API의 메서드가 하나로 통일되어 예외 설명이 필요 없다. | 방 수정은 계약이 일부 필드를 아예 거부하므로 전체 교체가 성립하지 않는다. 프로필 필드가 늘면 공개한 메서드를 되돌려야 하고, 이는 클라이언트를 깨뜨리는 변경이다. | 제외 |

## 결정

P0의 수정 API 세 개는 모두 `PATCH`를 사용한다. 엔드포인트별 근거는 다음과 같다.

`PATCH /api/users/me`는 요청 본문 `ProfileUpdateRequest`와 조회 응답 `UserSummary`의 스키마가 애초에 다르므로, 조회한 표현을 그대로 되돌려 보낸다는 `PUT`의 전제가 성립하지 않는다. 더 중요한 것은 확장이다. 프로필 사진이나 자기소개가 추가되면 `PUT`은 닉네임만 바꾸려는 클라이언트에게도 나머지 필드를 함께 보내도록 요구하고, 그러지 않으면 값이 지워진다. 그때 가서 메서드를 바꾸는 것은 이미 공개한 계약을 깨는 일이므로, 필드가 하나인 지금 `PATCH`로 두어 확장에 대비한다.

`PATCH /api/rooms/{roomId}`는 계약이 `roomType`, `region`, `status`를 **본문에 포함하기만 해도** `VALIDATION_ERROR`로 거부한다. 리소스 표현 중 클라이언트가 손댈 수 없는 부분이 명시적으로 존재하므로 전체 교체라는 개념 자체가 성립하지 않는다. "생략한 필드는 기존 값을 유지한다"는 현재 서술이 `PATCH`의 의미와 그대로 맞물린다.

`PATCH /api/rooms/{roomId}/status`는 클라이언트가 상태를 고르는 것이 아니라, `FINISHED`만을, 그것도 `status = CLOSED && now >= startsAt`일 때만 서버가 통과시키는 상태 전이다. 원하는 값을 클라이언트가 정한다는 `PUT`의 전제가 성립하지 않는다. 또한 첫 요청이 성공한 뒤 같은 요청을 반복하면 `INVALID_ROOM_STATUS_TRANSITION`이 반환되므로, `PUT`으로 표시해도 재시도가 안전해지지 않는다. 이 하위 리소스에는 조회용 `GET`도 없어 교체할 표현이 무엇인지 확인할 방법조차 없다.

앞으로 추가되는 수정 API도 같은 기준으로 판단한다. 요청 본문이 리소스 표현 전체를 담고 그 값을 클라이언트가 결정할 수 있을 때만 `PUT`을 쓰고, 그 밖에는 `PATCH`를 쓴다. 동시 수정에 대한 안전장치는 HTTP 메서드가 아니라 [ADR-0005](../participation/0005-room-participation-optimistic-locking.md)의 낙관적 잠금과 `ROOM_CONCURRENT_MODIFICATION` 응답으로 해결한다.

## 결과

- 얻는 것: 수정 API의 메서드 선택 규칙이 하나로 정리되어 엔드포인트마다 예외를 설명할 필요가 없다. 프로필과 방의 수정 가능 필드가 늘어도 공개한 계약을 바꾸지 않는다. `API.md`에 메서드 선택 근거를 산문으로 적지 않고 이 ADR을 링크해 계약 문서를 계약에만 집중시킬 수 있다.
- 감수할 비용·위험: `PATCH`는 명세상 멱등이 보장되지 않으므로 중간 계층의 자동 재시도에 기댈 수 없다. 요청 반복의 안전성은 애플리케이션이 상태 조건과 낙관적 잠금으로 직접 책임진다.
- 후속 작업: 세 엔드포인트의 컨트롤러를 `PATCH`로 구현하고, `SecurityConfig`의 CSRF·인가 대상 메서드가 계약과 일치하는지 테스트로 고정한다. 새 수정 API를 추가할 때 이 ADR의 기준을 확인한다.

## 보류 및 재검토

- 지금 하지 않는 것: JSON Patch(RFC 6902)나 JSON Merge Patch 같은 표준 패치 형식 도입, `ETag`·`If-Match` 기반 조건부 요청
- 보류 이유: P0의 수정 필드 수가 적어 일반 JSON 본문의 부분 수정으로 충분하고, 동시 수정 충돌은 낙관적 잠금으로 이미 다루고 있다.
- 다시 검토할 조건:
  - 클라이언트가 리소스 표현 전체를 소유하고 통째로 올리는 API가 생길 때
  - 네트워크가 불안정한 클라이언트에서 안전한 재시도가 요구될 때
  - 수정 필드가 많아져 부분 수정 본문만으로 의도를 표현하기 어려워질 때
