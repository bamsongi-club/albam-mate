# ADR-0006: P0 내부 식별자에 BIGINT 자동 증가 키를 사용

- 상태: 승인됨
- 작성일: 2026-07-23
- 결정일: 2026-07-24
- 관련: [ADR-0002](0002-postgresql-primary-database.md), [ERD](../../ERD.md#테이블-명세), [API 명세](../../API.md#1-공통-계약)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

Albam Mate의 P0 데이터 모델은 사용자, 게임, 방, 참가 관계를 내부 식별자로 연결한다. 이 식별자는 PostgreSQL 기본 키와 외래 키뿐 아니라 API 경로와 응답에서도 사용하므로, 엔티티와 스키마 마이그레이션을 구현하기 전에 타입과 생성 방식을 일관되게 정해야 한다.

게임 카탈로그를 논의할 때 외부 데이터의 게임 ID나 순위를 그대로 내부 기본 키로 사용하는 방식, UUID를 사용하는 방식, 내부에서 1부터 다시 번호를 부여하는 방식을 비교했다. 팀은 외부 데이터가 일부만 적재되거나 순위가 바뀌어도 내부 참조가 영향을 받지 않도록 게임의 내부 ID를 자동 증가 숫자로 두는 방향을 확인했다.

[현재 ERD](../../ERD.md#테이블-명세)는 사용자, 게임, 방, 참가 관계의 기본 키를 PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`로 정의하고, 외래 키도 참조 대상과 같은 `BIGINT`를 사용한다. [현재 API 명세](../../API.md#1-공통-계약)는 이 ID를 1부터 증가하는 양의 정수로 정의해 JSON에서는 숫자, 경로에서는 10진 정수로 전달하며 UUID를 사용하지 않는다. 이 규칙을 추가한 P0 문서 변경은 커밋 `15f5068`로 현재 브랜치 이력에 병합됐다. 이 ADR은 이미 정본 문서에 반영된 계약과 그 선택 근거를 함께 기록하며, 엔티티·마이그레이션 구현은 아직 남아 있다.

이번 결정의 기준은 다음과 같다.

- 외부 게임 데이터의 식별자·순위 변경과 내부 참조를 분리할 것
- P0 엔티티의 기본 키·외래 키와 API 식별자 타입을 일관되게 유지할 것
- 단일 PostgreSQL 데이터베이스에서 필요한 범위보다 복잡한 분산 식별자 생성을 도입하지 않을 것
- 향후 외부 데이터 출처나 공개 식별자가 추가되더라도 내부 기본 키를 그대로 노출 계약으로 고정하지 않을 것
- 식별자의 추측 난이도를 인증·인가 수단으로 사용하지 않을 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| P0의 모든 내부 기본 키에 `BIGINT` 자동 증가 사용 | PostgreSQL과 JPA에서 단순하게 생성할 수 있고 기본 키·외래 키·API 타입을 일관되게 유지한다. 외부 게임 데이터의 식별자와 내부 참조를 분리할 수 있다. | 중앙 데이터베이스가 식별자를 생성하므로 데이터베이스 밖에서 미리 ID를 만들 수 없다. 값이 예측 가능하며, 향후 여러 데이터베이스의 데이터를 병합할 때 충돌 처리가 필요하다. | 선택 |

| 게임은 자동 증가, 나머지는 UUID로 혼합 | 게임에 관한 회의 결론만 좁게 반영할 수 있다. | 엔티티마다 기본 키·외래 키·API 타입이 달라지지만 이를 정당화할 현재 요구가 없다. | 제외 |

## 결정

Albam Mate P0의 사용자, 게임, 방, 참가 관계 내부 기본 키는 PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`로 통일한다. JPA 엔티티에서는 `Long`과 `GenerationType.IDENTITY`로 매핑하고, API에서는 1부터 증가하는 양의 정수를 JSON 숫자 또는 10진 경로 값으로 전달한다. 외래 키는 참조 대상과 같은 `BIGINT`를 사용하며 자동 증가시키지 않는다. P0에서는 UUID를 내부 기본 키로 사용하지 않는다.

외부 게임 데이터의 식별자와 순위는 내부 `GAMES.id`로 사용하지 않는다. 외부 식별자를 보존할 필요가 확인되면 출처와 함께 별도 컬럼으로 저장하되, 그 출처·유일성·갱신 규칙은 카탈로그 적재 전략에서 별도로 결정한다.

자동 증가 ID는 추측할 수 있으므로 리소스 접근 권한을 보장하지 않는다. 모든 조회·변경 API는 식별자 값과 무관하게 인증과 소유·참가 관계를 검사해야 한다.

## 결과

- 얻는 것: P0 엔티티의 기본 키·외래 키와 API 식별자 표현을 하나의 숫자 타입으로 맞추고, 외부 게임 데이터와 내부 참조를 분리한다.
- 감수할 비용·위험: 데이터베이스 저장 전에 최종 ID를 확정하기 어렵고, 순차 값이 노출된다. 대규모 분산 쓰기나 여러 데이터베이스 병합이 필요해지면 현재 방식의 확장 비용이 생긴다.
- 후속 작업: 실제 엔티티와 Flyway 스키마 마이그레이션에 같은 타입·생성 전략을 적용한다. 통합 테스트는 기본 키 생성과 외래 키 타입을 확인하고, 권한 테스트는 순차 ID를 알고 있어도 권한 없는 리소스에 접근할 수 없음을 검증한다.

## 보류 및 재검토

- 지금 하지 않는 것:
  - 외부 게임 ID·순위의 저장 컬럼과 유일성 규칙 확정
  - 공개용 별도 불투명 식별자 도입
  - 분산 ID 생성기 도입
- 보류 이유: 외부 데이터의 정확한 출처·갱신 정책이 확정되지 않았고, P0는 단일 PostgreSQL 데이터베이스를 사용하며 분산 생성 요구가 없다.
- 다시 검토할 조건:
  - 여러 데이터베이스나 서비스에서 독립적으로 데이터를 생성·병합해야 할 때
  - 데이터베이스 저장 전에 전역 ID가 필요할 때
  - 외부 카탈로그를 여러 출처에서 동기화할 때
  - 내부 순차 ID와 분리된 안정적인 공개 식별자가 필요할 때

## 검증

- 상태: 검증됨
- 근거:
    - 구현:
        - `V1__create_p0_schema.sql`은 `users`·`games`·`rooms`·`participations` 기본 키를 identity `BIGINT`, 외래 키를 자동 증가 없는 `BIGINT`로 정의한다.
        - 관련 엔티티는 `Long`·`GenerationType.IDENTITY`를 사용하고, 외부 BGG ID는 유일한 `games.bgg_id`로 분리하며 API 경로 ID는 `@Positive`로 검증한다.
    - 테스트:
        - `SchemaValidationPostgresTest`는 PostgreSQL 18에서 `ddl-auto=validate`와 참가자·방 외래 키 위반 거절을 확인한다.
        - 순차 ID를 알고 있어도 권한이 없으면 접근할 수 없음은 `RoomUpdateServiceTest`, `RoomUpdateExecutorTest`, `RoomParticipationCancelExecutorTest`의 주최자·참가자 권한 실패 경로에서 확인한다.

> 상태 값과 번호·대체 규칙은 [루트 README](../README.md)를 따른다.
