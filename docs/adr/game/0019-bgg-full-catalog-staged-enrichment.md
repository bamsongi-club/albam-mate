# ADR-0019: BGG 전체 카탈로그는 적재하고 상세 정보는 단계적으로 보강

- 상태: 제안됨
- 작성일: 2026-07-28
- 결정일: 미정
- 관련: [제품 후속 기능 후보](../../PRD.md#후속-기능-후보-도입-차수-미정), [ERD GAMES](../../ERD.md#games), [게임 목록·검색 API](../../API.md#game-01-게임-목록검색), [ADR-0015](0015-bgg-baseline-team-collected-game-list.md), [ADR-0018](0018-expansion-type-and-relations.md)
- 대체 대상: 없음
- 후속 ADR: 없음

> 이 문서는 팀 논의를 위한 제안이다. 승인 전에는 구현 정본으로 사용하지 않는다.

## 맥락

P0에는 팀이 검수한 게임 2,000건이 있다. 이름·이미지·가능 인원·설명까지 갖춰 화면에 보여 주기 좋지만, 목록에 없는 게임은 검색하거나 방에서 선택할 수 없다.

2026-07-23 BGG 스냅샷에는 179,329행이 있다. 이 목록에는 본판뿐 아니라 확장판과 순위가 없는 항목도 포함된다. 스냅샷마다 행 수가 달라지므로 `17만 건`이라는 고정 숫자 대신 **팀이 승인한 한 스냅샷의 모든 유효 행**을 전체 적재 기준으로 삼아야 한다.

전체 약 17만 9천 건의 상세 정보·한국어 설명·검색 임베딩을 한 번에 준비하면 기본 검색 제공이 늦어지고, 수집 시간·번역 비용·검수 범위를 확인하기도 전에 큰 배치를 운영하게 된다. 반대로 현재 2,000건만 유지하면 서비스의 게임 검색 범위가 넓어지지 않는다.

비상업적 애플리케이션으로 제출한 BGG XML API 사용 신청은 2026-07-28 승인됐다. 공개 앱에는 `Powered by BGG` 로고를 표시해야 한다. 다만 승인 메시지에는 BGG 데이터를 기계 번역하거나 AI·LLM에 입력해 임베딩을 만드는 예외가 명시되어 있지 않다. BGG 표준 이용 조건에는 데이터 수정과 AI·LLM 사용을 제한하는 문구가 있으므로, 이 작업은 별도 서면 확인이 필요하다.

이번 제안의 판단 기준은 다음과 같다.

- 전체 유효 게임은 이름으로 검색할 수 있을 것
- 상세 보강은 작은 배치에서 검증한 뒤 단계적으로 확대할 것
- 현재 2,000건과 전체 목록이 같은 `bgg_id`와 내부 게임 ID를 사용할 것
- 원본, 정규화 값, 번역문과 임베딩의 출처를 구분할 것
- BGG 순위·평점을 Albam Mate 사용자 리뷰와 섞지 않을 것
- 잘못되거나 허용 범위가 불명확한 입력은 다음 단계로 보내지 않을 것

## 한눈에 보는 범위

~~~text
BGG 승인 스냅샷 약 17만 9천 건
        │ 원본 보존·검증
        ▼
전체 BASIC 카탈로그 ─────────────── 이름·키워드 검색
        │
        ├─ 현재 2,000건 ─────────── 보강 파이프라인 시범 검증
        │
        └─ 서면 허용 확인 + 시범 검증 통과
                    ▼
              우선 10,000건 보강
                    │ 품질·비용·성능 지표 통과
                    ▼
              최대 30,000건으로 확대

허용된 텍스트 ── 번역·임베딩 ── 의미 검색용 파생 인덱스
Albam Mate 활동 ───────────────── 사용자 리뷰
~~~

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 검수된 2,000건만 운영 | 현재 스키마와 품질을 그대로 유지할 수 있다. | 목록 밖 게임을 검색·선택할 수 없고 새 파이프라인의 확장성을 검증하지 못한다. | 제외 |
| 처음부터 30,000건을 상세 보강 | 넓은 범위를 한 번에 제공할 수 있다. | API 수집·번역·검색 품질과 비용을 모르는 상태에서 실패 비용이 커진다. | 제외 |
| 약 17만 9천 건을 모두 상세 보강 | 전체 게임에 같은 수준의 정보를 제공할 수 있다. | 이용 조건, 호출 시간, 번역 비용과 검수량이 가장 크며 사용되지 않는 항목에도 같은 비용을 쓴다. | 제외 |
| 전체는 기본 적재하고 2천→1만→3만 건으로 보강 | 전체 이름 검색을 먼저 제공하면서 실제 지표로 보강 범위를 확대할 수 있다. | `BASIC`과 보강 데이터의 차이를 API와 화면에서 처리해야 한다. | 선택 |

## 결정

아래 방식을 팀 논의안으로 제안한다.

### 1. 전체 유효 행을 `BASIC` 카탈로그로 적재한다

팀이 기준으로 승인한 단일 BGG 스냅샷의 모든 유효 행을 `GAMES`에 적재한다. 유효 행은 다음 조건을 만족해야 한다.

- `bgg_id`로 변환할 수 있는 양의 정수 ID가 있다.
- BGG 원문 게임명이 비어 있지 않다.
- CSV 구조와 필드 형식을 해석할 수 있다.
- 같은 배치 안에 중복 `bgg_id`가 없다.

순위가 없거나 사용자 평가가 적다는 이유만으로 제외하지 않는다. 형식 오류나 중복처럼 자동으로 확정할 수 없는 행은 임의로 고치지 않고, 제외 목록에 식별자와 이유를 남긴다.

`전체 적재`는 모든 유효 게임 행을 카탈로그에 넣는다는 뜻이다. BGG CSV의 모든 열을 그대로 `GAMES`에 복사하거나 모든 항목을 상세 보강한다는 뜻은 아니다.

### 2. 상세 보강은 `2천 → 1만 → 3만` 단계로 확대한다

| 단계 | 범위 | 목적 | 다음 단계 조건 |
| --- | ---: | --- | --- |
| 시범 검증 | 현재 검수 2,000건 | 수집·병합을 먼저 검증하고, 서면 허용 후 한국어화·검색 인덱스의 정확성, 시간과 비용을 확인 | 서면 허용 확인, 품질 보고서 승인 |
| 1차 운영 | 서로 다른 `bgg_id` 최대 10,000건 | 운영 가능한 규모에서 상세 정보와 의미 검색을 제공 | 합의한 품질·비용·성능 지표 통과 |
| 확대 운영 | 서로 다른 `bgg_id` 최대 30,000건 | 1차 운영에서 확인된 방식으로 검색 범위 확대 | 별도 배치 승인 |

1차 운영 대상은 현재 2,000건을 유지하고, 기준 스냅샷의 BGG 순위 상위권 게임을 우선해 중복 없는 총 10,000건을 채운다. 확대 운영도 같은 원칙으로 총 30,000건까지 늘린다. 순위가 없는 항목이나 제품상 필요한 예외를 포함할 경우 정확한 `bgg_id`와 이유를 manifest에 기록한다.

여기서 BGG 순위는 **배치 대상을 고르는 운영 기준**일 뿐 Albam Mate의 추천이나 평점이 아니다. 어떤 시점의 순위를 사용했는지 스냅샷과 체크섬을 함께 남긴다.

30,000건 확대 전에 최소한 다음 항목을 측정한다.

- XML API 수집 성공률, 재시도량과 총 소요 시간
- 누락·중복·출처 충돌과 필드 완전성
- 허용된 경우 한국어화 품질, 검수량과 건당 비용
- 대표 검색 질의의 결과 품질과 p95 응답 시간
- 임베딩 인덱스 생성 시간, 크기와 재생성 가능 여부

통과 수치는 구현 전에 별도 실험 계획에서 합의하고, 결과 보고서를 팀이 승인하기 전에는 30,000건으로 확대하지 않는다.

### 3. 기본 정보와 보강 정보를 구분한다

`GAMES`에는 다음 값을 갖는 필수 `enrichment_status`를 둔다.

- `BASIC`: 검색과 식별에 필요한 기본 정보만 검증됨
- `ENRICHED`: 해당 운영 단계가 요구하는 보강 필드와 수용한 품질 경고까지 검수됨

현재 2,000건은 별도 게임 목록으로 복제하지 않는다. 전체 스냅샷에서 같은 `bgg_id` 행을 찾은 뒤 검수된 표시값을 연결하고 `ENRICHED`로 바꾼다. 나머지는 `BASIC`으로 둔다.

`BASIC` 행에 없는 한국어 표시명·별칭·이미지·가능 인원·태그·예상 시간·난이도·설명은 `NULL`로 유지한다. 빈 문자열, `정보 없음`, 게임명을 끼워 넣은 반복 설명 같은 가짜 값을 저장하지 않는다.

### 4. 표시 필드와 다중 분류를 분리한다

전체 카탈로그 전환 시 다음 필드를 `GAMES` 보강 후보로 둔다.

| 필드 | 제안 타입 | 용도와 경계 |
| --- | --- | --- |
| `year_published` | `INTEGER NULL` | 원작 게임의 출시 연도 표시·정렬·필터. 판본별 출시 연도가 필요해지면 게임 공통 연도와 판본 연도를 분리한다. |
| `thumbnail_url` | `VARCHAR(500) NULL` | 목록 화면용 저용량 이미지. BGG 이미지의 표시·캐시·재호스팅 허용 범위를 확인한 뒤 적재한다. |

기존 `GAMES.tag VARCHAR(30)`과 API의 `tag`는 P0 목록 카드에 표시하는 **대표 스타일 태그 하나**로 유지한다. 여러 카테고리·메커니즘을 쉼표 문자열에 합치거나 `VARCHAR[]`·`JSONB`에 넣어 같은 필드의 의미를 바꾸지 않는다.

다중 카테고리·메커니즘이 검색·필터 범위에 들어오면 통제된 분류 항목과 게임의 다대다 매핑으로 분리하고, 각 항목에 종류와 출처를 기록한다. 물리 테이블명, 외부 식별자와 유일성 제약은 팀 승인 후 ERD·API·Flyway 변경에서 확정한다. 이렇게 하면 같은 이름의 중복 표기와 쉼표 파싱을 피하고, BGG 분류와 Albam Mate가 작성한 분류를 구분할 수 있다.

### 5. 원본과 파생 데이터를 분리해 재가공한다

| 단계 | 하는 일 | 결과 |
| --- | --- | --- |
| 원본 보존 | 파일·XML 응답을 수정하지 않고 출처·취득 시각·행 수·SHA-256을 기록 | 다시 검증할 수 있는 기준 스냅샷 |
| 기본 정규화 | ID·이름·숫자·빈 값을 검증하고 검색용 값을 별도로 생성 | 전체 `BASIC` 카탈로그 |
| 플레이 가능성 변환 | `is_expansion`을 [ADR-0018](0018-expansion-type-and-relations.md)의 `playability_type` 초기값으로 변환 | 방의 중심 게임 선택 기준 |
| 상세 병합 | 허용된 XML API 상세값과 현재 2,000건을 `bgg_id`로 연결 | 출처가 있는 보강 필드 |
| 관계 병합 | 출처가 확인된 본판–확장판 연결만 반영 | `GAME_EXPANSIONS` 입력 |
| 한국어화·임베딩 | 허용된 텍스트만 별도 버전의 파생 데이터로 생성 | 한국어 표시값과 의미 검색 인덱스 |
| 품질 검증 | 포함·제외 ID, 중복, 출처, 승인 경고와 결과 체크섬을 확인 | 품질 보고서와 적재 가능 여부 |

원문을 번역문이나 정규화 값으로 덮어쓰지 않는다. 파생 데이터에는 최소한 `source_hash`, 공급자, 모델·규칙 버전, 생성 시각과 검수 상태를 기록한다. 원문이나 모델이 바뀌면 새 버전을 만들고 기존 결과를 조용히 덮어쓰지 않는다.

### 6. BGG 원문의 한국어화·임베딩은 서면 허용 후 진행한다

기술적으로 가능하다는 사실과 이용이 허용되었다는 사실은 구분한다. 현재 승인 메시지만으로는 다음 사용이 허용됐다고 단정하지 않는다.

- BGG 원문 설명을 기계 번역하는 행위
- BGG 데이터를 DeepL·OpenAI 등 외부 처리자에게 보내는 행위
- BGG 데이터를 임베딩 모델에 입력하고 벡터를 저장·검색하는 행위
- 번역문이나 다른 파생 결과를 공개 서비스에 표시하는 행위

BGG에서 위 범위를 명시적으로 허용한 서면 근거를 확인하기 전에는 BGG 원문을 한국어화·임베딩 단계에 입력하지 않는다. 허용되지 않는 경우에는 팀이 직접 작성했거나 별도 라이선스를 확보한 텍스트만 한국어화·임베딩하고, BGG 데이터는 해당 AI 처리의 입력에서 제외한다.

번역 공급자와 모델, 사람 검수 범위, 임베딩 모델, 벡터 저장소는 이 ADR에서 선택하지 않는다. 현재 PostgreSQL과 함께 운영할 수 있는 `pgvector`를 첫 측정 후보로 둘 수 있지만, 동일 데이터의 검색 품질·응답 시간·비용을 비교한 뒤 별도 ADR로 결정한다.

### 7. 전체 검색, 의미 검색과 리뷰의 경계를 나눈다

- 이름·키워드 검색은 `BASIC`과 `ENRICHED` 전체를 대상으로 한다.
- 의미 검색은 허용된 입력으로 임베딩을 생성한 `ENRICHED` 게임만 대상으로 하며, 결과가 없을 때도 이름 검색은 가능해야 한다.
- 벡터 저장소는 PostgreSQL의 게임 정본을 대신하지 않는, 삭제 후 재생성 가능한 파생 인덱스로 둔다.
- `GAMES`에 특정 모델 차원을 전제로 한 `embedding vector(1536)`을 직접 추가하지 않는다. PostgreSQL을 선택하면 `game_id`, 입력 `source_hash`, 모델 식별자, 차원, 생성 시각과 벡터를 갖는 검색 전용 테이블을 두고, 외부 벡터 저장소를 선택하면 같은 내부 `game_id`로 연결한다.
- BGG 평균 평점은 허용된 원본 스냅샷의 재현성을 위해 원본에만 보존하고 Albam Mate 사용자 리뷰의 평점처럼 사용하지 않는다.
- 현재 범위에서는 별도의 자체 지수나 종합 점수를 계산하지 않고 사용자 리뷰만 관리한다. 리뷰의 필드와 노출 방식은 제품 명세에서 정한다.

### 8. 기존 P0 변환기와 새 배치를 분리하고 실패 시 적재하지 않는다

현재 `prepare-game-catalog.mjs`는 팀이 준비한 2,000건 JSON을 BGG 스냅샷과 대조하고, 모든 P0 표시 필드가 있을 때만 `service-catalog.json`과 `upsert-games.sql`을 만든다. 전체 스냅샷을 직접 기본 카탈로그로 바꾸는 도구가 아니므로 그대로 재사용하지 않는다.

전체 카탈로그·단계별 보강 배치는 별도 입력·출력 계약으로 만든다. manifest가 없거나 승인되지 않았거나, 입력 체크섬이 다르거나, 중복·필수값 오류와 승인하지 않은 경고가 있으면 품질 보고서만 만들고 적재 산출물은 만들지 않는다.

검증을 통과한 배치는 `bgg_id` 기준으로 `UPSERT`한다. 기존 `GAMES.id`와 팀 검수값을 유지하고, 새 스냅샷에 없다는 이유만으로 기존 게임을 삭제하지 않는다. 한 행이라도 적재에 실패하면 전체 반영을 롤백한다.

초기 적재와 이후 갱신은 같은 검증 절차를 사용한다. 갱신 주기는 API 운영 측정 후 정하되, 각 배치는 독립된 스냅샷·manifest·품질 보고서를 남긴다.

## 결과

- 얻는 것: 약 17만 9천 건의 이름 검색을 먼저 제공하면서 현재 2,000건의 검수값을 유지하고, 1만 건에서 실제 운영성을 검증한 뒤 3만 건으로 안전하게 넓힐 수 있다.
- 감수할 비용·위험: `BASIC` 게임은 상세 화면이 단순하고, API와 화면이 누락값을 처리해야 한다. 권리 확인이 끝날 때까지 BGG 원문 기반 한국어화·의미 검색 일정도 확정할 수 없다.
- 후속 작업: 팀 승인 후 ERD·API 계약, 2,000건 시범 검증의 통과 지표, BGG 서면 확인, 배치 구현 순으로 진행한다. 번역·임베딩 기술 선택은 별도 ADR에서 결정한다.

## 보류 및 재검토

- 지금 하지 않는 것: P0 계약의 즉시 변경, 실행 중 사용자 요청에서 BGG 직접 호출, 약 17만 9천 건 전체 상세 보강, 자동 갱신 주기 확정, 번역·임베딩 공급자 확정, 벡터 저장소 확정, 별도의 자체 지수·종합 점수 도입
- 보류 이유: 이번 제안은 전체 카탈로그와 보강 범위의 경계를 정한다. 권리 조건과 2,000건 시범 검증 측정값 없이 세부 기술과 30,000건 운영을 확정할 근거가 없다.
- 다시 검토할 조건: BGG의 서면 답변을 받았을 때, 2,000건 시범 검증 또는 10,000건 운영 지표가 목표를 통과하지 못했을 때, BGG 외 원천을 병합할 때, 삭제·비공개 정책이나 이용 조건이 바뀔 때
