# ADR-0019: 전체 보드게임 카탈로그는 BASIC으로 확장하고 상세 정보는 단계적으로 보강

- 상태: 제안됨
- 작성일: 2026-07-28
- 결정일: 미정
- 관련: [제품 후속 기능 후보](../../PRD.md#후속-기능-후보-도입-차수-미정), [ERD GAMES](../../ERD.md#games), [게임 목록·검색 API](../../API.md#game-01-게임-목록검색), [ADR-0015](0015-bgg-baseline-team-collected-game-list.md), [ADR-0018](0018-expansion-type-and-relations.md)
- 대체 대상: 없음
- 후속 ADR: 없음

> 이 문서는 팀 논의를 위한 제안이다. 승인 전에는 구현 정본으로 사용하지 않는다.

## 맥락

P0에는 현재 2,000건의 게임 자료가 있다. 먼저 이 범위를 상세 데이터로 제공한 뒤, 사용자가 원하는 게임을 찾지 못하는 문제를 줄이기 위해 전체 유효 보드게임을 식별 가능한 `BASIC` 목록으로 넓히고 싶다. 상세 정보는 인기, 국내 유통 여부와 사용자 요청을 기준으로 우선순위를 정해 단계적으로 보강한다.

여기서 확정하는 수량은 현재 2,000건뿐이다. 이후 10,000건·30,000건 같은 고정 목표를 미리 약속하지 않고, 배치마다 품질·수집 시간·운영 비용을 측정해 다음 범위를 정한다. 2026-07-23 BGG 스냅샷의 179,329행은 입력 후보의 규모를 보여 주는 측정값이지 제품 계약의 고정 건수가 아니다.

현재 2,000건은 팀원이 BGG 데이터를 가공해 만든 자료다. JSON 파일로 재가공했다는 이유만으로 팀의 독립 창작 데이터가 되지는 않는다. 기존 검수 결과는 유지하되, 각 필드가 BGG 원본인지, 공식 국내 유통 자료인지, 팀이 독립 작성한 값인지 다시 확인하기 전에는 전체 자료를 독립 데이터로 단정하거나 자동으로 상세 완료 처리하지 않는다.

2026-07-28 팀이 보관한 BGG 승인 메일을 확인한 결과 다음 범위는 명시되어 있다.

- 비상업적 애플리케이션으로 제출한 BGG XML API 사용 신청이 승인됐다.
- 공개 앱에는 `Powered by BGG` 로고를 표시해야 한다.
- 비상업적 신청에는 현재 수수료가 없으며 정책이 바뀌면 알린다고 안내한다.

반면 그 메일은 번역·요약·AI/LLM 입력, 커뮤니티 투표의 재가공·결합, 이미지 다운로드·변환·재호스팅, 광고·유료 기능 등 상업적 운영을 별도로 허용하지 않는다. BGG XML API 이용 조건도 비상업적 재현·표시와 출처 표기를 전제로 하고 데이터 수정 및 AI/LLM 사용을 제한한다. 따라서 기술적으로 가능한 수집과 이용이 허용된 가공을 구분해야 한다.

우리 서비스의 수익 모델은 아직 미정이므로 비영리 서비스라고 고정하지 않는다. 광고, 유료 기능, 후원·제휴처럼 상업적 운영을 시작하기 전에는 BGG에 변경된 사용 목적과 범위를 다시 확인한다.

이번 제안의 판단 기준은 다음과 같다.

- 보드게임과 보드게임 확장 자료만 다루고 액세서리·비디오게임·RPG 등은 제외할 것
- 서비스 실행 중 외부 API를 호출하지 않고 우리 DB와 API로 응답할 것
- BGG 원본 파이프라인과 독립 출처 수집 파이프라인을 분리할 것
- 현재 2,000건부터 제공하고 이후 범위는 측정값으로 정할 것
- 유용한 일부 필드만 있어도 제공하되 없는 값은 `NULL`로 표현할 것
- 필드마다 출처·수집 방식·이용 근거와 검증 상태를 추적할 것
- 모든 행을 자동 검증하고 작은 무작위 표본만 사람이 확인할 것
- 허용 범위나 품질이 불명확한 배치는 공개·적재하지 않을 것

## 결정

아래 방식을 팀 논의안으로 제안한다.

### 1. 현재 2,000건만 수량으로 확정한다

현재 2,000건을 첫 상세 제공 대상으로 삼는다. 다만 팀원이 BGG 데이터를 가공해 만든 자료인데 기존 source manifest는 전체를 팀 자체 작성 자료로 표현하므로, manifest 승인 상태를 provenance 재검증 대기로 전환한다. 필드별 실제 출처와 이용 근거를 정정해 다시 승인하기 전에는 기존 2,000건을 적재 가능한 입력으로 사용하지 않는다.

그다음 단계의 목표는 승인된 한 원본 스냅샷에서 보드게임과 보드게임 확장으로 확인된 모든 유효 항목을 `BASIC`으로 확장하는 것이다. `bgg_id`와 BGG 원문 이름을 핵심 식별 정보로 사용하되, BGG 이용 조건상 허용된 원본 재현 범위 안에서만 저장·표시한다. 형식 오류, 중복 ID, 제외 대상 유형은 식별자와 이유를 manifest에 남긴다.

상세 보강 우선순위는 다음과 같다.

1. 서비스 수요가 높은 인기 게임
2. 공식 한국어판 등 국내 유통이 확인된 게임
3. 사용자가 상세 보강을 요청한 게임

우선순위는 배치 대상을 고르는 운영 기준이며 서비스 추천 점수로 사용하지 않는다. 다음 배치 건수는 이전 배치의 자동 검증 결과, 표본 오류율, 수집 시간, 저장·AI 처리 비용과 운영 성능을 측정한 뒤 팀이 정한다.

### 2. 상세 상태를 세 단계로 구분한다

게임별 카탈로그 상세 상태로 다음 값을 갖는 `enrichment_status`를 관리하는 안을 제안한다.

- `BASIC`: ID, 원문 이름과 출처처럼 식별에 필요한 최소 필드만 허용·검증됨
- `PARTIAL`: 상세 필드 중 일부만 허용·검증됨
- `ENRICHED`: 버전이 지정된 상세 프로필의 필수 필드가 모두 허용·검증됨

`ENRICHED`는 버전이 지정된 상세 프로필을 만족한 상태다. 각 게임의 상세 상태에는 해당 상태를 판정한 프로필 버전 또는 이를 식별할 수 있는 검증 배치를 연결한다. 현재 프로필과 검증 당시 프로필이 다르면 현재 기준의 `ENRICHED`로 취급하지 않고 재검증 대상으로 관리한다. 물리적인 저장 위치는 이 제안이 승인된 뒤 ERD와 적재 계약에서 결정한다.

상태는 방 생성 가능 여부와 무관하다. 방의 중심 게임으로 선택할 수 있는지는 [ADR-0018](0018-expansion-type-and-relations.md)의 `playability_type`으로 별도 판단한다.

첫 상세 프로필 후보는 다음과 같다.

| 정보 | 저장 원칙 |
| --- | --- |
| 식별자 | 내부 ID와 `bgg_id`를 분리하고 출처를 기록 |
| 이름 | BGG 원문 이름을 보존하고, 공식 한국어 이름은 허용된 국내 공식 출처로 별도 저장 |
| 가능 인원 | `min_players`, `max_players` 숫자로 저장하고 출처를 기록 |
| 단독 플레이 가능성 | `playability_type`과 판단 근거를 분리 |
| 이미지 | 원본·썸네일 URL, 제공자와 표시 조건을 기록 |
| 난이도 | BGG Weight 원본과 Albam Mate 자체 난이도를 분리 |
| 출처 | 필드별 URL·수집 시각·수집 방식·이용 근거·검증 상태를 기록 |

설명, 대표 태그, 다중 카테고리·메커니즘, 예상 시간, 추천 인원과 최적 인원은 이후 보강 범위로 둔다. 값이 없으면 `NULL`로 유지한다. 빈 문자열, `정보 없음`, 이름을 반복한 설명 같은 가짜 값을 채우지 않는다.

### 3. BGG는 오프라인 원본 파이프라인으로만 처리한다

- XML·파일 응답은 서비스 요청과 분리된 배치에서 수집한다.
- 원본은 수정하지 않고 출처, 취득 시각, 요청 범위, 행 수와 SHA-256을 기록한다.
- BGG 입력은 명시적인 규칙을 가진 결정적 파서로 처리하고 AI·LLM에 보내지 않는다.
- 공개 서비스는 Albam Mate DB와 자체 API로만 응답하며 프런트엔드나 요청 처리 중 BGG API를 호출하지 않는다.
- BGG 평균 평점·Weight·커뮤니티 투표는 Albam Mate 값과 섞지 않고 출처가 표시된 원본 계열로 분리한다.

현재 확인된 범위에서는 허용된 BGG 원본을 변경 없이 재현·표시하는 처리만 한다. 다음 작업은 BGG의 명시적인 서면 허용이나 적용 가능한 이용 조건을 확인하기 전에는 하지 않는다.

- 이름·설명·분류의 정규화, 번역, 요약 또는 재작성
- BGG 값으로 `playability_type` 등 새로운 분류를 파생하는 작업
- 검색용 키워드·추천 점수·난이도·임베딩 같은 파생값 생성
- BGG 데이터를 AI·LLM이나 외부 번역·임베딩 처리자에게 전송
- BGG 커뮤니티 투표를 Albam Mate 사용자 투표와 합산·재계산

허용 범위가 확인되면 적용할 필드, 변환 방식, 공개 범위와 상업적 사용 가능 여부를 근거 문서의 버전과 함께 source policy에 추가한다. 단순 정규화도 데이터 변경에 해당할 수 있으므로 예외로 간주하지 않는다.

### 4. 독립 출처는 허용 목록과 필드별 출처를 전제로 수집한다

첫 허용 목록은 공식 제작사, 공식 한국 유통사와 공개 규칙서로 제한한다. 블로그·커뮤니티·리뷰 사이트는 각 사이트의 이용 조건과 재사용 허용 범위를 확인하는 후속 단계로 미룬다.

출처별 policy registry에는 최소한 다음을 기록한다.

- 도메인과 허용 경로
- 이용 조건·라이선스와 확인 날짜
- 자동 수집, AI 처리, 공개 재사용과 상업적 사용 가능 여부
- 허용 필드와 금지 필드
- `robots.txt` 규칙과 호출 속도
- 담당자와 근거 문서

`robots.txt`는 자동 수집기가 접근해도 되는 경로를 알리는 규칙이지, 콘텐츠를 번역·재배포하거나 AI로 처리할 권한을 부여하는 라이선스가 아니다. 두 조건을 모두 통과한 출처만 수집한다.

허용된 출처에서 AI가 추출한 결과는 즉시 서비스 값으로 쓰지 않고 공개 전 후보로 저장한다. 숫자 범위, URL, 필수값, 출처 연결과 교차 출처 충돌을 전체 행에 대해 자동 검증한다. 이 검사는 데이터 무결성과 근거 연결을 확인할 뿐 추출값이 원문의 의미와 일치함을 증명하지 않는다. 근거가 없거나 출처가 충돌하면 추측으로 합치지 않고 격리한다. 설명 문장과 이미지는 사실 필드보다 저작권 영향이 크므로 명시적인 사용 근거가 있을 때만 공개한다.

각 공개 필드에는 최소한 다음 provenance를 연결한다.

- 내부 게임 ID와 필드명
- 원본 URL·문서 식별자와 출처 종류
- 원문 내 페이지·절·구문 등 값을 재확인할 수 있는 근거 위치
- 수집 시각과 수집기·모델·규칙 버전
- 원문 해시 또는 재현 가능한 참조
- 이용 근거와 검증 상태

### 5. 추천·최적 인원은 가능 인원과 분리해 나중에 도입한다

현재 확정하는 인원 정보는 `min_players`, `max_players`로 표현하는 가능 인원뿐이다.

추천 인원과 최적 인원은 이후 다음 원칙으로 도입한다.

- BGG 커뮤니티 투표 원본과 Albam Mate 사용자 투표를 별도 테이블·집계로 보존한다.
- BGG 투표의 재사용·재가공 허용 범위를 먼저 확인한다.
- 인원별 투표 수와 표본 수를 보존하고 표시 문자열 하나로 저장하지 않는다.
- 두 출처를 합친 값을 만들 경우 계산식, 최소 표본, 가중치와 버전을 별도 결정으로 공개한다.
- 어느 한쪽의 투표를 다른 서비스의 사용자 투표처럼 표시하지 않는다.

따라서 지금은 추천·최적 인원 계산식이나 API 계약을 확정하지 않는다.

### 6. BGG Weight와 Albam Mate 난이도를 분리한다

BGG Weight를 허용 범위 안에서 저장·표시할 때는 평균값뿐 아니라 투표 수, 수집 시각과 원본 출처를 함께 보존한다. 값을 번역하거나 자체 난이도로 이름만 바꾸지 않는다.

Albam Mate 자체 난이도는 다음 두 축으로 나누는 안을 팀 논의 제안으로 둔다.

- `규칙 난이도`: 플레이어가 규칙을 이해하고 의사결정을 수행하기 어려운 정도
- `룰마 난이도`: 룰마가 게임을 준비·설명·진행하고 예외 상황을 처리하기 어려운 정도

`룰마 난이도`의 첫 계산 후보는 각 항목을 1~5점으로 평가한 산술평균이다.

~~~text
룰마 난이도 = (세팅 부담 + 설명 부담 + 진행 관리 부담 + 예외 처리 부담) / 4
~~~

필터에서는 두 축을 하나의 종합 점수로 섞지 않고 각각 선택하게 한다. 예를 들어 사용자가 `룰마 난이도 2 이하`를 고르면 해당 축이 2 이하인 게임만 찾는다. BGG Weight도 별도 출처 필터로만 제공한다.

평가 주체, 각 점수의 판정 기준, 표본 수와 갱신 방식은 아직 확정하지 않는다. 이 계산식은 팀 토론용 후보이며 P0 스키마·API·필터의 정본이 아니다. 난이도는 안내·검색 정보일 뿐 방 생성 허용 여부를 결정하지 않는다.

### 7. 이미지는 직접 표시와 재호스팅을 구분한다

현재는 BGG API가 제공한 이미지·썸네일 URL을 출처 표기와 `Powered by BGG` 요구사항을 지켜 직접 표시하는 안만 채택한다. 원본 제공자와 수집 시각을 함께 기록한다.

이미지를 다운로드해 우리 저장소나 CDN에 올리거나, 크롭·리사이즈·포맷 변환하는 재호스팅은 다음 장점이 있다.

- 목록 성능과 캐시 정책을 직접 통제할 수 있다.
- 외부 URL 변경과 장애의 영향을 줄일 수 있다.

반면 저장·전송 비용, 원본 갱신·삭제 반영 책임과 별도의 복제·변형 권한 확인이 필요하다. 현재 승인 메일에는 이 범위가 명시되지 않았으므로 서면 확인 전에는 다운로드·변환·재호스팅하지 않는다.

### 8. 카테고리·설명·임베딩은 후속 보강으로 둔다

기존 `GAMES.tag VARCHAR(30)`과 P0 API의 `tag`는 대표 스타일 태그 하나라는 의미를 유지한다. 여러 카테고리·메커니즘을 쉼표 문자열, 배열이나 JSONB로 섞어 의미를 바꾸지 않는다. 검색·필터가 필요해지면 통제된 분류 항목과 게임의 다대다 매핑으로 분리하고 항목별 출처를 기록한다.

설명과 임베딩은 이용이 허용된 독립 작성·라이선스 확보 텍스트만 입력으로 삼는다. 임베딩은 게임 정본이 아니라 삭제 후 재생성할 수 있는 검색 인덱스로 두고, `game_id`, 입력 해시, 모델 식별자, 차원과 생성 시각을 보존한다. 저장소와 모델 선택은 품질·응답 시간·비용을 측정한 뒤 별도 결정으로 확정한다.

`year_published`와 `thumbnail_url`은 상세 보강 후보로 유지한다. 출시 연도는 출처별 원작·판본 의미를 구분하고, 썸네일은 이미지 이용 범위를 통과한 URL만 저장한다.

### 9. 전체 무결성 검증과 무작위 표본 검사로 공개 게이트를 운영한다

사람이 모든 게임을 개별 검수하는 것을 기본 절차로 삼지 않는다. 대신 각 배치의 모든 행에 다음 자동 무결성 검증을 수행한다.

- 스키마, 필수값, 자료형과 범위
- 중복·포함·제외 ID와 보드게임 대상 유형
- 필드별 출처·이용 근거·수집 시각
- 원본 해시, 변환 버전과 결과 체크섬
- 출처 충돌, 허용되지 않은 필드와 승인되지 않은 경고

원문값과 필드의 대응을 결정적 규칙으로 재현·대조할 수 있는 사실 필드만 자동 검증을 거쳐 공개 가능 상태로 전환한다. 요약·난이도·단독 플레이 판단처럼 해석이 필요한 필드는 별도 검증 규칙과 승인 기준을 결정하기 전까지 공개 전 후보로 유지한다.

자동 검증을 통과한 뒤 사람은 무작위 표본만 원문과 대조한다. 이 표본 검사는 의미 오류를 발견하기 위한 운영 감시 수단이며 전체 배치의 의미 정확성을 통계적으로 증명하지 않는다. 배치는 동일한 source policy, 수집기·모델·규칙 버전과 상세 프로필을 사용하는 항목으로 구성해 표본에서 검증 대상이 섞이지 않게 한다.

- 새 출처·source policy 또는 새 수집기·모델·추출 규칙·상세 프로필 버전: 무작위 20건
- 팀이 안정화됐다고 기록한 동일 출처·source policy·수집기·모델·추출 규칙·상세 프로필 버전: 배치마다 무작위 5건

manifest에는 source policy, 수집기·모델·추출 규칙과 상세 프로필의 버전, 난수 seed, 표본 게임 ID, 검수자, 확인 항목과 결과를 기록한다. 안정화 전환은 자동 추정하지 않고 이전 배치 결과를 근거로 팀이 명시한다. 표본에서 오류가 발견되면 해당 조합의 안정화 상태를 해제한다.

표본에서 한 건이라도 필드 오류, 출처 불일치나 허용 범위 위반이 나오면 해당 행만 손으로 고치지 않는다. 전체 배치를 막고 추출기·규칙을 수정한 뒤 같은 원본에서 다시 생성·검증한다.

### 10. 새 배치는 실패 시 적재 산출물을 만들지 않는다

현재 `prepare-game-catalog.mjs`는 팀이 준비한 2,000건 JSON을 BGG 스냅샷과 대조하는 P0 전용 변환기다. 전체 `BASIC` 카탈로그나 다중 출처 보강 도구로 그대로 확장하지 않고 새 입력·출력 계약을 둔다.

manifest가 없거나 승인되지 않았거나, 입력 체크섬이 다르거나, 중복·필수값·출처·권리 검증이 실패하거나, 표본 검사가 통과하지 못하면 품질 보고서만 만들고 적재 산출물은 만들지 않는다.

검증을 통과한 배치는 안정적인 내부 ID 또는 `bgg_id` 매핑으로 `UPSERT`한다. 기존 내부 ID와 검증된 필드 이력을 유지하고 새 스냅샷에 없다는 이유만으로 게임을 삭제하지 않는다. 한 행이라도 적재에 실패하면 전체 반영을 롤백한다. 각 배치는 독립된 원본 스냅샷, source policy 버전, 상세 프로필 버전, manifest와 품질 보고서를 남긴다.

## 결과

- 얻는 것: 현재 2,000건을 먼저 제공하면서 전체 게임의 발견 가능성을 단계적으로 넓히고, 상세 비용은 실제 수요에 집중할 수 있다. BGG와 독립 출처, 원본과 AI 후보, 외부 지표와 자체 지표가 섞이지 않는다.
- 감수할 비용·위험: `BASIC`·`PARTIAL` 게임은 누락 필드를 화면이 처리해야 한다. 출처 정책과 필드별 provenance를 운영해야 하며, 권리 확인 전에는 BGG 기반 정규화·한국어화·의미 검색과 이미지 재호스팅을 진행할 수 없다.
- 후속 작업: 팀이 이 제안을 승인한 뒤 현재 2,000건의 provenance를 재점검하고, BGG 문의 결과와 독립 출처 policy registry를 기록한다. 이후 첫 배치 계약·자동 검증·표본 검사와 API의 누락값 표현을 별도로 확정한다.

## 보류 및 재검토

- 지금 하지 않는 것: P0 계약의 즉시 변경, 실행 중 BGG 호출, 이후 배치 건수 고정, 전체 상세 보강, 추천·최적 인원 계산식, 자체 난이도 스키마 확정, 블로그·커뮤니티 수집, BGG 원문 번역·요약·AI 입력, 이미지 재호스팅, 임베딩 모델·저장소 확정
- 보류 이유: 이번 제안은 데이터 범위, 출처 경계와 단계적 운영 원칙을 팀이 논의할 수 있게 한다. 권리 범위, 현재 2,000건의 실제 provenance와 첫 배치 측정값 없이 세부 구현을 확정할 근거가 없다.
- 다시 검토할 조건: BGG의 추가 서면 답변을 받았을 때, 수익 모델을 도입할 때, 현재 2,000건의 출처 재점검 결과가 나왔을 때, 첫 배치가 품질·비용 목표를 통과하거나 실패했을 때, 새 출처 유형을 추가할 때
