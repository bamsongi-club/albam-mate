# ADR-0011: P0 게임 카탈로그를 검수된 BGG 수동 스냅샷으로 관리

- 상태: 대체됨
- 작성일: 2026-07-24
- 결정일: 2026-07-24
- 관련: [P0 게임 카탈로그 명세](../../p0/game-catalog.md), [API 게임 목록·검색](../../API.md#게임-목록검색), [ERD GAMES](../../ERD.md#games), [ADR-0006](../platform/0006-p0-bigint-identity-ids.md), [ADR-0008](../platform/0008-flyway-database-migrations.md)
- 대체 대상: 없음
- 후속 ADR: [ADR-0014](0014-bgg-curated-service-catalog.md)

## 맥락

Albam Mate P0의 게임은 방에서 플레이할 보드게임을 찾고 선택하는 참조 데이터다. 사용자에게 게임 생성·수정·삭제 API를 제공하지 않고, 운영자가 미리 준비한 카탈로그를 공개 조회에 사용한다. 현재 P0 명세와 API는 이 제품 범위를 정했지만, 데이터를 어디서 얻고 어떻게 검수·갱신하며 외부 식별자를 어떻게 보존할지는 정하지 않았다.

기존 `GAMES` 모델에는 내부 `id`와 표시용 정보만 있고 BGG 식별자·스냅샷 이력이 없었다. BGG 식별자를 내부 기본 키로 쓰면 외부 데이터 범위가 바뀔 때 방·참가 데이터의 참조가 함께 흔들린다. 반대로 외부 식별자를 버리면 같은 게임을 다시 적재할 때 중복을 안정적으로 판별하기 어렵다.

팀은 P0에서 BoardGameGeek(이하 BGG)를 우선 출처로 사용하고, 외부 API와 주기적으로 동기화하기보다 운영자가 검수한 스냅샷을 수동으로 반영하는 방향을 검토했다. 이 방식은 실행 중인 서비스를 BGG의 가용성과 응답 제한에서 분리하지만, 스냅샷 생성·검수·적재와 갱신 주기를 팀이 직접 관리해야 한다.

BGG의 공식 문서에서 CSV 데이터 덤프도 XML API 이용 조건의 적용 대상이다. 2026-07-24에 확인한 공식 안내는 등록·승인, 엄격한 비상업적 사용 범위, 공개 화면의 BGG 출처 표시, 상업적 사용을 위한 별도 허가 가능성과 AI·LLM 학습 금지를 명시한다. 따라서 무료로 접근할 수 있다는 사실만으로 적재 권한을 가정하지 않고, 최초 적재 전에 현재 서비스 용도와 필드별 이용 범위를 검수해야 한다.

이번 결정의 기준은 다음과 같다.

- 운영 서비스의 조회 가용성을 외부 카탈로그 API에 의존시키지 않을 것
- 어떤 출처와 스냅샷을 적재했는지 재현·감사할 수 있을 것
- 이용 조건과 출처 표시 요구를 적재 전에 확인할 것
- 내부 게임 ID와 외부 식별자를 분리하고 반복 적재의 중복을 막을 것
- 대규모 외부 데이터의 생명주기를 스키마 마이그레이션에 결합하지 않을 것
- P0에 필요한 최소한의 운영 복잡도로 시작할 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 검수된 BGG 수동 스냅샷을 별도 절차로 적재 | 서비스 실행과 외부 취득을 분리하고, 적재 전에 출처·필드·변경 내용을 검수할 수 있다. | 스냅샷 생성과 갱신이 사람의 작업에 의존하고, 최신성이 실시간으로 보장되지 않는다. | 선택 |
| BGG API와 주기적으로 자동 동기화 | 수동 갱신 노력을 줄이고 최신 데이터를 더 자주 반영할 수 있다. | 인증 정보, 호출 제한, 재시도, 부분 실패와 조건 변경을 운영해야 한다. P0에는 이 최신성을 요구하는 기능이 없다. | 보류 |
| 대규모 카탈로그 데이터를 Flyway 버전 마이그레이션에 포함 | 스키마와 데이터를 하나의 버전 순서로 적용할 수 있다. | 외부 스냅샷 갱신이 애플리케이션 시작·배포와 결합되고, 대용량 데이터가 마이그레이션 이력과 저장소 크기를 키운다. | 제외 |

## 결정

P0 게임 카탈로그의 우선 외부 출처로 BGG를 사용한다. 단, 최초 적재 전에 현재 서비스의 사용 목적과 출처·필드별 이용 범위가 BGG의 현행 조건을 충족하는지 검수하고, 필요한 등록·승인과 공개 화면의 출처 표시 조치를 완료한다. 상업적 사용이면 해당 허가를 별도로 확인하고, BGG 데이터를 AI·LLM 학습에 사용하지 않는다. 이 근거가 확인되기 전에는 BGG 데이터와 이미지를 공유 환경에 적재하지 않는다.

카탈로그는 BGG와 실시간 또는 주기적으로 자동 동기화하지 않는다. 운영자가 외부 데이터를 스냅샷으로 준비하고, 이용 권한·출처·필드 매핑·중복·누락·변경 내역을 검수한 후 별도의 일회성 적재 절차로 PostgreSQL에 반영한다. 실행 중인 애플리케이션은 BGG를 직접 조회하지 않고 PostgreSQL에 승인된 카탈로그만 조회한다.

각 스냅샷은 적재 전에 다음 메타데이터를 작업 기록으로 남긴다. 스냅샷 파일을 저장소에 보관할지는 이용 조건과 데이터 크기를 확인한 뒤 적재 절차에서 정한다.

- 출처와 취득 방식
- 스냅샷 기준 시각
- 현재 이용 조건·승인의 검수일과 검수자
- 사용할 필드와 변환·제외 규칙
- 레코드 건수와 원본 체크섬

`GAMES.id`는 [ADR-0006](../platform/0006-p0-bigint-identity-ids.md)의 `BIGINT` 자동 증가 내부 기본 키를 유지한다. BGG가 부여한 게임 식별자는 `GAMES.bgg_id`에 `BIGINT NOT NULL`로 별도 보존하고 유일성 제약을 둔다. 외부 순위는 식별자로 사용하지 않는다. P0의 카탈로그 출처는 BGG 하나이므로 별도 `catalog_source` 컬럼은 두지 않으며, 여러 출처를 병합할 때 출처 모델을 다시 결정한다.

재적재는 `bgg_id`로 기존 게임을 찾아 내부 `id`를 바꾸지 않고 허용된 필드만 갱신해야 한다. 하나의 스냅샷에 같은 `bgg_id`가 두 번 들어오면 전체 적재를 실패시킨다. 이전 스냅샷에 있던 게임이 새 스냅샷에 없다는 이유만으로 물리 삭제하지 않는다. 기존 방의 참조를 보존하면서 게임을 비공개·비활성화해야 할 요구가 생기면 별도 상태 모델을 추가한다.

스키마 변경과 유일성 제약은 [ADR-0008](../platform/0008-flyway-database-migrations.md)에 따라 Flyway로 관리한다. 대규모 스냅샷 데이터 자체는 Flyway 기준 데이터로 포함하지 않고, 애플리케이션 시작 initializer에서도 적재하지 않는다. 게임명 기본 키워드 검색은 P0·API 명세의 조회 계약이며, 이 ADR은 검색 구현 방식을 추가로 확장하지 않는다.

## 결과

- 얻는 것: 실행 중인 서비스는 외부 API 상태와 무관하게 승인된 게임 카탈로그를 조회한다. 스냅샷과 `bgg_id` 기록을 통해 반복 적재와 문제 추적의 기준을 얻는다.
- 감수할 비용·위험: 갱신이 운영자 작업에 의존하고, 스냅샷 사이에 데이터가 노후화할 수 있다. BGG 이용 조건이 바뀌거나 현재 서비스 용도와 맞지 않으면 필드 범위를 줄이거나 다른 출처를 선택해야 한다.
- 후속 작업: BGG 이용 조건·등록·승인·출처 표시를 검수하고 허용된 필드 매핑을 정한다. Flyway에 `bgg_id`와 유일성 제약을 반영하고, 스냅샷 검증·적재 절차와 작업 기록 형식을 구현한다. 먼저 1,000건 스냅샷으로 중복·누락·반복 적재·검색·이미지 표시를 검증한다.

## 보류 및 재검토

- 지금 하지 않는 것: BGG 자동·주기 동기화, 실행 중 BGG 조회, 대규모 스냅샷의 Flyway 포함, 애플리케이션 시작 initializer 적재, 스냅샷 누락 게임의 자동 삭제
- 보류 이유: P0는 사용자가 게임을 관리하지 않고 운영자가 준비한 참조 데이터를 조회하므로, 실시간 최신성보다 검수·재현·운영 단순성이 더 중요하다.
- 다시 검토할 조건: 사용자가 기대하는 최신성을 수동 갱신으로 맞추기 어려울 때, 갱신 횟수·데이터 규모·운영 부담이 증가할 때, 여러 외부 출처를 병합할 때, BGG의 이용 조건이 변경되거나 서비스 용도와 맞지 않을 때

## 검증

- 상태: 미검증
- 근거: `GAMES` ERD에는 `bgg_id`와 유일성 제약을 반영했지만, 카탈로그 스냅샷 검증·적재 코드와 테스트는 아직 없다. BGG 등록·승인·필드별 이용 범위와 출처 표시 근거도 프로젝트 정본에 기록되지 않았다. 후속 구현 PR에서 1,000건 검증 결과와 실제 PostgreSQL 적재 테스트를 연결한 뒤 검증 상태를 갱신한다.
