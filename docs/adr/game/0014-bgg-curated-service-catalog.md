# ADR-0014: BGG 수집 데이터를 팀 검수 서비스 카탈로그로 재가공

- 상태: 대체됨
- 작성일: 2026-07-24
- 결정일: 2026-07-24
- 관련: [P0 게임 카탈로그 명세](../../archive/p0/game-catalog.md), [API 게임 목록·검색](../../API.md#game-01-게임-목록검색), [ERD GAMES](../../ERD.md#games), [ADR-0006](../platform/0006-p0-bigint-identity-ids.md), [ADR-0008](../platform/0008-flyway-database-migrations.md)
- 대체 대상: [ADR-0011](0011-bgg-manual-catalog-snapshot.md)
- 후속 ADR: [ADR-0015](0015-bgg-baseline-team-collected-game-list.md)

## 맥락

Albam Mate P0의 게임은 사용자가 직접 관리하는 데이터가 아니라 운영자가 준비해 공개 조회에 사용하는 참조 데이터다. [ADR-0011](0011-bgg-manual-catalog-snapshot.md)은 검수한 BGG 스냅샷을 수동 적재하기로 했지만, BGG에서 취득한 원천 데이터와 서비스에 실제 노출할 재가공 결과를 구분하지 않았다.

팀이 사용하려는 카탈로그는 BGG 원천 데이터를 그대로 적재한 것이 아니다. 서비스 필드에 맞춰 값을 선별·정규화하고, 본판·확장·버전을 구분하며, 팀이 작성하거나 검수한 표시값으로 보완한 결과다. 표본 작업에서는 한국어명 누락, 본판과 변형·확장의 혼동, 취득 날짜에 따른 순위와 포함 행의 변동이 확인됐다. 따라서 원천 데이터와 서비스용 데이터셋을 분리하고 변환·검수 과정을 재현할 수 있어야 한다.

현재 공개된 BGG XML API 이용 조건은 API로 받은 데이터의 수정을 금지하며, BGG가 제공하는 전체 게임 CSV에도 같은 라이선스를 적용한다. 표준 조건만으로는 이 ADR의 재가공을 실행할 수 없으므로, 최초 수집 전에 재가공·저장·공개 범위를 포함한 별도 서면 허가를 받아야 한다. 취득 방식을 포괄적인 "수집"으로만 기록하지 않고 실제 CSV·API 등 사용한 경로를 남긴다.

이번 결정의 기준은 다음과 같다.

- 실행 중인 서비스가 BGG의 가용성과 응답 제한에 의존하지 않을 것
- BGG 원천 데이터와 팀이 재가공한 서비스용 데이터셋을 구분할 것
- 같은 입력과 변환 규칙으로 같은 결과를 재현할 수 있을 것
- 내부 게임 ID와 BGG 식별자를 분리하고 반복 적재의 중복을 막을 것
- 취득·재가공·저장·공개가 허가된 범위 안에서만 이루어질 것
- P0의 스키마 마이그레이션과 대규모 카탈로그 적재를 분리할 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| BGG 데이터를 수집해 팀 검수 서비스 카탈로그로 재가공 | P0 화면과 스키마에 필요한 형식으로 품질을 통제하고, 실행 중 외부 연동을 제거할 수 있다. | 변환 규칙·검수·갱신을 운영해야 하며 BGG의 별도 서면 허가가 필요하다. | 선택 |
| BGG 원천 스냅샷을 변경 없이 적재 | 변환 과정과 파생 오류가 줄어든다. | 필요한 한국어명·표시값·버전 구분을 충족하지 못하고 서비스 모델이 원본 형식에 종속된다. | 대체 |
| BGG API를 실행 중 직접 조회하거나 주기적으로 자동 동기화 | 최신 데이터를 더 자주 반영할 수 있다. | 인증, 호출 제한, 부분 실패와 조건 변경이 서비스 운영에 들어오며 P0에 필요한 최신성이 아니다. | 보류 |
| BGG를 사용하지 않고 모든 게임 데이터를 직접 작성 | 외부 데이터 수정 조건과 원본 형식에 의존하지 않는다. | 초기 작성·검수 비용이 크고 BGG 식별자를 이용한 중복 판별과 추적 기준을 잃는다. | 재검토 후보 |

## 결정

BGG가 허용한 취득 경로로 원천 데이터를 수집하고, Albam Mate의 명시적인 변환 규칙과 팀 검수를 거친 서비스용 카탈로그 데이터셋만 PostgreSQL에 적재한다. 실행 중인 애플리케이션은 BGG나 원천 파일을 직접 조회하지 않는다.

이 결정은 BGG로부터 재가공·저장·공개 범위를 포함한 별도 서면 허가를 받는 것을 실행 선행 조건으로 한다. 애플리케이션 등록·승인과 공개 화면의 출처 표시 요구도 함께 충족한다. 허가 근거가 없거나 허가 범위가 현재 재가공 방식과 맞지 않으면 BGG 데이터를 수집·재가공·공유 환경에 적재하지 않는다. 공개되지 않은 API나 사이트 크롤링으로 이 조건을 우회하지 않으며, BGG 데이터를 AI·LLM 학습에 사용하지 않는다.

카탈로그 흐름은 `BGG 승인 경로 → 원천 스냅샷 → 변환·검수 → 서비스용 데이터셋 → PostgreSQL`로 분리한다. 각 실행에는 다음 기록을 남긴다. 원천·결과 파일의 보관 위치와 기간은 허가 범위와 데이터 크기를 확인한 뒤 적재 절차에서 정한다.

- BGG 허가 근거와 실제 취득 경로·기준 시각
- 원천 스냅샷의 행 수와 체크섬
- 변환 규칙 버전 또는 실행 코드 커밋, 적용한 매핑·정규화·보완·제외 규칙
- 결과 데이터셋의 행 수와 체크섬, 제외·오류 건수
- 검수일과 검수자

`GAMES.id`는 [ADR-0006](../platform/0006-p0-bigint-identity-ids.md)의 `BIGINT` 자동 증가 내부 기본 키를 유지한다. BGG 식별자는 `GAMES.bgg_id`에 별도로 보존하고 유일성 제약을 둔다. BGG 순위처럼 취득 시점에 따라 변하는 값은 식별자로 사용하지 않는다.

재적재는 `bgg_id`로 기존 게임을 찾아 내부 `id`를 유지한 채 허용된 필드만 갱신한다. 입력 또는 결과 데이터셋에 같은 `bgg_id`가 중복되거나 필수 필드가 누락되면 전체 적재를 실패시킨다. 새 데이터셋에 없다는 이유만으로 기존 게임을 물리 삭제하지 않는다.

스키마와 유일성 제약은 [ADR-0008](../platform/0008-flyway-database-migrations.md)에 따라 Flyway로 관리한다. 원천 스냅샷과 서비스용 데이터셋은 Flyway 마이그레이션이나 애플리케이션 시작 initializer에 포함하지 않고 별도 변환·검증·적재 절차로 관리한다.

## 결과

- 얻는 것: 서비스 필드에 맞게 검수한 카탈로그를 외부 API 상태와 분리해 제공하고, 원천부터 적재 결과까지 추적·재현할 수 있다.
- 감수할 비용·위험: 별도 허가를 받기 전에는 실행할 수 없고, 변환 규칙과 수동 검수의 오류·노후화·운영 비용을 팀이 부담한다.
- 후속 작업: BGG에 재가공·저장·공개 범위를 서면으로 확인하고, 필드 매핑과 본판·확장·버전 제외 기준을 확정한다. 변환·검증·적재 절차를 구현한 뒤 1,000건 표본으로 누락·중복·변형 혼동·결정적 재실행·반복 적재·검색을 다시 검증한다.

## 보류 및 재검토

- 지금 하지 않는 것:
  - 허가 전 BGG 데이터 수집·재가공·공유 적재
  - 실행 중 BGG 조회
  - 자동 주기 동기화
  - 비공개 API나 사이트 크롤링
  - 대규모 데이터의 Flyway·initializer 적재
- 보류 이유: P0는 실시간 최신성보다 검수된 참조 데이터와 단순한 운영 경계가 중요하며, 재가공 권한과 변환 품질이 아직 검증되지 않았다.
- 다시 검토할 조건:
  - BGG가 필요한 재가공을 허가하지 않을 때
  - 허용 필드만으로 P0 카탈로그를 만들 수 없을 때
  - 수동 갱신으로 필요한 최신성을 맞추기 어려울 때
  - 여러 외부 출처를 병합할 때

## 검증

- 상태: 미검증
- 근거: 없음
- 미검증:
    - BGG 재가공 서면 허가, 확정된 변환 규칙과 재현 가능한 원천·결과 체크섬이 프로젝트 정본에 없다.
    - 변환·적재 코드와 1,000건 검증 결과가 없으므로, 이를 확보하기 전에는 BGG 기반 데이터셋을 공유 환경에 적재하지 않는다.
