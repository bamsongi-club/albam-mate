# ADR-0028: 사용자가 표시한 해 본 게임만 관계로 저장

- 상태: 승인됨
- 작성일: 2026-07-31
- 결정일: 2026-08-03
- 관련: [SEARCH-03 사용자별 해 본 게임](../../p1/search.md#search-03-사용자별-해-본-게임), [P0 권한과 공개 범위](../../archive/p0/P0-spec.md#권한과-공개-범위), [게임 API](../../API.md#6-게임-api), [ERD GAMES](../../ERD.md#games), [ADR-0003](../auth/0003-p0-server-session-spring-security.md), [ADR-0006](../platform/0006-p0-bigint-identity-ids.md), [ADR-0008](../platform/0008-flyway-database-migrations.md), [ADR-0020](../auth/0020-api-endpoint-authorization-policy-registry.md)
- 대체 대상: 없음
- 후속 ADR: 없음

> 이 결정은 P1 필수 범위가 아니라 확장 후보다. 상위 P1 범위에 채택되기 전에는 API·ERD·구현 계약에 반영하지 않는다.

**결정 요약:** 사용자가 해 봤다고 표시한 게임만 저장하며, 관계가 없으면 `해보지 않음`이 아니라 `표시되지 않음`으로 본다.

## 맥락

확장 후보가 채택되면 사용자가 해 본 게임만 보거나 이미 표시한 게임을 결과에서 제외해야 한다. 현재 사용자와 게임 사이에는 이런 관계가 없다.

방 참가 이력은 실제 플레이 완료를 증명하지 못하고, 서비스 밖에서 플레이한 게임도 알 수 없다. 따라서 방 이력에서 추정하지 않고 사용자가 직접 표시하게 한다.

관계가 없다는 사실만으로 실제 미플레이를 증명할 수 없으므로 `해보지 않은 게임`이라는 상태는 만들지 않는다.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| `PLAYED`·`NOT_PLAYED`를 직접 저장하고 미등록을 `UNKNOWN`으로 구분 | 실제 미플레이 의사까지 표현할 수 있다. | 음수 상태를 따로 입력·관리해야 한다. | 제외 |
| 사용자가 표시한 게임만 관계로 저장 | 실제 등록 수만큼만 저장하며 등록·취소가 단순하다. | 미등록과 실제 미플레이를 구분하지 못한다. | 선택 |
| 플레이 날짜·횟수 이력을 먼저 저장 | 통계와 최근 플레이로 확장하기 좋다. | 현재 검색보다 범위와 정책이 크게 늘어난다. | 보류 |
| 종료된 방의 참가자로 자동 판정 | 별도 사용자 입력이 필요 없다. | 실제 플레이를 증명하지 못하고 서비스 밖 플레이를 누락한다. | 제외 |

## 결정

사용자가 해 봤다고 표시한 게임만 `user_played_games` 관계로 저장한다.

- 관계가 있으면 `해 본 게임으로 표시됨`이다.
- 관계가 없으면 `표시되지 않음`이며 `해보지 않음`으로 해석하지 않는다.
- `(user_id, game_id)` 조합은 하나만 허용한다.
- 생성 시각은 표시한 시각이며 실제 플레이 날짜가 아니다.
- 별도 상태 enum, 플레이 날짜·횟수·점수·후기는 저장하지 않는다.

사용자는 자신의 목록에만 게임을 등록하거나 취소할 수 있다. 같은 요청을 반복해도 최종 결과가 같아야 하며, 방 생성·참가·종료나 외부 서비스 기록으로 관계를 자동 변경하지 않는다.

검색은 현재 사용자가 표시한 게임만 보거나 표시하지 않은 게임을 볼 수 있다. 후보 단계의 요청·응답 의미는 P1 검색 명세에서 관리하고, 채택되면 인증·오류를 포함한 API 계약을 API 명세에 확정한다.

향후 플레이 기록 기능이 승인되면 날짜·횟수 이력은 별도 모델로 추가한다. 기존 관계는 사용자의 수동 표시로 유지하고, 관계 생성 시각을 실제 플레이 날짜로 바꾸지 않는다.

## 결과

- 얻는 것: 전체 게임 수가 아니라 실제 등록 수만큼만 데이터가 증가하고, 등록·취소와 검색 의미가 단순하다.
- 감수할 비용·위험: 사용자가 표시하지 않으면 누락되며, 취소한 이전 표시나 실제 플레이 날짜·횟수는 알 수 없다.
- 후속 작업: SEARCH-03이 상위 P1 범위에 채택되고 ADR이 승인되면 ERD·API·마이그레이션과 사용자 격리·멱등성·복합 검색 테스트에 반영한다.

## 보류 및 재검토

- 지금 하지 않는 것: 플레이 이력, 방 이력 기반 자동 등록, 점수·후기, 하고 싶은 게임·보유 게임·즐겨찾기, 다른 사용자의 목록 공개
- 보류 이유: 현재 필요한 기능은 사용자가 표시한 집합의 등록·취소와 검색이다.
- 다시 검토할 조건: 플레이 기록·통계 기능이나 사용자 상태 공개 범위가 승인될 때
