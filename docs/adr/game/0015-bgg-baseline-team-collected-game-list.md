# ADR-0015: BGG 기준 스냅샷과 팀 수집 자료로 서비스 게임 목록 구성

- 상태: 승인됨
- 작성일: 2026-07-26
- 결정일: 2026-07-26
- 관련: [P0 게임 목록 명세](../../p0/game-catalog.md), [API 게임 목록·검색](../../API.md#game-01-게임-목록검색), [ERD GAMES](../../ERD.md#games), [ADR-0006](../platform/0006-p0-bigint-identity-ids.md), [ADR-0008](../platform/0008-flyway-database-migrations.md)
- 대체 대상: [ADR-0014](0014-bgg-curated-service-catalog.md)
- 후속 ADR: 없음

## 맥락

Albam Mate P0는 운영자가 준비한 게임 목록을 공개 조회에 사용한다. 2026-07-23 회의에서는 이미지 URL을 포함한 1,000건으로 먼저 적재를 시험하고, 게임의 내부 ID는 1부터 증가하는 값으로 두는 방향을 정했다. 2026-07-24 회의에서는 내부 게임 ID와 BGG 외부 ID를 별도 열로 두고, 서로 다른 날짜의 CSV를 섞지 않고 하나의 스냅샷을 기준으로 정제하기로 했다.

실제 표본 작업에서는 BGG CSV만으로 한국어명·별칭·이미지·설명 등 서비스에 필요한 필드를 채우기 어려웠다. 상위 1,000건 표본에서도 예상한 게임이 빠지고, 한국어명 수집이 중단되거나 같은 게임의 본판·확장·변형이 섞이는 문제가 확인됐다. 같은 CSV라고 생각한 파일 사이에서도 순위와 포함 행이 달랐지만, 당시 사용한 파일의 출처 URL·파일명·체크섬·행 수는 기록되지 않았다. 따라서 1,000건 작업은 성공한 적재 결과가 아니라 다시 검증해야 할 표본이다.

회의에서는 BGG를 외부 식별자와 기준 목록에 사용하고, 부족한 표시 정보는 팀원이 수집한 자료로 보완하는 방향을 논의했다. 이 ADR은 팀원이 이미 수집해 보유한 자료를 서비스 게임 목록의 입력 후보로 사용하되, 실제 출처와 게임 매핑을 검수한 뒤 반영하는 절차를 정한다.

BGG 이용 범위에 관해서는 별도 서면 문의가 필요하다는 의견과 비상업 프로젝트에는 필요 없다는 의견이 함께 나왔으며, 문의의 실제 발송이나 회신은 확인되지 않았다. [ADR-0014](0014-bgg-curated-service-catalog.md)는 이 불확실한 논의를 모든 수집·재가공의 별도 서면 허가 선행 조건으로 확정했으나, 이는 회의에서 일관되게 확인된 결론이 아니다. 이번 ADR은 별도 서면 회신을 P0 게임 목록 준비 작업의 일괄 선행 조건에서 제외하되, 각 자료의 실제 출처와 적용 조건을 확인할 책임까지 없애지는 않는다.

이번 결정의 기준은 다음과 같다.

- BGG 기준 데이터와 팀원이 수집한 보완 자료를 함께 사용할 것
- 서로 다른 시점의 BGG 스냅샷을 섞지 않고 입력을 재현할 수 있을 것
- 수집 자료를 출처가 없는 팀 작성값처럼 바꾸어 기록하지 않을 것
- 내부 게임 ID와 BGG 식별자를 분리하고 반복 적재의 중복을 막을 것
- 본판·확장·변형을 확실히 구분하지 못한 게임은 임의로 합치지 않을 것
- 실행 중인 서비스가 BGG나 다른 외부 사이트의 가용성에 의존하지 않을 것

## 결정

P0 게임 목록은 `단일 BGG 기준 스냅샷 → 팀 수집 자료 매핑 → 팀 검수 → 서비스용 데이터셋 → PostgreSQL` 흐름으로 준비한다.

BGG 기준 스냅샷은 게임 후보와 `bgg_id`를 식별하는 기준으로 사용한다. 초기 검증은 회의에서 선택한 2026-07-24 스냅샷 하나를 기준으로 하되, 실제 파일을 특정할 수 없으면 서로 다른 기존 파일을 섞지 않고 새 기준 스냅샷 하나를 정해 메타데이터부터 기록한다. BGG 순위는 시점에 따라 바뀌므로 게임 식별자나 장기적인 포함 기준으로 사용하지 않는다.

팀원이 수집한 자료는 한국어명·별칭·이미지·설명 등 BGG 기준 스냅샷만으로 채우기 어려운 서비스 필드의 입력 후보로 사용한다. 각 값은 대응하는 `bgg_id`와 게임의 본판·확장·변형 여부를 확인한 뒤 반영한다. 어떤 게임과 연결되는지 확실하지 않거나 필수 필드의 근거가 부족한 행은 임의로 합치거나 추정하지 않고 제외 목록에 남긴다.

BGG 값과 수집 자료의 값을 모두 출처가 없는 팀 작성값으로 합치지 않는다. 적재 작업에는 다음 기록을 남긴다.

- BGG 기준 스냅샷의 출처, 취득 시각, 파일명, 행 수와 SHA-256
- 팀 수집 자료별 실제 출처·취득 방식·취득 시각과 제공하는 필드
- `bgg_id` 매핑, 본판·확장·변형 구분, 선택·제외 규칙
- 서비스용 결과 데이터셋의 행 수와 SHA-256, 제외·오류 건수
- 검수일, 검수자와 실행 코드 커밋

별도 서면 허가 여부 하나를 전체 작업의 공통 중단 조건으로 사용하지 않는다. 대신 실제로 사용한 각 출처의 이용 조건과 표시 요구를 확인한다. 특정 취득 경로나 필드가 별도 허가를 요구하면 그 요구를 충족하거나 해당 값을 제외한다. 적발 가능성이 낮다는 이유로 사용 가능하다고 판단하지 않으며, 실제 취득 방식을 포괄적인 "수집" 표현으로 감추지 않는다.

`GAMES.id`는 [ADR-0006](../platform/0006-p0-bigint-identity-ids.md)에 따라 `BIGINT` 자동 증가 내부 기본 키를 유지한다. BGG 식별자는 `GAMES.bgg_id`에 별도로 보존하고 유일성 제약을 둔다. 각 적재 배치의 결과 데이터셋에는 같은 `bgg_id`가 한 번만 존재해야 한다. 데이터베이스에 같은 `bgg_id`가 있으면 내부 `id`를 유지하고 필드 매핑표의 출처·갱신 규칙에 따라 해당 게임을 업데이트하며, 없으면 신규 게임으로 삽입한다. BGG 기준 스냅샷이 담당하는 필드와 팀 수집 자료가 담당하는 필드를 구분하고, 새 BGG 스냅샷이 들어왔다는 이유만으로 팀 검수 필드를 덮어쓰지 않는다. 새 데이터셋에 없다는 이유만으로 기존 게임을 물리 삭제하지 않는다.

배치 내부에 같은 `bgg_id`가 둘 이상 있으면 어떤 값을 반영할지 임의로 선택하지 않고 데이터베이스 쓰기 전에 검증 실패로 처리한다. 전체 입력의 필수값·매핑·중복 검증을 통과한 서비스용 결과 데이터셋만 하나의 데이터베이스 트랜잭션에서 `UPSERT`한다. 어느 행에서든 적재가 실패하면 전체 트랜잭션을 롤백해 기존 게임 목록을 그대로 유지하고, 성공한 커밋 이후에만 새 게임 목록을 공유 환경에 노출한다.

스키마와 유일성 제약은 [ADR-0008](../platform/0008-flyway-database-migrations.md)에 따라 Flyway로 관리한다. 회의에서 초기 데이터의 SQL 적재와 애플리케이션 initializer를 비교했지만 실행 방식은 확정하지 않았으므로, 대규모 게임 목록 데이터는 현재 승인된 ADR-0008의 경계에 따라 Flyway 마이그레이션이나 애플리케이션 시작 initializer에 넣지 않는다. 새로 검수한 스냅샷을 반영할 때마다 같은 검증·`UPSERT` 규칙을 다시 실행할 수 있는 별도 배치 적재 절차로 관리한다. 실행 중인 애플리케이션은 외부 원천을 직접 조회하지 않는다.

## 결과

- 얻는 것: BGG 외부 식별자를 유지하면서 팀원이 수집한 자료를 실제 P0 표시 필드에 활용하고, 각 값의 출처와 게임 매핑을 추적할 수 있다.
- 감수할 비용·위험: 수집 자료의 출처·이용 범위와 본판·확장·변형을 사람이 검수해야 한다. 일부 값은 근거 부족으로 제외될 수 있고, 수동 스냅샷은 시간이 지나면 노후화한다. 전체 배치를 하나의 트랜잭션으로 반영하므로 적재 중 잠금 시간과 실패 시 롤백 비용도 관리해야 한다.
- 후속 작업: 2026-07-24 기준 파일을 특정하거나 새 단일 스냅샷을 정하고, 팀원이 수집한 자료의 출처 목록과 필드별 갱신 규칙을 포함한 매핑표를 만든다. 1,000건 표본으로 누락·배치 내부 중복·한국어명·버전 구분·신규 삽입·기존 게임 갱신·실패 롤백·반복 적재·검색을 다시 검증한다.

## 보류 및 재검토

- 지금 하지 않는 것: 서로 다른 날짜의 BGG 파일 혼합, 실행 중 외부 조회, 자동 주기 동기화, 출처를 감춘 수집값 적재, 확인되지 않은 본판·확장·변형 병합, 대규모 게임 목록의 Flyway·initializer 적재
- 보류 이유: P0는 실시간 최신성보다 검수된 참조 데이터와 재현 가능한 입력 경계가 중요하다.
- 다시 검토할 조건: 수동 갱신으로 필요한 최신성을 맞추기 어려울 때, 여러 외부 출처를 정식으로 병합할 때, 게임 버전 모델을 도입할 때, 출처의 이용 조건이나 서비스 용도가 바뀔 때
