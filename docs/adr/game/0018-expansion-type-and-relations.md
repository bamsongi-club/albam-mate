# ADR-0018: P0 이후 단독 플레이 가능 여부와 확장 관계를 분리해 관리

- 상태: 제안됨
- 작성일: 2026-07-28
- 결정일: 미정
- 관련: [제품 후속 기능 후보](../../PRD.md#후속-기능-후보-도입-차수-미정), [ERD GAMES](../../ERD.md#games), [ERD ROOMS](../../ERD.md#rooms), [ADR-0015](0015-bgg-baseline-team-collected-game-list.md), [ADR-0019](0019-bgg-full-catalog-staged-enrichment.md)
- 대체 대상: 없음
- 후속 ADR: 없음

> 이 문서는 팀 논의를 위한 제안이다. 승인 전에는 구현 정본으로 사용하지 않는다.

## 맥락

확장판을 다룰 때는 서로 다른 두 질문에 답해야 한다.

1. 이 항목만으로 플레이할 수 있는가?
2. 다른 게임을 필요로 하거나 다른 게임과 결합할 수 있는가?

예를 들어 일반 게임과 독립형 확장판은 모두 단독 플레이할 수 있다. 종속 확장판은 단독 플레이할 수 없고 하나 이상의 다른 게임을 필요로 할 수 있다. 독립적으로 플레이할 수 있는 두 게임이 서로 결합되는 경우도 있다.

| 구분 | 단독 플레이 | 다른 게임과의 관계 |
| --- | --- | --- |
| 일반 게임 또는 본판 | 가능 | 없거나 다른 항목이 이 게임을 요구함 |
| 종속 확장판 | 불가능 | 필요한 게임과 비대칭 관계가 있음 |
| 독립형 확장판·호환 게임 | 가능 | 다른 게임과 대칭적인 결합 관계가 있을 수 있음 |

따라서 `BASE_GAME`, `DEPENDENT_EXPANSION`, `STANDALONE_EXPANSION` 중 하나만 고르는 `game_type`은 단독 플레이 가능성과 관계의 종류를 한 값에 섞는다. 한 게임이 독립형 확장판이면서 다른 확장판의 필수 게임이 되는 경우처럼 역할이 겹치면 표현도 모호해진다.

BGG의 `is_expansion`만으로 단독 플레이 가능 여부를 확정할 수도 없다. BGG 등록 지침은 일반적인 종속 확장판에는 `Expands` 관계를, 독립적으로 플레이할 수 있으면서 결합 가능한 게임에는 `Integrates with` 관계를 사용하도록 안내한다. 다만 Collectible/Customizable Game 계열의 subsidiary product처럼 단독 플레이할 수 있어도 확장판으로 등록될 수 있는 예외가 있다. 그러므로 `is_expansion = 1`을 곧바로 `REQUIRES_BASE_GAME`으로 변환하면 독립 플레이 가능한 항목을 막을 수 있다.

이번 제안의 판단 기준은 다음과 같다.

- 방의 중심 게임으로 단독 선택할 수 있는지 근거와 함께 판단할 것
- `Expands`처럼 방향이 있는 필수 관계와 `Integrates with`처럼 대칭인 결합 관계를 구분할 것
- 본판 하나와 여러 확장판, 확장 항목 하나가 요구하는 여러 게임을 표현할 것
- 출처에 없는 관계를 이름·시리즈 유사성이나 AI 추측으로 만들지 않을 것
- 아직 필요하지 않은 판본·재구현 관계까지 일반화하지 않을 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| `is_expansion` 불리언만 저장 | 적재와 필터가 단순하다. | BGG의 등록 예외, 독립형 확장판과 호환 게임을 표현하지 못한다. | 제외 |
| 하나의 `game_type`으로 본판·종속·독립형을 구분 | 화면에 표시할 유형을 한 값으로 조회하기 쉽다. | 단독 플레이 가능 여부와 관계 역할이 섞이고 한 게임의 여러 역할을 표현하기 어렵다. | 제외 |
| 단독 플레이 가능 여부와 관계 종류를 분리 | 두 질문에 각각 답하고 필요한 화면 표현도 조합할 수 있다. | 값과 관계를 함께 조회·검증해야 한다. | 선택 |
| 모든 게임 관계를 범용 `GAME_RELATIONS`로 관리 | 판본·재구현·합본까지 확장할 수 있다. | 아직 필요하지 않은 관계까지 추상화해 의미와 제약이 느슨해진다. | 보류 |

## 결정

아래 구조를 팀 논의안으로 제안한다.

### 1. 단독 플레이 가능 여부

`GAMES`에는 다음 값을 갖는 필수 `playability_type`을 둔다.

- `STANDALONE`: 다른 게임 없이 플레이 가능하다는 근거가 있음
- `REQUIRES_BASE_GAME`: `GAMES`에 등록된 하나 이상의 다른 게임 또는 확장 항목이 필요하다는 근거가 있음
- `UNVERIFIED`: 근거가 부족하거나 출처가 서로 충돌함

BGG와 독립 출처를 재가공할 수 있는 범위가 확인된 뒤에도 `is_expansion` 하나만으로 값을 정하지 않는다.

| 확인된 입력 | 초기 `playability_type` | 비고 |
| --- | --- | --- |
| 검증된 `Expands` 관계 또는 공식 규칙서·제작사의 필수 게임 설명 | `REQUIRES_BASE_GAME` | 필요한 `GAMES` 항목과의 관계도 함께 저장해야 함 |
| 검증된 `Integrates with` 관계 또는 공식 출처의 단독 플레이 가능 설명 | `STANDALONE` | 결합 관계와 단독 플레이 가능성을 함께 보존 |
| `is_expansion = 0`이고 충돌 근거가 없음 | `UNVERIFIED` | 단독 플레이 가능 후보 신호로만 기록하고 검증 전에는 승격하지 않음 |
| `is_expansion = 1`만 있음 | `UNVERIFIED` | BGG 등록 예외 때문에 본판 필요로 단정하지 않음 |
| 값 누락 또는 출처 충돌 | `UNVERIFIED` | 사람이 임의로 추정하지 않음 |

BGG 원본을 위 값으로 재분류하는 행위에는 [ADR-0019](0019-bgg-full-catalog-staged-enrichment.md)의 이용 범위 확인 절차를 적용한다. 허용 근거가 없는 동안에는 BGG 원본 값을 수정·재분류한 공개 필드를 만들지 않는다.

`is_expansion` 원본값만 있는 항목은 `UNVERIFIED`로 저장한다. 출처 이용 범위와 품질 게이트를 통과한 단독 플레이 근거를 확보하면 `STANDALONE`으로, 필수 게임 근거를 확보하면 `REQUIRES_BASE_GAME`으로 전환한다. 검증 전 후보 상태를 `STANDALONE`으로 저장하거나 별도의 비공식 enum 값으로 추가하지 않는다.

원본 값, 관계 출처, 수집 시각, 변환 규칙 버전과 검증 상태를 필드·관계 단위로 남긴다. 이후 더 신뢰할 수 있는 근거로 판단이 달라지면 새 검증 기록과 함께 값을 갱신한다.

### 2. 방향이 다른 관계를 별도로 저장한다

두 종류의 관계를 하나의 방향성 테이블에 억지로 담지 않는다.

- `GAME_REQUIREMENTS(dependent_game_id, required_game_id)`: 종속 항목이 어떤 게임을 필요로 하는지 나타내는 비대칭 관계
- `GAME_INTEGRATIONS(game_id_low, game_id_high)`: 두 게임을 결합할 수 있음을 나타내는 대칭 관계

`GAME_REQUIREMENTS`는 두 식별자의 조합을 유일하게 유지한다. `GAME_INTEGRATIONS`는 작은 내부 ID를 항상 `game_id_low`에 저장하는 등 정규 순서를 강제하고 두 식별자의 조합을 유일하게 유지한다. 물리 테이블명과 상세 제약은 이 제안이 승인된 뒤 ERD와 Flyway 변경에서 확정한다.

이번 ADR에서 필수 요구 관계는 `GAMES`에 등록된 게임 또는 확장 항목 간 관계로 한정한다. 특정 카드, 보드, 토큰 등 개별 물리 구성물의 요구 관계는 현재 모델의 범위에 포함하지 않으며 후속 설계에서 검토한다.

CSV의 이름이나 `is_expansion`만으로 관계를 만들지 않는다. BGG의 `Expands`·`Integrates with`, 공식 규칙서나 제작사 설명처럼 관계 종류를 확인할 수 있는 근거만 후보로 수집하고, 출처별 이용 범위와 [ADR-0019](0019-bgg-full-catalog-staged-enrichment.md)의 품질 게이트를 통과한 관계만 반영한다.

화면 표현은 저장값을 다음처럼 조합한다.

| 표시할 개념 | 판단 기준 |
| --- | --- |
| 종속 확장 항목 | `REQUIRES_BASE_GAME`이면서 검증된 필수 관계가 있음 |
| 독립적으로 플레이 가능한 호환 게임 | `STANDALONE`이면서 검증된 결합 관계가 있음 |
| 독립형 확장판 | 위 조건에 더해 공식 출처가 독립형 확장판으로 설명함 |
| 일반 게임 또는 본판 | `STANDALONE`이며 자신이 요구하는 관계가 확인되지 않음 |
| 분류 미확인 | `UNVERIFIED`이거나 필요한 관계 검증이 끝나지 않음 |

`Integrates with`가 있다는 이유만으로 모든 항목을 독립형 확장판이라고 부르지 않는다. `game_type` 컬럼도 별도로 두지 않는다.

### 3. 검색과 방 선택 규칙

- 기본 검색은 본판 중심으로 `STANDALONE` 게임을 보여 준다. 독립적으로 플레이 가능한 호환 게임도 일반 검색에 포함할 수 있다.
- `REQUIRES_BASE_GAME`은 기본 검색에서 제외하고, 관련 항목이나 명시적인 확장 검색에서 보여 준다.
- `UNVERIFIED`는 기본 검색과 방의 중심 게임 선택에서 제외한다.
- 방을 생성하거나 중심 게임을 변경하는 시점에는 `ROOMS.game_id`로 검증된 `STANDALONE` 게임만 선택할 수 있다.

선택 뒤 더 신뢰할 수 있는 근거로 게임이 `REQUIRES_BASE_GAME` 또는 `UNVERIFIED`로 바뀌면 새 방의 선택 대상에서는 즉시 제외한다. 기존 방을 자동 삭제하거나 취소하지 않고 선택 당시의 검증 버전과 근거를 보존한다. 완료·취소되지 않은 기존 방은 영향 목록에 포함해 호스트가 다른 `STANDALONE` 게임을 선택하거나 운영자가 근거를 재확인하기 전까지 새 참가를 받지 않는다. 알림과 수정 제한의 물리 구현은 이 제안이 승인된 뒤 room 공개 계약과 ERD에서 확정한다.

방에서 사용할 확장판을 고르는 기능이 제품 범위에 들어올 때만 `ROOM_EXPANSIONS(room_id, expansion_game_id)`를 추가한다. 선택한 종속 항목이 요구하는 모든 게임을 해당 방이 충족하는지 검증해야 하며, 관계를 아직 수집하지 못한 항목은 방 확장판으로 선택할 수 없다.

게임의 플레이 가능성과 두 관계는 game 도메인이, 방에서 고른 확장판은 room 도메인이 소유한다. room 도메인은 game 엔티티나 저장소를 직접 참조하지 않고 공개 계약으로 플레이 가능성과 호환 관계를 확인한다.

## 결과

- 얻는 것: 단독 플레이 가능성과 관계 방향을 혼동하지 않는다. BGG의 등록 예외와 대칭 관계를 보존하면서 종속 확장판, 독립형 확장판, 여러 필수 게임 관계를 표현할 수 있다.
- 감수할 비용·위험: 한 컬럼만으로 화면 유형을 읽을 수 없고 관계 조회가 필요하다. 근거를 아직 확보하지 못한 항목은 검색·방 선택 범위가 제한된다.
- 후속 작업: 팀 승인 뒤 출처별 관계 파서, 필드·관계 단위 출처 기록, 자동 검증과 표본 검사를 설계한다. 이후 ERD·API·Flyway·Entity와 방 선택 공개 계약을 변경하고 BGG 등록 예외, 다중 필수 관계와 대칭 결합 관계를 검증한다.

## 보류 및 재검토

- 지금 하지 않는 것: P0 스키마 변경, 방별 확장판 선택 구현, 판본·재구현·합본 관계, 확장판끼리의 선행·충돌 조건, 사용자 보유 확장판 관리
- 보류 이유: P0의 2,000건을 우선 제공하는 단계이며 방별 확장판 선택 범위와 관계 수집 권한이 아직 확정되지 않았다.
- 다시 검토할 조건: 확장판이 다른 확장판을 필수로 요구할 때, 판본·재구현 관계도 같은 화면에서 조회해야 할 때, BGG 외 여러 출처의 관계를 통합할 때
