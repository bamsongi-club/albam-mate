# ADR-0018: P0 이후 단독 플레이 가능 여부와 확장 관계를 분리해 관리

- 상태: 제안됨
- 작성일: 2026-07-28
- 결정일: 미정
- 관련: [제품 후속 기능 후보](../../PRD.md#후속-기능-후보-도입-차수-미정), [ERD GAMES](../../ERD.md#games), [ERD ROOMS](../../ERD.md#rooms), [ADR-0015](0015-bgg-baseline-team-collected-game-list.md), [ADR-0019](0019-bgg-full-catalog-staged-enrichment.md)
- 대체 대상: 없음
- 후속 ADR: 없음

> 이 문서는 팀 논의를 위한 제안이다. 승인 전에는 구현 정본으로 사용하지 않는다.

## 맥락

확장판을 구분할 때는 서로 다른 두 질문에 답해야 한다.

1. 이 게임만으로 플레이할 수 있는가?
2. 다른 게임을 확장하는 관계가 있는가?

예를 들어 본판과 독립형 확장판은 모두 단독 플레이할 수 있다. 하지만 독립형 확장판은 다른 게임과의 확장 관계도 가진다. 종속 확장판은 확장 관계가 있으면서 호환 게임도 필요하다.

| 구분 | 단독 플레이 | 확장 관계 |
| --- | --- | --- |
| 일반 게임 또는 본판 | 가능 | 없거나 기준 게임 쪽에 존재 |
| 종속 확장판 | 불가능 | 존재 |
| 독립형 확장판 | 가능 | 존재 |

따라서 `BASE_GAME`, `DEPENDENT_EXPANSION`, `STANDALONE_EXPANSION` 중 하나만 고르는 `game_type` 컬럼은 두 개념을 억지로 하나에 담는다. 한 게임이 독립형 확장판이면서 자기 확장판의 기준 게임이 되는 경우처럼 역할이 겹치면 의미도 모호해진다.

BGG 전체 목록의 `is_expansion`은 단독 플레이 가능 여부를 처음 판단하는 데 사용할 수 있다. BGG 등록 지침상 확장판 표시는 다른 게임이 필요한 항목에 사용되므로 `is_expansion = 1`은 본판 필요, `is_expansion = 0`은 단독 플레이 가능으로 해석한다. 다만 이 CSV만으로는 어떤 게임을 확장하는지, 단독 플레이 가능한 게임이 독립형 확장판인지까지 알 수 없다. 그 관계는 BGG 상세 데이터 등 별도 근거가 필요하다.

이번 제안의 판단 기준은 다음과 같다.

- 방의 중심 게임으로 단독 선택할 수 있는지 바로 판단할 것
- 본판 하나와 여러 확장판, 확장판 하나와 여러 호환 게임을 표현할 것
- 독립형 확장판을 일반 본판이나 종속 확장판으로 잘못 고정하지 않을 것
- 출처에 없는 관계를 이름이나 시리즈 유사성으로 추정하지 않을 것
- 아직 필요하지 않은 판본·재구현 관계까지 일반화하지 않을 것

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| `is_expansion` 불리언만 저장 | 적재와 필터가 단순하다. | 독립형 확장판과 호환 게임을 표현하지 못한다. | 제외 |
| 하나의 `game_type`으로 본판·종속·독립형을 구분 | 화면에 표시할 유형을 한 값으로 조회하기 쉽다. | 단독 플레이 가능 여부와 관계 역할이 섞이고, 한 게임의 여러 역할을 표현하기 어렵다. | 제외 |
| 단독 플레이 가능 여부와 확장 관계를 분리 | 두 질문을 각각 정확히 답하고, 필요한 화면 유형도 두 값을 조합해 만들 수 있다. | 컬럼과 관계 테이블을 함께 조회·검증해야 한다. | 선택 |
| 모든 게임 관계를 범용 `GAME_RELATIONS`로 관리 | 판본·재구현·합본까지 확장할 수 있다. | 아직 필요하지 않은 관계까지 추상화해 의미와 제약이 느슨해진다. | 보류 |

## 결정

아래 구조를 팀 논의안으로 제안한다.

### 1. 단독 플레이 가능 여부

`GAMES`에는 다음 값을 갖는 필수 `playability_type`을 둔다.

- `STANDALONE`: 다른 게임 없이 플레이 가능
- `REQUIRES_BASE_GAME`: 호환 게임이 있어야 플레이 가능
- `UNVERIFIED`: 출처가 없거나 서로 충돌해 판단할 수 없음

전체 BGG 스냅샷을 처음 재가공할 때는 다음처럼 매핑한다.

| BGG 입력 | 초기 `playability_type` | 방의 중심 게임 선택 |
| --- | --- | --- |
| `is_expansion = 0` | `STANDALONE` | 가능 |
| `is_expansion = 1` | `REQUIRES_BASE_GAME` | 불가능 |
| 값 누락 또는 출처 충돌 | `UNVERIFIED` | 불가능 |

BGG 원본 값과 매핑 근거는 배치 기록에 남긴다. 이후 더 신뢰할 수 있는 출처로 판단이 달라지면 검수 기록과 함께 값을 갱신한다.

### 2. 확장 관계

검증된 본판–확장판 연결은 `GAME_EXPANSIONS(base_game_id, expansion_game_id)`에 저장하고 두 식별자의 조합을 유일하게 유지한다. CSV의 이름이나 `is_expansion` 값만으로 관계를 만들지 않는다. 관계를 제공하는 BGG 상세 데이터와 매핑 결과를 확인한 뒤 반영한다.

화면에서 필요한 구분은 다음처럼 저장값을 조합해 판단한다.

| 표시할 개념 | 판단 기준 |
| --- | --- |
| 종속 확장판 | `REQUIRES_BASE_GAME`이면서 검증된 확장 관계가 있음 |
| 독립형 확장판 | `STANDALONE`이면서 다른 게임의 확장으로 연결됨 |
| 일반 게임 또는 본판 | `STANDALONE`이며 다른 게임의 확장으로 확인되지 않음 |
| 분류 미확인 | `UNVERIFIED`이거나 필요한 관계 검수가 끝나지 않음 |

`game_type` 컬럼을 별도로 두지 않는다. 위 표시값은 API나 조회 모델에서 `playability_type`과 확장 관계를 조합해 만든다.

### 3. 방 선택 규칙

`ROOMS.game_id`에는 `STANDALONE` 게임만 선택할 수 있다. `REQUIRES_BASE_GAME`과 `UNVERIFIED` 게임은 검색 결과에는 표시하되 방의 중심 게임으로 선택하지 못한다.

방에서 사용할 확장판을 고르는 기능이 제품 범위에 들어올 때만 `ROOM_EXPANSIONS(room_id, expansion_game_id)`를 추가한다. 선택한 확장판은 중심 게임과 검증된 `GAME_EXPANSIONS` 관계가 있어야 한다. 관계를 아직 수집하지 못한 확장판은 본판 필요 여부를 알더라도 방 확장판으로 선택할 수 없다.

`GAME_EXPANSIONS`는 game 도메인이, `ROOM_EXPANSIONS`는 room 도메인이 소유한다. room 도메인은 game 엔티티나 저장소를 직접 참조하지 않고 공개 계약으로 단독 플레이 가능 여부와 호환 관계를 확인한다.

## 결과

- 얻는 것: 단독 플레이 가능 여부와 확장 관계를 혼동하지 않는다. 독립형 확장판과 여러 본판에 연결되는 확장판도 같은 구조로 표현할 수 있다.
- 감수할 비용·위험: 화면 유형을 한 컬럼에서 바로 읽을 수 없고 관계 조회가 필요하다. 전체 CSV를 적재한 직후에는 관계가 비어 있으므로 일부 확장판을 방에서 사용할 수 없다.
- 후속 작업: 전체 데이터 재가공에서 `playability_type`을 만들고, BGG 상세 데이터로 `GAME_EXPANSIONS`를 생성하는 별도 검수 단계를 둔다. 이후 ERD·API·Flyway·Entity와 방 선택 계약을 변경하고 초기 매핑·출처 충돌·독립형 확장판·다중 호환 관계를 검증한다.

## 보류 및 재검토

- 지금 하지 않는 것: P0 스키마 변경, 방별 확장판 선택 구현, 판본·재구현·합본 관계, 확장판끼리의 선행·충돌 조건, 사용자 보유 확장판 관리
- 보류 이유: P0의 검수된 2,000건에는 확장판이 없고, 방별 확장판 선택 범위는 아직 제품 명세로 정해지지 않았다.
- 다시 검토할 조건: 확장판이 다른 확장판을 필수로 요구할 때, 판본·재구현 관계도 같은 화면에서 조회해야 할 때, BGG 외 여러 출처의 관계를 통합할 때
