# ADR-0036: 시간 기반 ROOM 자동 전환을 제한된 ID와 ROOM별 독립 처리로 수행

- 상태: 제안됨
- 작성일: 2026-07-31
- 결정일: 미정
- 관련: [P1 ROOM-09](../../p1/room.md#room-09-시간-기반-room-상태-자동-전환의-대량-처리-고도화), [P0 ROOM-06](../../archive/p0/room.md#room-06-방-상태-정합화), [ADR-0012](0012-room-request-boundary-state-reconciliation.md), [ADR-0005](../participation/0005-room-participation-optimistic-locking.md), [ADR-0037](../participation/0037-room-waitlist-latest-state-atomic-promotion.md), [`RoomRepository.findDueRooms`](../../../src/main/java/cloud/bamsongi/albammate/room/repository/RoomRepository.java), [`RoomStatusCorrectionExecutor`](../../../src/main/java/cloud/bamsongi/albammate/room/statuscorrection/RoomStatusCorrectionExecutor.java)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

ADR-0012는 API 요청 경계와 내부 스케줄러가 같은 시간 기반 ROOM 전이 규칙을 사용하도록 결정했다. 현재 스케줄러 실행 경로는 전환 대상 ROOM Entity 전체를 목록으로 조회하고 한 실행 단위에서 순서대로 처리한다. 대상 수가 늘어나면 한 번에 적재하는 Entity 수와 트랜잭션 범위가 함께 커지고, 특정 ROOM의 실패가 다른 ROOM의 처리 결과에 영향을 줄 수 있다. 실패한 ROOM을 식별해 그 대상만 다시 처리하기도 어렵다.

P1 대기열에서는 시작 시각에 ROOM 상태를 전환하는 것뿐 아니라 남은 대기열도 종료해야 한다. 정원 충족으로 이미 `CLOSED`인 ROOM도 시작 경계에서 대기열 종료 대상이므로, 단순 상태 일괄 갱신만으로는 ROOM별 후속 규칙을 함께 보장하기 어렵다.

이 결정은 다음 기준을 우선한다.

- P0의 `RECRUITING → CLOSED → FINISHED` 시간 조건과 ADR-0012의 요청 경계·내장 스케줄러 역할을 유지한다.
- 처리 대상 증가가 서버 메모리와 한 트랜잭션의 범위를 무제한으로 키우지 않게 한다.
- 한 ROOM의 실패를 다른 ROOM의 성공과 격리하고 실패 대상을 식별할 수 있게 한다.
- 각 ROOM을 최신 상태와 버전으로 다시 판단해 동시 명령의 결과를 덮어쓰지 않는다.
- 측정 근거 없이 JPA 상태 전이를 DB 직접 갱신으로 바꾸지 않는다.

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 전환 대상 ROOM Entity 전체를 한 번에 조회해 하나의 실행 단위에서 처리 | 구현이 단순하고 현재 Entity 전이 규칙을 그대로 호출할 수 있다. | 대상 수에 상한이 없고 메모리·트랜잭션 범위와 실패 영향 범위가 커진다. ROOM별 실패 식별과 재처리가 어렵다. | 제외 |
| 제한된 수의 ROOM ID를 선별하고 각 ROOM을 최신 상태로 다시 읽어 독립 처리 | 한 번에 다루는 대상을 제한하고 ROOM별 실패 격리·식별·재처리가 가능하다. 기존 도메인 전이와 버전 검사를 유지할 수 있다. | ROOM별 조회와 트랜잭션 비용이 늘고, 선별 순서·반복·재시도 정책을 별도로 정해야 한다. | 선택 |

## 결정

시간 기반 자동 전환의 스케줄러 경로는 한 번에 모든 ROOM Entity를 적재하지 않는다. 전환 또는 시작 경계 처리가 필요할 수 있는 ROOM ID를 제한된 수로 선별하고, 선별된 각 ROOM을 독립된 처리 단위에서 최신 상태와 버전으로 다시 읽어 기존 도메인 전이 규칙을 적용한다.

ROOM별 처리는 서로의 커밋 결과를 공유하지 않는다. 한 ROOM이 실패해도 이미 성공한 다른 ROOM의 결과를 롤백하지 않으며, 실패한 ROOM ID와 원인을 식별해 그 ROOM만 다시 처리할 수 있어야 한다. 동시에 실행된 참가·취소·종료 요청이 만든 최신 최종 상태를 자동 전환이 덮어쓰지 않도록 상태 조건과 낙관적 버전 계약을 유지한다.

`startsAt`에 도달한 ROOM은 정원 충족으로 이미 `CLOSED`인지와 관계없이 남은 대기열을 종료한다. 해당 ROOM의 상태 판정과 대기열 종료 사이에 부분 성공 상태가 남지 않도록 같은 ROOM 처리의 일관성 경계 안에서 수행한다.

API 요청 경계의 현재 상태 판정과 요청이 없는 ROOM을 정리하는 내장 스케줄러라는 ADR-0012의 역할은 유지하며, 양쪽은 같은 도메인 전이 규칙을 사용한다. 이 ADR은 ADR-0012를 대체하지 않고 스케줄러의 다수 ROOM 처리 경계를 구체화한다.

한 번에 선별할 ID 수와 한 실행에서의 반복 상한, 재시도 횟수와 실행 주기의 운영 고정값은 이 ADR에서 임의로 정하지 않는다. 현재 구현을 비교 기준선으로 남기고 제한 처리의 후보값을 같은 조건에서 측정한 뒤 초기 운영값을 확정한다. 이 값들은 측정으로 조정할 운영값이며, 제한된 ID 선별과 ROOM별 독립 처리라는 결정 자체를 바꾸지 않는 조정에는 새 ADR을 요구하지 않는다.

측정 데이터 규모와 후보값, 선별 순서, 구체적인 트랜잭션 전파 방식과 관측 항목은 [P1 ROOM 명세](../../p1/room.md)의 `이슈 생성 전 결정`에 명시한다. 에이전트는 측정 전에 성능 합격 수치나 운영 고정값을 임의로 만들지 않는다.

DB 직접 갱신은 현재 선택하지 않는다. 제한된 ROOM별 처리의 기준선을 먼저 측정하고 병목이 확인된 뒤, 상태 조건·버전·대기열 일관성·변경 ROOM 식별·실패 관측을 같은 수준으로 검증할 비교안이 마련된 경우에만 사용자 승인과 후속 ADR로 재검토한다.

## 결과

- 얻는 것:
    - 한 번에 적재하는 대상과 작업 범위를 제한할 수 있다.
    - ROOM 하나의 실패를 다른 ROOM의 성공에서 격리하고 실패 ID만 재처리할 수 있다.
    - 기존 도메인 상태 전이와 낙관적 버전 검사를 유지하면서 대기열 종료를 ROOM 단위로 묶을 수 있다.
- 감수할 비용·위험:
    - 전체 일괄 갱신보다 데이터베이스 요청과 독립 트랜잭션 수가 늘어 처리량이 낮을 수 있다.
    - 선별 순서와 반복 정책이 부적절하면 오래된 대상이 지연되거나 같은 실패 대상이 반복 선택될 수 있다.
    - 실패 격리만으로 재시도 폭주를 막을 수 없으므로 운영 정책과 관측 기준이 필요하다.
- 후속 작업:
    - 측정 데이터 규모·후보값·선별 순서·반복 조건과 로그·메트릭을 이슈 생성 전에 확정한다.
    - 제한 ID 조회와 ROOM별 독립 처리, 대기열 종료의 트랜잭션 경계를 구현한다.
    - PostgreSQL에서 현재 구현과 제한 처리 후보를 같은 조건으로 측정하고, 시간 경계와 참가·대기 변경의 동시 실행을 검증한 뒤 처리량·실행시간·DB 비용을 근거로 초기 운영값을 확정한다.

## 보류 및 재검토

- 지금 하지 않는 것: 제한 범위의 조건부 DB 직접 갱신, 외부 스케줄러·작업 큐와 다중 인스턴스 분배
- 보류 이유: 현재는 ROOM별 실패 식별과 대기열 일관성을 우선하며, 직접 갱신 또는 외부 분산이 필요한 병목과 운영 요구가 측정되지 않았다.
- 다시 검토할 조건: 제한된 ROOM별 처리의 재현 가능한 측정에서 처리 지연·미처리 누적·DB 비용이 실제 문제로 확인되어 사용자가 비교를 승인하거나, 다중 인스턴스 중복 실행·처리 지연 SLA가 실제 운영 요구로 확인될 때
