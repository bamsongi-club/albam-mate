# ADR-0036: 시간 기반 ROOM 자동 전환을 제한된 ID와 ROOM별 독립 처리로 수행

- 상태: 승인됨
- 작성일: 2026-07-31
- 결정일: 2026-08-01
- 관련: [P1 ROOM-09](../../archive/p1/room.md#room-09-시간-기반-room-상태-자동-전환의-대량-처리-고도화), [P0 ROOM-06](../../archive/p0/room.md#room-06-방-상태-정합화), [ADR-0012](0012-room-request-boundary-state-reconciliation.md), [ADR-0005](../participation/0005-room-participation-optimistic-locking.md), [ADR-0037](../participation/0037-room-waitlist-latest-state-atomic-promotion.md), [ADR-0038 다중 인스턴스 스케줄 실행 조정](../platform/0038-multi-instance-session-and-scheduler-coordination.md), [`RoomRepository.findDueRooms`](../../../src/main/java/cloud/bamsongi/albammate/room/repository/RoomRepository.java), [`RoomStatusCorrectionExecutor`](../../../src/main/java/cloud/bamsongi/albammate/room/statuscorrection/RoomStatusCorrectionExecutor.java)
- 대체 대상: 없음

## 맥락

ADR-0012는 API 요청 경계와 내부 스케줄러가 같은 시간 기반 ROOM 전이 규칙을 사용하도록 결정했다. 현재 스케줄러 실행 경로는 전환 대상 ROOM Entity 전체를 목록으로 조회하고 한 실행 단위에서 순서대로 처리한다. 대상 수가 늘어나면 한 번에 적재하는 Entity 수와 트랜잭션 범위가 함께 커지고, 특정 ROOM의 실패가 다른 ROOM의 처리 결과에 영향을 줄 수 있다. 실패한 ROOM을 식별해 그 대상만 다시 처리하기도 어렵다.

P1 대기열에서는 시작 시각에 ROOM 상태를 전환하는 것뿐 아니라 남은 대기열도 종료해야 한다. 정원 충족으로 이미 `CLOSED`인 ROOM도 시작 경계에서 대기열 종료 대상이므로, 단순 상태 일괄 갱신만으로는 ROOM별 후속 규칙을 함께 보장하기 어렵다.

이 결정은 다음 기준을 우선한다.

- P0의 `RECRUITING → CLOSED → FINISHED` 시간 조건과 ADR-0012의 요청 경계·내장 스케줄러 역할을 유지한다.
- 처리 대상 증가가 서버 메모리와 한 트랜잭션의 범위를 무제한으로 키우지 않게 한다.
- 한 ROOM의 실패를 다른 ROOM의 성공과 격리하고 실패 대상을 식별할 수 있게 한다.
- 같은 실패 ROOM이 제한된 선별 한도를 반복해서 점유해도 다른 due ROOM이 처리 기회를 얻는 진척성을 보장한다.
- 각 ROOM을 최신 상태와 버전으로 다시 판단해 동시 명령의 결과를 덮어쓰지 않는다.
- 측정 근거 없이 JPA 상태 전이를 DB 직접 갱신으로 바꾸지 않는다.

## 결정

시간 기반 자동 전환의 스케줄러 경로는 한 번에 모든 ROOM Entity를 적재하지 않는다. 전환 또는 시작 경계 처리가 필요할 수 있는 ROOM ID를 제한된 수로 선별하고, 선별된 각 ROOM을 독립된 처리 단위에서 최신 상태와 버전으로 다시 읽어 기존 도메인 전이 규칙을 적용한다.

다중 인스턴스의 실행 주체는 [ADR-0038](../platform/0038-multi-instance-session-and-scheduler-coordination.md)을 따른다. 모든 인스턴스가 ROOM 상태 자동 전환 Spring Scheduler를 등록하되, 유효한 잠금 임대 동안에는 현재 PostgreSQL ShedLock을 얻은 실행 주체만 새 후보 선별을 시작하고 잠금을 얻지 못한 인스턴스는 기다리지 않고 해당 실행을 건너뛴다. 이전 실행이 끝나기 전에 임대가 만료되면 이전·신규 실행 주체가 겹칠 수 있으며, 이때는 아래 영속 진행 상태 불변식으로 수렴한다. 잠금 획득·해제 트랜잭션은 cursor 진행 상태와 각 ROOM 처리 트랜잭션에 결합하지 않으며, 잠금은 ROOM별 상태·버전 검사나 업무 정합성을 대체하지 않는다.

제한된 ID 선별은 결정적 due 순서, cursor와 고정된 순회 경계를 기준선으로 사용한다. 각 순회를 시작할 때 순회 기준 시각(`turn cutoff`)을 고정하고, 그 순회에서는 논리적 처리 예정 시각이 순회 기준 시각 이하인 ROOM만 대상으로 삼는다. 이 순서는 불변 키를 저장한다는 뜻이 아니라, 각 선별 시점에 ROOM에 남은 시간 기반 작업 중 가장 이른 논리적 처리 예정 시각과 `roomId`를 오름차순으로 비교해 `(논리적 처리 예정 시각, roomId)` 키를 결정적으로 재계산한다는 뜻이다. `roomId`는 같은 논리적 처리 예정 시각의 동률을 해소한다. 논리적 처리 예정 시각은 `RECRUITING` 상태 전환과 시작 경계 대기열 종료의 `startsAt`, `CLOSED → FINISHED` 전환의 `startsAt + 24시간`을 모두 포괄하며, 이미 `CLOSED`여도 시작 경계 대기열 종료가 남아 있으면 `startsAt`을 사용한다. 한 ROOM의 시간 기반 작업을 완료한 뒤 남은 다음 논리적 처리 예정 시각은 직전 선별에 사용한 시각과 같거나 뒤로만 이동하거나 더 이상 존재하지 않아야 한다.

한 순회에서는 `(논리적 처리 예정 시각, roomId)`가 cursor 뒤이면서 논리적 처리 예정 시각이 순회 기준 시각 이하인 ROOM만 선별한다. cursor는 ROOM 처리 뒤 재계산한 키가 아니라 처리 성공 여부와 무관하게 마지막으로 시도한 선별 위치를 기준으로 전진한다. 이 범위에서 선별 결과가 비면 현재 순회를 마치고 cursor를 처음으로 회전하며, 다음 선별을 시작할 때 새로운 순회 기준 시각을 고정한다. 순회 시작 뒤 새로 due가 된 ROOM은 현재 순회를 연장하지 않고 다음 순회부터 선별한다. 따라서 스케줄러 실행이 계속되고 한 순회 기준 시각의 due ROOM 집합이 유한하면, cursor보다 큰 키의 신규 due ROOM이 계속 유입되거나 같은 ROOM이 반복 실패해도 현재 순회는 유한하게 끝나고 cursor 앞의 due ROOM도 다음 순회에서 다시 처리 기회를 얻어야 한다. 반복 실행 때마다 같은 앞순번으로 초기화하거나, 신규 due ROOM 때문에 순회를 닫지 못해 다른 due ROOM을 무기한 지연시키는 방식은 허용하지 않는다.

cursor와 진행 중인 순회의 기준 시각은 애플리케이션 메모리에만 두지 않고 인스턴스 재시작과 ShedLock 실행 주체 변경 뒤에도 같은 순회를 이어갈 수 있는 영속 저장 경계에 둔다. 구체적인 저장 위치, 마지막 선별 위치의 갱신 시점, 순회 기준 시각의 생성·갱신과 wrap-around 표현, 순회 전환 또는 ROOM 처리 사이에서 장애가 발생했을 때의 재선별·복구 범위는 구현 전에 확정한다. 어떤 경계를 선택하더라도 처리 중 장애가 ROOM을 영구히 건너뛰거나 같은 앞순번부터 다시 시작하거나 현재 순회를 무한히 연장해 다른 due ROOM을 무기한 지연시키지 않아야 한다.

ShedLock 임대 만료로 이전 실행 주체와 신규 실행 주체가 겹쳐도 영속 진행 상태는 이미 관측된 진척보다 역행하거나 갱신을 잃거나 조기에 wrap-around해서는 안 된다. 순회 기준 시각은 뒤로 이동하지 않고, 같은 순회 기준 시각 안의 cursor는 마지막으로 확정된 선별 위치보다 앞으로만 이동한다. wrap-around는 최신 진행 상태에서 현재 순회의 남은 선별 대상이 없음을 확인한 실행 주체가 더 뒤의 순회 기준 시각과 처음 cursor를 하나의 원자적 변경으로 확정할 때만 허용한다. 각 실행 주체는 선별 때 읽은 진행 상태의 version 또는 실행 generation을 갱신 조건으로 제출해야 하며, 신규 실행 주체가 진척을 확정한 뒤 이전 실행 주체가 늦게 제출한 cursor 전진·순회 전환은 적용하지 않고 거절해야 한다. 행 잠금 방식을 선택해도 잠금 획득 뒤 최신 진행 상태와 기대 version·generation을 다시 비교해 stale 갱신을 거절해야 하며, 단순히 쓰기를 직렬화하는 것만으로는 이 계약을 충족하지 않는다. 행 잠금과 조건부 갱신, compare-and-set, fencing 중 어떤 방식을 사용할지는 구현 전에 확정하되 이 불변식을 약화할 수 없다.

ROOM별 처리는 서로의 커밋 결과를 공유하지 않는다. 한 ROOM이 실패해도 이미 성공한 다른 ROOM의 결과를 롤백하지 않고, 같은 실행에서 아직 처리하지 않은 다른 선별 ROOM의 처리도 중단하지 않는다. 실패한 ROOM ID와 원인을 식별해 그 ROOM만 다시 처리할 수 있어야 한다. 동시에 실행된 참가·취소·종료 요청이 만든 최신 최종 상태를 자동 전환이 덮어쓰지 않도록 상태 조건과 낙관적 버전 계약을 유지한다.

`startsAt`에 도달한 ROOM은 정원 충족으로 이미 `CLOSED`인지와 관계없이 남은 대기열을 종료한다. 해당 ROOM의 상태 판정과 대기열 종료 사이에 부분 성공 상태가 남지 않도록 같은 ROOM 처리의 일관성 경계 안에서 수행한다.

API 요청 경계의 현재 상태 판정과 요청이 없는 ROOM을 정리하는 내장 스케줄러라는 ADR-0012의 역할은 유지하며, 양쪽은 같은 도메인 전이 규칙을 사용한다. 이 ADR은 ADR-0012를 대체하지 않고 스케줄러의 다수 ROOM 처리 경계를 구체화한다.

한 번에 선별할 ID 수와 한 실행에서의 반복 상한, 재시도 횟수와 실행 주기의 운영 고정값은 이 ADR에서 임의로 정하지 않는다. 현재 구현을 비교 기준선으로 남기고 제한 처리의 후보값을 같은 조건에서 측정한 뒤 초기 운영값을 확정한다. 이 값들은 측정으로 조정할 운영값이며, 제한된 ID 선별과 ROOM별 독립 처리라는 결정 자체를 바꾸지 않는 조정에는 새 ADR을 요구하지 않는다.

측정 데이터 규모와 후보값, 논리적 처리 예정 시각과 `roomId` 정렬, 영속 cursor와 순회 기준 시각의 저장 위치·갱신 시점·wrap-around·장애 재선별과 복구 방식, 임대 만료 중첩 실행의 진척성 동시성 제어, 구체적인 트랜잭션 전파 방식과 관측 항목은 [P1 ROOM 명세](../../archive/p1/room.md)의 `구현 전 결정`에 명시한다. cursor와 순회 경계의 구현 방식은 이 ADR의 진척성 불변식과 ADR-0038의 실행 주체 계약을 약화하지 않아야 한다. 에이전트는 측정 전에 성능 합격 수치나 운영 고정값을 임의로 만들지 않는다.

실패 backoff·격리는 현재 기준선에 추가하지 않는다. cursor 회전 기준선의 측정에서 영구 실패 ROOM의 반복 시도 비용이나 재시도 폭주가 실제 문제로 확인되면, 실패 상태의 저장·복구·해제 정책과 backoff 후보값을 제시하고 사용자 승인 뒤 비교한다. backoff를 추가하더라도 다른 due ROOM의 진척성 불변식은 유지한다.

DB 직접 갱신은 현재 선택하지 않는다. 제한된 ROOM별 처리의 기준선을 먼저 측정하고 병목이 확인된 뒤, 상태 조건·버전·대기열 일관성·변경 ROOM 식별·실패 관측을 같은 수준으로 검증할 비교안이 마련된 경우에만 사용자 승인과 후속 ADR로 재검토한다.

## 결과

- 얻는 것:
    - 한 번에 적재하는 대상과 작업 범위를 제한할 수 있다.
    - ROOM 하나의 실패를 다른 ROOM의 성공에서 격리하고 실패 ID만 재처리할 수 있다.
    - 같은 실패 ROOM이 선별 한도를 반복해서 점유해도 다른 due ROOM이 한 순회 안에 처리 기회를 얻는다.
    - 인스턴스 수가 늘어도 유효한 잠금 임대 하나가 새 ROOM 후보 선별 시작을 조정하고, 임대 만료 중첩은 영속 진행 상태 불변식으로 수렴한다.
    - 기존 도메인 상태 전이와 낙관적 버전 검사를 유지하면서 대기열 종료를 ROOM 단위로 묶을 수 있다.
- 감수할 비용·위험:
    - 전체 일괄 갱신보다 데이터베이스 요청과 독립 트랜잭션 수가 늘어 처리량이 낮을 수 있다.
    - 논리적 처리 예정 시각 정렬과 영속 cursor·순회 기준 시각의 저장·갱신·복구를 일관되게 구현해야 하며, 신규 due ROOM은 다음 순회까지 기다릴 수 있고 영구 실패 ROOM은 전체 순회마다 다시 시도된다.
    - ShedLock 임대 만료로 실행이 겹칠 수 있으므로 이전 실행 주체의 늦은 진행 상태 갱신을 차단하는 동시성 제어가 필요하다.
    - PostgreSQL 잠금 행과 임대 시간을 운영하고 잠금 획득 실패·실행시간·주체 변경을 관측해야 한다.
    - 실패 격리만으로 재시도 폭주를 막을 수 없으므로 운영 정책과 관측 기준이 필요하다.
- 후속 작업:
    - 측정 데이터 규모·후보값·논리적 처리 예정 시각과 `roomId` 정렬·영속 cursor와 순회 기준 시각의 저장과 갱신·wrap-around·장애 재선별과 복구·임대 만료 중첩 갱신 제어·반복 조건·로그·메트릭을 구현 전에 확정한다.
    - ROOM 상태 보정용 잠금 이름, `lockAtMostFor`와 실행시간 경고 기준을 측정 근거로 확정한다.
    - 제한 ID 조회와 ROOM별 독립 처리, 대기열 종료의 트랜잭션 경계를 구현한다.
    - PostgreSQL에서 현재 구현과 제한 처리 후보를 같은 조건으로 측정하고, 반복 실패 ROOM과 연속 신규 due ROOM 유입이 있는 고정 순회 경계의 cursor 전진·회전, 인스턴스 재시작·ShedLock 실행 주체 변경·임대 만료 중첩 실행 주체 갱신·처리 중 장애 뒤 영속 진행 상태 복구와 시간 경계·참가·대기 변경의 동시 실행을 검증한 뒤 처리량·실행시간·DB 비용을 근거로 초기 운영값을 확정한다.

## 보류 및 재검토

- 지금 하지 않는 것: 제한 범위의 조건부 DB 직접 갱신, 외부 스케줄러·작업 큐, Quartz 클러스터, Redis 분산 락
- 보류 이유: 현재는 ROOM별 실패 식별·진척성·대기열 일관성과 ADR-0038의 PostgreSQL 단일 실행 조정으로 요구를 충족하며, 영속 Job 복구나 Redis 업무 락이 필요한 근거가 없다.
- 다시 검토할 조건: 제한된 ROOM별 처리의 재현 가능한 측정에서 처리 지연·미처리 누적·DB 비용 또는 영구 실패 ROOM의 반복 시도 비용이 실제 문제로 확인되어 사용자가 backoff·직접 갱신 비교를 승인하거나, 동적 Trigger·Misfire·영속 Job 복구가 실제 요구가 될 때

## 검증

- 상태: 미검증
- 근거:
    - 구현: `V22__create_room_status_correction_progress.sql`과 `RoomStatusCorrectionCandidateSelector`·`RoomStatusCorrectionCoordinator`·`RoomStatusCorrectionProgressStore`·`RoomStatusCorrectionScheduler`가 제한 ID 선별, ROOM별 독립 처리, 영속 turn cutoff·cursor와 generation/version CAS를 구현한다.
    - 단위 검증: `RoomStatusCorrectionCandidateSelectorTest`, `RoomStatusCorrectionBoundedCoordinatorTest`, `RoomStatusCorrectionSchedulerLockTest`가 결정적 순서, 실패 격리, cursor 전진·회전, 잠금 미획득과 stale 실행 주체 중단을 검증한다.
    - PostgreSQL 검증: `RoomStatusCorrectionBoundedPostgresTest`, `RoomStatusCorrectionProgressPostgresTest`, `RoomStatusCorrectionProgressLocalMultiPostgresTest`가 대기열 종료와 ROOM 상태의 원자성, 재시작·장애 재선별, `local` 두 인스턴스의 ShedLock 임대 경쟁과 progress CAS를 검증한다.
    - 기준선 측정: [ROOM-09c 현행 일괄 처리 기준선](../../measurements/room-09-bounded-processing-baseline.md)이 데이터 규모별 처리량·실행시간·PostgreSQL 비용의 재현 계약을 남긴다.
    - 후보 측정과 초기 운영값: 같은 문서의 ROOM-09d 절이 현행과 제한 처리 후보를 같은 규모의 fixture로 측정해 대비 표와 보존 원자료를 남기고, 그 결과로 한 번당 ID 수 `100`, 실행시간 경고 `180s`, `lockAtMostFor` `10m`을 확정했다. `RoomStatusCorrectionPropertiesTest`가 확정값이 생산 `application.yml`과 설정 바인딩에 동일하게 적용되는지 검증한다.
    - 측정이 보여준 경계: 후보는 ROOM당 비용이 규모와 무관하게 약 `12ms`로 평탄하고, 현행은 중형까지 상각 효과로 유리하다가 대형에서 역전당한다. 이 결정이 우선한 기준은 메모리·트랜잭션 범위 제한, 실패 격리와 진척성이며 처리 속도가 아니다. 따라서 측정은 결정을 바꾸지 않고 초기 운영값을 정하는 근거로만 사용했다.
- 미검증:
    - 측정 결과가 요구하면 실패 backoff·격리 또는 제한 범위의 조건부 DB 직접 갱신 비교 착수 여부를 사용자 결정으로 남겨야 한다.
