# ADR-0004: 방의 시간 기반 상태 전이에 내장 스케줄러를 사용

- 상태: 승인됨
- 작성일: 2026-07-23
- 결정일: 2026-07-24
- 관련: [ADR-0001](../platform/0001-java-21-spring-boot-4-baseline.md), [ADR-0002](../platform/0002-postgresql-primary-database.md), [ADR-0009](../platform/0009-utc-time-standard.md), [P0 방 상태 전이 계약](../../P0-spec.md#방-상태roomstatus)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

방은 개설자가 상태 변경을 잊더라도 모집과 모임 종료를 시간 기준에 따라 자동으로 반영해야 한다. 팀은 사용자의 조회 요청이 들어올 때만 상태를 계산하는 방식, Java·Spring 내장 스케줄러로 주기적으로 갱신하는 방식, Quartz 같은 외부 스케줄러를 도입하는 방식을 비교했다.

현재 P0에서 필요한 작업은 특정 초에 한 번만 실행해야 하는 예약 작업이 아니라, 기준 시각이 지난 방을 주기적으로 찾아 조건에 맞는 상태로 갱신하는 작업이다. 현재 범위에서 다중 인스턴스 실행 조정 요구는 확인되지 않았다.

[P0 방 상태 전이 계약](../../P0-spec.md#방-상태roomstatus)은 방을 `RECRUITING`으로 생성하고, 시작 시각에 도달하면 `CLOSED`로, `CLOSED`인 방이 `startsAt + 24시간`에 도달하면 시스템이 `FINISHED`로 전환하도록 정한다. 정원 도달·참가 취소·개설자 명령으로 발생하는 전이는 해당 사용자 명령의 트랜잭션에서 처리한다.

이번 결정의 기준은 다음과 같다.

- 개설자의 수동 처리에 의존하지 않고 시간 기반 상태를 갱신할 것
- 같은 작업이 다시 실행돼도 결과가 달라지지 않도록 조건부 갱신과 멱등성을 확보할 것
- 현재 단순한 주기 작업을 위해 별도 스케줄링 시스템을 미리 운영하지 않을 것
- 정확한 시각 실행이나 다중 인스턴스 조정이 필요해지면 다시 비교할 수 있을 것

방 상태 이름과 각 전이의 기준 시각은 P0 계약을 따른다. 이 ADR은 해당 값을 다시 정의하지 않고 시간 기반 전이를 실행하는 기술 방식만 다루며, 실행 주기는 구현 시 정한다.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| Java·Spring 내장 스케줄러 | 현재 Spring 애플리케이션 안에서 단순한 주기 작업을 구현할 수 있고 별도 스케줄링 시스템을 운영하지 않아도 된다. | 실행 주기만큼 상태 반영이 늦을 수 있다. 다중 인스턴스에서는 같은 작업이 중복 실행될 수 있으므로 조건부 갱신과 멱등성이 필요하다. | 선택 |
| Quartz 등 외부 스케줄러 | 정확한 시각 실행과 다중 인스턴스의 실행 조정이 필요할 때 확장 후보가 될 수 있다. | 현재 P0 요구보다 설정과 운영 범위가 커지고 별도 의존성을 관리해야 한다. | 보류 |
| 조회·명령 요청 시 상태를 계산하거나 갱신 | 별도 주기 작업이 필요 없다. | 요청이 없는 방의 저장 상태가 바뀌지 않고, 개설자가 처리하지 않은 종료 상태를 서버가 일정하게 정리하기 어렵다. | 제외 |

## 결정

Albam Mate의 P0에서 방의 시간 기반 상태 전이는 Java·Spring 내장 스케줄러로 처리한다. 스케줄러는 다음 P0 계약을 주기적으로 적용한다.

- `RECRUITING`이고 `now >= startsAt`인 방을 `CLOSED`로 전환한다.
- `CLOSED`이고 `now >= startsAt + 24시간`인 방을 `FINISHED`로 전환한다.

현재 시각은 [ADR-0009](../platform/0009-utc-time-standard.md)에 따라 UTC 기준 `Clock`에서 얻는다. 스케줄러는 전이 전 상태와 기준 시각을 조건으로 갱신하고, 반복 실행돼도 같은 결과가 되도록 멱등하게 구현한다.

정원 도달, 참가 취소, 개설자의 방 취소·종료처럼 사용자 명령으로 발생하는 상태 변화는 스케줄러가 아니라 해당 명령의 트랜잭션에서 처리한다. 스케줄러의 실행 주기, 배치 크기와 트랜잭션 경계는 구현에서 정하되 P0의 전이 조건은 변경하지 않는다.

## 결과

- 얻는 것: 별도 스케줄링 시스템 없이 방의 시간 기반 상태를 P0 계약에 맞춰 주기적으로 정리할 수 있다.
- 감수할 비용·위험: 상태 반영은 실행 주기만큼 늦을 수 있고, 다중 인스턴스에서는 중복 실행 가능성이 있으므로 데이터베이스 조건과 멱등성으로 방어해야 한다.
- 후속 작업: 실행 주기와 배치 크기를 정하고, P0 전이 조건·조건부 갱신·반복 실행·부분 실패를 검증하는 테스트를 추가한다.

## 보류 및 재검토

- 지금 하지 않는 것: Quartz 등 외부 스케줄러 도입, 다중 인스턴스의 작업 실행 조정 방식 확정
- 보류 이유: 현재는 단순한 주기 갱신만 필요하고 정확한 시각 실행이나 여러 서버 간 작업 조정 요구가 확인되지 않았다.
- 다시 검토할 조건: 애플리케이션을 다중 인스턴스로 운영하면서 중복 실행이 문제가 될 때, 특정 시각의 정확한 실행 보장이 필요할 때
