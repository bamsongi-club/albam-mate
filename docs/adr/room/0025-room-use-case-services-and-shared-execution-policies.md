# ADR-0025: 방 유스케이스 Service 유지와 실행 정책 공통화

- 상태: 승인됨
- 작성일: 2026-07-30
- 결정일: 2026-07-30
- 관련: [Issue #208](https://github.com/bamsongi-club/albam-mate/issues/208), [PR #210](https://github.com/bamsongi-club/albam-mate/pull/210), [아키텍처](../../ARCHITECTURE.md), [ADR-0005](../participation/0005-room-participation-optimistic-locking.md), [ADR-0012](0012-room-request-boundary-state-reconciliation.md)
- 대체 대상: 없음
- 후속 ADR: 없음

## 맥락

방 기능은 목록·상세·내 모임 조회와 생성·수정·참가·취소·종료마다 권한, 오류 우선순위와 트랜잭션 경계가 다르다. 클래스 수만 줄이려고 조회와 변경을 각각 하나의 Facade로 합치면 서로 다른 유스케이스가 함께 변경되고 독립 트랜잭션과 재시도 경계가 흐려진다.

반대로 유스케이스별 Service와 Executor를 평면 패키지에 계속 추가하면 탐색 비용이 커지고, 기준 시각 고정·낙관 락 재시도·상태 보정처럼 실행 방식이 같은 정책이 중복될 수 있다.

## 검토한 대안

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 조회·변경 Facade로 합치고 Service 수를 고정 | Controller 의존성과 클래스 수가 줄어든다. | 유스케이스별 권한·오류·트랜잭션 변경이 한 클래스에 결합된다. | 제외 |
| 유스케이스별 클래스를 평면 패키지에 유지 | 구조 변경이 작고 한 파일의 책임이 좁다. | 기능 증가에 따라 탐색 비용과 공통 실행 정책의 중복이 커진다. | 제외 |
| 유스케이스별 클래스를 유지하고 역할별 폴더와 공통 실행 정책을 사용 | 업무 경계와 트랜잭션 경계를 보존하면서 탐색과 정책 중복을 줄인다. | 내부 협력자와 하위 폴더가 늘어난다. | 선택 |

## 결정

- 방의 외부 유스케이스는 Service 단위로 유지하고 모든 조회·변경을 하나의 Facade로 합치지 않는다.
- 조회는 `room/service/query`, 변경은 `room/service/command`, 자동 상태 보정은 `room/statuscorrection`에 둔다.
- 유스케이스별 업무 규칙과 권한·오류 우선순위는 해당 Service와 Executor가 소유한다.
- 기준 시각 고정, 낙관 락 재시도와 자동 상태 보정처럼 실패 의미와 실행 방식이 같은 정책만 Coordinator와 Retrier로 공통화한다.
- 재시도하는 변경은 트랜잭션 없는 Service·Coordinator와 시도마다 `REQUIRES_NEW`를 시작하는 Executor를 분리한다. 재시도하지 않는 방 생성에는 이 분리를 강제하지 않는다.
- 시간 기반 상태 전이 규칙은 `Room` Entity의 단일 보정 메서드가 소유하며 상태 보정과 상태 의존 변경은 이를 호출한다.
- Controller는 엔드포인트 수가 아니라 HTTP 리소스와 변경 이유로 나눈다.
- Service 개수를 목표값으로 고정하지 않는다.

## 결과

- 얻는 것: 유스케이스별 업무·트랜잭션 경계를 유지하면서 query·command·statuscorrection에서 관련 코드를 찾을 수 있다. 공통 실행 정책은 한곳에서 변경한다.
- 감수할 비용·위험: 파일 수와 내부 호출 단계가 유지되며, 역할별 폴더를 넘나드는 변경이 생길 수 있다.
- 후속 작업: 방 패키지를 결정한 폴더로 이동하고 Coordinator·Retrier의 직접 사용자와 트랜잭션 경계를 구조·동작 테스트로 고정한다.

## 보류 및 재검토

- 지금 하지 않는 것: Entity·Repository·데이터베이스를 나누는 CQRS, 고정된 Service 개수, 모든 Command를 묶는 Facade
- 보류 이유: 현재 문제는 업무 모델 분리가 아니라 탐색성과 실행 정책 중복이며 기존 트랜잭션 경계를 유지해야 한다.
- 다시 검토할 조건: 실시간 매칭처럼 방과 독립된 수명주기·불변식·확장 요구를 가진 기능이 생기거나, 현재 호출 단계가 측정 가능한 유지보수 병목이 될 때
