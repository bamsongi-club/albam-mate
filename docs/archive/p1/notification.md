# P1 알림 구현 명세

이 문서는 최종 성공한 방·참가 변경을 사용자별 서비스 내 웹 알림으로 전달하고, 본인 알림을 조회·읽음 처리하는 `NOTI-01`~`NOTI-03`의 구현 규칙과 완료 기준을 정의한다. 현재 계약·생산 코드·자동 검증·운영 상태는 [P1 기능 종료 상태](README.md#기능별-종료-상태)을 따른다. 여기서 앱 내 알림은 브라우저나 OS의 Web Push가 아니라 Albam Mate 웹 알림함을 뜻한다.

공통 범위와 개인정보 원칙은 [P1 공통 명세](P1-spec.md), P1 HTTP 계약은 [API 명세](../../API.md), 저장 계약은 [ERD의 P1 알림 저장 계약](../../ERD.md#p1-알림-저장-계약), 모듈과 트랜잭션 구조는 [아키텍처](../../ARCHITECTURE.md)를 따른다. 이 문서는 해당 정본의 계약을 구현·검증할 기준이며, 문서 존재만으로 현재 제공 상태를 판정하지 않는다.

알림 원인·수신자·트랜잭션·중복 방지·조회 권한의 공통 불변식은 [알림 생성과 조회](P1-spec.md#알림-생성과-조회)에 한 번만 둔다. 이 문서는 알림 유형 매핑, 기능별 HTTP·화면 동작과 완료 기준만 추가한다.

`NOTI-01`~`NOTI-03`은 사용자 관점의 제품 기능 ID이자 하위 구현 완료 단위를 묶는 상위 ID다. 각 기능 아래의 `NOTI-01a` 같은 하위 ID는 하나의 이슈·브랜치·PR로 구현·검증할 완료 단위이며 자기 완료 기준을 가진다. 상위 기능은 필수 하위 단위와 상위 통합 완료 기준을 모두 충족해야 완료된다. 구체적인 작업 파일·선행 관계와 승인된 테스트 계약은 이 문서에 반복하지 않으며, 기능 전체의 현재 상태는 [P1 기능 종료 상태](README.md#기능별-종료-상태)만 갱신한다.

### 알림 유형 매핑

아래 표는 Outbox 원인 사실의 `eventType`을 사용자 알림의 `type`으로 변환하는 정본이다. relay는 enum 문자열을 그대로 복사하거나 이름 규칙으로 추론하지 않고 이 매핑을 적용한다.

| Outbox `eventType` | Notification `type` | 사용자 의미 |
| --- | --- | --- |
| `PARTICIPATION_JOINED` | `PARTICIPANT_JOINED` | 참가·재참가 성공으로 주최자에게 새 참가자 알림 |
| `PARTICIPATION_CANCELED` | `PARTICIPANT_CANCELED` | 자동 승격 없이 참가 취소가 끝나 실제 빈자리가 남은 경우 주최자에게 빈자리 알림 |
| `WAITLIST_PROMOTED` | `WAITLIST_PROMOTED` | 참가 취소와 함께 자동 승격된 사용자에게 참가 확정 알림 |
| `ROOM_CANCELED` | `ROOM_CANCELED` | 방 취소 성공으로 확정 참가자에게 방 취소 알림 |

### 기능 규칙

NOTI-01은 [P1 공통 알림 불변식](P1-spec.md#알림-생성과-조회)과 위 [알림 유형 매핑](#알림-유형-매핑)을 함께 적용한다. 트랜잭션·시각·저장·relay 규칙은 [구현 컨텍스트](#구현-컨텍스트)에 연결한 정본을 따르며 이 절에서 반복하지 않는다. 구현 완료 여부는 아래 완료 기준과 [P1 기능 종료 상태](README.md#기능별-종료-상태)으로 판정한다.

### 상위 통합 완료 기준

`NOTI-01`은 `NOTI-01a`~`NOTI-01g`의 완료 기준과 아래 상위 완료 기준을 모두 충족해야 완료된다. 하위 완료 기준은 각 구현 경계를 독립적으로 닫고, 상위 완료 기준은 하위 경계를 연결한 사용자 알림 생성 흐름의 최종 불변식을 판정한다.

- `NOTI-01-AC1` 참가·재참가, 참가 취소, 대기자 자동 승격과 방 취소의 최종 성공 트랜잭션이 원인 업무 변경과 Outbox 이벤트를 함께 커밋하고 정의된 수신자를 보존한다.
- `NOTI-01-AC2` 실패·롤백된 업무와 낙관적 락 충돌 시도는 처리 가능한 이벤트나 알림을 남기지 않으며, 재시도 뒤 성공하면 최종 성공 시도의 이벤트만 남는다.
- `NOTI-01-AC3` 방 취소와 참가·취소가 동시에 실행돼도 실제 커밋 순서에 따른 `ACTIVE` 수신자와 기존 방·참가 불변식을 함께 만족한다.
- `NOTI-01-AC4` 원인 업무 커밋 직후 프로세스가 종료돼도 재기동한 relay가 남은 이벤트로 알림을 생성한다.
- `NOTI-01-AC5` 같은 이벤트의 반복·동시 처리와 일부 수신자 저장 뒤 재처리에서도 대상자별 알림은 한 건이고 누락 대상은 최종적으로 채워진다.
- `NOTI-01-AC6` relay 처리 실패는 재시도 근거와 최종 실패 상태를 남기며 이미 성공한 방·참가 업무의 응답과 데이터를 바꾸지 않는다.
- `NOTI-01-AC7` 승인 ADR과 PostgreSQL 검증은 relay 선점, 재시도 상한·간격, 처리 지연 목표, 실패 이벤트 보존·재처리와 외부 broker 재검토 지표를 고정한다.

### 하위 구현 완료 단위

아래 일곱 단위는 `NOTI-01`을 구현·검증 가능한 경계로 나눈다. 각 단위는 독립 완료 기준을 가지지만 별도의 제품 기능은 아니다.

#### NOTI-01a 알림 저장 모델·모듈 기반

Outbox 이벤트·수신자와 사용자별 알림의 물리 저장 구조, 기본 영속 경계와 알림 모듈 기반을 담당한다.

##### 완료 기준

- `NOTI-01a-AC1` ERD의 세 알림 테이블·필드·FK·유일 제약·이름 있는 CHECK·인덱스가 전진 Flyway 마이그레이션과 Entity 매핑에 일치한다.
- `NOTI-01a-AC2` `source_event_id`의 논리 키 경계, PostgreSQL 시각 컬럼, 상태별 nullable 조합과 보존 시각 불변식을 데이터베이스와 Entity가 함께 지킨다.
- `NOTI-01a-AC3` H2로 대신할 수 없는 Flyway·PostgreSQL 제약과 알림 모듈 경계를 자동 검증한다.

#### NOTI-01b Room 변경 트랜잭션 Outbox 연결

원인 업무의 최종 성공 변경, 수신자 스냅샷과 Outbox 기록을 같은 트랜잭션에 연결한다.

##### 완료 기준

- `NOTI-01b-AC1` `room.contract`만 공개하고 컴파일 의존은 `notification → room.contract` 방향을 유지한다.
- `NOTI-01b-AC2` 이 단위가 도입한 기존 세 원인 업무의 최종 성공 시도만 업무 변경·Outbox·수신자 스냅샷을 함께 커밋하며, 기록 실패·롤백·낙관 락 실패 시도에는 모두 남기지 않는다.
- `NOTI-01b-AC3` 방 취소는 커밋 시점의 `ACTIVE` 참가자를 수신자로 고정하고 수신자가 없으면 Outbox를 만들지 않는다.
- `NOTI-01b-AC4` 참가 취소는 같은 트랜잭션에서 자동 승격 없이 실제 빈자리가 남을 때만 주최자 빈자리 이벤트를 기록한다.

#### NOTI-01c relay 선점·알림 생성·멱등 처리

처리 가능한 Outbox 선점부터 수신자별 Notification 생성과 성공 상태 전환까지의 relay 정상 경로를 담당한다.

##### 완료 기준

- `NOTI-01c-AC1` 모든 인스턴스의 bounded scheduler가 처리 가능한 가장 이른 이벤트를 건별 독립 트랜잭션으로 선점한다.
- `NOTI-01c-AC2` PostgreSQL에서 고정한 `operationTime`으로 처리 가능 시각을 판정하고 같은 이벤트에서 새로 만드는 Notification의 `recordedAt`을 통일한다.
- `NOTI-01c-AC3` 알림 유형 매핑과 수신자 스냅샷으로 누락 대상만 생성하며 `(sourceEventId, recipientUserId)` 중복은 성공으로 수렴한다.
- `NOTI-01c-AC4` Notification 생성과 `PROCESSED`·`processedAt`·`cleanupAt` 전환은 함께 커밋하거나 함께 롤백한다.
- `NOTI-01c-AC5` 정상 처리와 batch 구조화 로그는 운영 런북의 필드와 비민감정보 경계를 지킨다.

#### NOTI-01d relay 실패·재시도·격리

relay 처리 실패의 분류, 조건부 기록, 자동 재시도와 최종 격리를 담당한다.

##### 완료 기준

- `NOTI-01d-AC1` 일시 오류는 PostgreSQL `operationTime`과 운영 정본의 간격에 따라 `RETRY_WAIT`에 두고 자동 처리 상한에서 `FAILED`로 격리한다.
- `NOTI-01d-AC2` 결정적 오류와 만료 이벤트는 즉시 `FAILED`로 전환하며 Notification이나 `PROCESSED` 상태를 만들지 않는다.
- `NOTI-01d-AC3` 처리 롤백 뒤 별도 독립 트랜잭션의 조건부 실패 기록이 이미 `PROCESSED`인 이벤트를 덮어쓰지 않는다.
- `NOTI-01d-AC4` 개별 이벤트 실패가 뒤 이벤트 처리를 막지 않고 scheduler·선점 전 인프라 실패는 이벤트 실패 횟수에 포함하지 않는다.
- `NOTI-01d-AC5` 저장 설명과 구조화 로그는 원본 SQL·파라미터·수신자·payload·인증정보·정제 전 예외를 노출하지 않는다.

#### NOTI-01e 실패 Outbox one-shot 운영 복구

실패 이벤트의 조회, dry-run, 재처리와 명시적 폐기를 수행하는 운영 경계를 담당한다.

##### 완료 기준

- `NOTI-01e-AC1` `notification-ops` profile은 웹 서버·일반 scheduler 없이 application service를 호출하고 명시적 종료 코드로 끝난다.
- `NOTI-01e-AC2` `INSPECT`와 기본 dry-run은 상태를 바꾸지 않으며 실제 변경은 이벤트 ID·사유·사유 참조·실행자와 폐기 확인 계약을 모두 검증한다.
- `NOTI-01e-AC3` 대상 ID를 오름차순으로 한 번 잠그고 전체 적격성을 검증해 하나라도 잘못되면 모두 변경하지 않는다.
- `NOTI-01e-AC4` 적격 `REPROCESS`는 새 자동 처리 주기로 보내고 부적격·만료 `FAILED`는 명시적 `DISCARD`로만 전환하며, 폐기할 때 수신자를 함께 제거한다.
- `NOTI-01e-AC5` 자유 서술 `reason`은 데이터베이스에만 저장하고 로그·stdout·stderr·예외에는 허용 형식의 `reasonReference`만 남긴다.

#### NOTI-01f Notification·Outbox bounded cleanup

만료 Notification과 정리 가능한 Outbox를 다중 인스턴스에서 제한된 batch로 삭제하는 경계를 담당한다.

##### 완료 기준

- `NOTI-01f-AC1` 모든 인스턴스의 scheduler는 이전 완료 뒤 `interval+jitter`와 실행당 target별 batch 상한만 조정한다.
- `NOTI-01f-AC2` Notification과 Outbox를 독립 target으로 처리하고 각 batch 실행은 PostgreSQL `measurementTime`을 한 번 고정한다.
- `NOTI-01f-AC3` 정리 대상 ID를 인덱스 순서로 `SKIP LOCKED` 선점해 같은 트랜잭션에서 제한 삭제하며, 적은 batch나 실패를 만나면 bounded 종료한다.
- `NOTI-01f-AC4` 만료 Notification과 `PROCESSED`·`DISCARDED`의 `cleanupAt` 대상만 삭제하고 `PENDING`·`RETRY_WAIT`·`FAILED`는 자동 삭제하지 않는다.
- `NOTI-01f-AC5` batch 완료·실패 로그는 `measurementTime`과 비민감 필드 계약을 지킨다.

#### NOTI-01g 대기자 자동 승격 알림

참가 취소와 함께 첫 대기자가 자동 승격되는 최종 성공 결과를 실제 승격 사용자에게 기존 웹 알림 흐름으로 전달한다. [ADR-0053](../../adr/notification/0053-waitlist-promotion-notification.md)이 원인 이벤트·수신자·제외 범위를 확정한다.

##### 완료 기준

- `NOTI-01g-AC1` `room.contract`는 알림 구현을 참조하지 않는 `WaitlistPromotedEvent(roomId, occurredAt)`을 공개하고, Outbox와 Notification은 명시적 `WAITLIST_PROMOTED` 매핑을 사용한다.
- `NOTI-01g-AC2` 참가 취소와 자동 승격의 최종 성공 트랜잭션은 실제 `PROMOTED`·`ACTIVE` 사용자의 ID 한 개만 수신자로 기록한다. 승격 성공 시 주최자 빈자리 이벤트를 만들지 않고, 승격이 없으면 기존 주최자 빈자리 이벤트만 유지한다.
- `NOTI-01g-AC3` 조건부 승격 경쟁에서 탈락한 후보, 낙관적 락 실패 시도와 전체 롤백은 승격 이벤트를 남기지 않는다. Outbox 기록 실패는 참가 취소·ROOM 인원·참가·대기·Outbox 변경을 모두 롤백한다.
- `NOTI-01g-AC4` 전진 Flyway 마이그레이션은 기존 V4를 수정하거나 과거 데이터를 backfill하지 않고 두 이름 있는 CHECK에 기존 값과 `WAITLIST_PROMOTED`만 허용한다.
- `NOTI-01g-AC5` relay는 새 Outbox 유형을 새 Notification 유형으로 변환하며 반복·동시 처리에도 수신자별 한 건으로 수렴한다. 기존 보존·polling·목록·미확인 개수와 단건·일괄 읽음 계약은 바뀌지 않는다.
- `NOTI-01g-AC6` 웹 알림함은 `'<방 제목>' 모임 대기에서 참가자로 확정됐어요.`를 일반 텍스트로 표시하고, 선택 시 기존 읽음 처리와 현재 권한 기반 방 상세 이동을 사용한다. 채팅 직행과 외부 푸시는 추가하지 않는다.

### 제외 범위

- Kafka, RabbitMQ와 별도 메시지 broker
- 이메일·모바일 푸시·SMS와 업무 트랜잭션 안의 동기 외부 발송
- 방 수정·종료·자동 종료·시작 임박·후기·운영 알림
- 대기 순번 변경, 대기 만료와 방 취소 시 대기자 알림
- 모든 도메인 이벤트를 수집하는 범용 이벤트 플랫폼
- 이벤트의 전역 총순서와 정확히 한 번 실행된다는 보장
- 운영자용 실패 이벤트 관리 화면

### 기능 규칙

- 로그인한 사용자의 알림만 반환한다. 다른 사용자의 알림은 목록·개수 계산에 포함하지 않는다.
- 목록은 `createdAt DESC, id DESC`로 정렬해 생성 시각이 같아도 순서를 고정한다.
- 결과가 없으면 빈 목록을 반환한다. 정확한 응답 필드와 페이지네이션 방식은 [API 명세의 NOTI-02 계약](../../API.md#noti-02-내-알림-목록)을 따른다.
- 미확인 알림은 본인 알림 중 `readAt IS NULL`인 행이다.
- 목록 항목은 알림 ID, 유형, 관련 방 ID, 읽은 시각과 생성 시각을 구분할 수 있어야 한다.
- 목록과 미확인 개수는 SSE·WebSocket 없이 polling만으로 완전하게 동작한다.
- 알림을 선택해 관련 방으로 이동할 때 현재 세션과 관계로 방 상세 권한을 다시 검사한다.

| 기능 | Method / Path | 인증 | CSRF |
| --- | --- | :---: | :---: |
| 내 알림 목록 | `GET /api/users/me/notifications` | 필요 | 불필요 |
| 내 미확인 수 | `GET /api/users/me/notifications/unread-count` | 필요 | 불필요 |

### 상위 통합 완료 기준

`NOTI-02`는 `NOTI-02a`, `NOTI-02b`의 완료 기준과 아래 상위 완료 기준을 모두 충족해야 완료된다. 하위 완료 기준은 서버 조회와 웹 알림함을 각각 닫고, 상위 완료 기준은 두 경계를 연결한 사용자 조회 흐름을 판정한다.

- `NOTI-02-AC1` 로그인한 사용자는 본인 알림만 `createdAt DESC, id DESC` 순서로 조회하고 결과가 없으면 빈 목록을 받는다.
- `NOTI-02-AC2` 페이지 경계를 이동해도 정렬이 안정적이고 다른 사용자의 알림이 섞이지 않는다.
- `NOTI-02-AC3` 본인 미확인 개수는 같은 DB 상태에서 `readAt IS NULL`인 본인 알림 수와 일치한다.
- `NOTI-02-AC4` 응답·본문·로그는 참가자 식별자, 이메일, 정확한 장소, 전체 참가자 목록과 인증 정보를 노출하지 않는다.
- `NOTI-02-AC5` 실시간 연결 없이 목록과 미확인 개수 polling이 동작하고 두 `GET` 경로가 현재 세션·엔드포인트 정책 대조 검증을 통과한다.
- `NOTI-02-AC6` 관련 방 이동은 저장된 알림을 권한으로 사용하지 않고 현재 방 조회 권한과 존재 여부 은닉 규칙을 적용한다.

### 하위 구현 완료 단위

#### NOTI-02a 알림 목록·미확인 개수 백엔드

본인 알림 목록·미확인 개수 HTTP와 Query 경계, 정렬·만료와 현재 방 제목 투영을 담당한다.

##### 완료 기준

- `NOTI-02a-AC1` 두 `GET`은 로그인한 사용자 본인의 보존 기간 안 알림만 반환하고 인증·검증·응답 봉투 계약을 지킨다.
- `NOTI-02a-AC2` 목록 `content`와 `count`는 같은 짧은 읽기 트랜잭션의 PostgreSQL `queryTime`으로 만료를 판정하고 `createdAt DESC, id DESC` 순서를 유지한다.
- `NOTI-02a-AC3` 미확인 수는 별도 읽기 트랜잭션에서 본인·미만료·`readAt IS NULL`인 알림만 세며 빈 결과는 `0`이다.
- `NOTI-02a-AC4` 현재 `roomTitle`을 조회 시점에 투영하되 `roomId`·제목을 권한으로 사용하거나 민감한 참가자·장소·인증정보를 노출하지 않는다.

#### NOTI-02b 웹 알림함 조회·polling UX

알림함·미확인 배지, polling, 안전한 표시 문구·방 이동과 로딩·빈 목록·실패 경험을 담당한다.

##### 완료 기준

- `NOTI-02b-AC1` 세션 복구·알림함 열기·탭 재가시화 시 목록 첫 페이지와 미확인 수를 즉시 조회한다.
- `NOTI-02b-AC2` 보이는 로그인 문서에서 미확인 수와 열린 알림함 목록을 10초 polling하고 같은 종류 요청의 중첩과 숨김·로그아웃 상태의 polling을 막는다.
- `NOTI-02b-AC3` 배지는 미확인 API의 마지막 성공값을 사용하고 알림 유형과 현재 `roomTitle`로 일반 텍스트 문구를 렌더링한다.
- `NOTI-02b-AC4` 방 이동은 현재 방 상세 API로 권한을 다시 확인하고 접근할 수 없으면 계약된 메시지를 제공한다.
- `NOTI-02b-AC5` 최초 로딩·빈 목록·최초 실패 재시도와 기존 목록이 있는 polling 실패의 유지·중복 오류 억제를 구분한다.
- `NOTI-02b-AC6` polling·탭 상태·문구·로딩·실패 흐름의 프론트엔드 자동 검증과 프로덕션 빌드가 통과한다.

## NOTI-03 알림 읽음 처리

### 구현 컨텍스트

| 구분 | 정본 |
| --- | --- |
| API 인벤토리 | [P1 기능별 문서와 API 목록](P1-spec.md#기능별-문서와-api-목록) |

| 저장 계약 | [사용자별 알림과 읽음 시각](../../ERD.md#notifications), [P1 알림 CHECK 제약](../../ERD.md#p1-알림-check-제약) |

### 기능 규칙

- 수신자 본인만 알림을 읽음 처리할 수 있다. 존재하지 않는 알림과 다른 사용자의 알림은 같은 not-found 계약으로 처리한다.
- 단건 읽음은 읽음 SQL 내부에서 PostgreSQL `clock_timestamp()`를 한 번 평가한 `operationTime`을 최초 `readAt`에 기록한다. 저장·비교는 UTC 기준 Instant를 사용하고 API 응답은 공통 시각 계약에 따라 `+09:00`으로 표현한다. 반복 요청은 성공하되 최초 시각을 유지한다.
- 일괄 읽음은 기본 `READ COMMITTED`의 단일 data-modifying CTE/`UPDATE` 문장에서 `operationTime`, 본인에게 보이는 알림 집합의 최대 ID 경계, 갱신 건수와 응답을 같은 문장 스냅샷으로 고정한다.
- 일괄 요청은 경계 안의 미확인 알림에 같은 `operationTime`을 기록하고, 기존에 읽은 알림의 최초 `readAt`은 바꾸지 않는다.
- 문장 스냅샷 획득 뒤 생성·커밋된 알림은 ID나 생성 시각과 관계없이 읽지 않은 상태로 남긴다.
- 읽지 않음으로 되돌리는 기능은 제공하지 않는다.

| 기능 | Method / Path | 인증 | CSRF |
| --- | --- | :---: | :---: |
| 내 알림 단건 읽음 | `PATCH /api/users/me/notifications/{notificationId}` | 필요 | 필요 |
| 내 알림 일괄 읽음 | `PATCH /api/users/me/notifications` | 필요 | 필요 |

### 상위 통합 완료 기준

`NOTI-03`은 `NOTI-03a`, `NOTI-03b`의 완료 기준과 아래 상위 완료 기준을 모두 충족해야 완료된다. 하위 완료 기준은 서버 읽음 처리와 웹 상태 동기화를 각각 닫고, 상위 완료 기준은 두 경계가 같은 권위 있는 읽음 상태로 수렴하는지 판정한다.

- `NOTI-03-AC1` 본인 알림의 첫 단건 읽음 요청은 읽음 SQL이 고정한 PostgreSQL `operationTime`을 기록하고 반복 요청에도 최초 `readAt`을 유지한다.
- `NOTI-03-AC2` 존재하지 않는 알림과 다른 사용자의 알림은 같은 오류 계약을 반환하며 다른 사용자의 상태를 변경하지 않는다.
- `NOTI-03-AC3` 일괄 읽음은 단일 PostgreSQL 문장의 스냅샷·`operationTime`으로 고정한 경계 안의 본인 미확인 알림만 같은 시각으로 처리하고 기존 읽은 시각은 보존한다.
- `NOTI-03-AC4` 일괄 읽음과 알림 생성이 동시에 실행돼도 읽음 문장 스냅샷 획득 뒤 커밋된 새 알림은 응답 경계에 포함되지 않고 미확인 상태로 남는다.
- `NOTI-03-AC5` 단건·일괄 요청을 반복해도 추가 부수효과 없이 같은 상태로 수렴한다.
- `NOTI-03-AC6` 두 `PATCH` 경로가 로그인·CSRF 보호와 엔드포인트 정책 대조 검증을 통과한다.

### 하위 구현 완료 단위

#### NOTI-03a 단건·일괄 읽음 백엔드

단건·일괄 `PATCH`, PostgreSQL `operationTime`·문장 스냅샷, 최초 `readAt` 보존과 오류·보안 경계를 담당한다.

##### 완료 기준

- `NOTI-03a-AC1` 단건 `PATCH`는 본인 미만료 알림의 최초 `readAt`만 PostgreSQL `operationTime`으로 기록하고 반복 요청에 같은 값을 반환한다.
- `NOTI-03a-AC2` 존재하지 않거나 다른 사용자의 것이거나 만료된 알림은 상태를 바꾸지 않고 같은 `NOTIFICATION_NOT_FOUND` 계약으로 숨긴다.
- `NOTI-03a-AC3` 일괄 `PATCH`는 한 data-modifying CTE/`UPDATE` 문장 스냅샷에서 `operationTime`·경계·갱신 건수와 응답을 고정한다.
- `NOTI-03a-AC4` 문장 스냅샷 뒤 커밋된 알림과 기존 `readAt`·만료 알림을 변경하지 않고 반복 요청이 추가 부수효과 없이 수렴한다.
- `NOTI-03a-AC5` 입력 검증·로그인·CSRF와 MVC-엔드포인트 정책 대조가 API 계약과 일치한다.

#### NOTI-03b 웹 알림 읽음 상태 동기화

단건 낙관 표시, 일괄 요청 중 polling 중단, 조회 generation과 권위 있는 서버 재조회를 담당한다.

##### 완료 기준

- `NOTI-03b-AC1` 읽지 않은 알림 선택은 임의 `readAt` 없이 낙관 스타일·배지를 갱신하고 이동을 막지 않은 채 단건 `PATCH`를 보낸다.
- `NOTI-03b-AC2` 단건 성공은 응답 항목과 권위 있는 미확인 수를 반영하고 실패하면 목록·미확인 수 재조회로 서버 상태를 복구한다.
- `NOTI-03b-AC3` 일괄 요청은 중복 제출과 polling을 막고 generation을 올려 이전 `GET`을 취소·폐기한다.
- `NOTI-03b-AC4` 성공·실패 확정 뒤 새 generation으로 목록 첫 페이지와 미확인 수를 즉시 재조회하고 두 응답이 끝난 뒤 polling을 재개한다.
- `NOTI-03b-AC5` `boundaryNotificationId`·`updatedCount`로 현재 목록이나 배지를 직접 확정하지 않고 현재 generation과 일치한 서버 응답만 적용한다.
- `NOTI-03b-AC6` 동기화 재조회 실패는 마지막 성공 목록을 유지하고 명시적 재시도 동작을 제공한다.
- `NOTI-03b-AC7` 단건·일괄 읽음 동기화의 프론트엔드 자동 검증과 프로덕션 빌드가 통과한다.

### 제외 범위

- 알림을 읽지 않음으로 되돌리기
- 알림 삭제·보관과 보존 기간 사용자 설정
- 다른 사용자의 알림 상태 변경

## 프론트엔드 UX 계약

이 절은 `NOTI-02`·`NOTI-03`을 사용하는 P1 웹 알림함의 기본 동작을 정의한다. 서버는 표시용 `message`를 반환하지 않으며, 클라이언트가 `type`과 조회 시점의 `roomTitle`로 문구를 만든다. API 요청·CSRF 처리와 최종 서버 상태 반영은 [API 명세의 알림 계약](../../API.md#9-알림채팅-api)을 따른다.

### 조회와 polling

- 로그인 성공 또는 새로고침 뒤 세션 복구가 끝나면 알림 목록 첫 페이지(`page=0`, `size=10`)와 미확인 개수를 즉시 조회한다.
- 로그인 세션이 있고 문서가 보이는 동안 미확인 개수를 10초마다 조회한다. 알림함이 열려 있으면 목록 첫 페이지도 같은 주기로 다시 조회해 서버 응답으로 교체한다.
- 알림함을 열 때는 직전 polling 시각과 관계없이 목록 첫 페이지와 미확인 개수를 즉시 조회한다. 숨겨졌던 브라우저 탭이 다시 보이면 열린 알림함의 목록과 미확인 개수를 즉시 조회한다.
- 같은 종류의 이전 조회가 진행 중이면 다음 polling 요청을 겹쳐 보내지 않는다. 문서가 숨겨졌거나 로그아웃했으면 주기 조회를 중단하고, `401 UNAUTHENTICATED`는 공통 세션 만료 흐름으로 처리한다.
- 미확인 배지는 목록 한 페이지에서 계산하지 않고 미확인 개수 API의 마지막 성공 응답을 사용한다.

### 표시 문구와 이동

| `NotificationType` | 기본 문구 |
| --- | --- |
| `PARTICIPANT_JOINED` | `'${roomTitle}' 모임에 새 참가자가 있어요.` |
| `PARTICIPANT_CANCELED` | `'${roomTitle}' 모임에 빈자리가 생겼어요.` |
| `WAITLIST_PROMOTED` | `'${roomTitle}' 모임 대기에서 참가자로 확정됐어요.` |
| `ROOM_CANCELED` | `'${roomTitle}' 모임이 취소됐어요.` |

- `${roomTitle}`은 API가 반환한 현재 방 제목으로 치환하고 HTML로 해석하지 않은 일반 텍스트로 렌더링한다. 참가자 닉네임·사용자 ID·이메일·정확한 장소는 문구에 추가하지 않는다.
- 읽지 않은 알림을 선택하면 임의의 `readAt`을 만들지 않고 해당 행만 읽음 스타일로 바꾸며, 마지막 성공 미확인 개수를 `max(0, unreadCount - 1)`로 먼저 표시한 뒤 단건 읽음 요청을 보낸다. 읽음 요청 완료를 기다리느라 이동을 막지 않고 `roomId`로 방 상세 이동을 시도한다.
- 방 상세 이동은 현재 세션과 권한으로 다시 조회한다. 방이 없거나 현재 접근할 수 없으면 저장된 알림으로 우회하지 않고 `현재 확인할 수 없는 모임입니다.`를 표시한다.

### 읽음 상태 동기화

- 단건 읽음 성공 시 응답의 `readAt`을 같은 알림에 적용하고 미확인 개수를 즉시 다시 조회한다. 실패하면 낙관적 상태를 확정하지 않고 목록과 미확인 개수를 다시 조회한다.
- 일괄 읽음은 요청 중 중복 제출을 막는다. 요청을 시작하면 목록·미확인 개수 polling을 중지하고 알림 조회 세대(generation)를 증가시켜 이전 세대의 진행 중인 `GET`을 취소한다. 성공·실패가 확정되면 세대를 다시 증가시킨 뒤 목록 첫 페이지와 미확인 개수를 즉시 재조회하고, 각 응답은 요청이 캡처한 세대가 현재 세대와 같을 때만 적용하며 두 재조회가 끝난 뒤 polling을 재개한다.
- 일괄 읽음 성공 응답의 `boundaryNotificationId`는 실제 갱신 ID 집합이나 클라이언트 읽음 경계가 아니므로 현재 목록을 직접 변경하는 데 사용하지 않는다. 목록과 배지는 후속 재조회 응답으로만 교체하고 `updatedCount`만 보고 배지를 계속 `0`으로 두지 않는다.
- 읽음 동기화 재조회가 실패하면 마지막 성공 목록을 유지하고 `알림 상태를 갱신하지 못했습니다. 다시 시도해 주세요.`와 재시도 동작을 제공한다.

### 로딩·빈 목록·실패

- 최초 목록 응답 전에는 `알림을 불러오는 중입니다.`를 표시한다.
- 조회가 성공했고 `content`가 비어 있으면 `새로운 알림이 없습니다.`를 표시한다.
- 최초 목록 조회가 실패하면 `알림을 불러오지 못했습니다.`와 명시적인 재시도 동작을 제공한다.
- 이미 성공한 목록이 있는 상태에서 polling이 실패하면 기존 목록과 배지를 지우거나 오류 화면으로 바꾸지 않는다. 같은 오류 알림을 주기마다 반복 노출하지 않고 다음 polling 또는 사용자의 재시도에서 다시 조회한다.
