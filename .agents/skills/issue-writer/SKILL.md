# Issue Writer

## 역할

요청을 분류해 등록된 Issue Form 하나를 선택하고 실제 저장소 근거로 이슈를 작성한다. 사용자가 게시까지 명확히 요청한 경우에만 GitHub 이슈를 생성한다. 코드 구현, 커밋, PR 생성은 하지 않는다.

## 정본

- 선택 가능한 템플릿은 `templates.json`에서 매번 읽는다. `enabled: true`인 항목만 후보로 사용한다.
- 필드명·순서·필수 여부의 정본은 각 항목의 `template`이 가리키는 `.github/ISSUE_TEMPLATE/*.yml`이다. JSON에 본문을 복제하지 않는다.
- 분류할 때 `intent`를 우선하고 `signals`는 보조 힌트로만 사용한다.
- 작업 시작 시 `node .agents/skills/issue-writer/scripts/validate-template-registry.mjs`를 실행한다. 실패하면 선택·게시하지 않고 불일치를 보고한다.

## 요청 경계

- `이슈 작성해줘`, `초안 작성해줘`: 제목과 본문 초안만 제공한다.
- `이슈 올려줘`, `게시해줘`, `만들어줘`: 검증 후 이슈를 게시한다. 같은 요청에서 게시 의도가 이미 명확하면 별도 재확인을 요구하지 않는다.
- 템플릿 선택만 물으면 후보와 선택 근거만 답한다.
- 분류가 둘 이상에 걸치면 외부 동작 변화 여부를 기준으로 좁힌다. 그래도 모호하면 가장 짧은 확인 질문 하나만 한다.
- 맞는 템플릿이 없으면 blank issue를 만들지 않는다. 필요한 템플릿 또는 레지스트리 항목을 제안하고 중단한다.

## 작성 절차

1. `git remote -v`, 저장소 상태와 관련 코드·문서·기존 이슈를 읽어 현재 사실을 확인한다.
2. `templates.json`에서 후보를 고르고 선택한 `template` 파일을 끝까지 읽는다.
3. 정본 내용을 복사하지 말고 링크로 연결한다. 저장소에서 알 수 없는 범위, 소유 경로, 의존성과 완료 조건을 중심으로 작성한다.
4. Issue Form의 non-markdown 항목을 선언 순서대로 채운다. `validations.required: true` 필드는 비워 두지 않는다.
5. 제목은 선택한 Form의 `title` 접두사를 그대로 사용하고, 뒤에는 결과가 드러나는 짧은 한국어 제목을 붙인다.
6. 확인하지 않은 테스트·의존성·완료 상태를 완료로 표시하지 않는다. 계획 체크박스는 미체크 상태로 둔다.
7. 초안에 선택 템플릿 ID, 제목과 본문을 함께 제시한다.

## 게시 절차

1. `gh auth status`와 `gh repo view --json nameWithOwner`로 인증과 정확한 저장소를 확인한다. 저장소를 과거 맥락으로 추측하지 않는다.
2. `gh issue list --state all --limit 100 --json number,title,state,url`로 같은 목적·범위의 중복 이슈를 확인한다. 중복이면 새로 만들지 않고 기존 이슈를 제시한다.
3. 최종 제목·본문을 다시 대조한다. 레지스트리의 `labels`가 비어 있지 않으면 저장소에 실제 존재하는 라벨만 사용한다.
4. 셸 escaping으로 본문이 변형되지 않도록 고유한 임시 body 파일과 `gh issue create --repo <owner/repo> --title <title> --body-file <file>`을 사용한다. 저장소 안에 임시 파일을 남기지 않는다.
5. 생성된 번호를 `gh issue view <number> --json number,title,body,state,url`로 다시 읽어 제목·본문을 검증한다.
6. 최종 응답에는 선택한 템플릿, 이슈 번호와 URL을 반환한다.

## 중단 조건

- JSON과 Issue Form이 불일치하거나 필수 필드를 채울 근거가 없다.
- 저장소 정본이 충돌하거나 소유 범위 밖 공유 파일 변경이 필요하다.
- GitHub 인증·저장소 식별에 실패한다.
- 같은 목적과 범위의 열린 이슈가 이미 있다.

이 경우 추측하거나 우회 게시하지 말고 확인된 사실과 필요한 사용자 결정을 짧게 보고한다.
