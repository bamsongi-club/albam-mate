# 사용자 출력 표시 계약

검증된 일반 리뷰 결과만 아래 의미와 고정 형식으로 표시한다.

## 심각도

| | 레벨 | 의미 |
| --- | --- | --- |
| 🔴 | `critical` | 즉시 악용 가능한 취약점, 데이터 손상, 크래시, 핵심 요구사항 차단 |
| 🟠 | `major` | 머지 전 수정이 필요한 실질 버그 또는 설계 결함 |
| 🟡 | `minor` | 개선 권장이나 차단하지 않는 문제 |
| ⚪ | `nit` | 취향 또는 사소한 제안 |

## Finding 표시 형식

각 Finding은 아래 형식을 그대로 쓴다. 제목 구분자, 섹션 제목과 이모지를 바꾸거나 생략하지 않고 위치·문제점·수정 방향을 한 문장으로 합치지 않는다.

~~~text
<이모지> <레벨> | <제목>
위치: <file>:<line>

**🔍 문제점**
<실패 조건, 영향, 계약 근거>

**🔧 수정 방향**
<실행 가능한 수정 방향>
~~~

- GitHub inline comment에서는 diff 앵커가 위치를 대신하므로 `위치` 줄을 생략한다.
- 확인할 가치가 있는 사실만 수정 방향 뒤에 `**✅ 확인한 점**`으로 덧붙일 수 있다.
- severity와 emoji는 `critical=🔴`, `major=🟠`, `minor=🟡`, `nit=⚪`로 일치시킨다.

## PR 전체 요약 형식

PR 전체 요약은 아래 핵심 형식과 순서를 그대로 쓴다.

~~~text
## 판정: <Approve | Changes Requested | Blocked | Incomplete>

심각도: 🔴 <n>  🟠 <n>  🟡 <n>  ⚪ <n>

변경 요약: <이번 변경의 동작을 2~3줄로 설명>

### 잘된 점

- <확인된 사실 또는 `없습니다.`>

### 주요 지적 (critical/major만)

- <🔴 또는 🟠> <file>:<line> — <제목>
- 없으면 `없습니다.`

### 다음 액션

- <필요한 행동 또는 `추가 조치 없이 병합 가능합니다.`>
~~~

- 모든 `critical`·`major` Finding은 inline 게시 여부와 무관하게 `주요 지적`에 한 번씩 요약한다.
- `minor`·`nit`은 inline comment로 게시한다. diff 안에 있지만 안전한 inline 앵커가 없는 항목만 `### 앵커할 수 없는 지적` 절에 `<이모지> <file>:<line> — <제목>`으로 요약한다.
- 재리뷰에서는 판정 다음에 `재리뷰 기준 커밋: <40자 SHA>`를 쓰되 SHA를 backtick으로 감싸고, 변경 요약 다음에 `### 이전 지적 해소 확인`을 선택적으로 넣을 수 있다.
- 미검토 범위가 있으면 `### 미검토 범위`를 `다음 액션` 바로 앞에 넣고 판정을 `Incomplete`로 한다. 미검토 범위가 없으면 이 절을 만들지 않는다.
- 선택 절의 순서는 `이전 지적 해소 확인` → `잘된 점` → `주요 지적` → `앵커할 수 없는 지적` → `미검토 범위` → `다음 액션`이다.
- 미검토 범위가 있으면 `Incomplete`, 그렇지 않고 critical이 있으면 `Blocked`, major가 있으면 `Changes Requested`, 완료됐고 critical·major가 없으면 `Approve`다.
- 심각도 개수는 중복 제거한 전체 Finding과 일치시킨다.
- 확인된 장점만 적고 채우기 위한 칭찬은 만들지 않는다.
